# Research: Conflict resolution and Change Set log storage for cross-device sync

**Question.** `docs/product-requirements.md` FC-SYNC-001 asks the feasibility cycle to "investigate and research approaches for syncing independent local SQLite copies across devices (e.g. last-write-wins vs. CRDT vs. manual merge)". This sits alongside FC-SYNC-003 (demonstrate basic push/pull sync between two local SQLite instances via the Sync Server, including offline catch-up), FR.39a (the Sync Server persists a durable log of Change Sets so an offline Client can catch up without both peers being online simultaneously), NFR.8 (a still-placeholder NFR for Change Set log durability, container security posture, and backup/restore), and §5 Dependencies' note that "the Sync Server's own change-set store is TBD, to be decided as part of FC-SYNC-001." This note investigates two linked questions: (1) which conflict-resolution strategy — last-write-wins (LWW), CRDTs, or manual merge — fits Personal Ledger's sync model, and what each strategy demands of the Sync Server's durable Change Set log; and (2) which storage engine should back that log, evaluated concretely against this workspace's stack (`sqlx`, `tokio`, the `lib-database` conventions in `CLAUDE.md`) and its Docker-only, single-persistent-volume, homelab deployment model (FC-SYNC-005/006, NFR.6b, §6.1 Assumptions). Per `CONTEXT.md`, "reconcile"/"reconciliation" is reserved exclusively for Transaction Status's own bank-statement-matching workflow; this document uses "sync", "merge", "conflict resolution", and "Change Set" throughout, never "reconcile", even though the originating GitHub issue used that word in a now-superseded way.

Research was done by reading this workspace's own `crates/libs/lib-database` source (`connection.rs`, `error.rs`, `config.rs`, `categories/mod.rs`) and root `Cargo.toml` for its actual `sqlx`/`tokio` conventions, plus primary sources for every external claim: SQLite's own WAL and corruption-avoidance documentation, PostgreSQL's own WAL-reliability and Docker image documentation, `sled`'s and `redb`'s own READMEs/docs.rs pages, `cr-sqlite`'s own docs and its `crsql_changes` virtual-table schema, Automerge's own sync documentation, PowerSync's and Turso's own product docs, Apache CouchDB's own replication-conflicts documentation, and the original academic CRDT and Hybrid Logical Clock papers — not blog posts or secondary summaries, except where flagged explicitly.

## 1. Conflict-resolution strategies for syncing independent local SQLite copies

### 1.1 Last-write-wins (LWW)

**Mechanism.** Each Change Set (or each field within it) carries a timestamp; when two Clients have made conflicting edits to the same row/field, the sync layer keeps whichever Change Set has the later timestamp and silently discards the other. This can operate at row granularity (the whole row's last write wins) or field granularity (each field is compared independently, so non-overlapping field edits from two different Clients both survive).

**Guarantees and non-guarantees.** LWW guarantees convergence — every replica ends up applying the same deterministic choice given the same timestamps — but it does **not** guarantee no data loss: the losing Change Set's edit is discarded, not merged, not queued for review, and not surfaced to the user. It is also only as reliable as its timestamps: if two devices' clocks disagree, "last" by wall-clock time may not be "last" by the user's actual intent, and a device with a fast clock can permanently win against any future edit from a device with a slow clock until the clocks re-sync.

**Real implementations.**
- **PowerSync** documents last-write-wins as its default, at **field** granularity, not row granularity: "the default behaviour is last write wins per field... Updates to different fields on the same record don't conflict with each other" (PowerSync docs, "Custom Conflict Resolution", https://docs.powersync.com/handling-writes/custom-conflict-resolution). PowerSync's sync protocol represents each Client edit as a `CrudEntry` — one of `PUT` (replace all non-null columns), `PATCH` (update only the named fields), or `DELETE` — and states explicitly that "operations are idempotent — your backend may receive the same operation multiple times," meaning a real Change Set stream in this model must be safe to reprocess (PowerSync is server-authoritative — a single Postgres backend arbitrates order — which is a materially different topology from Personal Ledger's peer Clients around a store-and-forward Sync Server, but its per-field LWW default and its documented alternative strategies are still directly relevant precedent). PowerSync's docs also list concrete alternatives to plain wall-clock LWW worth noting as a spectrum, not just a binary choice: comparing a `modified_at` timestamp to reject stale writes, using a monotonically-incrementing **sequence number** instead of a timestamp specifically "to avoid clock drift," and recording both conflicting versions server-side for a human to resolve manually (same source) — i.e. PowerSync's own docs already blend LWW, version-counter, and manual-merge ideas rather than treating them as mutually exclusive.
- **Turso's libSQL offline sync** (public beta) explicitly separates conflict *detection* from conflict *resolution*: its own announcement states the beta ships "conflict detection (but resolution is not yet implemented)," with "an API [that] lets the application perform conflict resolution with user-defined strategies" once available (Turso blog, "Turso Offline Sync Public Beta", https://turso.tech/blog/turso-offline-sync-public-beta). This is a useful negative data point: even a well-resourced, purpose-built local-first SQLite sync product had not, at the time of this research, shipped a default automatic resolution policy — it ships detection and leaves the policy to the application, closer in spirit to manual merge (§1.3) than to an opinionated LWW default. Turso's separate **Embedded Replicas** feature (a read replica of a single cloud-primary database, not peer-to-peer) sidesteps the conflict question entirely by default — writes go to the remote primary first and are reflected back to the replica, so two replicas cannot normally diverge unless an `offline: true` local-write mode is explicitly enabled (Turso docs, "Embedded Replicas: Introduction", https://docs.turso.tech/features/embedded-replicas/introduction) — this is architecturally a hub-and-spoke primary, not the two-Client-plus-non-authoritative-Sync-Server topology FR.39a describes, so it is cited here only as a contrast, not as directly applicable precedent.
- **cr-sqlite** offers an LWW register as one of its per-column CRDT strategy choices (see §1.2) — worth flagging here because it shows LWW is commonly implemented *as one CRDT type among several*, not as a separate, cruder alternative to "real" CRDTs; a system can mix LWW registers on some columns with other CRDT types on others.

**What LWW demands of the Change Set log.** At minimum: a wall-clock timestamp per Change Set (or per field, if doing field-granularity LWW), and a deterministic tie-breaker for exact-timestamp ties — typically the originating Client/replica's stable ID, compared lexicographically, so every replica picks the same winner without needing to communicate. Because wall-clock timestamps from independent, possibly-offline devices are exactly the failure mode Hybrid Logical Clocks (HLCs) were designed to defend against, it is worth citing HLCs even for a nominally "pure LWW" design: Kulkarni, Demirbas, Madeppa, Avva, and Leone's "Logical Physical Clocks and Consistent Snapshots in Globally Distributed Databases" (2014) proposes a clock that "combines the best of logical clocks and physical clocks... captures the causality relationship like logical clocks... while it can be used in lieu of physical/NTP clocks since it maintains its logical clock to be always close to the NTP clock" (paper abstract, as summarised via Springer's chapter listing, https://link.springer.com/chapter/10.1007/978-3-319-14472-6_2 — this paper was not fetched as a full PDF in this research pass; the abstract/contribution summary above is drawn from secondary indexing of the paper's own abstract text, flagged here as the one place in this document relying on an index rather than the primary PDF directly). Practically, an HLC-backed timestamp (physical time plus a logical counter that only ever advances, even across clock corrections) is strictly more robust than a raw `SystemTime`/`chrono::Utc::now()` value for LWW tie-breaking, at the cost of a small amount of extra per-Change-Set state (the logical counter) and a bit of implementation complexity beyond a bare timestamp column.

### 1.2 CRDTs (Conflict-free Replicated Data Types)

**Formal definition and guarantee.** CRDTs originate from Shapiro, Preguiça, Baquero, and Zawirski's 2011 INRIA report "Conflict-free Replicated Data Types" (published at SSS 2011; PDF at https://www.lip6.fr/Marc.Shapiro/papers/2011/CRDTs_SSS-2011.pdf). The paper defines **Strong Eventual Consistency (SEC)**: "if an update is delivered to a node, then that update is eventually delivered to all nodes," and "correct nodes that have delivered the same updates will reach equivalent state" (as fetched from the paper). It gives two sufficient conditions for a data type to satisfy SEC without coordination: **state-based (CvRDT)**, where replicas exchange full state and a commutative, monotone merge function guarantees convergence regardless of message order or duplication; and **operation-based (CmRDT)**, where all *concurrent* operations commute with each other, so any node applying the same operation set in any order reaches the same result (same source). This is the formal basis for every "automatic merge" claim made by a CRDT library or CRDT-based sync tool — and it is important to be precise about what it promises: SEC guarantees **convergence** (all replicas agree on *some* final state), not that the converged state is the one a human user would consider *correct*. Two Clients concurrently editing the same Transaction's amount field under an LWW-register CRDT will deterministically converge — but the losing edit is still silently discarded, exactly as in plain LWW (§1.1); the CRDT guarantee only removes the *ambiguity* of which replica ends up with which value, not the *data loss*. Stronger CRDT types (e.g. a counter CRDT that sums concurrent increments, see below) avoid data loss for the specific operations they support, but only because their semantics are narrow enough that "merge" has an unambiguous domain meaning — which is not true of an arbitrary field like a Transaction amount or Category assignment.

**cr-sqlite** (`vlcn-io/cr-sqlite` on GitHub, https://github.com/vlcn-io/cr-sqlite) is the most directly relevant concrete implementation: a loadable SQLite/libSQL extension described as adding "multi-master replication and partition tolerance to SQLite via conflict free replicated data types (CRDTs)" (project README, same URL). It supports **multiple CRDT types selectable per column**, not one global strategy: "Last-Write-Wins just picks the latest write" (an LWW register), "Counter CRDT sums the values," fractional-index columns are "taken as last write," and "Multi-value registers keep all conflicting values" rather than picking one (README, same URL) — at the time of the README fetched, "LWW, Fractional Index, Observe-Remove sets are available now" while "Counter and rich-text CRDTs are still being implemented," so not every listed type is necessarily production-ready. cr-sqlite exposes its Change Set format directly as a queryable SQLite virtual table, `crsql_changes`, with this documented schema (vlcn.io docs, "crsql_changes", https://vlcn.io/docs/cr-sqlite/api-methods/crsql_changes):

```sql
CREATE TABLE crsql_changes(
  [table] TEXT NOT NULL,
  [pk] TEXT NOT NULL,
  [cid] TEXT NOT NULL,
  [val] ANY,
  [col_version] INTEGER NOT NULL,
  [db_version] INTEGER NOT NULL,
  [site_id] BLOB,
  [cl] INTEGER NOT NULL,
  [seq] INTEGER NOT NULL
) STRICT;
```

— i.e. changes are captured at **per-column** granularity (`table` + `pk` + `cid` identify exactly one cell), each carrying a `col_version` (that column's own version counter) and `db_version` (the writing database's overall version counter, used so a peer can ask "give me everything after `db_version` N"), a `site_id` identifying which replica made the change (cr-sqlite's own docs describe this as "the site responsible for the change," equivalent to what other systems call an actor/replica ID), a `cl` ("causal length") field that — per vlcn.io's own documentation of the CRDT type it backs, the "CL-Set" — functions as a tombstone-with-undelete mechanism: it is "similar to an OR-Set but supports 'un-delete' via a counter that is bumped for each delete and un-delete," so deletes are represented as a causal-length bump rather than a row disappearing, letting a later "un-delete" be distinguished from a stale delete arriving out of order. A `seq` field orders changes within one site's own stream. Pulling a peer's outstanding changes is documented as a plain SQL query with a version cursor: `SELECT "table","pk","cid","val","col_version","db_version","site_id","cl","seq" FROM "crsql_changes" WHERE "db_version" > ? AND "site_id" IS NOT ?` (same vlcn.io page) — this is a directly usable template for exactly the "queryable by Client cursor" property this project's own Change Set log needs, adapted to whatever storage engine ends up backing it (§2). The versioning mechanism itself is described elsewhere in cr-sqlite's own material as a Lamport-style logical clock, not a physical/wall-clock timestamp: "a logical clock is a mechanism to establish causality of changes, without needing an actual, synchronous global clock between different participants in a system... cr-sqlite specifically uses a 'Lamport timestamp' for this purpose" (as summarised from vlcn.io's own documentation, cited via search indexing rather than a full page fetch in this pass — flagged as the second instance in this document of relying on indexed secondary text rather than a directly fetched primary page; the `crsql_changes` schema and column semantics above, by contrast, were fetched directly from vlcn.io's own docs page).

**Automerge** (https://automerge.org) is a general-purpose CRDT library (JSON-like documents, not SQL rows) included per the task's framing as a general-CRDT-library comparison point. Its sync model assigns each editing instance an **actor ID** — "a UUID that is generated randomly whenever you do `Automerge.init()` or `Automerge.load()`" — and tracks, per actor ID, a strictly-incrementing sequence number for that actor's own changes; the map from actor ID to highest-seen sequence number is explicitly called a **vector clock**, used so "two peers... communicating... need to figure out which changes they need to send to each other in order to get in sync" (Automerge documentation, as summarised via indexed search of automerge.org/automerge documentation and the Rust API reference at docs.rs/automerge — a direct fetch of automerge.org's syncing reference page returned HTTP 404 during this research pass, so this description is drawn from Automerge's own docs.rs API documentation and CRAN R-binding reference text rather than the specific web page originally targeted; flagged accordingly). Automerge additionally tracks **heads** — lists of cryptographic change hashes identifying a specific point in the document's history, used for historical/point-in-time queries. This is the same conceptual shape as cr-sqlite's `(site_id, db_version)` pair, just with cryptographic hashes instead of a bare integer counter and a JSON-document model instead of relational rows/columns.

**Yjs** (https://github.com/yjs/yjs) is likewise a general CRDT library, implementing "a list CRDT based on a variant of the YATA (Yet Another Transformation Approach) algorithm" for collaborative-text/rich-document use cases, syncing via compact binary "update" objects that can be merged and diffed against a peer's state vector (`Y.encodeStateAsUpdate`, `Y.encodeStateVector`, `Y.mergeUpdates` — Yjs README/INTERNALS.md, https://github.com/yjs/yjs). No evidence was found of Yjs being used as a per-row/per-field conflict-resolution engine for a relational/SQLite dataset — it is document- and sequence-oriented (collaborative text editing, JSON-like nested structures), not row-oriented, and is included here strictly as the general-CRDT-library comparison point the task framing calls for, not as a real candidate for Personal Ledger's Change Set log.

**What CRDTs demand of the Change Set log**, synthesised from the above: (a) per-change causal/version metadata — cr-sqlite's `(site_id, db_version, col_version)` triple or Automerge's `(actor_id, seq)` vector-clock entries — sufficient for a peer to compute "what have I not seen yet" without a shared physical clock; (b) a tombstone mechanism for deletes that survives out-of-order delivery (cr-sqlite's causal-length counter, which distinguishes "deleted" from "never existed" and supports un-delete); (c) a real per-field or per-column granularity choice, since cr-sqlite's own design puts the primary key **and** the column ID (`cid`) in every change row rather than one row per Ledger-row edit — meaningfully more Change Set rows for a multi-field update than a row-granularity LWW design would produce, a genuine storage/bandwidth tradeoff against the finer-grained conflict handling it buys; and (d) an explicit acknowledgement that automatic convergence is not the same guarantee as domain-correct merging (per SEC's own scope, above) — CRDTs remove *ambiguity* about which replica's value wins, they do not add domain knowledge about which value the user actually wanted.

### 1.3 Manual merge

**Mechanism.** The sync layer does not silently pick a winner at all; instead it detects that a conflict exists — two edits both descend from the same prior version, each with a Change Set the other hasn't seen — and surfaces both versions for the application (or, ultimately, the user) to resolve explicitly.

**Precedent (not a SQLite tool, cited for its conflict-detection model only).** Apache CouchDB's replication protocol is the most concretely documented "detect-then-surface" system found in this research, using per-document revision trees: "when you update a document in CouchDB, it keeps a list of the previous revisions. In the case where conflicting updates are introduced, this history branches into a tree, where the current conflicting revisions for this document form the tips (leaf nodes) of this tree" (Apache CouchDB documentation, "Replication and conflict model", https://docs.couchdb.org/en/stable/replication/conflicts.html). Each revision ID is a checksum of the document body plus the previous revision ID, so a client can tell whether two documents share a common ancestor. Critically, CouchDB does **not** auto-merge divergent branches: "by default, CouchDB picks one arbitrary revision as the 'winner', using a deterministic algorithm so that the same choice will be made on all peers" for display purposes only — the losing revision is not discarded, and an application that asks for it (`GET /db/test?conflicts=true`) is told "the winner plus a `_conflicts` member containing an array of the revs of the other, conflicting revision(s)" (same source), leaving actual resolution — picking a value, merging fields by hand, or asking the user — entirely up to the application. This is CouchDB's own documented model, not a SQLite-specific tool, and is cited here purely as the clearest primary-source example of "detect a real conflict via version/ancestor metadata, then defer resolution" found in this research; no evidence was found of a SQLite-native library implementing this exact revision-tree model (cr-sqlite and Automerge, by contrast, resolve automatically per §1.2).

**Turso's offline-sync beta** (§1.1) is also, in effect, a manual-merge system today by omission: it documents conflict *detection* as shipped while resolution is explicitly "not yet implemented," leaving the application to supply a strategy via an API once available (Turso blog, "Turso Offline Sync Public Beta", https://turso.tech/blog/turso-offline-sync-public-beta) — i.e. a real, current, SQLite-adjacent system that has, as of this research, chosen exactly the "detect, don't auto-resolve" scope this section describes, whether by design or as an interim state.

**What manual merge demands of the Change Set log.** At minimum, enough causal/version metadata to detect that two Change Sets are genuinely concurrent (both descend from the same prior version, neither is a descendant of the other) rather than a normal sequential edit — a parent-version pointer, a version-vector, or (as in CouchDB) a revision-history chain. Unlike LWW, no tie-breaker is needed at this layer, because no automatic tie-breaking happens; unlike CRDTs, no merge-function semantics need to be baked into the log format, because merging is deferred to the application layer. The cost shifts instead to the application/UI: something has to actually present the conflict and capture a decision, which is real work this feasibility cycle would need to build (there is no framework-level "conflict inbox" shipped by any tool surveyed here) — CouchDB's own model, for instance, still leaves "what UI shows the user the `_conflicts` array and lets them pick" entirely to the application built on top of it.

### 1.4 Cross-cutting summary — what each strategy asks of the Change Set log

| | LWW | CRDT (cr-sqlite style) | Manual merge |
|---|---|---|---|
| Per-Change-Set metadata (minimum) | timestamp (ideally HLC-backed) + tie-breaker (replica/site ID) | `(site_id, db_version, col_version)`-style version triple, or actor-ID + sequence-number vector clock | parent-version pointer or version vector (no tie-breaker needed) |
| Granularity options | row or field | typically per-column (cr-sqlite: `table`+`pk`+`cid`) | row or field, but must capture enough to diff two branches |
| Delete handling | last delete/undelete wins like any other write | explicit tombstone/causal-length counter to survive out-of-order delivery | surfaced as a conflict like any other divergent edit |
| Data-loss behaviour | losing edit silently discarded | losing edit silently discarded, *unless* the CRDT type is loss-avoiding by construction (e.g. counters) | nothing discarded automatically; both versions retained until a human/app decides |
| App-layer work required | none beyond accepting the outcome | none beyond accepting the outcome (per column semantics chosen) | a real conflict-presentation/decision UI, which does not exist yet in this project |
| Real precedent found | PowerSync (default), part of cr-sqlite's own per-column toolkit | cr-sqlite, Automerge | CouchDB/PouchDB (non-SQLite precedent); Turso's offline-sync beta today, by omission |

## 2. Candidate storage engines for the Sync Server's own Change Set log

The Sync Server's own durable store is a different problem from a Client's full Ledger copy: it needs to hold an append-heavy, growing log of Change Sets and answer "give me everything after cursor X" queries from possibly-many-Clients-at-once, not run the full Category/Account/Transaction/Budget/Balance-Check query surface `lib-database` already implements for Clients. This section evaluates SQLite (via the same `sqlx` stack `lib-database` already uses), PostgreSQL (a client-server RDBMS), and two embedded Rust-native KV stores, `sled` and `redb`, against this workspace's actual constraints: `sqlx`/`tokio` conventions, Docker-only deployment behind a single persistent volume with no separate DB server process unless justified (FC-SYNC-005/006, NFR.6b), and each engine's own durability documentation.

### 2.1 SQLite via `sqlx` (the incumbent-stack option)

This workspace already pins `sqlx = "0.8.6"` with `features = ["any", "chrono", "derive", "macros", "migrate", "postgres", "runtime-tokio-rustls", "sqlite", "uuid"]` at the workspace level (`Cargo.toml`), and `crates/libs/lib-database` is built entirely on `sqlx::SqlitePool` (`connection.rs`, lines 78, 119–175) with a `thiserror`-based `DatabaseError` (`error.rs`, lines 60–182, including a `Sqlx(#[from] sqlx::Error)` variant and a `Migration(#[from] sqlx::migrate::MigrateError)` variant), an INI-driven `DatabaseConfig` defaulting to `sqlite:./personal-ledger.sqlite` (`config.rs`, lines 71, 200–210), and a per-entity `find`/`insert`/`update`/`delete`/`builder`/`model` file split (`categories/mod.rs`, lines 60–65). A Sync Server binary opening its own, second `SqlitePool` against its own SQLite file for the Change Set log would reuse every one of these conventions unchanged — a new `sync_log/` (or similarly named) module following the same per-entity file split, the same `DatabaseError`/`DatabaseResult` pattern, and `sqlx::migrate!` for schema evolution, exactly as `lib-database`'s existing `migrations/20241209000000_create_categories_table.sql` already does.

**Durability.** SQLite's own WAL documentation (https://sqlite.org/wal.html) states the write path is append-only and single-writer: "there can only be one writer at a time," but "writers and readers can run at the same time" because "writers merely append new content to the end of the WAL file" and do nothing that would interfere with concurrent readers (same source) — a good structural match for an append-heavy Change Set log read concurrently by multiple polling Client cursors. Durability is a `PRAGMA synchronous` choice: "writers sync the WAL on every transaction commit if `PRAGMA synchronous` is set to `FULL` but omit this sync if `PRAGMA synchronous` is set to `NORMAL`" (same source) — i.e. crash-safety after a power loss is opt-in per the chosen synchronous level, the same tradeoff any SQLite-backed service makes, not something specific to this use case. Checkpointing (folding the WAL back into the main database file) happens automatically "whenever a COMMIT occurs that causes the WAL file to be 1000 pages or more in size, or when the last database connection on a database file closes" (same source), but the same page warns that "a long-running read transaction can prevent a checkpointer from making progress" — worth flagging as an operational watch-item if a Client cursor implementation were to hold a long-lived read transaction open rather than issuing short, discrete polling queries (the `crsql_changes`-style cursor query pattern in §1.2 — a `SELECT ... WHERE seq > ?` per poll — avoids this by construction, since each poll is its own short transaction). `sqlx`'s own SQLite driver supports WAL directly via `SqliteConnectOptions::journal_mode()`, and per its own docs, "a database created in WAL mode retains the setting and will apply it to all connections opened against it that don't set a journal_mode" (docs.rs, `sqlx_sqlite::SqliteConnectOptions`) — a one-line addition to whatever `DatabaseConfig`-equivalent the Sync Server ends up using.

**Backup/restore.** SQLite's own corruption-avoidance guidance (https://sqlite.org/howtocorrupt.html) is explicit that a live database file must not be copied with a plain file-copy tool while it might be written to, and specifically for WAL mode: any backup "must" also copy "the write-ahead log (the `*-wal` file)... together with the database file itself," or the copy can end up "with some old and some new content" and be corrupt. The same page recommends three sanctioned live-backup approaches instead: the `sqlite3_rsync` tool (SQLite 3.47.0+), the `VACUUM INTO filename` SQL statement, or the C-level Online Backup API — any of these, run against the Sync Server's own database file from inside its container (or via a sidecar/cron job targeting the mounted volume), gives a concrete, primary-source-backed backup story for NFR.8's still-open backup/restore question, at essentially zero new operational surface beyond "run a SQL statement or a bundled CLI tool against the one file already living on the one persistent volume."

**Docker/single-volume fit.** Because the Sync Server's Change Set store is just a file (plus its `-wal`/`-shm` siblings), it needs nothing beyond the same single persistent volume mount FC-SYNC-006 already specifies for "the Sync Server's own durable store" — no second container, no separate healthcheck, no network port to secure.

### 2.2 PostgreSQL

**Durability.** PostgreSQL's own WAL-reliability documentation states that "all data recorded by a committed transaction should be stored in a nonvolatile area safe from power loss, OS failure, and hardware failure" (PostgreSQL documentation, "Reliability and the Write-Ahead Log", https://www.postgresql.org/docs/current/wal-reliability.html), achieved via `fsync` calls governed by `wal_sync_method`, full-page images written before in-place page modification so partial writes can be repaired on crash recovery, and a CRC-32C checksum on every WAL record verified during crash and replication recovery. The `synchronous_commit` setting (https://www.postgresql.org/docs/current/runtime-config-wal.html) defaults to `on`; PostgreSQL's own docs note that turning it `off` "does not create any risk of database inconsistency: an OS or database crash might result in some recent allegedly-committed transactions being lost, but the database state will be just the same as if those transactions had been aborted cleanly" — i.e. Postgres's durability engineering is, unsurprisingly, mature and well-documented, and would be more than sufficient for a Change Set log.

**Operational cost versus this project's actual deployment model.** The practical issue is not durability but topology. PostgreSQL's official Docker image (https://hub.docker.com/_/postgres) is a full server process, not an embeddable library — it needs its own container, its own healthcheck, and (per the image's own documented behaviour) version-specific volume-mount care: PostgreSQL 18+ changed the default data directory and `VOLUME` declaration to be version-namespaced (`/var/lib/postgresql/18/docker`), while versions ≤17 require the volume to be mounted at `/var/lib/postgresql/data` specifically — mounting the parent `/var/lib/postgresql` directory instead is documented as an anonymous-volume trap that "will NOT persist database data when the container is re-created." Running as non-root inside the container is supported but "does care (and needs the user to exist in `/etc/passwd`)" per the same image documentation — more setup friction than a SQLite file simply owned by whatever non-root user the Sync Server's own process already runs as. None of this is a durability problem; it is a second moving part (a second container/service in the Compose file, its own volume-mount discipline, its own backup tooling — `pg_dump`/`pg_basebackup`, neither of which was found documented on the official image page itself and would need separate research) that this project's stated deployment model — "no separate DB server process desired unless justified," a single persistent volume, Docker-only, homelab-trusted-network (§6.1 Assumptions) — does not obviously need for a Change Set log sized for one self-hoster's device fleet. It is also worth noting as a standing observation, not a recommendation either way: `sqlx`'s `postgres` feature is already compiled into this workspace's dependency graph (root `Cargo.toml`, `[workspace.dependencies].sqlx.features`) even though `CLAUDE.md` and `lib-domain` are SQLite-only today — i.e. Postgres capability already exists in the build without a documented reason found elsewhere in this workspace, which slightly lowers (but does not eliminate) the marginal integration cost of adopting it here specifically, since the driver dependency is already present.

### 2.3 `sled`

Per crates.io (https://crates.io/api/v1/crates/sled), `sled`'s newest version is `1.0.0-alpha.124`, dual MIT/Apache-2.0, created 2017-09-06, and was **last published 2024-10-11** — roughly two years stale relative to this research date, against a GitHub repository (`spacejam/sled`) still showing some push activity (`pushed_at: 2026-04-04`, 9,080 stars, 172 open issues, not archived) — the same "stale published crate, somewhat-active repo" pattern this repo's own `desktop-gui-frameworks.md` flagged for `plotters`/`cursive`. More materially, `sled`'s own README is explicit about its own production-readiness, in its own words: "if reliability is your primary constraint, use SQLite. sled is beta," "quite young, should be considered unstable for the time being," and "the on-disk format is going to change in ways that require manual migrations before the 1.0.0 release!" (https://github.com/spacejam/sled). Its durability model is also weaker by default than SQLite's per-commit-`fsync` option: "sled automatically fsyncs every 500ms by default" unless the application explicitly calls `flush()`/`flush_async()` — a documented window of up to half a second of un-fsynced writes on crash, versus SQLite WAL's per-commit `FULL`-synchronous option (§2.1). `sled` also states it "does not support multiple open instances for the time being," a single-process constraint that would not obviously matter for one Sync Server process but is worth recording. There is no SQL query layer — cursor-range queries over a sequence-number key would be hand-rolled against `sled`'s sorted-keyspace API — and no schema-migration tooling comparable to `sqlx-cli`/`sqlx::migrate`. Combined with its own README steering reliability-sensitive users toward SQLite instead, `sled` does not present a compelling case against the incumbent option for this specific use case.

### 2.4 `redb`

Per crates.io (https://crates.io/api/v1/crates/redb), `redb`'s newest version is `4.2.0`, dual MIT/Apache-2.0, created 2018-09-23, and was **last published 2026-08-17** — current as of this research — with 10.3 million downloads; its GitHub repository (`cberner/redb`) shows 4,765 stars, only 12 open issues, and `pushed_at: 2026-09-03`, the most actively-maintained of the two KV candidates by a wide margin. Its own README markets it explicitly on crash-safety terms: "fully ACID-compliant transactions," "crash-safe by default," "savepoints and rollbacks," and "MVCC support for concurrent readers & writer, without blocking" (https://github.com/cberner/redb), benchmarked by its own maintainers against `lmdb`, `rocksdb`, `fjall`, and SQLite itself, claiming "similar performance to other top embedded key-value stores." Its `Durability` API (docs.rs, https://docs.rs/redb/latest/redb/enum.Durability.html — a non-exhaustive enum, so may gain variants across versions) documents, in the version fetched, two levels: `None` ("commits with this durability level will not be persisted to disk unless followed by a commit with `Durability::Immediate`") and `Immediate` ("commits with this durability level are guaranteed to be persistent as soon as `WriteTransaction::commit` returns") — i.e. `redb` does offer a documented, per-transaction, immediate-fsync durability guarantee comparable in spirit to SQLite's `synchronous=FULL`. Its data model (`Table`/`MultimapTable`, typed via `Key`/`Value` traits, with a `Range` type for key-range iteration) supports cursor-style range queries over a sequence-number key directly — closer to a SQL `WHERE seq > ?` than `sled`'s raw KV scan — via `ReadTransaction`/`WriteTransaction` objects with savepoint/rollback support.

Two real gaps remain against this project's stack specifically. First, `redb`'s API is synchronous/blocking — no async or `tokio` integration is mentioned anywhere in its README or root docs.rs page — so a `tokio`-based Sync Server (this workspace pins `tokio = "1.48.0"` with the `full` feature set at the workspace level) would need to route every `redb` transaction through `tokio::task::spawn_blocking` or a dedicated blocking thread, the standard pattern for blocking I/O inside an async runtime; this is an inference from `redb`'s documented API shape, not something `redb`'s own docs discuss or recommend, since they do not address async usage at all. Second, like `sled`, there is no SQL layer and no schema-migration tooling comparable to `sqlx-cli`/`sqlx::migrate` — any indexing, cursor-range logic, or future schema change would be hand-written against `redb`'s typed-table API rather than expressed as `.sql` migration files the way the rest of this workspace already does (`lib-database`'s `migrations/` directory, `[package.metadata.sqlx] migrations = "migrations"` in `lib-database/Cargo.toml`). No evidence was found in `redb`'s own README, docs.rs pages, or redb.org of a documented log/queue-shaped usage example specifically (as distinct from its general key-value/range-query capability) — its own comparisons are framed against other general-purpose embedded KV stores, not against log-structured or queue-shaped systems.

## 3. Recommendation

This is feasibility-cycle research feeding a later, separate ADR-writing ticket — not the ADR itself. The reasoning below is scoped deliberately to what FC-SYNC-001/003 actually need: a working demonstration of push/pull sync with offline catch-up for a **single self-hosted user's own small device fleet**, deployed in a **trusted homelab network** (§6.1 Assumptions), not a fully generalised, multi-tenant, adversarial-network sync protocol (explicitly out of scope per §7's "multi-device sync protocol" and "conflict resolution strategy" future-considerations entries).

**On conflict resolution (§1):** start with **last-write-wins**, at **per-field** granularity (following PowerSync's documented default, §1.1), backed by a Hybrid-Logical-Clock-style timestamp rather than a bare wall-clock value, with the originating Client's stable ID as the tie-breaker. This is the smallest strategy that satisfies FC-SYNC-003's actual demonstration bar (basic push/pull sync with offline catch-up, not conflict-free correctness), and it matches the honest state of the art found in this research: even Turso's own purpose-built offline-sync product ships conflict *detection* without automatic *resolution* today (§1.1, §1.3), and PowerSync — the most mature LWW implementation surveyed — still frames pure timestamp-based LWW as a starting point with several documented escape hatches (sequence-number versioning, field-level tracking, server-side conflict recording) rather than a universally sufficient answer. Full CRDT adoption (cr-sqlite-style per-column CRDT registers, §1.2) is the natural next step if this feasibility demo reveals LWW's silent-data-loss behaviour is unacceptable even for a single user's own small device fleet — Personal Ledger's domain shape (single-entry Transaction rows with a narrow, mostly-independent field set: amount, Category, Account, Payee, description, date, Transaction Status, Flagged, per `CONTEXT.md`) is a reasonable fit for per-column LWW registers specifically, since most concurrent edits from one user's own devices would touch different fields (e.g. Flagging a Transaction on the phone while editing its description on the desktop) rather than the same field — but adopting cr-sqlite itself, or an equivalent per-column CRDT layer, is real additional engineering scope this feasibility cycle does not need to take on to satisfy FC-SYNC-003. Manual merge (§1.3) is not recommended as the primary strategy for this cycle: it requires a conflict-presentation UI that does not exist yet in either the Desktop or TUI client, which is a larger scope addition than FC-SYNC-003 calls for, though the causal/version metadata LWW needs anyway (a per-Change-Set version/parent pointer) is cheap enough to capture from the start so that a future manual-merge or CRDT upgrade path is not foreclosed. Concretely, whatever Change Set shape FC-SYNC-003 lands on should carry, at minimum: a stable Change Set ID (this project's own `RowID` — UUIDv7-based, time-ordered, already used project-wide per `crates/libs/lib-domain/src/row_id.rs` and FR.21 — is a natural, already-established fit rather than inventing a new ID scheme), the target table/row/field identifiers, the new value, an HLC-style timestamp, the originating Client's stable ID, and a version/parent-version field even if nothing consumes it yet — this keeps the CRDT and manual-merge upgrade paths open at near-zero cost now, rather than requiring a Change Set log schema migration later just to add the fields a stronger strategy would need.

**On the Change Set log storage engine (§2):** use **SQLite via `sqlx`**, consistent with the rest of the stack. Every constraint this PRD actually states points the same direction: no separate DB server process desired unless justified (nothing in this research justified one — PostgreSQL's durability is not in question, only its unnecessary operational weight for a single-user homelab deployment), a single persistent volume (a SQLite file plus its WAL sidecar file needs nothing else), Docker-only with a non-root container (a file owned by the container's own non-root user, versus Postgres's documented extra non-root/`initdb` friction), and near-zero integration cost against `lib-database`'s already-established `thiserror`-wrapped-error, explicit-column-SQL, per-entity-file-split, `sqlx::migrate!`-driven conventions (§2.1) — a new Change Set log module can copy `categories/`'s file layout directly. `sled` is not recommended: its own README recommends SQLite over itself for reliability-sensitive use, and its published crate is two years stale. `redb` is the most credible embedded-KV alternative found — current, well-documented durability levels, genuinely crash-safe by its own account — but it buys nothing SQLite doesn't already provide here, while costing a real integration gap (no `sqlx`/`tokio` story, meaning `spawn_blocking` plumbing throughout; no SQL query layer or migration tooling, meaning cursor-range logic and schema evolution would be hand-rolled instead of reusing patterns already proven in this codebase). PostgreSQL is not recommended for this cycle for the operational reasons above, not for any durability shortfall — it remains a reasonable candidate to revisit explicitly if a future cycle's requirements genuinely need a client-server RDBMS's concurrent-writer model (SQLite's WAL mode is single-writer, §2.1) at a scale this single-user, homelab-deployed product is not described as targeting.

Neither recommendation above is a locked decision — that is the job of the separate ADR-writing ticket this research feeds. What this document adds for that ticket: a concrete default (per-field LWW over an HLC-backed timestamp, on a `sqlx`-backed SQLite Change Set log reusing `lib-database`'s existing conventions) that satisfies FC-SYNC-003's demonstration bar without foreclosing a later upgrade to CRDT-based or manual-merge conflict handling, and a primary-source-cited account of why each alternative was set aside for *this* cycle specifically, so the ADR can either ratify this default or explain, with the same rigor, why it chose otherwise.
