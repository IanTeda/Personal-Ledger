# Research: Sync Server authentication mechanisms

**Research.** GitHub issue #43 ("Research sync-server auth mechanisms"), a child of the "Sync Server feasibility" Wayfinder map (issue #40, FC-SYNC-001–007), asks for primary-source research into authentication mechanisms for securing gRPC calls between the Sync Server and its Clients, corresponding to `docs/product-requirements.md` §2.1 requirement FC-SYNC-002: "Investigate and research authentication mechanisms (e.g. OAuth2, JWT, etc.) and implement a secure auth flow for the sync server and client." This note covers only the investigate/research half of FC-SYNC-002; implementation is separate, later work, and the actual choice is deferred to decision ticket #45 ("Decide auth mechanism and record ADR"). The deployment profile shapes the whole analysis: the Sync Server is a headless, Docker-packaged gRPC service (Rust + `tonic`) run by a single self-hoster in their own homelab, syncing 2-3 Rust Clients (Desktop and TUI app instances, each holding a full local SQLite Ledger copy). Per the PRD's Assumptions (§6.1), "the Sync Server is assumed to run within the user's own trusted network (e.g. a homelab), not exposed directly to the public internet; authentication protects against other devices on that trusted network, not against a hostile network." This is a single-user/single-household deployment, not multi-tenant SaaS — there are no third-party clients and no need to support arbitrary untrusted app developers.

All claims below are cited to primary sources — the relevant RFCs (RFC 6749, RFC 7519, RFC 8705, RFC 8446), crates.io's JSON API (`https://crates.io/api/v1/crates/<name>`), the GitHub REST API (`api.github.com`) for star/fork/issue counts and last-push timestamps, and the crates'/frameworks' own repositories and documentation (`tonic`'s own `examples/` directory, `jsonwebtoken`'s README, `rustls`/`rcgen` repos, spiffe.io, Tailscale's own docs) — not blog posts or third-party tutorials. Research was carried out on 2026-09-03; version numbers, download counts, and star/issue counts are a snapshot as of that date and will drift. One notable finding from this research: the `tonic` gRPC crate's canonical GitHub repository has moved from `hyperium/tonic` to `grpc/grpc-rust` (confirmed via the GitHub API, which 301-redirects `api.github.com/repos/hyperium/tonic` to `api.github.com/repos/grpc/grpc-rust`); its `Cargo.toml` still lists `homepage`/`repository` as `https://github.com/hyperium/tonic`, and the crates.io package name and API remain `tonic` — code and citations below use the `grpc/grpc-rust` path since that is what the redirect resolves to today.

## 1. Summary comparison table

| Mechanism | Threat-model fit (trusted-but-not-fully-trusted LAN) | Implementation complexity (Rust/`tonic`) | Operational burden (self-hoster, Docker Compose) | Single-household fit |
|---|---|---|---|---|
| **OAuth2** (§2) | Protects against unauthorised Clients if an authorization server exists — but that server is itself a piece of infrastructure that would need building/running just for this | High — no identity provider exists in this deployment; even the narrowest grant (client-credentials) requires implementing or running an authorization server | High — a second service to deploy, configure, and keep patched, for a single household | Poor — designed for third-party delegated access; the delegation/consent machinery has no one to serve here |
| **JWT (as bearer-token format)** (§3) | Protects against a device on the LAN without the shared signing secret impersonating a Client | Low-medium — `jsonwebtoken` crate (encode/decode) plus a `tonic::Interceptor`; self-issued, no IdP | Low-medium — one secret (or keypair) to provision per deployment; token rotation/expiry needs a renewal path | Good — token format without OAuth2's role/consent machinery |
| **mTLS** (§4) | Protects against impersonation *and* eavesdropping/tampering (transport-layer); strongest of the candidates here | Medium — `tonic`'s built-in `ServerTlsConfig`/`ClientTlsConfig` + `rustls` backend, demonstrated in `tonic`'s own example | Medium — self-signed CA once, then a cert issued per Client; rotation/revocation is manual (no CRL/OCSP wiring shown in `tonic`'s API) | Good for 2-3 Clients; issuance/rotation toil scales with Client count, which is small here |
| **Pre-shared token / API key** (§5) | Protects against a device without the shared secret; weakest against a compromised/leaked secret (no per-Client revocation without redistributing to all) | Very low — a metadata header check in a `tonic::Interceptor`, `subtle`-crate constant-time compare | Very low — one `.env` value in Docker Compose | Good — matches the scale and the "config, not infrastructure" feel of a homelab deployment |
| **HMAC-signed requests** (§6.1) | Adds per-request integrity/replay protection over a bearer token; marginal gain if transport is already TLS-protected | Medium — `hmac`/`sha2` crates, but needs canonical request serialisation + nonce/timestamp/replay-window logic hand-rolled | Medium — same secret-distribution story as pre-shared tokens, plus more code to maintain | Questionable — extra complexity for a threat (request tampering in flight) already covered by TLS |
| **SPIFFE/workload identity** (§6.2) | Strong identity guarantees, but for a *fleet* of dynamic workloads, not a fixed handful of long-lived processes | High — requires running a SPIFFE-compatible identity infrastructure (e.g. SPIRE) | High — an entire additional distributed system to operate | Poor — explicitly designed for the opposite scale (Kubernetes/microservice fleets) |
| **Tailscale/WireGuard (network layer)** (§6.3) | Different layer entirely — restricts *which devices can reach the Sync Server at all*, complementary to (not a substitute for) application-layer auth | Low for the self-hoster (managed product), but out of this repo's control — no Rust integration work | Low-medium — another account/tool to operate, outside Docker Compose itself | Good as a complement; doesn't answer FC-SYNC-002 on its own |

## 2. OAuth2

**What it is designed for.** RFC 6749's abstract states OAuth2 "enables a third-party application to obtain limited access to an HTTP service, either on behalf of a resource owner by orchestrating an approval interaction between the resource owner and the HTTP service, or by allowing the third-party application to obtain access on its own behalf" (RFC 6749, https://www.rfc-editor.org/rfc/rfc6749). It defines four roles — resource owner, client, authorization server, resource server — built around delegated access: a user (resource owner) granting a third-party app (client) limited access to their data on some service, without handing over their password. None of the Sync Server's Clients are third-party apps acting on behalf of an end user in this sense; both the Desktop and TUI Clients are the same person's own software, syncing their own Ledger.

**Client Credentials grant as the minimal fit.** The closest OAuth2 flow to this deployment's shape is the Client Credentials grant (RFC 6749 §4.4): "the client can request an access token using only its client credentials (or other supported means of authentication) when the client is requesting access to the protected resources under its control" — i.e. machine-to-machine, no resource-owner interaction. This is essentially OAuth2 stripped down to "present a client ID/secret, receive a bearer token" — but even this minimal flow still requires an authorization server that validates client credentials and issues/signs tokens. In this deployment, nothing already plays that role: there is no existing identity provider (no Keycloak, Auth0, Okta, etc. deployed), and standing one up purely to authenticate 2-3 Clients against a single Sync Server means running and maintaining a second service for a self-hosted single-household deployment.

**Rust ecosystem.** `oauth2` (crates.io API, `https://crates.io/api/v1/crates/oauth2`) is "An extensible, strongly-typed implementation of OAuth2," max version 5.0.0, last published 2025-01-21 — but it is an OAuth2 *client* library (for consuming someone else's authorization server), not a server implementation. `oxide-auth` (crates.io API, `https://crates.io/api/v1/crates/oxide-auth`) is "A OAuth2 library for common web servers, featuring a set of configurable and pluggable backends" for building an authorization *server*, max version 0.6.1, last published 2024-06-02 — over two years stale relative to this research date. Building a minimal client-credentials authorization server on `oxide-auth` (which targets `actix-web`/generic HTTP servers, not `tonic`/gRPC natively) would be extra integration work layered on top of an infrequently-updated crate.

**Bottom line.** OAuth2's entire value proposition — delegated, revocable, scoped access on behalf of a resource owner across multiple independent client developers — has no one to serve in a single-household deployment with no third-party clients and no existing identity provider; even its narrowest grant type still requires standing up authorization-server infrastructure that doesn't otherwise need to exist here.

## 3. JWT (JSON Web Tokens)

**What it is, independent of OAuth2.** RFC 7519's abstract: "JSON Web Token (JWT) is a compact, URL-safe means of representing claims to be transferred between two parties" (RFC 7519, https://www.rfc-editor.org/rfc/rfc7519). JWT is a token *format*, not a protocol for how tokens get issued or exchanged — it says nothing about OAuth2, authorization servers, or delegation. It can be used standalone: the Sync Server self-issues signed tokens to Clients out-of-band (e.g. printed to a terminal on first Client setup, or set via a config value), Clients present the token as a bearer credential on each call, and the Sync Server verifies the signature and the `exp` claim without needing any external IdP.

**Signing algorithm choice.** RFC 7519 §8 requires implementations to support HS256 (HMAC-SHA256, symmetric/shared-secret) and "none" (unsecured, and which any real deployment should reject), and recommends RS256 (RSA, asymmetric) and ES256 (ECDSA P-256, asymmetric) as widely supported (RFC 7519, §8). For this deployment — one Sync Server minting tokens, verifying its own tokens, with no third party ever needing to verify a token independently — HMAC (HS256) is the simpler choice: a single shared secret does both signing and verification, with no keypair management. Asymmetric signing (RS256/ES256) would only earn its extra complexity if some other party needed to verify tokens without being able to mint them, which doesn't apply here.

**Expiry/rotation.** RFC 7519 §4.1.4: "The 'exp' (expiration time) claim identifies the expiration time on or after which the JWT MUST NOT be accepted for processing," with implementations permitted "some small leeway, usually no more than a few minutes, to account for clock skew." A self-issued-token design needs to decide a rotation story independent of the RFC: either long-lived tokens (months/years, reissued only when a Client is reset) or short-lived tokens with a refresh mechanism — the latter reintroduces meaningful complexity (a refresh endpoint, refresh-token storage) that OAuth2 exists to standardise, so a homelab-scale JWT design would likely lean toward simple long-lived tokens tied to Client re-provisioning rather than building a refresh flow from scratch.

**Rust crate: `jsonwebtoken`.** crates.io API (`https://crates.io/api/v1/crates/jsonwebtoken`) shows max/stable version 11.0.0, 180,801,219 total downloads, 45,064,283 recent downloads, MIT-licensed (crates.io + GitHub API, `Keats/jsonwebtoken`). GitHub API: 2,089 stars, 362 forks, 59 open issues, not archived, last pushed 2026-07-24 — actively maintained. Its README (`https://github.com/Keats/jsonwebtoken/blob/master/README.md`) lists supported algorithms HS256/384/512, RS256/384/512, PS256/384/512, ES256/384, and EdDSA, and requires selecting one of two crypto backend features, `aws_lc_rs` or `rust_crypto` (or supplying a custom `CryptoProvider`). **Interceptor-friendliness with `tonic`:** `jsonwebtoken::encode`/`decode` are synchronous, pure functions operating on `Header`/`Claims`/`EncodingKey`/`DecodingKey` values with no async runtime or transport dependency — this shape drops directly into `tonic`'s synchronous interceptor signature `Fn(Request<()>) -> Result<Request<()>, Status>`, the same signature `tonic`'s own bearer-token example (`grpc/grpc-rust`, `examples/src/authentication/server.rs`, fetched during this research — see §5) uses for a static-string comparison; swapping that static comparison for a `jsonwebtoken::decode` call is a small, mechanical change.

**Bottom line.** JWT-as-a-format (self-issued, HMAC-signed, no external IdP) gives most of what a pre-shared token gives — a single shared secret, cheap `tonic`-interceptor validation — plus structured claims (issuer, expiry, arbitrary per-Client metadata) and a well-maintained, widely-used crate (`jsonwebtoken`) for encoding/decoding, at the cost of slightly more code than a bare string-equality check.

## 4. mTLS (mutual TLS)

**What it is.** RFC 8446 (TLS 1.3) states the protocol is designed to "prevent eavesdropping, tampering, and message forgery" (RFC 8446, https://www.rfc-editor.org/rfc/rfc8446), and specifies that "the server side of the channel is always authenticated; the client side is optionally authenticated" — client authentication uses a `CertificateRequest` message from the server and `Certificate`/`CertificateVerify` messages from the client, the same certificate-based mechanism used for server authentication. mTLS means turning on that optional client-side authentication: both parties present X.509 certificates and each verifies the other's, at the transport layer, before any application data flows. RFC 8705 (OAuth2's mutual-TLS extension) is relevant here purely for its framing of "client-cert-as-identity," independent of OAuth2 itself: it describes mTLS client authentication as verifying "the client's certificate subject against registered values" — i.e. the certificate itself, not a bearer token, is what proves identity (RFC 8705, https://www.rfc-editor.org/rfc/rfc8705). RFC 8705 also separately defines certificate-bound access tokens, which is an OAuth2-specific mechanism not relevant to a non-OAuth2 mTLS design.

**`tonic`'s native support.** `tonic` 0.14.6's own `Cargo.toml` (fetched from `grpc/grpc-rust`, `tonic/Cargo.toml`) exposes TLS as first-party feature flags: `tls-ring`/`tls-aws-lc` (rustls crypto backends via `tokio-rustls`), plus `tls-native-roots`/`tls-webpki-roots` for root-store sourcing — TLS is not bolted on via a third-party crate for the base functionality. `tonic`'s own worked example demonstrates client-certificate auth directly (`grpc/grpc-rust`, `examples/src/tls_client_auth/{server,client}.rs`, fetched during this research):

- Server side builds `ServerTlsConfig::new().identity(server_identity).client_ca_root(client_ca_cert)` and reads the verified peer certificates per-request via `request.peer_certs()`.
- Client side builds `ClientTlsConfig::new().domain_name(...).ca_certificate(server_root_ca_cert).identity(client_identity)`.

This confirms `tonic` supports both directions of mTLS (server verifying client certs against a configured CA, and client verifying the server) as built-in `tonic::transport` API, not a third-party add-on. A separate crate, `tonic-rustls` ("Provide support for custom rustls configs in tonic servers and clients," crates.io API, `https://crates.io/api/v1/crates/tonic-rustls`, v0.3.0, ~1.25M total downloads) exists for cases needing a customised `rustls::ClientConfig`/`ServerConfig` beyond what `tonic`'s built-in wrapper exposes, but is not required for the baseline mTLS shown above.

**Certificate tooling.** `rcgen` ("Rust X.509 certificate generator," crates.io API, `https://crates.io/api/v1/crates/rcgen`) is at v0.14.10, 94.9M total / 25.7M recent downloads, maintained under the `rustls` GitHub org, last updated 2026-08-28 — actively maintained and a natural fit for generating a self-signed CA plus per-Client leaf certificates without external tooling (no need for `openssl` CLI). `rustls` itself (crates.io API) is at stable 0.23.43, 880M total / 189M recent downloads, GitHub API shows 7,592 stars, pushed 2026-09-02 (i.e. the day before this research) — very actively maintained.

**Operational burden.** A self-hoster running the Sync Server plus 2-3 Clients would need to: (1) generate a self-signed CA once, (2) issue a leaf certificate + key per Client (a handful of certs, not a fleet), (3) distribute each Client's cert/key alongside its connection config, and (4) reissue if a Client's key is ever compromised or a cert expires. Neither `tonic`'s TLS API surface nor its example shows any certificate-revocation-list (CRL) or OCSP integration — the demonstrated pattern relies on expiry (and manual reissuance) rather than live revocation, which is a realistic simplification at this scale (a handful of long-lived Client certs, not thousands) but is worth flagging as a gap versus what mTLS looks like in larger deployments. For 2-3 Clients this issuance/rotation toil is small; it would not stay small if this design were later reused for many more Clients.

**Bottom line.** mTLS is the only candidate here that protects the transport itself (confidentiality/integrity), not just identity, and `tonic` supports it natively with a working first-party example to build from — the cost is running a (self-signed, single-CA) PKI, which is modest but non-zero at 2-3 Clients and has no built-in revocation story beyond cert expiry.

## 5. Pre-shared tokens / API keys

**Mechanism.** A static (or semi-static) secret, distributed out-of-band — e.g. a Docker Compose environment variable or `.env` file value — sent by the Client as a gRPC metadata header and checked server-side. `tonic`'s own example directory demonstrates exactly this pattern (`grpc/grpc-rust`, `examples/src/authentication/{server,client}.rs`, fetched during this research). Server side:

```rust
let svc = pb::echo_server::EchoServer::with_interceptor(server, check_auth);
// ...
fn check_auth(req: Request<()>) -> Result<Request<()>, Status> {
    let token: MetadataValue<_> = "Bearer some-secret-token".parse().unwrap();
    match req.metadata().get("authorization") {
        Some(t) if token == t => Ok(req),
        _ => Err(Status::unauthenticated("No valid auth token")),
    }
}
```

Client side attaches the header via the same `with_interceptor` mechanism on `EchoClient`, inserting an `authorization` entry into `req.metadata_mut()`. This is `tonic::service::Interceptor` — a plain closure of type `Fn(Request<()>) -> Result<Request<()>, Status>` — which is the cheapest integration point in the stack: no extra crate is required for the mechanism itself (`tonic`'s `metadata::MetadataValue`/`MetadataMap` types are already part of the base `tonic` dependency).

**Comparison-safe validation.** The literal example above uses `MetadataValue`'s `PartialEq`, which is not guaranteed constant-time; a production version should use a constant-time comparison to avoid timing side-channels. `subtle` ("Pure-Rust traits and utilities for constant-time cryptographic implementations," crates.io API, `https://crates.io/api/v1/crates/subtle`) is at v2.6.1, 672M total / 152M recent downloads, maintained by `dalek-cryptography` — an easy, already-widely-used dependency for this. Whether timing side-channels matter on a LAN-only, single-household deployment is itself part of the "trusted but not fully trusted" framing: the PRD's assumption is that auth protects against another device on the trusted network, not a hostile network attacker capable of the kind of precise timing measurement a side-channel attack needs — so constant-time comparison is cheap insurance rather than a load-bearing requirement here.

**Hashing the stored token.** Whether the Sync Server should store the token hashed (vs. plaintext in its own config) is a smaller question here than in a multi-tenant service: the token is self-hoster-controlled config (a `.env` value), not a secret the Sync Server itself generates and must protect from its own administrators — the administrator and the token owner are the same person. This repo's existing convention (`CLAUDE.md`: "Wrap secrets/tokens in `secrecy::Secret` so they can't leak into logs/traces") already covers the in-memory handling concern regardless of at-rest hashing; hashing mainly matters if the token store could be read by someone other than the person who already has the token, which isn't the case for a single Compose `.env` file.

**Rotation story.** Rotation means generating a new token value and updating it in every Client's config plus the Sync Server's config — for 2-3 Clients this is a few file edits and a restart, not a distributed rollout problem. There's no way to rotate one Client's credential without also updating the Sync Server's accepted value unless multiple tokens are accepted simultaneously (a small extra bit of server-side logic: a set of valid tokens rather than one, so old and new can overlap during rotation).

**Bottom line.** This is the cheapest mechanism to implement in the `tonic` stack — `tonic`'s own examples directory shows the exact pattern already — and its operational model (`.env` value, manual rotation) matches how a Docker Compose homelab deployment already manages other config/secrets; its main weakness is that a leaked token grants full access until manually rotated, with no scoping or per-Client revocation unless the server is extended to track multiple valid tokens.

## 6. Other credible candidates

### 6.1 HMAC-signed requests

Rather than a bearer token attached once, each request (or request envelope) is signed with an HMAC computed over its contents plus a nonce/timestamp, and the server recomputes and compares. `hmac` ("Generic implementation of Hash-based Message Authentication Code (HMAC)," crates.io API, `https://crates.io/api/v1/crates/hmac`) is at v0.13.0, 555M total / 138M recent downloads, maintained under the `RustCrypto/MACs` GitHub org. Unlike the bearer-token pattern, `tonic` has no worked example for this — it would need custom code to canonicalise request content, generate/track nonces, and define a replay window, on top of the HMAC computation itself. The main thing HMAC-signing buys over a static bearer token is protection against a captured token being replayed by an attacker who can observe traffic but not derive the key, and integrity-checking of request contents in transit — both of which TLS already provides if the transport is encrypted (which any of JWT or pre-shared-token designs would presumably run over TLS regardless, for confidentiality). On a trusted LAN with TLS already in place for transport, HMAC-signed requests mostly duplicate protection TLS already gives, at the cost of meaningfully more code to write and maintain than a bearer token.

### 6.2 SPIFFE / workload identity

SPIFFE (Secure Production Identity Framework For Everyone) provides "a set of open-source standards for securely identifying software systems in dynamic and heterogeneous environments," addressing the fact that "conventional security practices struggle in modern cloud-native infrastructures like microservices and container orchestrators," via short-lived X.509 or JWT "SVIDs" workloads use to authenticate each other across Kubernetes, VMs, and distributed systems (spiffe.io, "Overview," https://spiffe.io/docs/latest/spiffe-about/overview/). Adopting it means running a SPIFFE-compatible identity infrastructure (e.g. the SPIRE reference implementation) alongside the Sync Server — an entire additional distributed system whose value proposition is managing identity across many dynamically-scheduled workloads. A single, long-lived Sync Server process plus 2-3 long-lived Clients is exactly the opposite of the "dynamic and heterogeneous" fleet SPIFFE targets.

### 6.3 Network-layer alternatives: Tailscale / WireGuard

Tailscale is "a secure networking solution" built on "the open source WireGuard protocol" that "creates a peer-to-peer mesh network (known as a tailnet)," where devices authenticate (tied to an identity/SSO login on Tailscale's side) to join the tailnet and then get encrypted, direct WireGuard connections to each other (Tailscale docs, "What is Tailscale?", https://tailscale.com/kb/1151/what-is-tailscale). This is explicitly a different layer from anything else in this document: it governs *which devices can reach the Sync Server's network address at all*, not what a Client presents to the gRPC service once connected. If the Sync Server and all Clients already run on the same tailnet (or a WireGuard mesh set up by hand), that materially shrinks who can even attempt to speak to the Sync Server's gRPC port — but it does not by itself distinguish one Client from another once inside the tailnet, and it depends on a third-party service (for Tailscale specifically) or manual WireGuard key management (for a hand-rolled mesh), neither of which is Rust/`tonic` application code. It is worth the decision ticket noting as a complementary layer that could reduce (not eliminate) the need for strong application-layer auth, but it doesn't answer FC-SYNC-002 on its own since the requirement is specifically about the sync server/client auth flow.

## 7. Summary for the decision ticket

This research does not recommend or select a mechanism — that is decision ticket #45's job. The trade-offs surfaced here, for whoever picks up #45:

- **OAuth2** is the clearest non-fit: its entire value proposition (delegated access across independent third-party clients via an authorization server) doesn't correspond to anything in this deployment, and even its minimal client-credentials grant requires standing up authorization-server infrastructure that doesn't otherwise need to exist for 2-3 self-owned Clients. The Rust ecosystem's OAuth2-server option (`oxide-auth`) is also over two years stale as of this research.
- **JWT-as-a-format** and **pre-shared tokens** are close cousins in this deployment: both are single-shared-secret schemes checked in a `tonic::Interceptor`, and `tonic`'s own examples directory demonstrates the bearer-token shape both would use. JWT adds structured claims (expiry, issuer, arbitrary metadata) and a well-maintained crate (`jsonwebtoken`) for a modest amount of extra code over a bare string comparison; whether that structure is worth having versus a simpler opaque token is an open question for #45.
- **mTLS** is the only candidate that protects the transport itself, not just identity, and is natively supported by `tonic` with a working example — but it's the only candidate requiring PKI operations (self-signed CA, per-Client cert issuance, expiry-based rotation with no revocation-list support shown in `tonic`'s API). Open question for #45: is transport-level protection worth the added certificate-lifecycle operational surface at this small a Client count, especially if TLS is already going to be used for confidentiality regardless of which application-layer auth is chosen (i.e., is the question "TLS or not" separate from "mTLS or bearer-token auth over TLS")?
- **HMAC-signed requests** and **SPIFFE** both scored poorly against this deployment's scale in this research — HMAC-signing mostly duplicates protection TLS already provides, and SPIFFE targets a fleet-scale problem this deployment doesn't have — but are included for completeness in case #45 wants to explicitly rule them out with reasons on record.
- **Tailscale/WireGuard** sits outside the application-layer question entirely; #45 should decide whether it's in scope to lean on at all (the PRD's trusted-network assumption already gestures at something like this), or whether FC-SYNC-002's auth flow should be designed to stand on its own regardless of network topology.
- A cross-cutting open question not resolved here: whichever application-layer mechanism is chosen, is it expected to run over plain TLS (server-authenticated only, for confidentiality) regardless — in which case mTLS is really "the same TLS setup, plus client certs," not a wholly separate transport decision from JWT/pre-shared-token?
