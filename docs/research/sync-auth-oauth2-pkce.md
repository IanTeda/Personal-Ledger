# Research: Native-app OAuth2 Authorization Code + PKCE for Sync Server login

**Research.** A follow-up to `docs/research/sync-auth-mechanisms.md` (GitHub issue #43), scoped during decision ticket #45 ("Decide auth mechanism and record ADR") once the actual desired UX was pinned down: the user puts the Sync Server's address into the Desktop or TUI Client and clicks "authenticate"; a system browser opens to a login page served by the Sync Server itself; the user enters a username and password there; once validated, the browser closes and the Client holds credentials to call the gRPC API, staying logged in indefinitely afterwards (silent renewal, not a re-prompt on every launch). This is not a delegated-access scenario — there is no third-party identity provider, and the Sync Server plays both the OAuth2 authorization-server and resource-server roles for its own Clients. `docs/research/sync-auth-mechanisms.md` §2 already covers OAuth2's basic roles and RFC 6749's Client Credentials grant; this note does not repeat that and instead covers the specific native-app/browser/PKCE variant of OAuth2 the chosen UX requires, plus the crates and architectural changes it needs in this codebase.

All claims below are cited to primary sources — RFC 8252, RFC 7636, RFC 6749 §6, Google Identity's own native-app OAuth2 documentation, `tonic`'s own `docs.rs` API reference and `examples/` directory, and crates.io's/GitHub's APIs — not blog posts or third-party tutorials. Research was carried out on 2026-09-03, continuing the same session/date as `sync-auth-mechanisms.md`; version numbers and download counts are a snapshot as of that date.

## 2. RFC 8252 — OAuth 2.0 for Native Apps

**Scope.** RFC 8252's abstract states: "OAuth 2.0 authorization requests from native apps should only be made through external user-agents, primarily the user's browser. This specification details the security and usability reasons why this is the case and how native apps and authorization servers can implement this best practice" (RFC 8252, https://www.rfc-editor.org/rfc/rfc8252). This is exactly the shape of the requested UX: Desktop/TUI Client → system browser → Sync Server's own login page → back to the Client.

**Loopback redirect, §7.3.** The RFC permits native apps on desktop operating systems to receive the authorization response via a loopback address with a dynamically chosen port: "That is, `http://127.0.0.1:{port}/{path}` for IPv4, and `http://[::1]:{port}/{path}` for IPv6." Critically, the authorization server cannot require a fixed port to be pre-registered: "The authorization server MUST allow any port to be specified at the time of the request for loopback IP redirect URIs, to accommodate clients that obtain an available ephemeral port from the operating system at the time of the request" (RFC 8252 §7.3). Practically, this means the Sync Server's `/authorize` and `/token` endpoints must accept whatever `redirect_uri` port the Client presents at request time (as long as the host is a loopback address), rather than a single hardcoded value in Sync Server config.

**Why not an embedded webview, §8.12.** RFC 8252 §8.12 is explicit about why the Client must hand off to the *system* browser rather than opening its own embedded webview to render the login form: "the app that hosts the embedded user-agent can access the user's full authentication credential, not just the OAuth authorization grant that was intended for the app," including that "the host application can record every keystroke entered in the login form to capture usernames and passwords, automatically submit forms to bypass user consent, and copy session cookies." This directly serves the stated goal of this ticket — never storing a persistent username/password in the Client's own config/memory — by keeping the password entirely inside the system browser's process, never inside the Desktop/TUI binary at all.

## 3. RFC 7636 — Proof Key for Code Exchange (PKCE)

**Problem it solves.** RFC 7636's abstract: "OAuth 2.0 public clients utilizing the Authorization Code Grant are susceptible to the authorization code interception attack" (RFC 7636, https://www.rfc-editor.org/rfc/rfc7636). A "public client" here means exactly what the Desktop/TUI Clients are: an app with no way to hold a confidential client secret (unlike a server-side web app), because the Client binary itself — installed on the user's own machine — is not a secret-keeping environment. PKCE mitigates this "through the use of Proof Key for Code Exchange."

**Mechanics.** Per RFC 7636 §3–§4.6: the Client generates a `code_verifier`, "a cryptographically random string that is used to correlate the authorization request to the token request," and derives a `code_challenge` from it — for the `S256` method (RFC 7636 §4.2, and mandatory when supported: "If the client is capable of using 'S256,' it MUST use 'S256'"), `code_challenge = BASE64URL-ENCODE(SHA256(ASCII(code_verifier)))`. The Client sends only the `code_challenge` in the authorization request (§4.3); the Sync Server "records `code_challenge` and `code_challenge_method`" alongside the issued authorization code (§4.4); when the Client redeems the code at the token endpoint, it additionally sends the original `code_verifier` (§4.5); the Sync Server re-derives the challenge from the presented verifier and compares it to what it recorded, continuing "as normal" only on a match (§4.6). This closes the exact gap a public client (no secret) has: even if the authorization code is intercepted in transit to the loopback listener, the interceptor cannot redeem it without the `code_verifier`, which never left the Client's memory until the token request.

## 4. Real-world precedent

Google's own OAuth2-for-native-apps documentation describes the identical pattern for desktop apps: "Query your platform for the relevant loopback IP address and start an HTTP listener on a random available port," with the redirect URI taking the form `http://127.0.0.1:port` or `http://[::1]:port`; after the user authenticates in the browser, "Google redirects back to the local server with the authorization code" (Google Identity, native-app OAuth2 docs, fetched 2026-09-03). The same page states Google "supports the Proof Key for Code Exchange (PKCE) protocol to make the installed app flow more secure," and marks the loopback approach as the recommended option specifically for "macOS, Linux, and Windows desktop apps" (deprecated for mobile/Chrome, which use different native mechanisms) — the same target set as this repo's Desktop Client. This confirms the loopback-redirect-plus-PKCE design is an established, widely deployed pattern for exactly this app shape (a desktop-class native app authenticating a user via a browser), not something specific to third-party-delegated-access services; nothing about the pattern requires the authorization server to belong to a different organisation than the client, so the Sync Server acting as its own AS is a legitimate use of the same mechanics.

## 5. Rust crates

**`axum` — HTTP surface for `/authorize` and `/token`.** crates.io API (`https://crates.io/api/v1/crates/axum`): "HTTP routing and request handling library that focuses on ergonomics and modularity," max stable version 0.8.9, 452,141,765 total / 111,250,619 recent downloads. GitHub API (`tokio-rs/axum`): 27,011 stars, 1,474 forks, 78 open issues, not archived, pushed 2026-09-01 — actively maintained, and under the same `tokio-rs` umbrella as `tonic`'s ecosystem.

**Sharing one port with the existing `tonic` service.** `docs.rs/tonic/0.14.6` (the same version already pinned by `sync-auth-mechanisms.md`'s research) documents `tonic::service::Routes::into_axum_router()`, described as: "Convert this `Routes` into an `axum::Router`," plus `axum_router_mut()` for mutating it further, and `impl From<axum::Router> for Routes` for the reverse direction. This means the existing `bin-sync-server` gRPC `Routes` and a new axum `Router` serving `/authorize` and `/token` (and the login HTML form) can be merged into a single `axum::Router` and served from one Hyper server on one port — no second listener, no second exposed port to add to the Docker image or Compose file.

**`oauth2` — Client-side PKCE/token-exchange helper.** crates.io API (`https://crates.io/api/v1/crates/oauth2`): "An extensible, strongly-typed implementation of OAuth2," max stable version 5.0.0, 48,135,437 total / 11,669,440 recent downloads. GitHub API (`ramosbugs/oauth2-rs`): 1,203 stars, 212 forks, 49 open issues, not archived, pushed 2026-02-22. This is the same crate `sync-auth-mechanisms.md` §2 already found to be a maintained *client*-only library (not an authorization-server implementation). It models the generic Authorization Code + PKCE flow (verifier/challenge generation, building the authorization URL, exchanging the code) against a spec-shaped AS reachable over HTTP(S) — usable for the Desktop/TUI Client's half of this flow. Whether it is *worth* adopting versus hand-rolling the small amount of PKCE logic directly (generate 32+ random bytes, base64url-encode, SHA-256, build two URLs) is an open question: the crate buys type-safety and spec conformance for a flow this repo's Sync Server won't implement 100% conformantly on the server side anyway (no dynamic client registration, no discovery document), so its generic abstractions may cost more integration effort than they save at this small a scope.

**`argon2` — password hashing for the new user store.** crates.io API (`https://crates.io/api/v1/crates/argon2`): "Pure Rust implementation of the Argon2 password hashing function with support for the Argon2d, Argon2i, and Argon2id algorithmic variants," max stable version 0.6.0, 49,644,124 total / 17,898,603 recent downloads. GitHub API (`RustCrypto/password-hashes`): 904 stars, 114 forks, 15 open issues, not archived, pushed 2026-08-27 — actively maintained, same `RustCrypto` org already implicitly trusted by this repo's dependency tree (per `sync-auth-mechanisms.md` §5/§6.1's `hmac`/`subtle` findings).

**`keyring` — Client-side long-lived credential storage.** crates.io API (`https://crates.io/api/v1/crates/keyring`): "All-in-One Rust Keyring," max stable version 4.2.0, 23,141,409 total / 9,535,484 recent downloads. GitHub API (`open-source-cooperative/keyring-rs`): 765 stars, 66 forks, 0 open issues, not archived, pushed 2026-08-29 — actively maintained. Its own name and crates.io positioning claim cross-platform OS-credential-store backing (Linux Secret Service/keyutils, macOS Keychain, Windows Credential Manager), which matches this repo's existing three-OS Desktop packaging (`docs/adr/0008-cargo-packager-for-desktop.md`); this note does not independently verify each backend's behaviour beyond what crates.io/GitHub surface — that would be an implementation-time check, not a research-time one.

## 6. Refresh tokens and "stay logged in indefinitely"

RFC 6749 §1.5 defines the mechanism this UX needs: "Refresh tokens are credentials used to obtain access tokens. Refresh tokens are issued to the client by the authorization server and are used to obtain a new access token when the current access token becomes invalid or expires," and critically, refresh tokens are presented only to the authorization server, never to the resource server — "The client requests a new access token by authenticating with the authorization server and presenting the refresh token" (§1.5, flow step G), decoupling this from any change to how the gRPC resource-server side validates access tokens. This is what "stay logged in indefinitely" actually means in OAuth2 terms: the browser login happens once, mints a refresh token stored in the Client's OS keychain (via `keyring`), and the Client silently exchanges it for short-lived JWT access tokens thereafter — the user is never returned to the browser unless the refresh token itself is revoked or lost (e.g. keychain cleared, explicit logout).

RFC 6749 gives almost no guidance beyond this: issuing a refresh token at all is explicitly discretionary ("Issuing a refresh token is optional at the discretion of the authorization server," §1.5), and the RFC "does not detail refresh token expiration policies, rotation mechanisms, or revocation procedures" — these are implementation-specific decisions. Concretely, for whoever writes the ADR, "indefinitely" resolves to one of two shapes, both of which are the Sync Server's own design choice, not something RFC 6749 hands us:

- **A long-lived, non-rotating refresh token** — simplest; a single stored secret with no expiry (or a very long one, e.g. one year), checked against a server-side record on each use. A leaked refresh token (e.g. exfiltrated from a compromised Client machine) grants indefinite access until manually revoked.
- **A rotating refresh token** — each use of the refresh token both mints a new access token *and* issues a new refresh token, invalidating the old one; the Client updates what's stored in its keychain each time. This adds a small amount of server-side bookkeeping (tracking the "current" valid refresh token per Client, detecting reuse of an already-rotated-out token as a signal of theft) in exchange for a live signal if a refresh token is ever cloned/exfiltrated and used from two places.

## 7. Architectural implications for this codebase

This flow is a materially bigger increment than the mechanisms compared in `sync-auth-mechanisms.md`, worth flagging explicitly for the ADR:

- **New HTTP surface.** `crates/bins/bin-sync-server` currently wires only a `tonic` gRPC serve loop around `lib_rpc`'s stub `Ping` RPC (per `CLAUDE.md`). This flow requires adding `/authorize` (renders/accepts the login form) and `/token` (exchanges an authorization code + `code_verifier` for tokens) HTTP endpoints. §5 above shows this can share one port with the existing gRPC service via `tonic`'s `Routes::into_axum_router()` — it does not need a second exposed port or a second container — but it is still new request-handling surface (HTML rendering or a minimal login form, HTTP-level CSRF/state-parameter handling) that doesn't exist in the codebase today.
- **New persisted schema.** Validating a username/password requires a user store — at minimum a username and an Argon2 hash — which is new schema, distinct from and unrelated to the Change Set log schema `ADR-0009` fixed for reconciliation. Whether this lives in the same SQLite database/file as the Change Set log (reusing `lib-database`'s conventions per `CLAUDE.md`) or a separate one is an open question for the ADR.
- **New Client-side responsibilities.** The Desktop and TUI Clients both need: a way to launch the system browser (platform-specific, though crates like `open` exist for this — not researched here as it's a small, uncontroversial utility), a temporary loopback HTTP listener to catch the redirect, PKCE verifier/challenge generation, and `keyring`-backed refresh-token storage. This is new code in whatever crate ends up hosting Client-side sync logic (per issue #40's notes, that placement — new crate vs. inside `lib-database` — is left as implementation detail for issue #46).
- **Single-user vs. multi-user user store.** The PRD's deployment profile (§6.1) is a single self-hoster with 2-3 of their own Clients — nothing in the requirements calls for *multiple distinct human users* of one Sync Server. Whether the new user store supports exactly one hardcoded/first-run-provisioned account or is designed to hold multiple is a scope question the ADR should settle explicitly, since it changes whether "user management" (adding/removing accounts) needs any interface at all.

## 8. Summary for the decision

This research does not make the final call — that's the ADR's job. What it establishes:

- The requested UX (browser-based login, no stored password in the Client, stay logged in indefinitely) maps cleanly onto a well-established, non-novel pattern: OAuth2 Authorization Code + PKCE over a loopback redirect (RFC 8252 §7.3, RFC 7636), the same pattern Google's own native-app guidance recommends for desktop apps — and it can be self-hosted (Sync Server as both AS and resource server) without needing a third-party IdP, resolving the earlier research's core objection to OAuth2.
- It is implementable without a second exposed port or container: `tonic` 0.14.6 already supports merging its gRPC `Routes` into an `axum::Router` and serving both from one Hyper listener.
- It costs more new surface than any mechanism `sync-auth-mechanisms.md` compared: a login HTTP surface, a password/user store (new schema, new hashing dependency), and meaningfully more Client-side code (browser launch, loopback listener, PKCE, keychain storage) versus JWT-bearer or pre-shared-token's "check a header in an interceptor."
- Open questions for the ADR: (1) rotating vs. non-rotating refresh tokens (§6); (2) where the new user-store schema lives relative to the Change Set log database; (3) whether the user store is designed for exactly one account or several, given the PRD's single-self-hoster profile; (4) whether to adopt the `oauth2` crate client-side or hand-roll the (small) PKCE logic directly, given the crate targets spec-conformant authorization servers more general than what this Sync Server will implement.
