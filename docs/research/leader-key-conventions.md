# Research: Leader-key conventions for a shared bin-tui/bin-desktop grammar

**Question.** [Issue #156](https://github.com/IanTeda/Personal-Ledger/issues/156), a child of the [TUI Keybindings & Shared Navigation Grammar](https://github.com/IanTeda/Personal-Ledger/issues/155) map, asks: should the shared grammar use a leader key, and what shape? Both clients already lean this way without a formal decision behind it — `bin-tui`'s `Shell` (`crates/bins/bin-tui/src/shell.rs`) has a `g`-then-letter jump leader (`pending_leader`) and opens its command popup on `Ctrl+;`; `bin-desktop`'s `Shell` (`crates/bins/bin-desktop/src/shell.rs`) has its own `g`-then-letter jump leader (`pending_g`, `jump_noun_for_key`) and opens its command palette on a bare `:`. The two already agree on a `g`-leader for jumps but disagree on how the command surface itself opens. This note investigates leader-key conventions in comparable tools, assesses whether one mechanism could cover both the jump grammar and command-surface opening, recommends an answer for the command-surface key, and works out how a leader-key scheme interacts with `KeyBindingConfig::super_key` (`crates/libs/lib-config/src/keybindings.rs`).

Research was done by reading this workspace's own `bin-tui`/`bin-desktop` `shell.rs` sources, `docs/ux/tui/navigation.md` (the TUI's own living navigation spec), the closed tickets behind the TUI command popup (`#85`, `#89`–`#98`) and the desktop shell map (`#144`–`#154`), the relevant commit history (`6777461`, `git log`), and `KeyBindingConfig`'s own doc comments — plus external primary sources for vim's leader-key and `g`-prefix conventions, Hyprland's/i3's modifier-key ("`$mainMod`") convention, and Helix's/k9s's/lazygit's own keybinding philosophies.

## Recommendation

1. **Do not unify the `g`-jump leader and command-surface opening into one mechanism.** They solve different problems and every relevant precedent (vim, Helix) keeps them separate too — see "Should one leader-key scheme cover both?" below. Keep two tiers instead: a released-prefix `g`-then-letter leader for the finite, mnemonic jump namespace, and a separate, single-keystroke way to open the command surface. This *is* the shared "general leader-key scheme" the ticket asks for — one documented grammar, not one literal keybinding.
2. **Converge on `bin-desktop`'s bare `:` for opening the command surface, not `bin-tui`'s `Ctrl+;`.** `bin-tui`'s own `Ctrl+;` was never a considered decision — it was an unreasoned deviation from the original handoff's bare `:`, flagged by its own implementer as "worth noting... in case that's meant to change" (issue #85) and never revisited. Bare `:` is the dominant convention among the closest peer tools (vim, k9s), costs one keystroke instead of two, and removes a real fragility `Ctrl+;` carries today: legacy terminal encoding collapses `Ctrl+;` onto the same control code as `Esc`, so it only became distinguishable at all by opting into the Kitty keyboard protocol's disambiguation extension (`crates/bins/bin-tui/src/shell.rs` commit `6777461`'s own message) — a non-universal terminal capability. `bin-desktop`'s `InputMode` state machine already proves the precondition that makes bare `:` safe (see below) holds in this codebase.
3. **`super_key` and the leader-key scheme compose; they don't compete, and neither leader makes `super_key` redundant.** `super_key` is a held-modifier chord (WM-style, its own doc comment says so explicitly); the `g`-leader is a released-prefix chord with its own pending/timeout state machine. They're mechanically different and cover disjoint command sets — `super_key` for atomic single-step global commands (`quit`, and optionally others), `g` for the multi-step jump namespace. Opening the command surface (`:`) is a third, separate, bare convention key, matching vim/k9s precedent, and should not be routed through `super_key` either. This directly informs [#158](https://github.com/IanTeda/Personal-Ledger/issues/158): not every "truly global" command needs `super_key`'s protection — both existing clients and vim's own precedent already treat `back`/`help`/opening-the-command-surface as bare keys, reserving the modifier for the one mistake that's actually costly to make by accident (`quit`).

## Survey: leader-key conventions in comparable tools

### Vim's two different "leader" concepts

Vim actually has two mechanisms commonly conflated as "the leader key," and the distinction matters directly for this app's own `g`-leader:

- **The user-customizable `<leader>`** (default `\`, commonly remapped to `,` or `Space`) is an open, user/plugin-defined namespace with no fixed meaning — "the beauty of the Leader key is it effectively gives us a namespace for customised keyboard shortcuts" ([Vim 101: What is the Leader Key?](https://medium.com/usevim/vim-101-what-is-the-leader-key-f2f5c1fa610f)). Because the namespace is open-ended and user-specific, its bindings aren't enumerable in advance, which is precisely why a discoverability layer grew up around it: `vim-which-key` "displays available keybindings in popup... an interactive cheat-sheet of the tree of keybindings" upon pressing the leader ([vim-which-key](https://github.com/chandlercjy/vim-which-key)). Choosing a leader key also has a real cost: it sacrifices that key's own default binding — `,` is popular specifically because "it's very easy to type" even though "it shadows a useful function" ([Vim 101](https://medium.com/usevim/vim-101-what-is-the-leader-key-f2f5c1fa610f)).
- **Built-in, vendor-defined reserved prefixes**, most notably `g` ("goto" motions: `gg`, `ge`, `gv`, `gf`, ...) and `z` (view/fold commands). These are finite, documented, non-customizable, and don't need a which-key layer because the completion set is small and stable. This is the precedent this app's own `g`-jump leader actually follows — not the open-ended `<leader>` namespace.

### Helix's `g`oto mode: the direct precedent for this app's `g`-jump leader

Helix, a modal terminal editor explicitly modelled in part on vim, has its own `g`oto submode (`gg` file start, `ge` file end, `gd` go to definition, and so on) — the same "reserved letter opens a small, mnemonic, single-completion namespace" shape as vim's own `g`-prefix, and the same shape `bin-tui`'s and `bin-desktop`'s `g`-then-letter jump chords already use. Helix's community has separately experimented with a `<leader>`-style key (its own discussion threads on "which key is good for a user leader key" treat it as a distinct, open, user-facing namespace question) — again keeping the two concepts apart rather than merging them ([Helix Discussion #7822](https://github.com/helix-editor/helix/discussions/7822)). This app's existing `g`-jump leader is already well-grounded in convention on both counts: it's the vim/Helix `g`oto-mode shape, not the vim `<leader>` shape, and it doesn't need to change to be "more general" — it already is the general, precedented form for a finite navigation namespace.

### The command-line key: bare `:`, and why it's safe

Vim's own ex-command line opens on a bare, unmodified `:` — no modifier, one keystroke. This is safe specifically because vim's Normal mode is airtight: no printable character ever means "insert this character into the buffer" while in Normal mode, so every bare key is available for commands. **k9s**, a Kubernetes TUI, follows the identical convention for the identical reason — bare `:` switches resource views, and its list/detail screens don't have ambient free-text fields competing for that keystroke. This corroborates bare `:` as the dominant convention among modal, keyboard-driven TUI tools specifically because — and only because — the mode separation underneath it is real, not just documented.

**Lazygit** is a useful contrast, not a confirming precedent: it has no unifying command palette at all. It favours direct, per-panel mnemonic single keys (`c` commit, `p` pull, and so on) plus a `?`/`x` cheat-sheet menu as its discoverability backstop, betting on breadth of direct keys over indirection through a namespace. This app has already made the opposite bet, explicitly: `docs/ux/tui/navigation.md`'s own "Philosophy" section states the TUI "has no menus, no breadcrumb trail, and no sidebar... everything else is reached through a single floating command popup," and that "every action must be reachable by name... a keybinding is a shortcut to a command, never the only path to it." Lazygit's model is noted here because it's a real, working alternative, not because it's live for this app — the registry+popup bet is already made and out of scope to revisit.

### Tiling window managers: `$mainMod` is a held modifier, not a released prefix

Hyprland's and i3's leader-equivalent is a modifier held down for the whole chord (`$mainMod`, defaulting to Super), not a key pressed and released before a following key. Hyprland's own convention binds essentially everything through `$mainMod+<key>` (`$mainMod+Tab` cycle focus, `$mainMod+1..0` switch workspace, `$mainMod+Shift+1..0` move window to workspace) ([Hyprland Binds](https://wiki.hypr.land/Configuring/Basics/Binds/)). This is a mechanically different class of "leader" from vim's `g` or `<leader>`: a modifier+key chord is atomic (one physical gesture, no pending state), can never collide with typed text (a modified keypress doesn't produce an insertable character), and needs no timeout or state machine. tmux's `Ctrl-b`/`Ctrl-a` prefix is the middle case — a genuine released-then-second-key leader like vim's `g`, but deliberately Ctrl-modified so the *first* key of the sequence also can't leak into whatever's running inside the pane. `bin-tui`'s own deviation to `Ctrl+;` for opening the command popup was reaching for this same tmux-style safety margin, just applied to a key (`:`) that, on this app's own evidence, didn't need it (see the recommendation above).

`KeyBindingConfig::super_key`'s own doc comment already draws the Hyprland analogy directly: "the modifier held down for global shortcuts (mirroring a window manager's `$mainMod`/prefix key, e.g. Hyprland's `$mainMod`)" (`crates/libs/lib-config/src/keybindings.rs`). So the codebase's existing design intent for `super_key` is already, explicitly, the WM held-modifier class of leader — not the vim `g`/`<leader>` released-prefix class.

## Should one leader-key scheme cover both the `g`-jump grammar and command-surface opening?

No — and every relevant precedent surveyed above agrees. vim keeps `g` (a reserved goto-mode prefix) and `:` (the ex-command line) as two separate mechanisms; Helix keeps its own `g`oto mode and its user-leader question separate too. The two problems this app has are genuinely different in shape:

- **`g`-jump is a finite, enumerable, mnemonic namespace** — one letter per domain noun, a small closed set, safely explorable because getting the second key wrong just aborts the chord (both `Shell`s already implement exactly this: `bin-tui`'s `pending_leader` and `bin-desktop`'s `pending_g` both clear unconditionally on the next keypress, "so an aborted chord never leaks into later keypresses").
- **Opening the command surface is a mode transition into an open-ended, typed-text, fuzzy-searched interaction** — not a "pick one of ~10 completions" action. It's also this app's own documented escape hatch: `docs/ux/tui/navigation.md` states plainly that a keybinding, including a chord, is "never the only path" to a command, precisely so a forgotten or mistyped chord never locks a user out. Nesting the popup's own open-shortcut inside the `g`-namespace (e.g. `g :` or similar) would make the single most important, most-used entry point in the whole app depend on remembering yet another chord — exactly backwards from what that escape-hatch commitment is for.

Collapsing both into one mechanism also buys nothing mechanically: whichever key opens the command surface still needs to be distinguishable from the very next keystroke of a `g`-chord in progress, so a truly unified scheme still ends up needing the same two pieces of state (a pending-jump flag and a mode flag) it has today, just relabelled. The right sense in which this ticket's "single, general leader-key scheme" should be read is **one coherent, documented grammar** — a single mental model of "modifier chord for atomic global actions, `g`-then-letter for jump navigation, `:` plus the popup for everything else by name" — not one literal keybinding covering every case. That's what `docs/navigation.md` (the sibling ticket, [#159](https://github.com/IanTeda/Personal-Ledger/issues/159)) should write down.

## Recommendation in detail: `Ctrl+;` vs bare `:`

[#155](https://github.com/IanTeda/Personal-Ledger/issues/155)'s own Notes flag `bin-desktop` as "prior art to converge toward by default, but not untouchably" — so the case for bare `:` has to stand on its own, not just inherit that default.

**Case for bare `:` (recommended):**

- It's the standard: vim's ex-command line, k9s's resource-navigation line, and this app's *own original* `docs/ux/tui/README.md` handoff (which `bin-tui`'s implementation deviated from) all use it.
- It's one keystroke instead of two, for the single highest-frequency entry point in the entire app per its own "everything is reached through the popup" philosophy.
- `bin-tui`'s `Ctrl+;` carries a real, documented fragility bare `:` doesn't: commit `6777461`'s own message states "`Ctrl+;` needed the Kitty keyboard protocol's `DISAMBIGUATE_ESCAPE_CODES` to be distinguishable at all on capable terminals (legacy encoding collapses it onto the same control code as `Esc`)" — i.e. on a terminal that doesn't support that Kitty extension, the shortcut degrades. Bare `:` has no such dependency.
- `bin-desktop`'s `InputMode` state machine (`Normal`/`Insert`/`Command`/`Search`) already proves, in working code, that the precondition making bare `:` safe holds here: `handle_key_down` gates every zone/movement/mode-entry key (`:` included) behind `if self.nav.mode() != InputMode::Normal { return had_status_message; }`, so `:` can never fire while some other mode owns the keyboard.
- The deviation was never a reasoned decision in the first place: issue `#85`'s closing comment flags it explicitly ("One deviation from spec worth noting: the window opens on `Ctrl+;` rather than a bare `:`... Flagging in case that's meant to change") and it was never revisited until now.

**Case against (why `bin-tui` chose `Ctrl+;`, and why it's not disqualifying):** `bin-tui`'s `Shell` doesn't yet have `bin-desktop`'s explicit top-level `InputMode` gate — its "popup-owned keys" tier (`command_popup`/`unit_popup`/`category_popup`/etc. all being `Option<...>`) only takes over once one of those popups already exists, so a *hypothetical future* `View` wanting inline free-text entry at the top level (a filter box, say) with no dedicated popup of its own could collide with a bare `:`. This risk is real in principle but speculative today — no current `View` needs top-level free text — and it has a cheap, already-proven mitigation: give that future `View` the same "fully own the keyboard while focused" treatment `unit_popup`/`category_popup`/`account_popup`/`tag_popup`/`payee_popup`/`settings_popup` already get, which is exactly the tiered-precedence model `docs/ux/tui/navigation.md` already documents. This is a real design discipline to hold going forward, not a reason to keep `Ctrl+;` today.

**Concrete shape of the change** (for the separate execution ticket, #159/whichever wires `bin-tui`'s `Shell` to `KeyBindingConfig` — not built here): `is_open_command_popup` in `crates/bins/bin-tui/src/shell.rs` becomes a bare, unmodified `:` check (optionally still accepting `Ctrl+;` for one release as a soft-deprecation, if backward compatibility during the transition matters); the prompt glyph stays `:` either way, since `docs/ux/tui/navigation.md` already notes it "still appears as the prompt glyph itself" even under the current `Ctrl+;` binding.

## `super_key` composition

`KeyBindingConfig::super_key` (`crates/libs/lib-config/src/keybindings.rs`) is, by its own doc comment, a held-modifier field "mirroring a window manager's `$mainMod`/prefix key" — mechanically the same class of leader as Hyprland's/i3's `$mainMod`, not the same class as this app's own `g`-then-letter jump leader (a released prefix with its own pending/timeout state) or the bare `:` command-surface key (a plain unmodified convention key). All three are real, legitimate mechanisms; they don't compete for the same keystrokes and none of them makes another redundant:

- **`super_key` composes with individual command bindings directly, and already does so selectively, not universally.** `KeyBindingConfig::bindings` is a flat command-name → key-string map (`#[serde(flatten)]`), not a forced `super_key + key` template — so whether a given command's key is modifier-gated is already a per-command choice the config format supports today. The shipped defaults already reflect this: `quit = "ctrl+c"` is modifier-gated (matching `super_key`'s own default of `"ctrl"`), while `back = "esc"` and `help = "?"` are bare, unmodified keys. Nothing about adopting a leader-key scheme for jumps/command-surface-opening requires changing this — `super_key` was already composing selectively, by design.
- **The `g`-jump leader doesn't make `super_key` redundant, and vice versa**, because they cover disjoint command sets by the map's own scoping: [#155](https://github.com/IanTeda/Personal-Ledger/issues/155)'s "Out of scope" section explicitly limits actual remapping to "the truly-global set (`quit`, `back`/`Esc`, `help`, opening the command popup)" and excludes "per-view/per-domain key remapping" — and `g`-jump chords are themselves per-view navigation shortcuts, not part of that truly-global set. `super_key`'s entire value (one atomic modifier+key press, no pending state, no chord-collision risk) is exactly what a released-prefix leader like `g` deliberately gives up in exchange for a larger, more mnemonic completion space; they're complementary tools for different jobs, not two implementations of the same job.
- **Opening the command surface (`:`) sits outside `super_key` entirely**, by the recommendation above — it's a third, bare convention key, matching vim/k9s precedent, not a `super_key`-modified command. That means the "truly global" set the map scoped in already splits into three different key *shapes*, today, in both existing clients: `quit` is modifier/shift-driven (`Ctrl+C` in `bin-tui`, `Q`/`q`), `back` is bare `Esc`, `help` is bare `?`, and opening the command surface is (recommended) bare `:`. This mirrors vim's own precedent directly — nothing in vim's core Normal mode requires a modifier for its most-global actions either (`:`, `?`, `Esc` are all bare there too).
- **What this means for [#158](https://github.com/IanTeda/Personal-Ledger/issues/158)** (which owns the actual super_key-composition decision, not this ticket): the evidence here supports scoping `super_key`'s protection to specific commands rather than requiring it universally across the truly-global set — in particular `quit`, where an accidental bare keypress ending the whole session is a materially costlier mistake than an accidental bare `Esc`, `?`, or `:`, each of which is cheap or free to undo (`Esc` is explicitly documented as "always safe to press" in `docs/ux/tui/navigation.md`). This isn't a decision this ticket makes — it's the input #158 asked for.
