# Research: `gpui-component` theming and the Desktop

**Question.** GitHub issue #297 ("Colour Themes: gpui-component theming and the Desktop"), a child of the "Colour Themes for the Desktop and TUI" Wayfinder map (#292), asks how `gpui-component` 0.5.x (pinned in `crates/bins/bin-desktop/Cargo.toml` as `gpui-component = { version = "0.5.1" }`, alongside `gpui = { version = "0.2.2" }`) does theming, and how Personal Ledger's own Colour Themes could drive it so its widgets (inputs, tables, charts, scrollbars, popovers) match the shell chrome. It asks specifically about `Theme`/`ThemeColor` fields, `ThemeRegistry` and its JSON theme files, `ThemeMode`, runtime switching and view re-render, chart series colours, and whether `bin-desktop`'s own `theme::color` constants should become a `gpui` `Global` of resolved Colour Roles, derive from `gpui-component`'s `Theme`, or feed it. This note is primary-source research only — it presents facts and options with trade-offs and does not decide anything, matching the map's "planning only" scope.

Vocabulary note, per `CONTEXT.md` and the map: a named set of colours here is a **Colour Theme**, never a "palette" (that word is reserved for the command palette in this codebase); a **Colour Role** is one named slot such as accent or background; a **Colour Variant** is the light or dark half of a Colour Theme; **Colour Appearance** is the user's Light/Dark/System choice.

## 2. `Theme` and `ThemeColor`: the global struct

`gpui_component::Theme` is a plain `struct` (not a trait), installed as a `gpui` `Global` (`impl Global for Theme {}`, `theme/mod.rs:98`) and read anywhere via the `ActiveTheme` trait's `fn theme(&self) -> &Theme`, implemented for `App` as `Theme::global(self)` (`theme/mod.rs:28-37`). `Theme` derefs to `ThemeColor` (`impl Deref<Target = ThemeColor> for Theme`, `theme/mod.rs:84-90`), so `cx.theme().background` reads straight through to the colour struct.

`Theme` itself (`theme/mod.rs:41-76`) bundles far more than colour:

- `colors: ThemeColor` — the ~90-field colour struct (below).
- `highlight_theme: Arc<HighlightTheme>` — syntax-highlight styling for the `Input` widget's code-editor mode (a Zed-theme-compatible `style` block); Personal Ledger has no code-editor surface, so this is inert for us but still ships with every `Theme`.
- `light_theme` / `dark_theme: Rc<ThemeConfig>` — the two `ThemeConfig`s (loaded JSON, see §4) that produced the currently-active `colors`, kept around so `Theme::change` can flip between them without reloading anything from disk.
- `mode: ThemeMode` — which of the two is currently active (§3).
- `font_family`/`font_size`/`mono_font_family`/`mono_font_size` — typography defaults (`.SystemUIFont` / 16px / platform-specific monospace / 13px).
- `radius`/`radius_lg` — corner radii (6px/8px defaults) and `shadow: bool` — whether components render drop shadows at all.
- `scrollbar_show: ScrollbarShow` — `Scrolling` (fade after idle, the default) / `Hover` / `Always`, seeded from the OS's own auto-hide-scrollbar preference via `Theme::sync_scrollbar_appearance` (`theme/mod.rs:141-147`, `cx.should_auto_hide_scrollbars()`).
- `tile_grid_size`/`tile_shadow`/`tile_radius` — the `dock`/tile-panel widget's own spacing/shadow/radius.

So `Theme` is `gpui-component`'s single global for *all* visual tokens (colour, type, radius, shadow, scrollbar behaviour), not a colour-only object — relevant to the map's note that "typography, spacing and radius get their own ticket": those live on this same struct, one level up from `ThemeColor`, and any option that adopts `Theme` wholesale inherits them too, whether or not Personal Ledger's own tickets are ready to make them configurable.

`ThemeColor` (`theme_color.rs:11-233`) is `#[derive(Debug, Default, Clone, Copy, ...)]` — a flat, `Copy`-able struct of `gpui::Hsla` fields, no nesting. Grouped by what it names (field name → doc comment, abbreviated):

- **Surfaces/text**: `background`, `foreground`, `border`, `muted`/`muted_foreground`, `overlay`, `window_border` (Linux-only, per its own doc comment).
- **Semantic actions**: `primary`/`primary_hover`/`primary_active`/`primary_foreground`, `secondary_*`, `accent`/`accent_foreground`.
- **Status**: `success_*`, `danger_*`, `warning_*`, `info_*` (background/hover/active/foreground quartets each).
- **Candlestick-specific**: `bullish`, `bearish` (up/down price colours — the crate's only chart-specific *semantic* pair beyond the generic `chart_N` series slots below).
- **Chart series**: exactly five slots, `chart_1`..`chart_5`.
- **Input**: `input` (border colour), `caret`, `selection`, `ring` (focus ring), `drag_border`, `drop_target`.
- **List/Table/Sidebar/Tab families**: each gets its own background/hover/active/border/foreground set, e.g. `table`, `table_active`, `table_active_border`, `table_even` (zebra striping), `table_head`, `table_head_foreground`, `table_hover`, `table_row_border`; `sidebar`, `sidebar_accent`, `sidebar_accent_foreground`, `sidebar_border`, `sidebar_foreground`, `sidebar_primary*`; `tab`, `tab_active`, `tab_active_foreground`, `tab_bar`, `tab_bar_segmented`, `tab_foreground`; `list`, `list_active`, `list_active_border`, `list_even`, `list_head`, `list_hover`.
- **Popover-family surfaces**: `popover`/`popover_foreground` — the shared background/text pair every floating panel (menu, tooltip, date picker, notification, search, colour picker) reads, per `Styled::popover_style` at `src/styled.rs:178-179` and its call sites.
- **Scrollbar**: `scrollbar`, `scrollbar_thumb`, `scrollbar_thumb_hover`.
- **Misc widget-specific**: `group_box`/`group_box_foreground`, `description_list_label`/`_foreground`, `progress_bar`, `skeleton`, `slider_bar`/`slider_thumb`, `switch`/`switch_thumb`, `tiles`, `link`/`link_hover`/`link_active`, `title_bar`/`title_bar_border`.
- **Base hues**: `red`/`red_light`, `green`/`green_light`, `blue`/`blue_light`, `yellow`/`yellow_light`, `magenta`/`magenta_light`, `cyan`/`cyan_light` — twelve raw colours most semantic fields fall back to (see §4) rather than user-facing roles in their own right.

`Theme::default()` builds from `ThemeColor::default()` (`theme/mod.rs:78-82`), and `ThemeColor` itself has no interesting `Default` (all-zero `Hsla`s) — the actually-used defaults come from `ThemeConfig` application (§4), not from `#[derive(Default)]`.

## 3. `ThemeMode` and Colour Appearance

`ThemeMode` (`theme/mod.rs:213-236`) is a two-variant enum, `Light` | `Dark`, `#[default]` `Light`. This maps exactly onto the domain's **Colour Variant** concept (light/dark half of a Colour Theme) — there is no third `ThemeMode` value, so "System" as a stored mode does not exist inside `gpui-component`; System-following is implemented one level up, by asking the platform. `From<WindowAppearance> for ThemeMode` (`theme/mod.rs:238-245`) collapses `gpui`'s own four-value `WindowAppearance` (`Dark`/`VibrantDark` → `Dark`, `Light`/`VibrantLight` → `Light`) down to the two-value `ThemeMode`.

`Theme::sync_system_appearance(window, cx)` (`theme/mod.rs:128-138`) reads the *current* OS/window appearance — preferring `window.appearance()` over `cx.window_appearance()` with a comment citing a Linux-specific bug (`longbridge/gpui-component#104`) if no window is given — and calls `Theme::change` with it. This is a one-shot read, not a subscription: `gpui-component` does not itself watch for a live OS appearance change and re-fire `Theme::change` automatically; `gpui_component::init(cx)` (`theme/mod.rs:21-26`) calls `sync_system_appearance` exactly once at startup. A Client wanting to *follow* an OS light/dark change while running (explicitly in the map's scope) would need to detect that change itself — via whatever `gpui`'s window-appearance-changed event is — and call `Theme::change`/`Theme::sync_system_appearance` again; this crate version does not wire that loop for you.

## 4. `ThemeRegistry`, `ThemeConfig`/`ThemeSet`, and the JSON theme files

`ThemeRegistry` (`registry.rs:76-268`) is a second `Global` (`impl Global for ThemeRegistry {}`), separate from `Theme`, holding: `themes_dir: PathBuf`, `default_themes: HashMap<ThemeMode, Rc<ThemeConfig>>` (exactly one light + one dark default), `themes: HashMap<SharedString, Rc<ThemeConfig>>` (every known theme by name, default and custom), and `has_custom_themes: bool`.

**On-disk shape.** A theme file deserialises as a `ThemeSet` (`schema.rs:14-26`): `{ name, author?, url?, themes: [ThemeConfig, ...] }`. Each `ThemeConfig` (`schema.rs:28-70`) carries `is_default: bool`, `name`, `mode: "light"|"dark"`, optional `font.size`/`font.family`/`mono_font.family`/`mono_font.size`/`radius`/`radius.lg`/`shadow`, a nested `colors: ThemeConfigColors` object, and an optional `highlight` block (Zed-theme-compatible). `ThemeConfigColors` (`schema.rs:72-405`) mirrors `ThemeColor`'s fields but every value is `Option<SharedString>` holding a **hex colour string** (`"#RRGGBB"` or `"#RRGGBBAA"`, parsed by `try_parse_color` at `schema.rs:408-411` via `gpui::Rgba::try_from`), and most JSON keys are dotted (`#[serde(rename = "...")]`), e.g. `"primary.background"`, `"table.head.background"`, `"sidebar.accent.foreground"`. The crate ships exactly one `ThemeSet` inside itself, `default-theme.json` (`theme/default-theme.json:1-5`: `name: "Default"`, `author: "shadcn"`, sourced from `ui.shadcn.com`), containing precisely two `ThemeConfig`s — `"Default Light"` and `"Default Dark"`, both `is_default: true`. There is no built-in gallery of additional named colour sets inside the crate; anything beyond these two is supplied externally.

**A schema/data mismatch worth flagging, at this pinned version.** `schema.rs`'s `ThemeConfigColors` renames the five chart fields to dotted keys — `#[serde(rename = "chart.1")]` through `"chart.5"` (`schema.rs:105-118`) — but the shipped `default-theme.json` writes them with underscores instead: `"chart_1": "#93c5fd"` … `"chart_5": "#1e40af"` (`default-theme.json:20-24` and again at `223-227`, identical values in both the light and dark blocks). Because `ThemeConfigColors` is `#[serde(default)]` with no `deny_unknown_fields`, `serde_json` silently ignores the unrecognised `"chart_1"` key rather than erroring, so `config.colors.chart_1` deserialises to `None` for both shipped themes. `ThemeColor::apply_config`'s `apply_color!(chart_1, fallback = self.blue.lighten(0.4))` (`schema.rs:553-557`) then takes the `None` branch, so the *actual* chart series colours `ThemeColor::light()`/`ThemeColor::dark()` produce at runtime are `blue` lightened/darkened by fixed steps (`lighten(0.4)`, `lighten(0.2)`, `blue` itself, `darken(0.2)`, `darken(0.4)`), not the literal shadcn hexes written in the JSON file. This is a fact about the pinned 0.5.1 snapshot specifically (worth re-checking on any future upgrade) and a concrete reason to write a Colour Theme's own chart series values using the dotted `"chart.1"`..`"chart.5"` keys the Rust struct actually reads, if exact series hexes matter, rather than assuming the shipped JSON is a reliable template to copy verbatim.

**Fallback chaining.** `ThemeColor::apply_config` (`schema.rs:413-641`) applies every colour through an `apply_color!` macro with two forms: a bare form that falls back to a passed-in `default_theme`'s same field if the JSON omits the key or fails to parse, and a `fallback = <expr>` form that computes a value from *other already-applied fields on `self`* (e.g. `accent` falls back to `self.secondary`; `success` falls back to `self.green`; `table` falls back to `self.list`). This means a from-scratch `ThemeConfig` only needs a handful of base colours (`background`, `red`/`green`/`blue`/`yellow`/`magenta`/`cyan`, `border`, `foreground`, `muted`, `primary`, `secondary`) to produce a fully-populated `ThemeColor` — most of the ~90 fields are derived, not independently authored, via `Colorize::blend`/`opacity`/`darken`/`lighten` composition (`color.rs`). Three fields get a post-pass forced-opacity clamp regardless of source (`list_active`, `table_active` capped at alpha 0.2, `selection` capped at 0.3 — `schema.rs:636-639`).

**Loading and hot reload.** `ThemeRegistry::watch_dir(themes_dir, cx, on_load)` (`registry.rs:98-118`) points the registry at a directory, spawns a background task, and (via `_watch_themes_dir`, `registry.rs:171-206`) uses the `notify` crate to watch it recursively for create/modify/remove events; on any such event it calls `reload_themes` → `reload()` (`registry.rs:208-267`), which re-reads every `*.json` file in the directory, parses each as a `ThemeSet`, and merges: default themes always win the name collision (`if self.themes.contains_key(&theme.name) { continue; }` for a custom theme sharing a default's name), a custom theme marked `is_default: true` replaces the registry's own `default_themes` entry for that `ThemeMode`, and `has_custom_themes` is set. This is a real live-reload path: editing a theme JSON file on disk while the app is running triggers a reload without restarting — directly relevant to the map's still-open "user-defined Colour Themes... dropped in as a file" question.

**The registry-to-active-theme link.** `registry::init` (`registry.rs:42-74`) additionally installs a `cx.observe_global::<ThemeRegistry>` callback: whenever the registry global changes (i.e., after a reload), it looks up the *currently active* light/dark theme names in the freshly-reloaded `themes` map, updates `Theme::global_mut(cx).light_theme`/`dark_theme` if a same-named entry still exists, then calls `Theme::change(mode, None, cx)` followed by `cx.refresh_windows()` (§5). So editing the on-disk file behind the currently-selected theme's name is enough to repaint live; renaming or deleting it leaves the in-memory `Theme` untouched (the stale `Rc<ThemeConfig>` it already holds keeps being used) until a differently-named theme is explicitly selected.

## 5. Switching at runtime and how views re-render

`Theme::change(mode, window, cx)` (`theme/mod.rs:150-170`) is the actual switch primitive: it lazily bootstraps a `Theme` global from `ThemeRegistry`'s current default light/dark configs if none exists yet, sets `theme.mode`, then calls `theme.apply_config(&theme.light_theme.clone())` or `&theme.dark_theme.clone()` depending on the new mode — i.e. **switching Colour Variant is just re-reading whichever `Rc<ThemeConfig>` is already cached on the `Theme` struct**, no disk I/O, and both Colour Variants' full derived-colour computation (`ThemeColor::apply_config`) reruns each time rather than being cached per-mode. If a `Window` handle is passed, `window.refresh()` is called at the end; the registry's own reload path instead calls the app-wide `cx.refresh_windows()` (§4) when the change is triggered by a background file-watch event rather than a direct in-window call.

Re-render itself is `gpui`'s own mechanism, not anything theme-specific: `Window::refresh()` (`gpui-0.2.2/src/window.rs:1367-1372`) "mark[s] the window as dirty, scheduling it to be redrawn on the next frame," and `App::refresh_windows()` (`gpui-0.2.2/src/app.rs:753-756`) "schedules all windows in the application to be redrawn... multiple times in an update cycle and still result in a single redraw." Neither `Theme` nor `ThemeColor` triggers any kind of subscription-based recomputation in consuming widgets — every `Render`/`Plot`/paint implementation across the crate calls `cx.theme()` fresh each time it runs (see the call sites cited in §1 and §6-§7), so a plain redraw is sufficient: nothing needs to be told which colour changed, because the next frame's render pass re-reads the live global from scratch. This is the same model `bin-desktop`'s own `Shell`/`View` code already runs under (immediate colour lookups inside `Render::render`), so adopting live Colour Theme switching does not require introducing any new observer/subscription plumbing on the consuming side — only calling `Theme::change` (or reloading `ThemeRegistry`) needs to happen at the point the user picks a new Colour Theme or Colour Appearance, and a `window.refresh()`/`cx.refresh_windows()` needs to follow it if `Theme::change` itself didn't already trigger one for that code path.

## 6. Chart series colours

There is no single "chart palette" object; each chart widget decides its own colour(s) at paint time, using `ThemeColor`'s few chart-shaped fields as defaults that a caller may override per chart instance:

- **`PieChart<T>`** (`chart/pie_chart.rs`) takes an optional `.color(|d: &T| -> Hsla { ... })` closure (`pie_chart.rs:100-107`); at paint time, per-arc, it calls that closure if set, else falls back to the single colour `cx.theme().chart_2` for every slice (`pie_chart.rs:139`). A multi-colour pie/donut therefore requires the caller to supply a mapping function — the natural place to plug in `cx.theme().chart_1..chart_5` (as this repo's own `feasibility_demo.rs:510-514` already does) or, per the options in §9, resolved Colour Role values instead.
- **`LineChart`**/**`AreaChart`** default their single series stroke/fill to `cx.theme().chart_2` if the caller didn't set `.stroke(...)`/`.strokes(...)` (`line_chart.rs:156`, `area_chart.rs:168,170`); axis text and gridlines use `muted_foreground`/`border` regardless.
- **`BarChart`** defaults its fill the same way (`bar_chart.rs:144: let default_fill = cx.theme().chart_2`).
- **`CandlestickChart`** uses the two semantic fields directly rather than the `chart_N` series: `cx.theme().bullish`/`cx.theme().bearish` chosen per-bar by whether `close > open` (`candlestick_chart.rs:183-188`).

So the crate's chart-colour contract is: five generic series slots (`chart_1`..`chart_5`) for callers who want theme-driven, multi-series colouring (most naturally via a `.color()`/`.strokes()` closure reading them, exactly as `feasibility_demo.rs` already does for its `PieChart`), plus two candlestick-only semantic slots (`bullish`/`bearish`) that are *not* configurable per-call — they always come from `cx.theme()`. Anything past five simultaneous series colours (a chart with more categories than that) is left entirely to the calling code; the crate has no cycling/interpolation helper for a sixth-plus series.

## 7. Widget survey: inputs, tables, scrollbars, popovers

- **Inputs** (`src/input/*.rs`): the text-input surface itself reads `background`/`editor_background()` (the latter falling back to `background` if `highlight_theme.style.editor_background` is unset, `theme/mod.rs:172-179`) for its fill, `input` for its border, `radius`/`shadow` for shape, `muted_foreground` for the spinner and placeholder-adjacent text, `caret` for the blinking cursor, and `selection` for selected-text highlight (`input/element.rs:1339-1349`, with `selection.alpha` pre-clamped to ≤0.3 per §4). The clear button and search dropdown separately reuse `muted_foreground` and the shared `popover`/`popover_foreground` pair (`input/clear_button.rs:15`, `input/search.rs:427-430`).
- **Tables** (`src/table/*.rs`): a dedicated family of ~9 fields — `table`/`table_active`/`table_active_border`/`table_even`/`table_head`/`table_head_foreground`/`table_hover`/`table_row_border` — plus `border`/`radius`/`drag_border` for the outer frame and column drag affordance (`table/mod.rs:126-130`, `table/column.rs:201-205`, `table/state.rs:643-901`). `table_even` is the zebra-stripe colour; note it falls back to `list_even` (`schema.rs:623`), which itself falls back to plain `list` (`schema.rs:588`) — so an author who only sets `list`/`list_even`-shaped roles gets table striping "for free" via the fallback chain, without setting the `table_*` keys at all.
- **Scrollbars** (`src/scroll/scrollbar.rs`): three fields (`scrollbar`, `scrollbar_thumb`, `scrollbar_thumb_hover`) plus the independent `scrollbar_show: ScrollbarShow` enum on `Theme` itself (not `ThemeColor`) controlling *when* the bar is drawn at all (`Scrolling`/`Hover`/`Always`), seeded once from the OS's own auto-hide preference (`theme/mod.rs:141-147`) and overridable per-scrollbar-instance (`scrollbar.rs:360`, `"if not set use the cx.theme().scrollbar_show"`).
- **Popovers** (menus, tooltips, the date picker, notifications, the colour picker, search's dropdown): all share one `Styled::popover_style()` helper (`src/styled.rs:178-179`) that sets `bg(cx.theme().popover)` and `text_color(cx.theme().popover_foreground)` — confirmed call sites in `menu/popup_menu.rs`, `tooltip.rs`, `time/date_picker.rs`, `notification.rs`, `color_picker.rs`, `input/search.rs`. There is no per-popover-kind colour override at the `ThemeColor` level; every floating panel in the crate shares this one background/foreground pair (distinguishing itself, if at all, by shadow/`radius_lg`/border rather than a different fill).

## 8. Where `bin-desktop` currently touches `ActiveTheme`/`Theme`

At `concept` HEAD (commit `7d3dcb1`), only two files in `crates/bins/bin-desktop/src` reference `gpui-component`'s theme system at all:

- **`main.rs`** calls `gpui_component::init(cx)` inside `Application::new().run(...)` (`main.rs:95`), which (per §2/§3) runs `ThemeRegistry::init`, seeds the two built-in default themes, and calls `Theme::sync_system_appearance(None, cx)` plus `Theme::sync_scrollbar_appearance(cx)` once at startup. Nothing in `main.rs` calls `ThemeRegistry::watch_dir`, sets a custom `ThemeConfig`, or calls `Theme::change` again after that one-shot init — `bin-desktop` currently runs on whatever `ThemeColor::light()`/`ThemeColor::dark()` (i.e. the shipped shadcn-derived default, chart-key mismatch and all, per §4) resolves to for the OS's current appearance at launch, with no in-app Colour Appearance/Colour Theme switching wired up yet.
- **`feasibility_demo.rs`** (the disconnected, `#[allow(dead_code)]` module ADR-0016 describes — kept compiling, not reachable from `main()`) is the *only* place that reads `cx.theme()`: `success`/`danger` for a chart legend, the `chart_1..chart_5` five-slot array for its `PieChart` colour closure, `border` for a zero-line, `muted_foreground` for axis text, and `background`/`foreground` for the demo window's own root fill (`feasibility_demo.rs:344-346,510-514,578-580,639,645,692-693`). ADR-0016's own doc comment on `theme.rs` states the intended split explicitly: `gpui-component`'s `ActiveTheme` "stays scoped to the chart/table widgets it already renders," while shell chrome code is meant to reach for `theme::color`'s own fixed constants instead.
- **`theme.rs`** itself (`bin-desktop/src/theme.rs:1-11`) is a from-scratch, hand-written module — `pub mod color { pub const GROUND: Rgba = ...; }` etc. — with **no dependency on `gpui_component::Theme`/`ThemeColor` at all**, not even a `use` of them. Its module doc explicitly frames its ~20 named constants (`GROUND`, `CHROME`, `INK`/`INK_SECONDARY`/`INK_TERTIARY`, `ACCENT`/`ACCENT_TEXT`, `BORDER`, `POSITIVE`, etc.) as "literal constants, not a themeable palette" sourced from the Modernist design handoff, deliberately outside `gpui-component`'s colour system, with only one dark-adjacent set of tokens (`INK_ON_DARK*`) for inverted rows — there is no light/dark Colour Variant pair here today, matching the map's own "Current state" note that `theme.rs` "holds the fixed 'Modernist' tokens (no dark variant)."

So today the two colour systems are entirely separate and neither observes the other: `theme::color`'s ~20 shell-chrome constants are compiled-in literals with no Colour Appearance awareness, and `gpui-component`'s `Theme`/`ThemeColor` (~90 fields plus type/radius/shadow/scrollbar tokens) drives only the disconnected chart/table feasibility demo, seeded once from the OS appearance at startup and never touched again.

## 9. Options for how `theme::color` could relate to `gpui-component`'s `Theme`

Three shapes the issue names, with the trade-offs this research surfaced for each. None is recommended here.

### Option A — our own `gpui` `Global` of resolved Colour Roles, independent of `Theme`

Personal Ledger defines its own `struct ColourTheme { ... }` (or similar), installs it as a `gpui::Global` the same way `gpui-component` installs `Theme`/`ThemeRegistry`/`GlobalState` (`global_state.rs` is a small, uncomplicated in-crate precedent for exactly this pattern: `cx.set_global(...)`, `Global` marker impl, `global(cx)`/`global_mut(cx)` accessors), resolves the active Colour Theme + Colour Appearance into it, and shell code reads it via its own accessor (an `ActiveColourTheme`-style trait, mirroring `ActiveTheme`).

- *For*: total control over the Colour Role set's shape/names (matches CONTEXT.md's own vocabulary exactly, not constrained by `ThemeColor`'s ~90-field, `gpui-component`-invented naming); no coupling to `gpui-component`'s schema/versioning; `theme.rs`'s existing constant-module structure could become this `Global`'s `Default` value with comparatively little churn to call sites already written as `theme::color::ACCENT`-style paths (only the access pattern, constant → global lookup, changes).
- *Against*: `gpui-component`'s own widgets (inputs, tables, charts, scrollbars, popovers) never read this global — they only ever read `Theme`/`ThemeColor` (§2, confirmed by every call site cited in §6-§7). Leaving `Theme` on its shipped default while our own `Global` changes means `gpui-component` widgets visually diverge from shell chrome the moment a non-default Colour Theme or Colour Appearance is chosen — the exact "match the shell chrome" requirement in the issue's own question would not be met without *also* pushing values into `Theme` some other way (which starts to overlap with Option C). Two parallel colour stores also means keeping the light/dark Colour Variant switch and any live Colour-Appearance-follow logic (§3) synchronised in two places rather than one.

### Option B — derive our Colour Roles from `gpui-component`'s `Theme`

Colour Role accessors become thin wrappers reading `cx.theme().<field>` directly (e.g. a `Roles::accent(cx)` that returns `cx.theme().primary`), with no separate `Global` of our own; `theme::color`'s constants are replaced by functions/methods over the live `Theme`.

- *For*: exactly one colour source of truth at runtime — `gpui-component` widgets and shell chrome always agree, by construction, because both read the same global; switching Colour Variant/Colour Appearance (§5) is a single `Theme::change` call and every consumer, ours and `gpui-component`'s, repaints from the same values on the next `refresh`; the ~90 already-derived fields (§4's fallback chaining) mean a Colour Theme author gets a lot of coverage from only a handful of authored base colours.
- *Against*: our Colour Role set is then constrained to (a subset of, or a relabelling of) `ThemeColor`'s existing field names and semantics, which were designed by `gpui-component`/shadcn for a general component library, not for this app's own Colour Role vocabulary from CONTEXT.md — a Colour Role the design work wants that doesn't map cleanly onto an existing `ThemeColor` field (or maps onto one whose *other* consumers give it a different implied meaning, e.g. `accent` is documented as "used for accents such as hover background on MenuItem, ListItem," not necessarily the same thing as this app's own accent-discipline rule in `theme.rs`'s module doc) has nowhere to live without extending `ThemeColor` itself, which is a type owned by an upstream crate — not something this codebase can add fields to without forking. `theme.rs`'s existing Modernist-specific tokens with no `ThemeColor` analogue at all (`STRUCTURAL_RULE`, `RAIL_DIVIDER`, `HOVER_TINT`, `DIVIDER`, `PALETTE_SHADOW`, `DIALOG_SHADOW`, `TAG_ACCENT_BG`/`_TEXT` — none of these correspond to any of the ~90 `ThemeColor` fields enumerated in §2) would need a home outside this option entirely, i.e. Option B likely can't be the *whole* answer on its own.

### Option C — feed `gpui-component`'s `Theme` from our Colour Themes

Personal Ledger's Colour Theme resolution (whatever the architecture ticket on the map settles on) produces a `gpui_component::ThemeConfig` (or an on-disk `ThemeSet` JSON matching `theme/schema.rs`'s shape, §4) per Colour Variant, and installs it via `Theme::apply_config`/`ThemeRegistry` machinery rather than by hand-authoring a parallel struct; `theme::color`'s own Modernist-specific extra tokens (the ones with no `ThemeColor` analogue, listed under Option B) stay as a small separate set layered on top, but the ~90 shared roles flow through `gpui-component`'s own struct so its widgets automatically match.

- *For*: `gpui-component` widgets are guaranteed in sync with zero extra plumbing, the same as Option B, but without giving up a Colour-Role-shaped surface for *our own* code to read from — code can be written against whatever Colour Role names we choose, translated into `ThemeConfigColors`' dotted JSON keys (or built as a `ThemeConfig` value directly in Rust, bypassing JSON) at the point a Colour Theme is resolved; hot-reload (`ThemeRegistry::watch_dir`, §4) comes for free if theme files are written to a watched directory, which is one plausible mechanism for the map's still-open "drop in a whole custom Colour Theme as a file" question. `ThemeMode`'s two-value shape (§3) already matches our Colour Variant concept exactly, so there is no impedance mismatch there.
- *Against*: authoring correctness now depends on `ThemeConfigColors`' exact (and, per §4's finding, not perfectly self-consistent even in the crate's own shipped file) dotted-key JSON schema, owned by an upstream crate that could rename/add/remove fields on a future `gpui-component` upgrade with no compile-time signal on our side if we generate JSON strings rather than constructing `ThemeConfig` values in Rust (constructing the Rust struct directly would catch a removed/renamed field at compile time; going through JSON would not, until parsed at runtime). `Theme::apply_config`/`ThemeColor::apply_config`'s fallback chaining (§4) means an incompletely-specified Colour Theme silently inherits `gpui-component`'s own shadcn-derived defaults for whatever it omits, which may or may not be the right silent behaviour for a from-scratch Modernist-family Colour Theme (a bug in our own Colour Theme authoring — a missing field — could manifest as a shadcn blue leaking through, not an error). `Theme`'s non-colour fields (font/radius/shadow/scrollbar/tile, §2) come along for the ride in this option more directly than in A or B, front-loading a decision the map has explicitly deferred to a separate ticket (whether typography/spacing/radius become configurable at all).

### A structural point applying to all three

Regardless of which option (or hybrid) is chosen, `Theme::change`'s bootstrap path (`theme/mod.rs:152-157`) always seeds a not-yet-existing `Theme` global from `ThemeRegistry::global(cx).default_light_theme()`/`default_dark_theme()` — i.e. `gpui-component` widgets have *some* live `Theme` from the moment `gpui_component::init(cx)` runs in `main.rs`, before any Personal-Ledger-specific Colour Theme resolution logic gets a chance to run. Under Option A this is harmless (our own `Global` is a separate object). Under Options B or C, whichever code path resolves the user's chosen Colour Theme and calls `Theme::change`/`ThemeRegistry` needs to run early in `main.rs`, likely right after (or replacing part of) today's single `gpui_component::init(cx)` call, or `gpui-component` widgets will briefly show the shipped shadcn default before the real Colour Theme applies.

## 10. Open questions this research surfaces for a later decision ticket

- Whether "feed" (Option C) targets `ThemeConfig` values built directly in Rust or on-disk JSON files consumed via `ThemeRegistry::watch_dir` — the two have different compile-time-safety and hot-reload trade-offs noted above.
- How the map's own "one high-contrast built-in Colour Theme" and "chart/series colours" scope items interact with §4's `apply_config` fallback chaining and §6's five-series-slot ceiling respectively — a high-contrast theme presumably wants to override far more fields explicitly (relying on fewer computed fallbacks) than a normal theme would.
- Whether Personal Ledger needs live OS-appearance-follow (in the map's scope, per the ticket) to be built on top of `Theme::sync_system_appearance` plus a listener for `gpui`'s window-appearance-changed signal, since (§3) `gpui-component` does not itself re-fire that call after startup.
- Where the Modernist-only tokens with no `ThemeColor` counterpart (§9, Option B's "against") end up under whichever option is chosen — they need a home regardless of how the shared ~90 roles are wired.
