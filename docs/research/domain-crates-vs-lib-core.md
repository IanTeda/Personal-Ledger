# Research: Fold the domain crates into lib-core, or keep them and add lib-ledger?

**Question.** Should the eleven per-domain lib crates (`lib-accounts`, `lib-bills`, `lib-budgets`, `lib-categories`, `lib-documents`, `lib-institutions`, `lib-inventory`, `lib-payees`, `lib-tags`, `lib-transactions`, `lib-units`) be folded into `lib-core` as one domain crate, with their free and associated functions moved into `impl` methods on the types? Or should they stay separate, with the `lib-ledger` aggregate crate on top that [ADR-0038](../adr/0038-clients-reach-ledger-data-through-a-ledger-aggregate.md) decides? The constraint behind the question is that an aggregate holding domain entity types cannot live in `lib-core` while the domain crates depend on `lib-core`. Sources are the Cargo Book, the Rust Reference, the rustc dev guide, the Rust blog, the Rust API Guidelines, rust-analyzer's architecture document, and matklad's (rust-analyzer's original author) "Fast Rust Builds" and "Large Rust Workspaces", plus this repository's files and local build measurements. Research was carried out on 2026-10-10 against the `concept` branch at `7710742`, with Rust 1.98.0 on an 8-thread Linux machine.

## 1. Current state in this repository

**Sizes.** Line counts of `src/` (tests included): `lib-budgets` 4,846, `lib-documents` 2,756, `lib-bills` 2,083, `lib-inventory` 1,270, `lib-categories` 936, `lib-payees` 684, `lib-accounts` 606, `lib-tags` 568, `lib-units` 213, `lib-transactions` 132, `lib-institutions` 92. That is about 14,200 lines across the eleven domain crates. `lib-core` is 3,760 lines over 15 files.

**Sideways dependencies.** From each crate's `[dependencies]`:

- `lib-transactions`, `lib-accounts`, `lib-inventory` depend only on `lib_core` (plus `bigdecimal`, `chrono`); `lib-units` and `lib-institutions` depend on nothing in the workspace.
- `lib-categories`, `lib-payees` and `lib-tags` depend on `lib_accounts` and `lib_transactions`. In `lib-categories` the use is `transactions: &[lib_transactions::Transaction]` in the month-to-date amount functions.
- `lib-bills` depends on `lib_accounts`, `lib_categories`, `lib_payees` and `lib_transactions`.
- `lib-budgets` depends on `lib_accounts`, `lib_bills`, `lib_categories`, `lib_transactions` (and `lib_payees`, `lib_tags` as dev-dependencies).
- `lib-documents` depends on `lib_accounts`, `lib_bills`, `lib_categories`, `lib_inventory`, `lib_payees` and `lib_transactions`.

So the graph is a chain: `lib_core` → `lib_transactions` → `lib_categories`/`lib_payees`/`lib_tags` → `lib_bills` → `lib_budgets`/`lib_documents`. Issue #590 hit the consequence: `default_transactions` and the pure parts of `transactions/query.rs` need Account, Category, Payee and Tag, so they cannot move into `lib_transactions` without a cycle, and stayed in `bin-desktop`.

**Write interfaces.** `TransactionService::edit<R>(&mut self, change: impl FnOnce(&mut Vec<Transaction>) -> R) -> R` is the whole write interface of `lib-transactions`. `BillService::edit` hands out `&mut Vec<BillPlan>` and `&mut Vec<BillScheduleEntry>` together. `lib_bills::pay` is a free function over `plans: &[BillPlan], entries: &mut [BillScheduleEntry], transactions: &mut Vec<Transaction>`. `lib_categories::delete_category` takes `&mut Vec<Category>` and carries the comment "future: re-point splits to this category", because the Splits it should re-point live in another crate.

**`lib-core`'s dependents.** `cargo tree -i lib_core -e normal --depth 1 --workspace` lists every domain crate plus `lib_config`, `lib_locale`, `lib_colour_theme`, `lib_database`, `lib_rpc`, `bin_sync_server`, `bin_tui` and `bin_desktop`. `lib-core` has `sqlx` as a normal dependency and implements `sqlx` traits in ten of its modules (`row_id.rs`, `money.rs`, `transaction_status.rs`, …), because `lib-database` and the Sync Server use its value types in persisted rows.

**Consumers.** `bin-desktop` depends on all eleven domain crates and imports them in 29 files under `src/`. `bin-tui` depends on `lib_core` only and uses none of the domain crates: its Views still run on their own models (#572).

## 2. Compile time

**What the primary sources say.**

- The crate is rustc's unit of work. "When you compile a Rust program, Cargo launches multiple rustc processes, compiling multiple crates in parallel", and within one crate "The front-end is entirely serial", while the back-end "generates code in chunks called 'codegen units' and then LLVM processes these in parallel" (Rust blog, "Faster compilation with the parallel front-end in nightly", https://blog.rust-lang.org/2023/11/09/parallel-rustc/).
- The dev profile splits each crate into many codegen units: "The default is 256 for incremental builds, and 16 for non-incremental builds", and `[profile.dev]` has `incremental = true`. "Incremental compilation is only used for workspace members and 'path' dependencies", which covers every crate in question (Cargo Book, Profiles, https://doc.rust-lang.org/cargo/reference/profiles.html). This repository's root `Cargo.toml` overrides neither setting.
- Incremental reuse is per query, not per crate: "queries are fingerprinted based on their arguments", and "The result of a query might change when we give it one argument and be coloured red, while it stays the same for another argument and is thus green" (rustc dev guide, Incremental compilation, https://rustc-dev-guide.rust-lang.org/queries/incremental-compilation.html). So an edit inside one module of a large crate does not redo the whole crate's analysis; it does re-run the crate's rustc invocation.
- The graph's shape matters more than the crate count. matklad: "The first advice you get when complaining about compile times in Rust is: 'split the code into crates'", but "if you ended up with a graph like the first one [a chain], you are not winning much", and "The most important property of a crate is which crates it doesn't (transitively) depend on". On incrementality: "In the wide graph, changing `B` doesn't entail recompiling `C` and `D`" ("Fast Rust Builds", https://matklad.github.io/2021/09/04/fast-rust-builds.html).
- Cargo's own advice: "Split large crates into smaller pieces" and "If there are a large number of crates bottlenecked on a single crate, focus your attention on improving that one crate to improve parallelism" (Cargo Book, Reporting build timings, https://doc.rust-lang.org/cargo/reference/timings.html).
- Generics at crate boundaries cost the caller: "Most of the compile time cost of generic functions is borne out by the crates that use the functionality", so "do not put generic code at the boundaries between the crates" (matklad, "Fast Rust Builds"). The `edit<R>(FnOnce …)` hatches are generic and get monomorphised in `bin-desktop`; ADR-0038's named, non-generic `Ledger` commands avoid that whichever layout is chosen.

**Measured.** To compare, the eleven crates were folded mechanically into a scratch copy of `lib-core` as modules (`lib-core/src/<domain>/`, `lib_<domain>` paths rewritten to `crate::<domain>`, `lib_core` to `crate`). It compiled with no errors or warnings and its 404 unit tests passed. All runs used `SQLX_OFFLINE=true`, the dev profile and `--offline`, with an edit to one function body toggled back and forth, three runs each. The times are consistent to within about 50 ms per configuration.

| Scenario | Split crates (today) | Folded into `lib-core` |
| --- | --- | --- |
| Domain layer from clean (third-party deps already built), wall time | 3.99 s, 12 units, critical path `lib_core` → `lib_transactions` → `lib_categories` → `lib_bills` → `lib_budgets` | 4.26 s, one 3.96 s unit |
| `cargo build` after editing `Transaction::is_split` | 0.91–0.97 s, 7 crates recompiled | 0.89–0.91 s, 1 crate |
| `cargo build` after editing a `lib-budgets` figure function | 0.72–0.80 s, 1 crate | 1.19–1.26 s, 1 crate |
| `cargo test --no-run` after editing `Transaction::is_split` | 1.72–1.77 s | 1.37–1.41 s |
| `cargo test --no-run` after editing a `lib-budgets` function | 0.98–1.01 s | 1.68–1.76 s |
| `cargo build` of `lib_core` + `lib_config`, `lib_locale`, `lib_colour_theme`, `lib_database` after editing a `lib-budgets` function | 0.74–0.76 s, 1 crate | 2.73–2.76 s, 5 crates |

**Reading.** At about 18,000 lines the layout barely matters for the domain code itself: every incremental case is under 2 seconds either way, and the clean build of the domain layer takes 4 seconds in both. The split layout gets no parallelism today because the graph is a chain; the `--timings` report shows `lib_budgets` cannot start until `lib_bills` finishes, which waits on `lib_categories`, which waits on `lib_transactions`. ADR-0038 removes the chain (every domain crate on `lib-core` only), which would let the eleven compile side by side, but the saving is about 2 seconds of a clean build. The fold costs more where the edit is a leaf crate today (budgets: 0.75 s becomes 1.2 s), and less where the edit sits under seven dependents (transactions).

The decisive row is the last one. Folding into **`lib-core`** puts every domain edit on the rebuild path of everything that depends on `lib-core`: `lib-config`, `lib-locale`, `lib-colour-theme`, `lib-database`, `lib-rpc`, the Sync Server and the TUI, none of which uses a domain rule. Measured on four of those libraries (`lib-rpc` was left out because its build script needs `protoc`), a one-line Budgets edit goes from 0.75 s to 2.75 s, and the real cost is larger because the Sync Server and TUI binaries would relink too (not measured). That is the "wide graph" property matklad names, run in reverse: it is the crates `lib-core` is depended on by, not its size, that make it the wrong host.

## 3. Encapsulation

**Crate and module privacy.** "If an item is private, it may be accessed by the current module and its descendants", and "`pub(crate)` makes an item visible within the current crate", with `pub(super)` and `pub(in path)` for narrower scopes (Rust Reference, Visibility and privacy, https://doc.rust-lang.org/reference/visibility-and-privacy.html). So a single crate can still protect an invariant: a field that is private to the `bills` module, or `pub(in crate::ledger)`, cannot be touched from `budgets`. What a module boundary does not give is a one-way dependency rule, since any module may `use` any other module's visible items (see §4).

**Where `impl` blocks can live.** For inherent impls, "An implementing type must be defined within the same crate as the original type definition", and the Reference's own example puts a second `impl Color` in a sibling module (Rust Reference, Implementations, https://doc.rust-lang.org/reference/items/implementations.html). For traits, "a trait implementation is only allowed if either the trait or at least one of the types in the implementation is defined in the current crate" (the orphan rule, same page). Consequences:

- **Split crates:** `impl Transaction { … }` can only be written in `lib-transactions`. `lib-ledger` can write `impl Ledger { pub fn pay_bill(…) }`, because it defines `Ledger`, but it cannot add an inherent method to `BillScheduleEntry`. If it wants method syntax on another crate's type it needs an extension trait it defines itself, which the orphan rule allows (local trait).
- **One crate:** any module can add an inherent method to any domain type, so `impl Transaction` could appear in `transactions/`, `bills/` and `ledger/` at once. That is legal and sometimes handy, but it scatters a type's API, and it is exactly what "move the fns into impl" would invite for cross-entity rules.

**Who can call what.** A Cargo package can name only the crates it is given: the extern prelude holds crates "provided to the compiler (as with the `--extern` flag with `rustc`)" (Rust Reference, Preludes, https://doc.rust-lang.org/reference/names/preludes.html). With split crates, "every write goes through `Ledger`" can be enforced by the Clients' `Cargo.toml`: if `bin-desktop` depends on `lib-ledger` only, and `lib-ledger` re-exports the entity types but not the mutating domain functions, the Desktop cannot call `lib_bills::pay` at all. Today `bin-desktop/Cargo.toml` lists all eleven domain crates, so ADR-0038's rule is a convention until that list shrinks. In one crate the same guarantee comes from visibility instead: collection fields and single-domain mutators declared `pub(crate)` (or `pub(in crate::ledger)`) are callable by `Ledger` and invisible to the Clients. Both work; the one-crate version is enforced by the compiler without a re-export discipline, which is its main real advantage.

## 4. Dependency hygiene

**Folding hides the cycle; it does not remove it.** Cargo rejects package cycles: "Usually the resolver does not allow cycles in the graph", with an exception for dev-dependencies that "can lead to confusing errors" because "there are actually two copies of the library linked into the final test binary"; its advice is "try to split your package into multiple packages and restructure it so that it remains strictly acyclic" (Cargo Book, Dependency resolution, https://doc.rust-lang.org/cargo/reference/resolver.html). Inside one crate nothing checks module layering, so `transactions` could use `categories` and `categories` use `transactions`, and the #590 error would never appear. The coupling that caused it (Category month-to-date amounts reading Transactions, Bills writing Transactions, Documents reaching into six domains) would still be there, just unlisted. The scratch fold compiled first time for exactly this reason: nothing in a crate objects to the existing sideways uses.

matklad recommends the same check for libraries in a large workspace: a separate `libs/` folder "makes it easier to check that things in `libs/` don't use things from `crates/`" ("Large Rust Workspaces", https://matklad.github.io/2021/08/22/large-rust-workspaces.html). A crate boundary turns "the domain layer doesn't depend sideways" from a review comment into a build error.

**The aggregate in each option.**

- **A. Split crates + `lib-ledger` (ADR-0038).** `lib-core` (ids, value types) ← eleven domain crates (entity, single-entity rules, own seed) ← `lib-ledger` (`Ledger`, cross-domain commands and queries, `Ledger::stub()`, multi-domain tests) ← Clients. The cross-domain ids move down into `lib-core`, so no domain crate needs another. The cycle cannot return, because a domain crate that adds `lib_transactions` to its `Cargo.toml` is a visible, reviewable change, and a real cycle fails to resolve.
- **B. Fold into `lib-core`.** One crate holds value types, entities, rules and `Ledger` (as a module). The ADR-0038 constraint dissolves because there is no crate boundary left to cross. But `lib-core` stops being the small value-type crate that `lib-database`, `lib-rpc`, `lib-config`, `lib-locale` and the Sync Server share, and all of them recompile on every domain edit (§2) and see every domain type in their extern prelude.
- **C. Fold into one new domain crate above `lib-core`** (call it `lib-ledger`, holding entities, rules and `Ledger`). This keeps `lib-core` small and keeps the Sync Server and the persistence crates off the domain rebuild path, while giving the one-crate privacy story of §3. It loses the compiler-checked layering of option A, which would have to be kept by module conventions and review. Measured cost is the "folded" column of §2 minus its last row.

## 5. Free functions or methods for domain rules

**The guideline.** C-METHOD: prefer `impl Foo { pub fn frob(&self, w: widget) }` over `pub fn frob(foo: &Foo, w: widget)` "for any operation that is clearly associated with a particular type", because methods "do not need to be imported or qualified to be used", get autoborrowing, answer "what can I do with a value of type `T`" in rustdoc, and "provide `self` notation" (Rust API Guidelines, Predictability, https://rust-lang.github.io/api-guidelines/predictability.html). The qualifier is "clearly associated with a particular type".

**Single-entity rules have a clear receiver.** `lib_bills::status(entry, today)` and `needs_attention(entry, plan, today)` are `BillScheduleEntry::status(&self, today)`; `get(plans, id)`, `entry_mut(entries, id)`, `populate(plans, entries, today)` and `supersede_from(entries, plan_id, today)` are methods on the collection that owns plans and entries (today's `BillService`), not on a slice. These moves are possible in every option, and in options A and C they stay inside the crate that defines the type, as the inherent-impl rule requires.

**Cross-entity rules have one clear receiver too: the thing that owns all the collections.** `pay` mutates a schedule entry and inserts a Transaction; deleting a Category re-points Splits and drops Category Limits. Neither `BillScheduleEntry` nor `Category` owns the other rows, so making the rule a method on either one means passing the other domain's `&mut Vec` in as an argument, which is today's six-slice signature with `self` in front. ADR-0038 already rejected that ("Keep cross-domain rules in the owning domain crate, taking other domains' data as arguments"). The receiver is the aggregate: `Ledger::pay_bill(&mut self, id, amount, date)` and `Ledger::delete_category(&mut self, id)`. That is C-METHOD applied honestly, and it is the same in every option, so "move fns into impl" does not argue for or against folding.

**Precedent.** rust-analyzer has this shape. Its `hir-def`/`hir-ty` crates have "a strong ECS flavor" working with raw ids and "are not, and will never be, an api boundary", and the top-level `hir` crate "is an **API Boundary**" that "wraps ECS-style internal API into a more OO-flavored API" (rust-analyzer, Architecture, https://github.com/rust-lang/rust-analyzer/blob/master/docs/book/src/contributing/architecture.md). Domain crates with id-keyed rules under a `Ledger` façade that offers the method API is the same layering, kept as separate crates. That document does not give compile time as the reason for the split; its stated invariants are about which crates may know about which.

## 6. Consumers, tests and the CLAUDE.md convention

- **Desktop.** Any option rewrites the 29 importing files: `lib_bills::…` becomes `lib_ledger::…` (A, C) or `lib_core::bills::…` (B). ADR-0038's single `LedgerStore` and `LedgerChanged { what }` are the same in all three; `what` names domains whether they are crates or modules.
- **TUI.** It uses no domain crate today. Under A or C it gains one dependency, `lib-ledger`, when it adopts `Ledger` (#572). Under B it already depends on `lib-core`, so it would compile all domain code from day one and recompile on every domain edit, before it uses any of it.
- **Sync Server.** Unaffected by A and C. Under B it compiles the whole domain layer to use `RowID`.
- **Tests.** Unit tests "have access to private APIs located within the target they are defined in" (Cargo Book, Cargo targets, https://doc.rust-lang.org/cargo/reference/cargo-targets.html), and dev-dependencies "are *not* propagated to other packages which depend on this package" (Cargo Book, Specifying dependencies, https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html). In A, single-domain tests stay in their crate and multi-domain tests go to `lib-ledger`, the one crate that can see every domain; that is where `default_transactions` and the #590 leftovers land. In B and C every test can sit next to the code it tests, including multi-domain ones, which is simpler. None of the domain crates uses `sqlx::test` or `fake` today, so neither moves; `lib-core`'s `fake` dependency is unrelated.
- **Convention.** CLAUDE.md says "one pure, `gpui`-free, I/O-free crate per domain". A keeps it. B breaks it twice: there is no per-domain crate, and `lib-core` is not I/O-free in the same sense, because it implements `sqlx` traits and depends on `sqlx`. C replaces it with "one pure domain crate, one module per domain".

## 7. Recommendation

1. **Do not fold into `lib-core`.** It is the one option with a measured downside and no offsetting gain: every domain edit recompiles `lib-config`, `lib-locale`, `lib-colour-theme`, `lib-database`, `lib-rpc`, the Sync Server and the TUI (0.75 s → 2.75 s for the four libraries measured, more with the binaries), and it turns the shared value-type crate, which carries `sqlx`, into the domain model. ADR-0038 already rejected "Move the entity structs into `lib-core`" on the second ground.
2. **Keep ADR-0038's split crates plus `lib-ledger`.** The reason is not compile time (the measurements show at most a second either way at this size) but that Cargo enforces the acyclic, domain-only-on-`lib-core` graph that ADR-0038 relies on, while a single crate would hide the sideways coupling #590 exposed. It also matches the `hir`-over-`hir-*` layering in rust-analyzer.
3. **Do the "move fns into impl" part inside that layout.** Single-entity rules become inherent methods on the entity or its collection type, in the domain crate. Cross-entity rules become `impl Ledger` methods in `lib-ledger`, never methods on one entity taking another domain's `&mut Vec`. Don't add inherent methods to domain types from outside their crate; the language forbids it in A, and it should be avoided in C.
4. **Close the enforcement gap.** Once `LedgerStore` lands, `bin-desktop` (and later `bin-tui`) should depend on `lib-ledger` only, with `lib-ledger` re-exporting the entity types and not the mutating domain functions. Otherwise "every write goes through `Ledger`" is a convention, not a compile error.
5. **Option C is a fair second choice.** If the per-crate ceremony (eleven `Cargo.toml`s, re-exports, ids pushed down into `lib-core`) starts to cost more than it saves, one domain crate above `lib-core` with `pub(crate)` collections is defensible and keeps `lib-core` and the Sync Server clean. It trades the build-checked layering for compiler-checked privacy. Revisit if the domain layer stays small and `lib-ledger` ends up re-exporting nearly everything anyway.

## 8. What would change in ADR-0038

**If the recommendation is followed (keep A):**

- The Considered Options entry "Merge the domain crates into one. Rejected: it gives up incremental builds and the one-crate-per-domain split" overstates the build cost. At this size the measured difference is at most about a second either way. The stronger reasons are that Cargo enforces the acyclic graph across crates but not across modules, and that a merge into `lib-core` puts the domain on the rebuild path of `lib-database`, `lib-rpc` and the Sync Server. The entry could say so.
- The Decision could add that single-entity rules are inherent methods on the domain types (C-METHOD), and that Clients depend on `lib-ledger` only.

**If the domain crates were folded into `lib-core` (B):**

- The title and "Compose, don't merge" go, and so do "Domain crates depend only on `lib-core`" and "`lib-ledger` holds orchestration, not types". `Ledger` becomes a module of `lib-core` and holds entities and orchestration together.
- "No `edit` hatch" would be enforced by `pub(crate)` fields instead of by crate boundaries and re-exports.
- The rejected option "Move the entity structs into `lib-core`" becomes the decision, and its rejection reason ("`lib-core` would become the model crate") has to be answered, as does the rebuild fan-out in §2.
- CLAUDE.md's "one pure crate per domain" and its `lib-core` description ("shared domain value types with no I/O") change, and the Workspace-layout list loses eleven entries.

**If they were folded into one new crate above `lib-core` (C):** "Compose, don't merge", "Domain crates depend only on `lib-core`" and "`lib-ledger` holds orchestration, not types" change; moving the cross-domain ids into `lib-core` becomes optional; everything about `Ledger`'s commands, per-command refusal types, `LedgerStore`, `LedgerChanged` and the persistence deferral to #597 stays as written.

## 9. Unverified

- **Binary rebuilds.** The Desktop, TUI and Sync Server binaries were not built in the comparison (no `protoc` on `PATH` outside mise in this sandbox, and the Desktop's gpui build is long). The fan-out cost to them under option B is inferred from the `lib_core` dependents list, not measured.
- **The post-ADR-0038 graph.** The parallel build of eleven domain crates that depend only on `lib-core` was not measured, because that refactor hasn't happened; the estimate (about `lib_core` plus the slowest domain crate) is read off the current `--timings` report.
- **Scale.** Measurements are one machine, three runs each, at about 18,000 lines. They say nothing about the layer at ten times the size, where matklad's and the Cargo Book's advice to split would weigh more.
- **The parallel front-end.** The serial front-end quote is from the 2023 announcement of the nightly parallel front-end; whether it is on by default in stable 1.98.0 was not checked, and if it is, the one-crate option gains some within-crate parallelism.
- **The mechanical fold.** The scratch fold only rewrote paths. It did not move cross-entity rules into a `Ledger` module or make anything `pub(crate)`, so it measures layout, not the finished design of option B or C.
