# Research: Encrypted SQLite options for the `sqlx`/SQLite stack

**Question.** Personal Ledger stores all data locally in SQLite via `sqlx` (`crates/libs/lib-database`), and `docs/product-requirements.md` NFR.2 ("All data is stored locally in SQLite; no data leaves the device by default") makes at-rest encryption worth evaluating for a self-hosted, single-user personal-finance ledger. This note investigates: (1) what encrypted-SQLite implementations exist, (2) whether `sqlx` supports any of them directly, (3) what a workaround costs if not, and (4) whether OS/filesystem-level encryption is a simpler alternative. All claims below are cited to primary sources — vendor docs, source code (including this repo's own vendored copy of the crates in question), and the `sqlx`/`rusqlite` issue trackers — rather than blog posts.

Research was done by reading the actual `sqlx-sqlite`, `libsqlite3-sys`, and vendored SQLCipher source already present in this machine's Cargo registry cache for the versions this workspace pins (`sqlx = "0.8.6"`, which depends on `libsqlite3-sys = "0.30.1"`), plus the upstream `sqlx`, SQLCipher, and SQLite3 Multiple Ciphers repos/docs.

## 1. What encrypted-SQLite implementations exist

**SQLCipher** — maintained by Zetetic, LLC. It is "a standalone fork of the SQLite database library that adds 256 bit AES encryption of database files and other security features" (SQLCipher `README.md`, https://github.com/sqlcipher/sqlcipher/blob/master/README.md). It uses 256-bit AES in CBC mode with a per-page HMAC (SHA1/SHA256/SHA512 depending on version/config) for tamper detection, and derives the encryption key from a passphrase with PBKDF2-HMAC-SHA512 at 256,000 iterations by default (Zetetic, SQLCipher design doc, https://www.zetetic.net/sqlcipher/design/; the exact default pragma values — e.g. `kdf_iter` = 256000 — are also documented directly in the vendored `sqlx-sqlite` source, see §2). Licensing is dual: the code itself is BSD-3-Clause open source — confirmed via GitHub's license detector on the `sqlcipher/sqlcipher` repo (`spdx_id: "BSD-3-Clause"`, https://github.com/sqlcipher/sqlcipher) — alongside paid Commercial/Enterprise/Enterprise-FIPS editions with support and extra features (Zetetic, SQLCipher design page, https://www.zetetic.net/sqlcipher/design/).

**SQLite3 Multiple Ciphers (sqlite3mc)** — maintained by Ulrich Telle, the successor to his earlier **wxSQLite3** project for non-wxWidgets use. It is MIT-licensed (confirmed via GitHub's license detector on `utelle/SQLite3MultipleCiphers`, `spdx_id: "MIT"`) and, unlike SQLCipher's single scheme, bundles seven interchangeable cipher schemes: wxSQLite3's AES-128-CBC and AES-256-CBC (no HMAC), sqleet's ChaCha20-Poly1305 (the current recommended default), a SQLCipher-compatible AES-256-CBC-with-HMAC mode, a legacy System.Data.SQLite RC4 mode, Ascon-128 v1.2, and the AEGIS family (SQLite3 Multiple Ciphers docs, "Supported Ciphers", https://utelle.github.io/SQLite3MultipleCiphers/docs/ciphers/cipher_overview/). Its own installation docs state it can, "in principle," serve as a drop-in replacement for the stock SQLite amalgamation by swapping `sqlite3.c` for `sqlite3mc_amalgamation.c` (SQLite3 Multiple Ciphers docs, "Installation", https://utelle.github.io/SQLite3MultipleCiphers/docs/installation/install_overview/) — but that statement is about C-level source substitution, not about any specific Rust binding (see §3 for why this matters for `sqlx`).

**wxSQLite3** still exists but is explicitly superseded by sqlite3mc for general (non-wxWidgets) use; sqlite3mc's own docs describe it as the continuation of that codebase (SQLite3 Multiple Ciphers docs, https://utelle.github.io/SQLite3MultipleCiphers/).

**rusqlite's bundled SQLCipher features** are not a separate implementation — they are a Rust-ecosystem packaging of SQLCipher itself via `libsqlite3-sys`, covered in §2–3.

No other credible, actively maintained encrypted-SQLite implementation was found beyond these.

## 2. Compatibility with `sqlx` specifically

Reading the actual vendored `sqlx-sqlite` crate for the version this workspace pins confirms `sqlx`'s SQLite driver is a **binding over the C library via `libsqlite3-sys`**, the same low-level FFI crate `rusqlite` uses — it is not a pure-Rust reimplementation and not a wrapper around `rusqlite` itself. `sqlx-sqlite`'s own (registry-published) `Cargo.toml` declares:

```
[dependencies.libsqlite3-sys]
version = "0.30.1"
features = ["pkg-config", "vcpkg", "unlock_notify"]
default-features = false
```

(from `sqlx-sqlite-0.8.6/Cargo.toml`, as published to crates.io and vendored at `~/.cargo/registry/src/.../sqlx-sqlite-0.8.6/Cargo.toml`, matching this workspace's pinned `sqlx = "0.8.6"`). Because it is the same `libsqlite3-sys` crate that `rusqlite` depends on, it can — in principle — be built against an SQLCipher-flavoured `libsqlite3-sys` the same way `rusqlite` is, via Cargo's feature unification (see §3).

`sqlx-sqlite`'s own published Cargo features are `any`, `bundled`, `chrono`, `json`, `migrate`, `offline`, `preupdate-hook`, `regexp`, `time`, `unbundled`, `uuid` — there is **no first-party `sqlcipher` or `bundled-sqlcipher` feature on `sqlx-sqlite` itself**. However, `sqlx-sqlite`'s connection-options code does have explicit, built-in knowledge of SQLCipher: `SqliteConnectOptions::new()` pre-seeds an ordered pragma map that puts `key` first, followed immediately by `cipher_plaintext_header_size`, `cipher_salt`, `kdf_iter`, `cipher_kdf_algorithm`, `cipher_use_hmac`, `cipher_compatibility`, `cipher_page_size`, and `cipher_hmac_algorithm` — each pragma's default value and purpose is documented inline with a direct link to Zetetic's SQLCipher API docs (`sqlx-sqlite-0.8.6/src/options/mod.rs`, lines 124–161: "SQLCipher special case: if the `key` pragma is set, it must be executed first... Other SQLCipher pragmas that has to be after the key, but before any other operation on the database. https://www.zetetic.net/sqlcipher/sqlcipher-api/"). So `sqlx` knows how to *drive* an SQLCipher-enabled SQLite correctly; what it lacks is a first-party switch to *build/link* one.

The `sqlx` issue tracker (now `transact-rs/sqlx`, the renamed/transferred `launchbadge/sqlx`) confirms this is a known, long-running gap rather than an oversight, and shows how the current behaviour got built:

- **[Issue #621](https://github.com/transact-rs/sqlx/issues/621), "Hidden early PRAGMAs prevent using SQLCipher"** (closed 2021-09-13) — the original bug report: `sqlx` unconditionally issued `PRAGMA journal_mode` / `PRAGMA foreign_keys` immediately after connecting, before any user-supplied pragmas, which broke SQLCipher's hard requirement that `PRAGMA key` run first. This is what led to `key` being special-cased to run first.
- **[Issue #1436](https://github.com/transact-rs/sqlx/issues/1436), "Enable encryption for sqlite via the `bundled-sqlcipher` feature"** (closed 2021-09-14) — maintainer `@abonander`'s response is the canonical statement of `sqlx`'s position: *"I don't think we'll add a Cargo feature specially for this because this is a relatively common Cargo pattern (enabling a feature of a transitive dependency by adding it as a non-transitive dependency)."* He also gave the exact workaround (add `libsqlite3-sys` directly to your own `Cargo.toml` with `features = ["bundled-sqlcipher"]`, using a `[patch]` section at the time because the needed `libsqlite3-sys` release hadn't shipped yet).
- **[Issue #2009](https://github.com/transact-rs/sqlx/issues/2009), "[sqlite] Unable to provide sqlcipher encryption configuration"** — a follow-on report that only `key` was special-ordered while the other `cipher_*` pragmas were not, still causing "file is not a database" errors; resolved by **PR #2014, "Support additional SQLCipher options in SQLite driver"**, explicitly credited in `sqlx`'s own `CHANGELOG.md` (`sqlx-0.8.6/CHANGELOG.md`, line 1114: `* [[#2014]]: Support additional SQLCipher options in SQLite driver. [[@szymek156]]`) — this is exactly the pragma-ordering code found in `options/mod.rs` above.
- **[Issue #3626](https://github.com/transact-rs/sqlx/issues/3626), "Hope the sqlx support the bundled-sqlcipher-vendored-openssl for sqlx-sqlite"** — **still open**, requesting `sqlx-sqlite` add a passthrough Cargo feature for `bundled-sqlcipher-vendored-openssl` (mirroring `rusqlite`'s). Its continued open status as of this research confirms `sqlx` today still has no first-party feature toggle — the dependency-unification workaround from 2021 remains the documented path.

**Bottom line on §2:** `sqlx`'s SQLite driver is genuinely `libsqlite3-sys`-based (not a `rusqlite` wrapper, not pure-Rust), and it has real, tested SQLCipher-awareness baked into its pragma handling — but it does not, and as of the linked open issue still does not, expose a first-party Cargo feature to build/link an SQLCipher-capable SQLite. Support is "unsupported out of the box, but architecturally straightforward via a documented workaround."

## 3. Workarounds and their costs

### Workaround A — Cargo feature-unification trick (recommended if pursuing app-level encryption)

Add `libsqlite3-sys` as a direct dependency of your own crate (even if you never call it), pinned to the same version `sqlx-sqlite` resolves (`0.30.1` for `sqlx 0.8.6`), with `features = ["bundled-sqlcipher"]` (or `["bundled-sqlcipher-vendored-openssl"]`). Cargo unifies features across a single resolved version of a crate in the dependency graph, so the one copy of `libsqlite3-sys` that `sqlx-sqlite` actually links gets compiled with SQLCipher support too. This is precisely the mechanism `sqlx` maintainer `@abonander` described in [issue #1436](https://github.com/transact-rs/sqlx/issues/1436), and it's the same feature `rusqlite` itself uses for its own bundled encryption support — confirmed directly in `rusqlite`'s `Cargo.toml`: `bundled-sqlcipher = ["libsqlite3-sys?/bundled-sqlcipher", "bundled"]` and `bundled-sqlcipher-vendored-openssl = ["libsqlite3-sys?/bundled-sqlcipher-vendored-openssl", "bundled-sqlcipher"]` (https://github.com/rusqlite/rusqlite/blob/master/Cargo.toml).

**Build complexity.** `libsqlite3-sys` 0.30.1 (the exact version pinned transitively by this workspace's `sqlx 0.8.6`) vendors the actual SQLCipher amalgamation source in-tree at `sqlcipher/sqlite3.c` (verified locally — the file embeds `CIPHER_VERSION_NUMBER 4.5.7` / `community`), so `bundled-sqlcipher` compiles SQLCipher from source via `cc-rs`. This requires a crypto backend: either a system OpenSSL, located via `OPENSSL_DIR`/`OPENSSL_LIB_DIR`/`OPENSSL_INCLUDE_DIR` env vars (`libsqlite3-sys-0.30.1/build.rs`, ~lines 143–213), or a fully vendored OpenSSL pulled in through `bundled-sqlcipher-vendored-openssl` (adds `openssl-sys/vendored`, per the same `build.rs` and `libsqlite3-sys`'s own `Cargo.toml` feature list: `bundled-sqlcipher-vendored-openssl = ["bundled-sqlcipher", "openssl-sys/vendored"]`). The vendored-OpenSSL route avoids depending on a system OpenSSL install (useful for reproducible/cross builds, since `openssl-sys/vendored` is the standard Rust-ecosystem escape hatch for cross-compilation), but it means compiling OpenSSL itself at build time — a nontrivial addition (C toolchain + a longer, heavier build) compared to today's plain `sqlite`/`bundled` feature, which has no crypto-library build step at all.

**`sqlx::test`, `sqlx-cli migrate`, connection pooling.** No SQLCipher-specific special-casing exists in `sqlx-sqlite`'s `testing/` module or `migrate.rs` (checked directly — neither file references `cipher` or `key`). Architecturally this is because pragmas configured on `SqliteConnectOptions` (including `key` and the `cipher_*` values) are re-applied every time the pool or `sqlx::test` opens a *new* physical connection, not just once — so passphrase-gated connections should keep working unmodified as long as every code path that opens a connection (the pool, migrations, `sqlx::test`) is going through the same `SqliteConnectOptions`/connection URL that carries the `key` pragma. **This is an architectural inference from the source, not something either project's docs explicitly state or test** — no `sqlx` or `sqlx-cli` doc was found asserting "SQLCipher works with `sqlx::test`/`migrate`," so treat it as very likely but unverified by the upstream project itself.

**Key management.** SQLCipher requires `PRAGMA key = '<passphrase>'` to be the first statement on every new connection (Zetetic, SQLCipher API docs, https://www.zetetic.net/sqlcipher/sqlcipher-api/: "PRAGMA key should generally be called as the first operation on a database... the key (and any options) must be set before the first operation on the database"). In `sqlx` terms that means the passphrase must be supplied via `SqliteConnectOptions::pragma("key", ...)` (or embedded in the connection URL) wherever a connection is opened. `sqlx` has no keychain/secret-store integration of its own — the application is fully responsible for sourcing and protecting that passphrase (this repo's existing convention of wrapping secrets in `secrecy::Secret`, per `CLAUDE.md`, would need to extend to this value, and the passphrase's own storage location becomes the new thing that needs protecting).

**Performance.** Zetetic's own SQLCipher performance guidance states: *"It's not unusual to see as little as 5-15% overhead for SQLCipher encryption"* (Zetetic, SQLCipher Performance, https://www.zetetic.net/sqlcipher/performance/). The same page notes that key derivation (PBKDF2, 256,000 iterations by default) is "very expensive, by design," and that "frequent opening / closing of the database connection (e.g. for every query)... is a very common cause of performance issues," recommending a long-lived/singleton connection instead — which aligns well with `sqlx`'s connection-pooling model, provided the pool is sized to reuse connections rather than churn them. **No independently verified benchmark was found** — the 5-15% figure is Zetetic's own vendor-reported number, not a third-party or `sqlx`-project measurement, and no `sqlx`-specific performance data for SQLCipher was found anywhere in the `sqlx` repo or docs.

### Workaround B — swap the SQL driver to `rusqlite`

`rusqlite` has first-party `sqlcipher`, `bundled-sqlcipher`, and `bundled-sqlcipher-vendored-openssl` Cargo features (confirmed in its `Cargo.toml`, §"Workaround A" above). This sidesteps `sqlx` entirely, but it means giving up `sqlx`'s async runtime integration, compile-time-checked query macros, and connection pool — a rewrite of the query layer in `crates/libs/lib-database`, which per `CLAUDE.md` is already built around `sqlx`'s pooling and per-entity CRUD split. This is a much larger change than Workaround A for the same encryption outcome, and is not recommended unless there's an independent reason to drop `sqlx`.

### Workaround C — sqlite3mc

sqlite3mc's own docs say it can, "in principle," replace the standard `sqlite3.c` amalgamation (§1), but that claim is about the C source, not about any existing Rust `libsqlite3-sys` fork that `sqlx` or `rusqlite` could consume by default. The only concrete Rust integration found is `sqlite-wasm-rs`'s `sqlite3mc` feature, which targets the WASM/browser build of SQLite, not the native `libsqlite3-sys` FFI path `sqlx` uses. Adopting sqlite3mc with `sqlx` today would mean maintaining a custom `libsqlite3-sys`-compatible fork pointed at sqlite3mc's amalgamation — a materially larger, unproven lift than Workaround A, for a benefit (choice among seven cipher schemes) this project doesn't obviously need. No evidence was found of anyone doing this integration for `sqlx` specifically.

## 4. Recommendation

**OS/filesystem-level encryption** (LUKS on Linux, FileVault on macOS, BitLocker on Windows) protects the SQLite file — and everything else on the disk — with zero changes to `sqlx`, no new build dependency on OpenSSL, and no application-level passphrase/key-management code. Its limitation is scope and state: it only protects data while the volume is unmounted or the device is powered off. Once the OS is booted and the volume is mounted — which is the normal state whenever the app is actually running — the SQLite file sits on disk in plaintext to anything with local user/file-system access (another process running as the same user, a compromised dependency, a backup tool, or someone with physical access to a machine that's merely suspended rather than fully powered off). It also does nothing for a copy of the file that leaves the encrypted volume (an unencrypted backup, a USB copy, an unencrypted cloud-sync target) unless that copy path is separately secured.

**App-level encryption via SQLCipher** (Workaround A) protects the database file itself regardless of where it ends up — copied to an unencrypted USB stick, synced to a folder, attached to a bug report — and regardless of whether the host's disk encryption is even turned on (which, for a self-hosted, easy-to-run desktop tool, isn't guaranteed for every user). The cost is real and ongoing given `sqlx`'s lack of first-party support: a compiled-in OpenSSL dependency (or vendored-OpenSSL build cost), a Cargo feature-unification setup that's inherently version-fragile — `@abonander`'s own caveat in issue #1436 was that the trick holds "so long as the API between the version of `libsqlite3-sys` and `sqlx` doesn't change," and issue #3626 being still open four-plus years later confirms nothing has changed structurally since — and application-owned key management, which only helps if the passphrase itself is kept somewhere meaningfully more protected than the database file it's guarding.

Given Personal Ledger's stated profile — single-user, self-hosted, local-first, "no data leaves the device by default" (NFR.2) — OS/filesystem-level encryption is the more pragmatic default: it's frequently already on by default on the platforms this kind of app runs on (FileVault and BitLocker are commonly enabled out of the box on consumer installs; LUKS is a standard option in most Linux distro installers), it covers the whole device rather than one file, and it avoids taking on a new crypto build dependency and bespoke key-handling code to defend against a threat model (another local process/user reading the file while the disk is mounted) that a genuinely single-user desktop deployment may not need to defend against. App-level SQLCipher encryption becomes clearly worth the friction if the threat model expands — e.g. supporting users who won't enable disk encryption themselves, database files that get backed up or synced to less-trusted storage as a supported feature, or a future shared-machine/multi-profile mode — at which point Workaround A (Cargo feature unification against `libsqlite3-sys`'s `bundled-sqlcipher`/`bundled-sqlcipher-vendored-openssl`) is the realistic, precedented path; a driver swap to `rusqlite` or an sqlite3mc integration are not justified by anything found in this research.
