# Research: TUI terminal colours vs app-controlled RGB

**Question.** GitHub issue [#295](https://github.com/IanTeda/Personal-Ledger/issues/295) ("Colour Themes: TUI terminal colours vs app-controlled RGB"), a child of the [Colour Themes for the Desktop and TUI](https://github.com/IanTeda/Personal-Ledger/issues/292) Wayfinder map (#292), asks what the facts are behind choosing between the terminal's own colours (the 16 ANSI colours plus the default foreground/background, today's approach in `docs/ux/tui/README.md`'s "Style" section) and drawing the TUI in a Colour Theme's RGB values. It covers ratatui/crossterm colour support (`Color::Rgb`, `Indexed`, `Reset`), truecolor detection (`COLORTERM`, terminfo) and 256-colour fallback, what happens over SSH and tmux, and what comparable TUIs (Helix, gitui, lazygit, yazi, btop, bottom, k9s) do, including how each reacts when the user's terminal (for example Omarchy) theme changes. This note is primary-source research only: it presents facts and options with trade-offs and decides nothing, matching the map's "planning only" scope. It feeds the grilling ticket [#299](https://github.com/IanTeda/Personal-Ledger/issues/299) "TUI terminal theme or Colour Theme". Already settled at charting: every built-in Colour Theme has paired light and dark Colour Variants, the Colour Appearance (Light/Dark/System) picks the Colour Variant, and live switching is in scope. Detecting the OS or terminal light/dark setting (OSC 11 and similar) belongs to sibling ticket [#296](https://github.com/IanTeda/Personal-Ledger/issues/296) and is only touched on here where it overlaps. Research was carried out on 2026-09-26.

Vocabulary note, per `CONTEXT.md` and the map: a named set of colours of ours is a **Colour Theme**, never a "palette" (that word is reserved for the command palette in both bins) nor a bare "theme"; a **Colour Role** is one named slot such as accent or background; a **Colour Variant** is the light or dark half of a Colour Theme; **Colour Appearance** is the user's Light/Dark/System choice. Other programs' own terms ("theme", "skin", "flavor", "palette" in a terminal's config) are kept when describing those programs, and API identifiers keep their US spelling (`Color::Rgb`).

## 2. What ratatui and crossterm actually emit

**`Color` variants.** `ratatui_core::style::Color` (`ratatui-core-0.1.2/src/style/color.rs:69-126`) has exactly four kinds of value: `Reset` (the `#[default]`, "Resets the foreground or background color", `:70-72`); the sixteen named ANSI colours `Black` … `White` (`:73-109`, each documented with its SGR code, for example `Red` "Foreground: 31, Background: 41", `DarkGray` "Bright Black. Foreground: 90"); `Rgb(u8, u8, u8)` (`:122`); and `Indexed(u8)`, "An 8-bit 256 color" (`:126`). There is no Colour Role layer in ratatui itself, which the sibling note `colour-role-sets.md` §6 also found.

**ratatui's own warning about RGB.** The `Rgb` doc comment (`color.rs:110-121`) says: "Note that only terminals that support 24-bit true color will display this correctly. Notably versions of Windows Terminal prior to Windows 10 and macOS Terminal.app do not support this. If the terminal does not support true color, code using the `TermwizBackend` will fallback to the default text color. Crossterm and Termion do not have this capability and the display will be unpredictable (e.g. Terminal.app may display glitched blinking text)." (Terminal.app's current truecolor status was not checked against an Apple source; see §9.)

**Translation to crossterm.** `impl IntoCrossterm<CrosstermColor> for Color` (`ratatui-crossterm-0.1.2/src/lib.rs:407-431`) is a one-to-one mapping: `Reset → Reset`, `Red → DarkRed`, `LightRed → Red` (crossterm names the dim row `Dark*` and the bright row plain), `Indexed(i) → AnsiValue(i)`, `Rgb(r,g,b) → Rgb { r, g, b }`. No quantisation, no capability check. The backend's `draw` loop (`lib.rs:232-290`) starts each frame from `Color::Reset` fg/bg and emits `SetColors` whenever a cell's colour changes, then resets fg, bg, underline colour and attributes at the end.

**The bytes crossterm writes.** `impl fmt::Display for Colored` (`crossterm-0.29.0/src/style/types/colored.rs:96-152`): `Reset` foreground writes SGR `39`, background `49`, underline colour `59` (`:106-127`); every other colour writes `38;`/`48;`/`58;` followed by `5;N` for the named colours (`Black → 5;0`, `DarkRed → 5;1`, `Red → 5;9`, … `White → 5;15`, `:131-147`), `5;{val}` for `AnsiValue`, and `2;{r};{g};{b}` for `Rgb` (`:148`). So crossterm expresses even the sixteen named colours in the 256-colour SGR form `38;5;0-15` rather than the classic `30-37`/`90-97`. In every terminal checked in this survey's sources indices 0-15 of the 256-colour table *are* the terminal's own 16 ANSI colours (Ghostty's `palette = N=#hex`, Kitty's `color0`-`color15`, per `colour-role-sets.md` §2), so named colours still follow the user's terminal theme. Whether a strictly 8/16-colour terminal (for example an old Linux virtual console) understands `38;5;N` was **not verified** here.

**No colour-depth detection or downsampling in the render path.** Grepping `ratatui-0.30.2/src`, `ratatui-core-0.1.2/src` and `ratatui-crossterm-0.1.2/src` for `COLORTERM`, `truecolor`, `24bit`, `available_color_count` finds nothing: ratatui never asks what the terminal supports and never converts an `Rgb` to a nearer indexed colour. crossterm has a helper, `crossterm::style::available_color_count()` (`crossterm-0.29.0/src/style.rs:158-181`), documented "This does not always provide a good result": on Windows it returns `u16::MAX` if ANSI is supported, otherwise it reads `COLORTERM`, falling back to `TERM`, and returns `u16::MAX` if the value contains `24bit` or `truecolor`, `256` if it contains `256`, else `8`. Nothing in crossterm's own `Colored` formatting or ratatui's backend calls it; an application that wants fallback must call it (or its own detection) and choose colours itself. The only global switch crossterm applies is [NO_COLOR](https://no-color.org/): `Colored::ansi_color_disabled()` (`colored.rs:73-78`) makes the `Display` impl write nothing for any colour when `NO_COLOR` is set and non-empty (`:100-102`); modifiers such as reverse and dim still pass through.

**Modifiers.** `Modifier::DIM` and `Modifier::REVERSED` are bit flags in `ratatui-core-0.1.2/src/style.rs:106,111`. The crossterm backend maps them to `Attribute::Dim` (SGR 2) and `Attribute::Reverse` (SGR 7) (`ratatui-crossterm-0.1.2/src/lib.rs:441-457`), and because bold and dim share the "normal intensity" reset, removing either re-applies the other (`lib.rs:550-558`, comment "Bold and Dim are both reset by applying the Normal intensity"). These are attributes, not colours: `REVERSED` swaps whatever fg/bg are in effect, so over `Reset` it paints the terminal's own foreground as background and vice versa, and `DIM` is rendered however the terminal chooses (yazi's docs flag `dim` as "not supported by all terminals", [theme.md](https://github.com/yazi-rs/yazi-rs.github.io/blob/main/docs/configuration/theme.md)). Neither is affected by `NO_COLOR`.

**Consequence.** With the pinned stack, a Colour Theme drawn in `Color::Rgb` is sent as `38;2;r;g;b` to every terminal, supported or not. Any 256- or 16-colour fallback, and any truecolor detection, would be Personal Ledger's own code.

## 3. Truecolor detection, SSH and tmux

**`COLORTERM`.** The termstandard document says S-Lang "has a check that `$COLORTERM` contains either "truecolor" or "24bit" (case sensitive)", and that the variable is not portable: "by default it is not forwarded via sudo, ssh, etc, and so it may still be unreliable even where support is available in programs." Its suggested mitigation is to add `COLORTERM` to `SendEnv` in the client's `ssh_config`, to `AcceptEnv` in the server's `sshd_config`, and to `env_keep` in `/etc/sudoers` ([termstandard/colors](https://github.com/termstandard/colors)). It also says detection "err[s] on the side of safety … programs should fall back to using 8-bit color".

**SSH.** OpenSSH's server accepts nothing by default: `AcceptEnv` — "The default is not to accept any environment variables", while "The `TERM` environment variable is always accepted whenever the client requests a pseudo-terminal as it is required by the protocol" ([sshd_config(5)](https://man.openbsd.org/sshd_config)). So over a stock SSH session `TERM` arrives but `COLORTERM` does not, and a `COLORTERM`-only detector concludes "no truecolor" even when the local terminal supports it. Terminfo can then help only if the remote host has an entry for that `TERM` that declares RGB.

**terminfo.** ncurses defines a user-defined capability `RGB` that "asserts that the set_a_foreground (setaf) and set_a_background (setab) capabilities employ direct colors" ([user_caps(5)](https://invisible-island.net/ncurses/man/user_caps.5.html)); termstandard dates it to ncurses-6.0-20180121. tmux documents the older non-standard flag `Tc` as "equivalent to the RGB terminfo capability" (`tmux.1`, the `Tc` entry). Helix's detector (below) treats any of `RGB`, `Tc`, or both `setrgbf`/`setrgbb` as truecolor, which is a good summary of what exists in the wild.

**Querying the terminal directly.** Helix's newer `termina` backend asks the terminal itself: it sets a test colour and reads it back with a DECRQSS SGR query, setting `capabilities.true_color = sgrs.contains(&csi::Sgr::Background(TEST_COLOR.into()))` (`helix-tui/src/backend/termina.rs:170-190`). This works over SSH because it needs no environment variable, at the cost of a round-trip at startup. crossterm 0.29 has no such query built in (not found in its source).

**tmux.** Several facts from tmux's own source:

- Inside a tmux pane, `TERM` is the `default-terminal` option (`environ.c:264-266`), whose built-in default is `tmux-256color` when the build host's terminfo has it, else `screen` (`options-table.c:374-379`, `configure.ac` `DEFAULT_TERM`). The man page says it "must be set to screen, tmux or a derivative of them".
- tmux sets `COLORTERM=truecolor` in every pane's environment unconditionally (`environ.c:269`, `environ_set(env, "COLORTERM", 0, "truecolor")`), regardless of what the outer terminal supports. So a `COLORTERM` check inside tmux always says yes.
- That is safe because tmux itself downgrades at the outer edge: in `tty.c` (~`2699-2725`) a 24-bit colour is passed through only if the outer terminal has `TERM_RGBCOLOURS`; otherwise it is converted with `colour_find_rgb` to the nearest xterm 256-colour cube entry (`colour.c:131-137` documents the non-linear 0/95/135/175/215/255 levels), and a 256-colour value is further reduced with `colour_256to16` if the outer terminal has fewer than 256 colours. tmux learns the outer terminal's RGB support from terminfo or from the `terminal-features` option's `RGB` feature ("Supports RGB colour with the SGR escape sequences") or `terminal-overrides` `Tc`/`RGB` (`tmux.1`, `terminal-features` list). The man page warns "Care must be taken to configure this only with features the terminal actually supports."
- ANSI colours 0-15 pass through tmux to the outer terminal, so an ANSI-inheriting TUI inside tmux still takes the outer terminal's theme (tmux can remap them via its own `palette`, but that is opt-in).
- Newer tmux (the `master` man page read here; release version not verified) adds a `theme` option `detect | terminal | light | dark` — "Whether tmux should use the detected client theme (detect), use terminal ANSI colours (terminal), or force the light or dark theme" — plus `dark-theme-*`/`light-theme-*` named colours chosen "when the client reports a dark background … an unknown background is treated as dark", and `client-dark-theme`/`client-light-theme` hooks. That overlaps #296 and is noted only as evidence that tmux itself now offers exactly the hybrid shape discussed in §7.

**Net effect.** Locally, in a modern terminal (Alacritty, Ghostty, Kitty — Omarchy's terminals all set up for truecolor), `Color::Rgb` works. Over plain SSH, `COLORTERM` is usually missing and terminfo is the only environment signal; inside tmux, `COLORTERM` always claims truecolor and tmux quietly quantises to 256 or 16 colours if the outer terminal is not configured for RGB. A Colour Theme drawn in RGB may therefore arrive as the nearest 256-colour cube entries, which can collapse subtle neutrals (for example the README's greys `#605d5d`/`#9b9797`/`#d7d3d3`) or shift the accent, and the app cannot tell this has happened.

## 4. How a terminal-theme change reaches a running TUI (Omarchy)

Omarchy applies a theme by generating per-app config files from templates and then poking each app to reload. `omarchy-theme-set-templates` fills every `*.tpl` in `$OMARCHY_PATH/default/themed/` (plus `~/.config/omarchy/themed/`) from the theme's `colors.toml`; the shipped templates include `alacritty.toml.tpl`, `ghostty.conf.tpl`, `kitty.conf.tpl`, `foot.ini.tpl`, `btop.theme.tpl` and `helix.toml.tpl` among others. `omarchy-theme-set` then runs a list of reload steps (`/usr/bin/omarchy-theme-set:319-334`), including `omarchy-restart-terminal`, `omarchy-restart-btop`, `omarchy-restart-helix` and `omarchy-theme-set-tmux`.

- **Terminals** (`/usr/bin/omarchy-restart-terminal`): Alacritty reloads because its config file is `touch`ed (Alacritty watches its config); Kitty gets `SIGUSR1`; Ghostty gets `SIGUSR2`. The terminal's default fg/bg and ANSI 0-15 change in place, so every cell a running program drew with `Reset` or a named/indexed-0-15 colour recolours immediately, with no cooperation from the program. This is the "free" recolouring an ANSI-inheriting TUI gets.
- **btop** (`/usr/bin/omarchy-restart-btop`): `pkill -SIGUSR2 btop`, after `btop.theme.tpl` has been rewritten with hex values (`theme[main_bg]="{{ background }}"`, `theme[hi_fg]="{{ accent }}"` …). btop is an app-themed RGB TUI, so Omarchy has to maintain a btop-specific template and a btop-specific reload signal for it to follow.
- **Helix** (`/usr/bin/omarchy-restart-helix`): `pkill -USR1 helix`, after `helix.toml.tpl` has been regenerated; that template's syntax scopes reference a `[palette]` whose entries are filled with the theme's hex colours (`color4 = "{{ blue }}"` …, `helix.toml.tpl:118-130`), so again an RGB theme kept in step by an app-specific template.

So an RGB-themed TUI follows an Omarchy theme change only if (a) someone writes and maintains an Omarchy template for it and (b) it reloads on a signal or file watch. Personal Ledger has neither today; a user can add their own template under `~/.config/omarchy/themed/`, but that is user effort. An ANSI/`Reset`-drawn TUI needs nothing.

One detail from the TUI's own code shows the flip side: `popup/command/mod.rs:34-39` switched a footer label from `Color::DarkGray` to `Color::Rgb(90, 90, 90)` because the named colour "renders however the user's terminal theme happens to remap that palette slot, which isn't reliably 'dark' on every theme." Inheriting ANSI colours hands contrast control to the terminal theme author.

## 5. Comparable TUIs

**Helix** (Rust editor, its own `helix-tui` fork of tui-rs). Theme colours may be one of 17 names (`black` … `white`, plus `default`, meaning the terminal's own colour), `#RGB`/`#RRGGBB` hex, or `[palette]` references ([themes.md](https://github.com/helix-editor/helix/blob/master/book/src/themes.md)). Truecolor detection (`helix-term/src/lib.rs:29-49`): `COLORTERM` of `truecolor`/`24bit`, or `WSL_DISTRO_NAME`, or terminfo `RGB`/`Tc`/`setrgbf`+`setrgbb`; plus the backend's DECRQSS probe (§3), plus an `editor.true-color` setting documented as "override automatic detection of terminal truecolor support in the event of a false negative" ([editor.md](https://github.com/helix-editor/helix/blob/master/book/src/editor.md)). Fallback is all-or-nothing, not per-colour: `load_configured_theme` (`application.rs:470-505`) rejects a configured theme unless `true_color || theme.is_16_color()` ("cannot use it because true color support is not enabled"), and `default_theme(true_color)` returns the built-in `base16_default` when truecolor is absent (`helix-view/src/theme.rs:252-258`). `is_16_color` is simply "no style uses `Color::Rgb`" (`theme.rs:467-472`). `base16_default` is written entirely in ANSI names and `reversed` (`base16_theme.toml`), and the repo also ships `base16_terminal` and `base16_transparent`. Light/dark: `theme = { light = "…", dark = "…" }`, detected "On terminals supporting mode 2031 dark/light detection" (themes.md). Classification: **hybrid** — RGB default theme, with an ANSI built-in theme used automatically on non-truecolor terminals and selectable anywhere. On an Omarchy theme change: its RGB themes don't follow unless regenerated (Omarchy does this via its template plus `SIGUSR1`); `base16_*` themes follow for free.

**gitui** (Rust, ratatui). The default theme (`src/ui/style.rs:330-360`, `impl Default for Theme`) is built from named ANSI colours and `Reset` — `selection_bg: Color::Blue`, `disabled_fg: Color::DarkGray`, `diff_line_add: Color::Green`, `selected_tab: Color::Reset` and so on. Users override individual fields in `theme.ron` with any ratatui `Color` string, including hex; [THEMES.md](https://github.com/gitui-org/gitui/blob/master/THEMES.md) warns "rgb colors might not be supported in every terminal" and "using a color like `yellow` might appear in whatever your terminal/theme defines for `yellow`". No truecolor detection or fallback found in `style.rs`. The one RGB part is syntax highlighting of file content, which uses a syntect theme (`DEFAULT_SYNTAX_THEME`). Light/dark: none; its README shows the default "on light terminal", i.e. it relies on the terminal. Classification: **terminal-inherit by default, per-role RGB overrides**. On a theme change: default theme follows for free; hex overrides don't. No live reload of `theme.ron` found.

**lazygit** (Go, gocui on tcell). Default `gui.theme` values are ANSI names and attributes — `activeBorderColor: [green, bold]`, `inactiveBorderColor: [default]`, `selectedLineBgColor: [blue]`, `defaultFgColor: [default]` ([Config.md](https://github.com/jesseduffield/lazygit/blob/master/docs/Config.md) "theme"). Colour attributes accept the eight names or hex (`'#ff00ff'`) plus `bold`, `default`, `reverse` ("useful for high-contrast"), `underline`, `strikethrough`. Unlike ratatui, the renderer degrades RGB itself: "`tcell` colors are 24bit and they are translated by the library into the color which can be read by terminal"; truecolor is enabled by `COLORTERM=truecolor` or a `-truecolor` `TERM` suffix and disabled by `TCELL_TRUECOLOR=disable` ([CHANGES_tcell.md](https://github.com/jesseduffield/lazygit/blob/master/pkg/gocui/CHANGES_tcell.md)). Light/dark: none built in; Config.md suggests layering config files such as `--use-config-file="$HOME/.base_lg_conf,$HOME/.light_theme_lg_conf"`. Classification: **terminal-inherit by default, hex allowed**. On a theme change: defaults follow for free.

**yazi** (Rust, `ratatui-core`/`ratatui-widgets`, per its `Cargo.toml:70-71`). The preset UI theme (`yazi-config/preset/theme-dark.toml` and `theme-light.toml`, 1019 lines each) uses only named ANSI colours for its UI styles — no hex in the first ~280 lines; the 725 hex values in the file are file-type icon colours. The dark and light presets differ in only a handful of UI lines (for example `count_selected` `fg = "black"` vs `"white"`, `progress_normal` `bg = "black"` vs `"gray"`), because the terminal supplies most of the difference. Colours may be hex or one of 17 names including `"reset"` ([theme.md](https://github.com/yazi-rs/yazi-rs.github.io/blob/main/docs/configuration/theme.md)). Third-party "flavors" carry full RGB themes, and `[flavor] dark = "…" / light = "…"` picks one per mode; the docs list "auto dark/light mode switching with the terminal" as a reason to prefer flavors ([flavors/overview.md](https://github.com/yazi-rs/yazi-rs.github.io/blob/main/docs/flavors/overview.md)). How yazi detects the terminal's mode was **not verified in source**. No truecolor fallback found (it renders through ratatui, §2). Classification: **hybrid** — ANSI built-in default with paired light/dark presets, RGB flavors as the add-on. On a theme change: preset follows for free; a flavor does not.

**btop** (C++, hand-written escapes). Themes are hex; the built-in `"Default"` theme is RGB, and `"TTY"` is a second built-in theme defined as raw 16-colour SGR codes (`TTY_theme` in `src/btop_theme.cpp:103-145`, for example `{ "main_fg", "\x1b[37m" }`). Options (README `btop.conf`): `truecolor = true` — "will convert 24-bit colors to 256 color (6x6x6 color cube) if false" (implemented by `truecolor_to_256`, `btop_theme.cpp:156`); `force_tty` — "Will force 16-color mode and TTY theme"; `theme_background` — "set to False if you want terminal background transparency". The README says "16 color TTY mode will be activated if a real tty device is detected" and 256-colour terminals are supported "when setting "truecolor" to False … or with "-lc/--low-color"" — so the truecolor → 256 switch is **manual**, not detected from `COLORTERM`. `color_theme = "TTY"` can be chosen in a normal terminal emulator too (`btop_theme.cpp:432,462`). Classification: **app-themed with a built-in terminal-colour theme** (hybrid). On a theme change: the TTY theme follows for free; RGB themes follow only via Omarchy's `btop.theme.tpl` plus `SIGUSR2` (§4).

**bottom** (Rust, ratatui). Built-in themes `default`, `default-light`, `gruvbox`, `gruvbox-light`, `nord`, `nord-light` (`src/options/config/style.rs:178-183`); "These themes all also have light variants to support terminals using lighter colours" ([styling.md](https://github.com/ClementTsang/bottom/blob/main/docs/content/configuration/config-file/styling.md)). `default` is written only in named ANSI colours (`themes/default.rs`: `Color::Red`, `Color::Green`, `Color::LightBlue` …, no hex), while `nord`/`gruvbox` are hex (`themes/nord.rs`, for example `hex!("#5e81ac")`). Custom colours accept hex, `"r, g, b"` or names. Light/dark is chosen by the user picking the `-light` name; no detection found. No truecolor fallback found (ratatui). Classification: **hybrid** — ANSI default alongside RGB themes, each with an explicit light counterpart. On a theme change: `default`/`default-light` follow for free; `nord`/`gruvbox` don't.

**k9s** (Go, tview on tcell). "Skins" are YAML; "Colors can be defined by name or using a hex representation", and a colour named `default` indicates "a transparent background color to preserve your terminal background color settings" ([README](https://github.com/derailed/k9s/blob/master/README.md) "Skins"). In code, `DefaultColor = "default"` maps to `tcell.ColorDefault` and `TransparentColor = "-"` means "the terminal bg color" (`internal/config/color.go:14-18,72-74`). The built-in stock style uses W3C colour names that tcell resolves to RGB (`styles.go:339-360`, `colorCadetBlue`, `"mediumvioletred"`, `BgColor: colorBlack`); the repo's `skins/` includes RGB skins in paired `-dark`/`-light` files (for example `everforest-dark.yaml`/`everforest-light.yaml`, `rose-pine`/`rose-pine-dawn`) plus `transparent.yaml` and `solarized-16.yaml`. The README's config shows the default `skin: dracula`, per-context skins, `K9S_SKIN`, and an `invert: false` option — "Convert dark skins to light, or vice versa, preserving hue" — implemented as an OKLCH-style lightness flip that leaves `default`/transparent untouched (`color.go:140-160`, `styles.go:492-499`). RGB degradation is left to tcell (as for lazygit). The README says skin files are reloaded live when edited (not independently verified in source). Classification: **app-themed with terminal-default escape hatch** (per-field `default`, a `transparent` skin). On a theme change: RGB skins don't follow; fields set to `default` do.

## 6. The TUI today

`docs/ux/tui/README.md:196-207` maps the wireframe's hex values to "theme roles, not literal RGB, so the user's own terminal theme wins": ink/ground → default fg/bg, accent → red, dim → dark grey / `DIM`, selection → reversed, header bar → reversed, "One accent only. Never rely on color alone".

In `crates/bins/bin-tui/src/` (at `cdd51db`):

- About 350 lines under `view/` and `popup/` match `Color::|Modifier::|Style::|.fg(|.bg(` or use an `ACCENT`/`DIM` constant (352 lines across the whole crate), consistent with the map's "~340".
- The colour vocabulary actually used is small: `Color::Red` 25 times (almost all as a per-module `const ACCENT: Color = Color::Red;` — there are 25 separate `const ACCENT`/`const DIM` definitions, one per view or popup module, rather than one shared definition), `Color::DarkGray` 4, `Color::Rgb` 3, `Color::Gray` 2, and `Yellow`, `Reset` (in a test), `Black` once each. The heavy lifting is done by modifiers: `Modifier::DIM` 129, `Modifier::BOLD` 38, `Modifier::REVERSED` 25.
- The three RGB literals are all departures from the README's ANSI-only rule: `popup/command/mod.rs:39` `FOOTER_LABEL = Color::Rgb(90, 90, 90)` (§4), and in `view/dashboard.rs:670-692` the mock spending pie's slices, which mix `ACCENT`, `Rgb(139, 0, 0)`, `DarkGray`, `Gray` and `Rgb(211, 211, 211)` — chart series are the first place five-plus distinguishable colours are needed, and the ANSI-plus-modifiers vocabulary does not stretch that far. `popup/command/mod.rs:45` adds `MATCH_HIGHLIGHT = Color::Yellow`, a second accent-like colour beyond the README's "one accent only".

So today's TUI is overwhelmingly **terminal-inherit**: default fg/bg, one ANSI accent, and `DIM`/`REVERSED`/`BOLD` attributes, with RGB creeping in where contrast or series count demanded it.

## 8. Options for #299

These are the shapes the evidence supports; this note does not choose between them.

**A. Terminal-inherit only (ANSI roles, today's approach formalised).** Colour Roles resolve to `Color::Reset`, the sixteen named colours and modifiers (`DIM`, `REVERSED`, `BOLD`). No RGB anywhere.

- For: recolours instantly and for free when the terminal (Omarchy, or any terminal's own theme switch) changes (§4); no truecolor detection, no SSH/tmux quantisation problems (§3); always matches the user's terminal and any transparency; smallest code change from today (§6); the common default among comparable TUIs (§7).
- Against: Personal Ledger's built-in Colour Themes would not reach the TUI at all, so the Desktop and TUI would look unrelated; a "high-contrast built-in Colour Theme" (in the map's scope) cannot be enforced, because contrast is whatever the terminal theme author chose (the `FOOTER_LABEL` comment in §4 is a live example); only ~6 usable distinct hues for chart series; paired light/dark Colour Variants and Colour Appearance become meaningless in the TUI because the terminal is already light or dark — the Colour Appearance setting would have nothing to switch.

**B. App-controlled RGB Colour Themes, with 256/16-colour fallback.** Every Colour Role resolves to `Color::Rgb` from the chosen Colour Theme's chosen Colour Variant; Personal Ledger detects truecolor and degrades itself.

- For: one Colour Theme, one look, on Desktop and TUI; contrast rules and a high-contrast Colour Theme can be guaranteed; enough distinct chart colours; Colour Appearance and paired Colour Variants behave identically to the Desktop; live switching is entirely under the app's control (redraw with new resolved Colour Roles).
- Against: ratatui and crossterm do no detection or downsampling (§2), so the app owns detection (`COLORTERM`, terminfo, perhaps a DECRQSS probe like Helix) and a quantiser (nearest 256-cube, then 16), with known false negatives over SSH and false positives inside tmux (§3); the Colour Theme's background must either be painted (fighting terminal transparency, and needing a background on every cell) or left as `Reset` (in which case a light Colour Variant on a dark terminal fails); does **not** follow an Omarchy theme change unless Personal Ledger ships an Omarchy template and a reload signal (§4); diverges from the README's "terminal theme wins" design and touches all ~350 colour sites.

**C. Hybrid: a built-in "Terminal" Colour Theme alongside RGB Colour Themes.** Colour Roles are the single interface; each Colour Theme resolves them. RGB Colour Themes resolve to `Color::Rgb` (as in B); one built-in Colour Theme, say "Terminal", resolves every Colour Role to `Reset`, an ANSI colour, or a modifier (as in A). This is the Helix `base16_default`/`base16_terminal`, btop `TTY`, bottom `default`, yazi preset-plus-flavors and tmux `theme terminal` shape (§3, §5).

- For: the Terminal Colour Theme gives the free Omarchy recolouring and transparency; RGB Colour Themes give Desktop parity and guaranteed contrast; a natural fallback — if truecolor is not detected the app can swap to the Terminal Colour Theme (Helix's whole-theme approach) instead of writing a per-colour quantiser; the Terminal Colour Theme could be the TUI's default, keeping today's behaviour for existing users.
- Against: the Colour Role set must be expressible in both RGB and ANSI-plus-modifiers, which constrains it (for example a "selection" Colour Role might be `REVERSED` in Terminal but an RGB background elsewhere, so a Colour Role may need to carry a full `Style`, not just a `Color`); the Terminal Colour Theme is a Desktop-less, TUI-only Colour Theme (the Desktop cannot read the terminal's ANSI colours), so the synced Preference could name a Colour Theme one Client cannot show — needs a rule for that; two paths to test.
- Fit with paired Colour Variants: the Terminal Colour Theme's light and dark Colour Variants would be the same ANSI mapping (or differ only in small ways, as yazi's two presets do), because the terminal already supplies light or dark; Colour Appearance would effectively be a no-op for it. Whether that is acceptable, or whether the Terminal Colour Theme is exempt from the "every built-in Colour Theme has paired Colour Variants" rule, is a question for #299. For the RGB Colour Themes, Colour Appearance "System" in the TUI means "the terminal's light/dark", which is #296's detection problem (OSC 11 background query, mode 2031, or tmux's `client-*-theme` hooks).

A further variant worth naming for #299, not surveyed in depth: **C′ — read the terminal's own palette.** Terminals answer OSC 4/10/11 queries with their current ANSI and default fg/bg RGB values; an app could build a Colour Theme from those at startup (and on change), getting RGB-level control with terminal-matched colours. This shares #296's query machinery and inherits its SSH/tmux reliability questions; no surveyed TUI does this for its whole UI (not verified exhaustively).

Whichever option is chosen, the evidence in §6 suggests the implementation sweep starts by replacing the 25 per-module `ACCENT`/`DIM` constants with a single Colour Role lookup, which all three options need.
