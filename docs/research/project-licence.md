# Research: Project licence options

**Question.** GitHub issue #263 ("Research and consider changing project license to MIT") asks whether Personal Ledger should stay on the GNU GPL v3 or move to MIT, Apache-2.0, ISC or another licence, weighing AI code generation and training, compatibility with the Rust dependency graph (tonic, prost, SQLx, gpui), ease of contribution, and whether proprietary reuse is a concern for this project. It asks for a comparison table, a recommendation with reasoning, and migration steps if the licence changes. All claims below are cited to primary sources: the licence texts themselves (gnu.org, apache.org, opensource.org, mozilla.org), the FSF's GPL FAQ and licence list, the OSI's Open Source Definition, SPDX, the Cargo and cargo-deny reference docs, the Rust API Guidelines, the US Copyright Office's *Copyright and Artificial Intelligence* reports, and this repository's own files, Git history and `cargo metadata`/`cargo deny` output. Research was carried out on 2026-09-26 against the `concept` branch at `cdd51db`; the dependency graph is a snapshot of `Cargo.lock` at that commit and will drift. This is not legal advice, and the decision stays with the project owner.

## 1. Current state in this repository

- **`LICENSE`** at the repo root is the unmodified GPL v3 text: it is byte-identical to https://www.gnu.org/licenses/gpl-3.0.txt (checked with `cmp`). GitHub's licence detector reports the repo as `GPL-3.0` (`api.github.com/repos/IanTeda/Personal-Ledger`, `license.spdx_id`).
- **No licence notice says which files the licence covers, or whether it is "v3 only" or "v3 or later".** No `.rs` file carries a copyright or SPDX header, and the only statement is the README's "Distributed under the GPL3.0 License. See `LICENSE.txt` for more information." (`README.md`, "License" section). The FSF's FAQ warns that "Just putting a copy of the GNU GPL in a file in your repository does not explicitly state that the code in the same repository may be used under the GNU GPL" (https://www.gnu.org/licenses/gpl-faq.html#LicenseCopyOnly), and GPL-3.0 §14 says that if the Program "does not specify a version number ... you may choose any version ever published" (https://www.gnu.org/licenses/gpl-3.0.txt, §14). The README's "GPL3.0" arguably fixes the version at 3, but neither "-only" nor "-or-later" is stated.
- **The README has two broken licence links:** it points at `LICENSE.txt` (the file is `LICENSE`) and its `[license-url]` points at `.../blob/master/LICENSE.txt` (the default branch is `main`, per the GitHub API).
- **No crate declares a licence.** There is no `[workspace.package]` table in the root `Cargo.toml`, and a grep of every `Cargo.toml` finds no `license` or `license-file` key. Every crate instead sets `publish = false`, with the comment "Never published to crates.io; also lets cargo-deny skip licence checks on workspace crates."
- **`deny.toml`'s `[licenses]` section** allows `0BSD`, `Apache-2.0`, `Apache-2.0 WITH LLVM-exception`, `BSD-1-Clause`, `BSD-2-Clause`, `BSD-3-Clause`, `BSL-1.0`, `CC0-1.0`, `CDLA-Permissive-2.0`, `ISC`, `MIT`, `MIT-0`, `MPL-2.0`, `NCSA`, `Unicode-3.0`, `Unlicense` and `Zlib`, with the comment "Licences must be compatible with this project's GPL-3.0", and sets `[licenses.private] ignore = true`. cargo-deny's docs state that with `private.ignore = true`, "workspace members will not have their license expression checked if they are not published" (https://embarkstudios.github.io/cargo-deny/checks/licenses/cfg.html). So cargo-deny only checks dependencies against the allow list; it never compares them against the project's own licence, and the missing `license` fields on workspace crates are not flagged. Every licence on the allow list is permissive or MPL-2.0, so the list is equally valid under a permissive project licence.
- **User-facing licence text.** The Desktop Help screen reads "Distributed under the GPL-3.0 License" (`crates/bins/bin-desktop/i18n/en-US/help.ftl`; `en-GB/help.ftl` spells it "Licence"), links `LICENSE_URL = "https://www.gnu.org/licenses/gpl-3.0.html"` (`crates/bins/bin-desktop/src/help.rs`), and has a unit test asserting the "GPL-3.0 License" string. The same Help catalogue's copyright line reads "© 2025–2026 { $author }. All rights reserved.", which sits awkwardly beside an open-source licence under any choice. The footer note "Free software — no warranty, see the license for details." is accurate for every licence in §3, since all of them disclaim warranty.
- **Third-party assets bundled into `bin-desktop`** keep their own licences whatever the project licence is: the Lucide icons (`crates/bins/bin-desktop/assets/icons/LICENSE`, ISC with an MIT portion) and the Archivo fonts (`crates/bins/bin-desktop/assets/fonts/OFL.txt`, SIL Open Font License 1.1).
- **Packaging.** The Sync Server Docker image excludes the licence: `.dockerignore` lists `LICENSE*` under "Docs and non-build metadata", so the image published to GHCR by `.github/workflows/build-publish-sync-server.yaml` ships the binary without the licence text. GPL-3.0 §4 and §6 require conveying the licence text with copies and object code (https://www.gnu.org/licenses/gpl-3.0.txt), and MIT requires "The above copyright notice and this permission notice shall be included in all copies or substantial portions of the Software" (https://opensource.org/license/mit). So this is a gap under either licence. `bin-desktop`'s `[package.metadata.packager]` sets no `license_file` or `copyright`, though cargo-packager's `Config` has both fields (https://docs.rs/cargo-packager/latest/cargo_packager/config/struct.Config.html).

## 2. Licence texts: what each one actually requires

**GPL-3.0** (https://www.gnu.org/licenses/gpl-3.0.txt). This is strong copyleft: a modified version you convey must be licensed "as a whole" under the GPL (§5c), and object code must be accompanied by, or offer, the Corresponding Source (§6). Linking counts: "Linking a GPL covered work statically or dynamically with other modules is making a combined work based on the GPL covered work" (https://www.gnu.org/licenses/gpl-faq.html#GPLStaticVsDynamic). For patents, §11 has each contributor grant "a non-exclusive, worldwide, royalty-free patent license under the contributor's essential patent claims", and §10 forbids a licensee to "initiate litigation ... alleging that any patent claim is infringed by making, using, selling ... the Program". §15 and §16 disclaim warranty and limit liability. On "or later", §14 lets a program opt in to future FSF versions. The FSF recommends "Version 3 of the GPL or any later version" so that it can update terms across a collection of software (https://www.gnu.org/licenses/gpl-faq.html#VersionThreeOrLater). The text runs to about 5,600 words. **The network gap:** "The GPL permits anyone to make a modified version and use it without ever distributing it to others", so a company running a modified GPL program on a website "does not have to release the modified sources" (https://www.gnu.org/licenses/gpl-faq.html#UnreleasedMods). The FSF calls GPLv3 "a copyleft license. We recommend it for most software packages" (https://www.gnu.org/licenses/license-list.html#GNUGPLv3).

**AGPL-3.0** (https://www.gnu.org/licenses/agpl-3.0.txt). This is GPL-3.0 plus §13: "if you modify the Program, your modified version must prominently offer all users interacting with it remotely through a computer network ... an opportunity to receive the Corresponding Source of your version". GPL-3.0 §13 and AGPL-3.0 §13 explicitly allow combining the two. The FSF says: "We recommend that developers consider using the GNU AGPL for any software which will commonly be run over a network" (https://www.gnu.org/licenses/license-list.html#AGPLv3.0; rationale at https://www.gnu.org/licenses/why-affero-gpl.html).

**MPL-2.0** (https://www.mozilla.org/en-US/MPL/2.0/). This is file-level copyleft: "The copyleft applies to any files containing MPLed code" (https://www.mozilla.org/en-US/MPL/2.0/FAQ/#copyleft-scope). "new files containing no MPL-licensed code are not Modifications", so MPL code "can be statically linked to and distributed as part of a larger proprietary piece of software" (FAQ #virality). Binary distributors "must inform the recipients where they can get the source for the MPLed code" (FAQ #distribute-my-binaries). §3.3 provides compatibility with GPL-2.0+, LGPL-2.1+ and AGPL-3.0 through a "Larger Work" (https://www.gnu.org/licenses/license-list.html#MPL-2.0). It has an express patent grant with patent-litigation termination. The text is about 2,400 words.

**MIT (Expat)** (https://opensource.org/license/mit). One grant to "deal in the Software without restriction", one condition (keep the copyright and permission notice in "all copies or substantial portions"), and an "AS IS" warranty and liability disclaimer. About 160 words. It has no express patent grant. The FSF calls it "a lax, permissive non-copyleft free software license, compatible with the GNU GPL" and prefers the name "Expat" because "MIT" is ambiguous (https://www.gnu.org/licenses/license-list.html#Expat).

**ISC** (https://opensource.org/license/isc-license-txt). "Permission to use, copy, modify, and/or distribute this software for any purpose ... is hereby granted, provided that the above copyright notice and this permission notice appear in all copies", plus a disclaimer. About 110 words. It has no express patent grant. The FSF says it is GPL-compatible, but notes that the wording "use, copy, modify, and distribute" is the same Pine-licence language the University of Washington once claimed did not allow distributing modified versions (https://www.gnu.org/licenses/license-list.html#ISC). The current OSI text adds "and/or", which fixes this.

**Apache-2.0** (https://www.apache.org/licenses/LICENSE-2.0.txt). §3 is an express patent grant from each Contributor, with **patent retaliation**: "If You institute patent litigation against any entity ... alleging that the Work ... constitutes direct or contributory patent infringement, then any patent licenses granted to You under this License for that Work shall terminate". §4 requires giving recipients a copy of the licence, marking modified files ("prominent notices stating that You changed the files"), and carrying forward any `NOTICE` file's attributions (§4(d)). §5 makes contributions inbound under the same licence by default. §6 withholds trademark rights. §7 and §8 disclaim warranty and liability. About 1,600 words including the appendix. The FSF: "compatible with version 3 of the GNU GPL ... not compatible with GPL version 2 ... The patent termination provision is a good thing, which is why we recommend the Apache 2.0 license for substantial programs over other lax permissive licenses" (https://www.gnu.org/licenses/license-list.html#apache2). The FSF also recommends Apache-2.0 for small programs under 300 lines (https://www.gnu.org/licenses/license-recommendations.html#small).

**MIT OR Apache-2.0** is the Rust convention. The Rust API Guidelines' C-PERMISSIVE item recommends `license = "MIT OR Apache-2.0"`, noting "The software produced by the Rust project is dual-licensed, under either the MIT or Apache 2.0 licenses", and that "Apache-only software cannot be used in some situations where most of the Rust runtime stack can" (https://rust-lang.github.io/api-guidelines/necessities.html#c-permissive). The rust-lang repo's `COPYRIGHT` states "The Rust Project is dual-licensed under Apache 2.0 and MIT terms" and "Copyrights in the Rust project are retained by their contributors. No copyright assignment is required" (https://github.com/rust-lang/rust/blob/main/COPYRIGHT). The recipient picks one licence, so the pair keeps GPL-2.0 compatibility through MIT and offers Apache's patent grant to those who take the Apache option. It is the most common expression in this project's own dependency graph (§4).

**SPDX identifiers.** Cargo reads `license` as an SPDX 2.3 expression, and the `/` separator is deprecated in favour of `OR` (https://doc.rust-lang.org/cargo/reference/manifest.html#the-license-and-license-file-fields). The bare `GPL-3.0` identifier "has been deprecated since license list version 3.0" (https://spdx.org/licenses/GPL-3.0.html). Any GPL declaration should use `GPL-3.0-only` or `GPL-3.0-or-later` (https://spdx.org/licenses/GPL-3.0-only.html, https://spdx.org/licenses/GPL-3.0-or-later.html).

## 3. Comparison table

| Licence | Permissive / copyleft | Patent handling | Warranty / liability | Ease of understanding | Common use cases |
|---|---|---|---|---|---|
| **GPL-3.0** (current) | Strong copyleft on distribution: the whole combined work, including statically linked code, must be GPL. No obligation for network use. | Express patent grant (§11); anti-litigation term (§10); anti-"discriminatory patent licence" terms (§11) | Disclaimed (§15), liability limited (§16), with §17 interpretation fallback | Hard: ~5,600 words, FAQ needed for linking and "or later" questions | Desktop apps and tools whose authors want every distributed fork to stay open |
| **AGPL-3.0** | Strongest copyleft: GPL-3.0 plus source-offer duty to remote network users of modified versions (§13) | As GPL-3.0 | As GPL-3.0 | Hard: ~5,500 words, plus judging what counts as "interacting remotely" | Server software meant to stay open when run as a service; the FSF recommends it for software "commonly run over a network" |
| **MPL-2.0** | Weak, file-level copyleft: modified MPL files stay MPL, new files can be any licence including proprietary | Express grant; terminates on patent litigation | Disclaimed, liability limited | Moderate: ~2,400 words, file-scope rule is intuitive | Libraries that want improvements shared back but allow proprietary embedding (Firefox; `option-ext`, `dwrote`, `cbindgen` in this graph) |
| **MIT (Expat)** | Permissive: keep the notice, nothing else | None express (implied licence at best, see §8) | Disclaimed ("AS IS") with liability exclusion | Very easy: ~160 words | Most small and medium open-source libraries and apps; about 250 packages in this graph are MIT-only, including `tokio`, `tonic` and `ratatui` |
| **Apache-2.0** | Permissive, with conditions: licence copy, change notices, `NOTICE` propagation | Express grant (§3) with patent-retaliation termination | Disclaimed (§7), liability limited (§8) | Moderate: ~1,600 words, clear structure | Projects wanting explicit patent terms; in this graph `gpui`, `gpui-component`, `prost`, `ring` (with ISC) |
| **ISC** | Permissive, functionally equivalent to MIT/BSD-2 | None express | Disclaimed, liability excluded | Easiest: ~110 words | OpenBSD (the FSF notes it is "also known as the OpenBSD License"); in this graph `rustls-webpki`, `libloading`, the Lucide icons bundled here |
| **MIT OR Apache-2.0** | Permissive; recipient chooses | Apache option gives express grant and retaliation; MIT option keeps GPL-2.0 compatibility | Disclaimed under either | Easy to apply (convention); two files to ship | The Rust ecosystem default: rustc/std, `serde`, `sqlx` and about 600 packages in this graph |

## 4. Dependency compatibility

**Method.** `SQLX_OFFLINE=true cargo metadata --format-version 1 --offline --locked` over the workspace gives 1,021 registry package versions (908 distinct crate names) in the resolve. Their `license` fields were tallied with `jq`, and specific crates were traced with `cargo tree --offline -i <crate> --target all`. Separately, `SQLX_OFFLINE=true cargo deny --offline check licenses` against the current `deny.toml` (with `[graph] all-features = true`) reports `licenses ok`.

**Distribution.** By far the most common expressions are `MIT OR Apache-2.0`, which appears as 429 packages, plus 101 `Apache-2.0 OR MIT`, 53 `MIT/Apache-2.0` and 9 `Apache-2.0/MIT` in the older slash syntax. Next come `MIT` (247), `Unicode-3.0` (41, the ICU4X crates behind `lib-locale`), `Apache-2.0` alone (31) and `BSD-3-Clause` (13). The remaining packages carry ISC, Zlib, CC0-1.0, BSD-2-Clause, 0BSD, CDLA-Permissive-2.0 and Unlicense in various `OR` combinations.

**Items worth flagging:**

- **No dependency is GPL-only, LGPL-only or AGPL.** Nothing in the graph forces the project to stay copyleft, so relicensing to a permissive licence is not blocked by dependencies.
- **`self_cell 1.3.0`** is `Apache-2.0 OR GPL-2.0-only` (reached via `cosmic-text` ← `gpui`), and **`r-efi 5.3.0`/`6.0.0`** are `MIT OR Apache-2.0 OR LGPL-2.1-or-later` (via `getrandom`). Both are choice expressions, so the permissive option applies under any project licence.
- **MPL-2.0 (weak copyleft)** appears three times. `option-ext 0.2.0` comes in via `dirs-sys` ← `dirs` ← `lib_config`/`bin_desktop`/`zed-font-kit`, so it is in every Client binary. `dwrote 0.11.5` comes in via `zed-font-kit` ← `gpui` and is a Windows DirectWrite binding. `cbindgen 0.28.0` is a macOS-only *build*-dependency of `gpui` (`[target.'cfg(target_os = "macos")'.build-dependencies.cbindgen]` in the published `gpui-0.2.2/Cargo.toml`), so it is not linked into the binary. MPL-2.0 is compatible with any of the candidate licences: under GPL/AGPL through §3.3, and under a permissive licence because only the MPL files themselves stay MPL. It adds one duty when shipping binaries: tell recipients where the MPL source is (MPL FAQ #distribute-my-binaries). That holds whatever this project's licence is.
- **Lockfile-only, not built:** `terminfo 0.9.0` (WTFPL), `termina` (`MIT OR MPL-2.0`), `finl_unicode` and `wezterm-bidi` (`Unicode-DFS-2016`) appear in `cargo metadata` but `cargo tree -i` finds no path to them from any workspace crate. They sit behind features nothing enables, which is why cargo-deny passes even though WTFPL is not on the allow list.
- **Apache-2.0-only crates** (`gpui` and its `gpui_*` sub-crates, `gpui-component`, `prost`/`prost-build`/`prost-types`, `ring` as `Apache-2.0 AND ISC`, `approx`, `sync_wrapper` and others). These are compatible with GPL-3.0, AGPL-3.0, MIT, ISC and MIT OR Apache-2.0. They would only be a problem for a GPL-2.0-only project, and none of the candidates is that (FSF on Apache-2.0 above). Shipping a binary means complying with Apache-2.0 §4 for them (licence copy; `NOTICE` if present) under any project licence. Of the 1,021 package directories, only `cfg_aliases 0.2.2`, a build-time crate, ships a `NOTICE` file.
- **gpui and Zed.** The published `gpui 0.2.2` and `gpui-component 0.5.1` manifests both declare `license = "Apache-2.0"`, and both crate directories ship `LICENSE-APACHE` (checked in `~/.cargo/registry/src/.../gpui-0.2.2/` and `.../gpui-component-0.5.1/`). The upstream `zed-industries/zed` `crates/gpui/Cargo.toml` also reads `license = "Apache-2.0"` (https://github.com/zed-industries/zed/blob/main/crates/gpui/Cargo.toml). Zed's repository root carries both `LICENSE-APACHE` and `LICENSE-GPL` (GitHub contents API, `repos/zed-industries/zed/contents/`), because the editor itself has GPL parts. None of those GPL crates is a dependency here: every `gpui_*`, `zed-*` and `gpui-component*` package in the resolve is Apache-2.0, `MIT OR Apache-2.0` or MIT (`zed-scap`, `zed-xim`). GitHub reports `NOASSERTION` for the `longbridge/gpui-component` repo (`api.github.com/repos/longbridge/gpui-component/license`), but the crate as published and consumed declares Apache-2.0.
- **tonic / prost / SQLx / tokio / ratatui / ICU4X** are all `MIT` or `MIT OR Apache-2.0`, except prost (Apache-2.0) and ICU4X (Unicode-3.0). None constrains the project licence.

**Conclusion for this section.** The dependency graph is compatible with every candidate in §3, and cargo-deny's allow list needs no change for any of them. Under any choice, the distributed binaries carry the same third-party duties: Apache-2.0 licence copies, MPL-2.0 source pointers, Unicode-3.0 notices, and MIT/BSD/ISC notices. Today no packaging step collects these. A tool such as `cargo about` could generate a third-party notices file, but it was not evaluated here.

## 5. Relicensing mechanics

- **Who holds copyright.** `git shortlog -sne --all` shows a single author, `Ian Teda <ian@teda.id.au>`, on all 462 commits. The committer is Ian on 459 and `GitHub <noreply@github.com>` on 3 (web-UI merges). Of the 5 pull requests ever opened (`gh pr list --state all`), the 2 merged ones (#3, #51) were authored by IanTeda. The 3 Dependabot PRs (#4–#6) were closed unmerged. No commit carries a `Signed-off-by` or third-party `Co-authored-by` trailer other than the Claude trailers discussed in §6. On the Git evidence, there are no outside human copyright holders whose consent would be needed.
- **A sole copyright holder can relicense.** "If you are the copyright holder for the code, you can release it under various different non-exclusive licenses at various times" (https://www.gnu.org/licenses/gpl-faq.html#ReleaseUnderGPLAndNF). The developer "is not bound by" the GPL, which "is a license from the developer for others" (https://www.gnu.org/licenses/gpl-faq.html#DeveloperViolate).
- **Past copies stay GPL.** "the public already has the right to use the program under the GPL, and this right cannot be withdrawn" (https://www.gnu.org/licenses/gpl-faq.html#CanDeveloperThirdParty), and "The license that comes in your copy ... is the license that applies to your copy" (https://www.gnu.org/licenses/gpl-faq.html#HeardOtherLicense). Anyone who got the repository between its first commit (2024-01-04) and the relicensing commit keeps GPL-3.0 rights to that snapshot. There are no tags and `gh release list` is empty today. Still, the Build and Publish Sync Server workflow ran on a `release` event for `v0.0.1-sync-server-ci-test` on 2026-09-03 and pushes to `ghcr.io/ianteda/personal-ledger-sync-server`, and the TUI and Desktop workflows ran by `workflow_dispatch` on 2026-09-17, uploading CI artefacts. Any image or artefact that still exists is a GPL-3.0 distribution.
- **Bundled third-party files** (Lucide icons, Archivo fonts) are not the owner's to relicense and keep their ISC/MIT and OFL-1.1 licences.

## 6. AI considerations

- **Share of AI-assisted commits.** 278 of the 462 commits (60%) carry a `Co-Authored-By: Claude …` trailer (`git log --all -i --grep='Co-authored-by: Claude'`). Most name Sonnet 5, then Opus 5.5, Haiku 4.5 and Opus 5. The Git author on all of them is the owner.
- **Copyrightability of AI output (US).** The US Copyright Office's *Copyright and Artificial Intelligence, Part 2: Copyrightability* (29 January 2025, https://www.copyright.gov/ai/Copyright-and-Artificial-Intelligence-Part-2-Copyrightability-Report.pdf) concludes that "The use of AI tools to assist rather than stand in for human creativity does not affect the availability of copyright protection for the output". It also says "Copyright does not extend to purely AI-generated material, or material where there is insufficient human control over the expressive elements" and "prompts do not alone provide sufficient control". Human authors keep copyright in "the creative selection, coordination, or arrangement of material in the outputs, or creative modifications of the outputs", and whether the human contribution suffices "must be analyzed on a case-by-case basis". In this repo the owner specifies, reviews, edits and arranges the code, but some portions may have thin or no copyright protection in the US.
- **Why that matters more for copyleft than for permissive licences** (this is analysis, not a cited ruling). Every licence here works by granting permission under copyright. A permissive licence's practical job is to give permission and disclaim warranty, and it loses little if some code turns out to be uncopyrightable. Copyleft's job is to enforce reciprocity through copyright, and code nobody owns cannot be enforced. A large AI-assisted share therefore weakens the practical value of GPL/AGPL more than that of MIT/Apache, even though the licence text applies the same way to the human-authored parts.
- **Licence choice has little effect on AI training.** None of the GPL-3.0, AGPL-3.0, MPL-2.0, MIT, ISC or Apache-2.0 texts mentions machine learning or training (GPL-3.0's only "machine" is "machine-readable Corresponding Source", §6). The Copyright Office's *Part 3: Generative AI Training* (pre-publication, 9 May 2025, https://www.copyright.gov/ai/Copyright-and-Artificial-Intelligence-Part-3-Generative-AI-Training-Report-Pre-Publication-Version.pdf) frames training as prima facie use whose legality turns on fair use: "The key question ... is whether those acts of prima facie infringement can be excused as fair use", decided case by case. Where a use is fair, no licence permission is needed, so neither copyleft nor permissive terms reach it. A licence that tried to forbid training would stop being open source: the OSI's Open Source Definition clause 6 says "The license must not restrict anyone from making use of the program in a specific field of endeavor" (https://opensource.org/osd), and the FSF lists the "Responsible AI Licenses" (RAIL) as nonfree "because they deny freedom 0" (https://www.gnu.org/licenses/license-list.html#RAIL). The OSI's Open Source AI Definition 1.0 (https://opensource.org/ai/open-source-ai-definition) defines what makes an *AI system* open source. It does not address whether OSI-approved software licences permit using code as training data. No FSF or OSI first-party statement was found saying that GPL code in training data makes a model or its output GPL.
- **Net effect.** Staying on GPL does not stop this code from being used for training, and moving to MIT does not newly permit it in any way a licence controls. The AI question mainly argues that copyleft's enforcement value is weaker here than usual.

## 7. Personal Ledger context

- **Mission.** The PRD: "a self-hosted, local-first ledger that lets the owner fully control and own their data" and "without handing their financial data to a third party" (`docs/product-requirements.md` §1.1–1.2). NFR.2: "All data is stored locally in SQLite; no data leaves the device by default". The README's motivations: existing finance apps "were monthly subscription models with high fees", and it is a "Funsy project to hone my programming skills". The PRD's privacy goal concerns the *user's financial data*, which the software licence does not govern. A licence choice neither helps nor hurts it.
- **Shape of the software.** The Desktop and TUI Clients are distributed as binaries (GPL §6 applies). The Sync Server is a self-hostable network service shipped as a Docker image (NFR.6b), which falls in the GPL's network gap (§2). If the owner's concern is someone offering a closed, modified hosted "Personal Ledger sync" as a subscription, the very model the README reacts against, GPL-3.0 does not prevent it and AGPL-3.0 would. If that concern is not real for a personal project, copyleft buys little.
- **Reuse surface.** `lib-core`, `lib-locale`/`lib-locale-build` and `lib-config` are general-purpose Rust crates. Under GPL they cannot be reused in the permissively licensed Rust ecosystem that supplies almost all of this project's dependencies. Under MIT OR Apache-2.0 they could be published to crates.io as-is.
- **Contributors.** There are none yet besides the owner, so the choice can be made now without anyone else's consent. That gets harder once outside contributions arrive.

## 8. Recommendation

*This is a recommendation for the owner to weigh, not a decision. The decision and any ADR stay with the project owner.*

**Recommended: relicense future versions as `MIT OR Apache-2.0`.** Reasons:

1. **It matches the ecosystem the project is built from and would contribute back to.** It is the Rust API Guidelines' C-PERMISSIVE recommendation, the Rust project's own licence, and the largest single expression in this dependency graph. Any library crate here could later be published or reused without friction.
2. **Copyleft is protecting little here.** GPL-3.0 does not reach the Sync Server's network use, which is the only realistic commercial "capture" route. About 60% of commits are AI-assisted, which weakens the practical enforceability that copyleft depends on (§6). And the project's stated risk is subscription pricing, not proprietary forks.
3. **Apache-2.0's patent grant and retaliation clause are kept** for anyone who wants them, while the MIT option keeps GPL-2.0 compatibility and the simplest possible terms. This is better than plain MIT, which leaves patents implicit, and better than plain Apache-2.0, which the guidelines note "cannot be used in some situations where most of the Rust runtime stack can".
4. **It is cheap to do now.** There is a single copyright holder, no external contributors, no tagged releases, and no dependency forcing copyleft (§4–5).

**When to choose differently:**

- **If keeping hosted and distributed forks open matters to the owner, use `AGPL-3.0-or-later` rather than staying on GPL-3.0.** AGPL closes the network gap that GPL leaves open for the Sync Server, while having the same compatibility with every dependency (§4). Staying on plain GPL-3.0 keeps the costs of copyleft without covering the network case that matters most here.
- **Plain MIT (or ISC)** is a reasonable, simpler choice if one licence file is preferred over two. The cost is losing Apache's express patent terms and not following the Rust convention. ISC's "and/or" wording is fine, but it is less recognised than MIT.
- **MPL-2.0** fits if the owner wants changes to *existing files* shared back while allowing embedding in anything. It is uncommon for Rust application code, and it adds the per-file notice burden.

**Whatever the choice, fix the gaps from §1:** state the licence explicitly (an SPDX `license` field, and a README statement with "-only"/"-or-later" if staying GPL), fix the README links, ship `LICENSE*` in the Docker image and packages, and produce a third-party notices file for the binaries.
