# Research: Cross-platform packaging tools for a non-root Rust desktop GUI installer

**Snapshot date:** 2026-09-02.

**Question.** The Desktop App feasibility map (FC-DESKTOP-001–004, issue #23) needs release packaging for a real GUI application, not the TUI binary covered by the earlier survey (`docs/research/tui-packaging-tools.md`, ADR-0004). The same two product-requirements constraints apply — NFR.2 ("never requires root/administrator privileges") and NFR.6 (Linux/macOS/Windows) — but a GUI app raises requirements the TUI never exercised: an application icon that needs to render in a Dock, taskbar, and Start Menu; `.app`/`.dmg` metadata (bundle identifier, `Info.plist`, category, minimum OS version); a Linux `.desktop` entry so the app appears in application launchers; and, on Windows, a real installer may be warranted (Start Menu shortcut, uninstall entry, upgrade handling) rather than TUI's bare portable zip. This note surveys `cargo-packager`, `cargo-dist`, `cargo-bundle`, Tauri's own bundler (`tauri-bundler`, invoked via `tauri build`), `cargo-wix` (Windows MSI specifically), AppImage tooling used directly (`linuxdeploy`/`appimagetool`), and hand-rolled CI packaging, against three required outputs: (1) a portable non-elevated executable **or** a non-elevated installer on Windows, (2) a user-scope `.dmg`/`.app` on macOS, and (3) a user-scope installable package on Linux (`.deb` and/or AppImage). This is research input for decision ticket #27 ("Decide desktop packaging tool and record ADR"); it does not make the decision, and does not resolve the coupling with the framework-choice ticket #26 (see "Coupling with the framework choice" below) — both are left for #27.

Research was done by reading each tool's README and documentation source directly from its GitHub repository (via the `gh` CLI and `WebFetch` against `crabnebula-dev/cargo-packager`, `axodotdev/cargo-dist`, `burtonageo/cargo-bundle`, `tauri-apps/tauri` (for `tauri-bundler` and the Tauri v2 distribution docs), `volks73/cargo-wix`, `AppImage/appimagetool`, and `linuxdeploy/linuxdeploy`, including their config/API reference pages on docs.rs), cross-checking release/version/star/issue metadata via the GitHub REST API and the crates.io API, and consulting the WiX Toolset's own schema reference for MSI install-scope semantics. All claims below are cited to primary sources; none are drawn from blog posts or third-party tutorials.

## 2. cargo-packager — GUI-specific capabilities beyond TUI usage

The TUI cycle used `cargo-packager` only for macOS/Linux archive-shaped output; a GUI app exercises more of its config surface.

**Icons.** The top-level `Config::icons` field is documented simply as "The app's icon list. Supports glob patterns" (docs.rs, `cargo_packager::config::Config`, https://docs.rs/cargo-packager/latest/cargo_packager/config/struct.Config.html) — a flat glob list rather than per-platform fields; per-platform conversion (ICNS for macOS, ICO for Windows, PNG sizes for Linux) is implied but the field-level doc comment does not spell out the conversion behaviour the way tauri-bundler's does (§4).

**macOS metadata.** `MacOsConfig` exposes `info_plist_path` ("Path to the Info.plist file for the package"), `minimum_system_version` ("A version string indicating the minimum MacOS version that the packaged app supports (e.g. `"10.11"`)... you may also want have your `build.rs` script emit `cargo:rustc-env=MACOSX_DEPLOYMENT_TARGET=10.11`"), `entitlements` ("Path to the entitlements.plist file"), `background_app` ("Whether this is a background application. If true, the app will not appear in the Dock. Sets the `LSUIElement` flag"), and `embedded_provisionprofile_path` (docs.rs, `cargo_packager::config::MacOsConfig`, https://docs.rs/cargo-packager/latest/cargo_packager/config/struct.MacOsConfig.html). This is a real config surface for GUI-specific `.app` behaviour (Dock visibility, minimum OS gating) the TUI cycle never touched.

**Linux desktop entry.** `LinuxConfig` has exactly one field: `generate_desktop_entry: bool` ("Flag to indicate if desktop entry should be generated") (docs.rs, `cargo_packager::config::LinuxConfig`, https://docs.rs/cargo-packager/latest/cargo_packager/config/struct.LinuxConfig.html). It is a toggle, not a rich schema — no exposed fields for per-locale names, `GenericName`, or `Keywords`; the shared top-level `category` field (an `AppCategory` enum) is the only other GUI-relevant metadata found. This is thinner than cargo-bundle's equivalent surface (§4).

**Windows.** `WindowsConfig` (docs.rs, `cargo_packager::config::WindowsConfig`, https://docs.rs/cargo-packager/latest/cargo_packager/config/struct.WindowsConfig.html) contains only code-signing and version-management fields (`digest_algorithm`, `certificate_thumbprint`, `tsp`, `timestamp_url`, `allow_downgrades`, `sign_command`) — no icon or installer-branding fields live here; the app icon comes from the shared top-level `icons` list. The non-elevated `CurrentUser` NSIS install mode already noted in the TUI research still applies unchanged.

**Bottom line for GUI use.** cargo-packager's platform coverage is unchanged from the TUI survey, and it does add real GUI-relevant fields (Dock visibility, plist path, entitlements, minimum OS version) for macOS — but its Linux desktop-entry support is a bare on/off flag, notably thinner than cargo-bundle's.

## 3. cargo-dist

No material change from the TUI-cycle findings: still no native macOS or Linux packaging (confirmed unchanged — crates.io shows no release since v0.32.0/2026-05-21, and the GitHub repo's `pushed_at` of 2026-08-31 reflects ordinary maintenance, not a new packaging-format feature). It remains a strong Windows-archive + CI-generation tool with a documented Windows-signing integration, but is not a candidate for the macOS/Linux GUI outputs this ticket requires on its own.

## 4. cargo-bundle — the richest GUI-metadata surface among the dedicated tools

Re-reading the current README (https://github.com/burtonageo/cargo-bundle/blob/master/Readme.md) with a GUI lens (rather than the TUI survey's archive-shaped lens) surfaces meaningfully richer metadata support than cargo-packager's:

- **Icons:** `icon = ["32x32.png", "128x128.png", "128x128@2x.png"]` — "an array of file paths or globs (with images in various sizes/formats)," with the `@2x` Retina-suffix convention documented explicitly.
- **Category:** `category = "Developer Tool"` — "can be a human-readable string..., or a Mac OS X `LSApplicationCategoryType` value, or a GNOME desktop file category name, and `cargo-bundle` will automatically convert as needed for different platforms" — a genuine cross-platform category mapping, not just a pass-through value.
- **macOS `Info.plist`:** `osx_info_plist_exts` — "a list of path strings that contain extra values for `Info.plist`" appended during bundling, a more open-ended mechanism than cargo-packager's single `info_plist_path` replacement file.
- **Linux desktop entry:** `linux_localizations` supports per-locale `Name`, `GenericName`, `Comment`, and `Keywords` in the generated `.desktop` file — richer than cargo-packager's boolean toggle.

This doesn't change cargo-bundle's other TUI-survey findings (single maintainer, self-described "very early alpha," unstable config format, AppImage shared-library-collection gap, no CI-generation help) — those stand. But on pure GUI-metadata richness, cargo-bundle is ahead of cargo-packager.

## 5. tauri-bundler — Tauri's own bundler, invoked via `tauri build`

This is the framework-coupling candidate the ticket asked to check explicitly, and it is a **fork of cargo-bundle**, not of cargo-packager, and not a general-purpose tool at all:

**Lineage and scope.** Its own README states plainly: "This is a fork of the awesome cargo-bundle, turned into a library used by the Tauri CLI" (raw README, `tauri-apps/tauri` `crates/tauri-bundler/README.md`). It supports non-Tauri use in principle ("this library doesn't rely on [`tauri.conf.json`] and can be used by non-Tauri apps") but its own API-stability note undercuts that: "the public API does not strictly adhere to SemVer" because it is "intended to be used primarily in tauri-cli" (same README) — i.e. it is shipped and versioned as an implementation detail of the Tauri CLI, not as an independent cargo subcommand a project would `cargo install` on its own the way cargo-packager/cargo-bundle/cargo-dist are.

**Output coverage.** Via `tauri build`, Tauri v2's distribution docs list macOS (`.app`, `.dmg`, App Store), Linux (AppImage, `.deb`, RPM, Snapcraft, Flatpak, AUR), and Windows (MSI via WiX, NSIS, Microsoft Store) (v2.tauri.app, `/distribute/`) — broader per-platform format coverage than any of the three general-purpose crates, because it's building specifically for the one framework rather than arbitrary binaries.

**Windows elevation.** Tauri's NSIS installer defaults to the same non-elevated per-user model as cargo-packager: "By default the installer will install your application for the current user only. The advantage of this option is that the installer does not require Administrator privileges to run," configured via `tauri.conf.json`'s `bundle.windows.nsis.installMode` (`currentUser` default, `perMachine`/`both` requiring elevation) (v2.tauri.app, `/distribute/windows-installer/`). Tauri's WiX/MSI path is a second, separate installer option built on the same underlying WiX Toolset as cargo-wix (§6) and inherits WiX's own per-machine-by-default elevation semantics unless explicitly configured otherwise — Tauri does not appear to override that default the way it does for NSIS. Both WiX and NSIS "must be installed separately" by the developer; Tauri does not bundle or auto-download either toolchain (v2.tauri.app, `/distribute/windows-installer/`).

**Linux AppImage caveat specific to real GUI apps.** Tauri's own AppImage guide states "linuxdeploy, the AppImage tooling Tauri uses, currently does not support cross-compiling ARM AppImages" and — more importantly for the non-root/portability requirement generally — warns that the build must target "the oldest base system you intend to support" (e.g. Ubuntu 22.04/Debian 12 for `libwebkit2gtk-4.1-dev`) because a newer build host raises the minimum glibc/GTK version the resulting AppImage depends on at runtime (v2.tauri.app, `/distribute/appimage/`). This is a GUI-toolkit-specific (GTK/WebKitGTK) constraint the TUI never hit, and it is **inherent to shipping a GTK-linked GUI binary as an AppImage**, not specific to Tauri's tooling choice — any GTK-based GUI framework packaged via cargo-packager, cargo-bundle, or hand-rolled `linuxdeploy` would face the same base-system pinning requirement. Tauri also supports bundling GStreamer via a `bundleMediaFramework` flag for audio/video, at a real size and plugin-licensing cost.

**Coupling with the framework choice (explicit, unresolved here).** If the framework survey (#26) selects Tauri, `tauri build` already produces non-elevated Windows NSIS installers, `.dmg`/`.app` on macOS, and AppImage/`.deb` on Linux — the same three required outputs this ticket surveys — with no separate packaging tool invocation needed for the core bundle formats. That would make a separate general-purpose packaging tool (cargo-packager/cargo-dist/cargo-bundle) redundant for the bundling step itself, though such a tool could still add value orthogonal to bundling — e.g. cargo-dist's auto-generated release pipeline and built-in Windows SmartScreen signing integration, wrapped *around* `tauri build`'s output rather than replacing it. If the framework survey instead selects a non-Tauri toolkit (e.g. `egui`, `iced`, `slint`, or a plain windowing/rendering stack with no bundler of its own), none of that applies and the general-purpose tools (cargo-packager, cargo-bundle, cargo-dist, cargo-wix, hand-rolled) are the only candidates. This coupling is real and is left for #27 to resolve once #26 lands, per the ticket brief.

## 6. cargo-wix — Windows MSI specifically

**What it does.** "A subcommand for Cargo that builds a Windows installer (MSI) using the WiX Toolset from the build of a Rust binary project," with optional SignTool-based code signing (GitHub README, `volks73/cargo-wix`, https://github.com/volks73/cargo-wix). It requires the WiX Toolset installed separately — "WiX Toolset v3.14.1 or newer," supporting both the Legacy (v3.x) and Modern (v4+) toolchains, Legacy currently the default.

**Non-elevation caveat.** The cargo-wix README itself documents no install-scope/elevation configuration; that behaviour is governed by the underlying WiX Toolset's MSI package-scope semantics. WiX's own schema reference states that "a per-user installation declaration sets the `ALLUSERS` property to 2 and the package's `InstallPrivileges` attribute to `limited`" — i.e. non-elevated per-user MSI installs are a real, supported WiX capability, but they require explicit configuration (`PackageScopeType`) rather than being cargo-wix's or WiX's default (WiX Toolset schema docs, `PackageScopeType`, https://wixtoolset.org/docs/schema/wxs/packagescopetype). Left unconfigured, a WiX-built `.msi` installs per-machine and requires Administrator elevation — the opposite of NFR.2's default requirement, and a caveat neither cargo-packager's NSIS path nor Tauri's NSIS path shares (both default to `currentUser`/non-elevated).

**Maintenance.** Active — v0.3.9, 209,395 recent crates.io downloads (the highest of the non-Tauri tools surveyed, reflecting MSI's popularity as a Windows package format generally), 381 GitHub stars, dual MIT/Apache-2.0 licensed.

**Bottom line.** cargo-wix is the right tool if a project specifically wants a native `.msi` (Windows-native install/uninstall UX, Programs-and-Features integration, upgrade-code-based versioning) rather than an NSIS `.exe`, but it needs an explicit, easy-to-miss non-default configuration step to avoid an elevation prompt — a real non-root-specific caveat this ticket's brief asked to flag.

## 7. AppImage tooling used directly (`linuxdeploy` + `appimagetool`)

Beyond the TUI survey's brief mention, for a real GUI app the two tools split responsibility as follows: `linuxdeploy` is described in its own README as providing "extensive functionalities to create and bundle AppDirs for applications," via a plugin architecture with "bundling plugins" (add resources/shared libraries to the AppDir) and "output plugins" (convert the AppDir into a final bundle format such as AppImage) (GitHub README, `linuxdeploy/linuxdeploy`, https://github.com/linuxdeploy/linuxdeploy). Critically, `linuxdeploy` does **not** generate the `.desktop` file or select the icon for you — those must already exist in the AppDir the developer assembles; `linuxdeploy`'s job is collecting the shared libraries a GUI binary actually needs at runtime (via `ldd`-style dependency walking and its plugin system), which is exactly the gap the TUI survey flagged in cargo-bundle's AppImage support. `appimagetool` remains the lower-level tool that turns a finished AppDir into the final `.AppImage` file. Neither tool is company-backed; both are community-maintained but not stale (`linuxdeploy` pushed 2026-08-01, `appimagetool` pushed 2025-12-04).

**Bottom line.** Using `linuxdeploy`+`appimagetool` directly gives full control and solves the shared-library-collection gap cargo-bundle has, but the developer is fully responsible for authoring the `.desktop` file, choosing/placing the icon, and (per §5's GTK caveat) building on an old-enough base system — none of which any of the three dedicated Rust crates automate away either, they only vary in how much of the AppDir structure they scaffold for you.

## 8. Hand-rolled CI packaging

Unchanged in mechanism from the TUI survey (`hdiutil`/`create-dmg` for macOS, `dpkg-deb` for `.deb`, `linuxdeploy`/`appimagetool` for AppImage, `Compress-Archive`/`zip` for a portable Windows exe) — but the GUI framing changes the calculus on Windows specifically: the TUI ticket's "portable single exe" requirement was fully satisfied by a bare zip, whereas this ticket's brief explicitly allows for "a real GUI app may warrant an actual installer... unlike TUI's plain portable zip." A hand-rolled Windows path that wants a real installer (Start Menu entry, uninstaller, upgrade handling) rather than a portable zip would have to either script WiX/NSIS directly (duplicating what cargo-wix/cargo-packager/tauri-bundler already wrap) or stay with a portable zip and accept the reduced desktop-integration UX — this is a real trade-off introduced by the GUI context that didn't exist for the TUI.

## 9. Gotchas carried over and new for GUI apps

**macOS Gatekeeper and Windows SmartScreen** friction is unchanged from the TUI findings — both are reputation/signature-based and independent of which of these tools builds the artifact; only cargo-dist (Windows) and cargo-packager (macOS) expose first-party signing config, and Tauri exposes its own signing docs referenced above but the fetched distribution pages did not detail SmartScreen mitigations directly.

**`.deb` vs. root** — unchanged from the TUI findings (Debian Policy's root-owned, `/usr`-rooted convention is in tension with NFR.2; AppImage remains the Linux format that satisfies NFR.2 unmodified).

**New: WiX/MSI defaults to elevated** (§6) — a caveat that didn't arise in the TUI survey because the TUI's Windows output was a bare zip, never an installer. Any tool that produces an `.msi` (cargo-wix directly, or Tauri's WiX option) needs an explicit non-default configuration step to avoid Administrator elevation; NSIS-based installers (cargo-packager, Tauri's NSIS option) default to non-elevated already.

**New: GTK/WebKitGTK base-system pinning for AppImage** (§5) — a caveat inherent to any GTK-linked GUI binary (not specific to Tauri, but surfaced through Tauri's own docs because Tauri's WebView-based architecture makes the dependency concrete): the AppImage's runtime glibc/GTK floor is set by the *build* host, not a packaging-tool setting, so CI must build on the oldest OS the project wants to support regardless of which packaging tool assembles the AppImage.

**New: icon/metadata richness varies a lot** across the three general-purpose crates for a GUI app specifically — cargo-bundle's category-conversion, per-locale desktop-entry fields, and open-ended `Info.plist` extension mechanism are richer than cargo-packager's boolean desktop-entry flag and single-file plist replacement; this wasn't visible in the TUI survey because the TUI binary needed none of this metadata.

## Summary for the decision ticket

This is research only; no recommendation is made here. The material findings for #27 to weigh: cargo-dist's macOS/Linux gap is unchanged and still rules it out as a sole tool. cargo-packager retains its "one config for all three platforms" advantage but its GUI-metadata surface (icons aside) is thinner than cargo-bundle's, particularly for Linux desktop entries. cargo-bundle has the richest GUI-metadata support of the three general crates but carries the same bus-factor/stability caveats found in the TUI survey. cargo-wix is a viable Windows-MSI-specific option but defaults to an elevated install unless explicitly reconfigured — a real non-root caveat. Direct `linuxdeploy`/`appimagetool` use and hand-rolled CI remain fully capable but the most labor-intensive options, and for a GUI app, "hand-rolled Windows" now has to choose between a portable zip (less desktop integration) and hand-scripted WiX/NSIS (duplicating what dedicated tools already wrap).

The framework-coupling question is the largest open item, and is explicitly **not resolved here**: if the framework survey (#26) picks Tauri, `tauri build`'s own bundler (`tauri-bundler`, a cargo-bundle fork bundled into the Tauri CLI, not a standalone general-purpose tool) already produces all three required outputs, likely making a separate packaging-tool adoption unnecessary for the core bundling step — though a tool like cargo-dist could still be layered on top for its CI-generation/signing strengths. If the framework survey picks a non-Tauri toolkit, the general-purpose tools surveyed here (cargo-packager, cargo-bundle, cargo-dist, cargo-wix, hand-rolled) are the field to choose from on their own merits. Ticket #27 is gated on both this research and the framework-choice ticket #26 (https://github.com/IanTeda/Personal-Ledger/issues/26) landing first.
