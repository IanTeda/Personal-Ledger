# Research: Rust desktop GUI frameworks for charts and tables

**Question.** GitHub issue #24 ("Survey Rust desktop GUI frameworks for charts and tables"), a child of the "Desktop App feasibility" Wayfinder map (#23, FC-DESKTOP-001–004), asks for a primary-source survey of Rust desktop GUI framework/toolkit crates — `egui`, `iced`, `Tauri`, `Slint`, `gtk-rs`/`relm4`, and any other credible candidate — covering: (a) native or extension support for line, doughnut, candlestick, and divergent (bar) charts; (b) table/grid widgets; (c) cross-platform support and native-look fidelity on Linux/macOS/Windows; (d) maintenance activity and licensing; (e) whether the framework's architecture is compatible with reusing this repo's ADR-0003 hybrid TEA/component pattern (`docs/adr/0003-hybrid-tea-component-tui-architecture.md`). This note is primary-source research only, feeding a later decision ticket (#26, "Decide desktop GUI framework and record ADR"). It does not recommend or decide anything, following the same research-only scope as the TUI precedent (`docs/research/tui-charting-libraries.md`, feeding #11/ADR-0002).

All claims are cited to primary sources — crates.io's JSON API (`https://crates.io/api/v1/crates/<name>`), docs.rs, official project docs/websites, and the GitHub REST API (`api.github.com`) for issue/star counts and last-push timestamps — not blog posts, Reddit, or third-party tutorials. Research was carried out on 2026-09-02; version numbers, download counts, and issue counts are a snapshot as of that date and will drift.

## 1. `egui` (immediate-mode)

**Identity and maintenance.** Per crates.io (https://crates.io/api/v1/crates/egui), `egui` is "an easy-to-use immediate mode GUI that runs on both web and native," newest version **0.36.1**, dual MIT/Apache-2.0, created 2020-05-30, last published 2026-08-07, 22,672,739 total downloads. The GitHub API (`api.github.com/repos/emilk/egui`) reports 30,339 stars, 2,118 forks, 1,137 open issues, and `pushed_at: 2026-09-02` — very actively maintained.

**Architecture.** egui is explicitly immediate-mode (crate description, above). The `eframe::App` trait (https://docs.rs/eframe/latest/eframe/trait.App.html) has moved its core entry point from a deprecated `update(&mut self, ctx: &egui::Context, frame: &mut Frame)` to `ui(&mut self, ui: &mut Ui, frame: &mut Frame)`, called "each time the UI needs repainting, which may be many times per second" — the whole UI is redrawn from application state every frame rather than retained as a widget tree. There is no message/`Model`/`update`/`view` split built into the framework; an app owns one mutable struct and both reads and mutates it directly inside the per-frame closure. For background work, the documented mechanism is `egui::Context::request_repaint()`, callable "from another thread" after a clone of the `Context`, i.e. the standard pattern is spawning a thread/task that pushes results into a channel and calls `request_repaint()` — there is no framework-level equivalent of iced's `Task`/`Subscription`.

**Charts.** `egui_plot` (https://crates.io/api/v1/crates/egui_plot, "Immediate mode plotting for the egui GUI library," v0.37.0, published 2026-08-05, dual MIT/Apache-2.0, 8,216,215 downloads) is the maintained successor to egui's old built-in `Plot` widget. docs.rs (https://docs.rs/egui_plot/latest/egui_plot/) lists its plot item types as `Line`, `Points`, `Arrows`, `BarChart`, `BoxPlot`, `Heatmap`, `FilledArea`, `Polygon`, `PlotImage`, `Text`, `HLine`/`VLine`, and `Span` — **line and bar charts are natively covered; no pie/doughnut, candlestick/OHLC, or diverging-bar item type is documented.** A third-party crate, `egui-charts` (https://crates.io/api/v1/crates/egui-charts, "High-performance financial charting engine for egui — candlesticks, 95 drawing tools, 130+ indicators…", v0.2.0, created 2026-03-10, last published 2026-06-04, MIT/Apache-2.0) exists specifically for candlesticks, but is very small (441 total downloads) and young (~6 months old at research time) — its scale of claimed features (95 drawing tools, 130+ indicators) versus its download count is a notable mismatch worth flagging for anyone evaluating its actual adoption. No dedicated doughnut/pie or diverging-bar crate for egui was found via crates.io search.

**Tables.** `egui_extras` (https://crates.io/api/v1/crates/egui_extras, v0.36.1, published 2026-08-07, part of the main egui repo) provides `TableBuilder` (https://docs.rs/egui_extras/latest/egui_extras/struct.TableBuilder.html): resizable columns (`resizable()`), vertical scrolling (`vscroll()`, on by default), drag-to-scroll, `scroll_to_row()`, `stick_to_bottom()`, and header/body row builders — **no built-in sorting is documented.** A separate, newer crate from the Rerun project, `egui_table` (https://crates.io/api/v1/crates/egui_table, "Table viewer for egui," v0.10.0, created 2024-10-14, published 2026-08-05, MIT/Apache-2.0) exists for large/virtualized tables (used in Rerun's own viewer) but sorting support was not confirmed in the material reviewed.

**Cross-platform and native look.** egui targets native (via `eframe`) and web (WASM) from one codebase (crate description). It does not use OS-native widget toolkits — all widgets are drawn by egui itself and styled via `Context::set_style()` (per egui's own GitHub FAQ/discussion material), so cross-platform consistency is high (the same renderer everywhere) but native OS look-and-feel is not the default; achieving it would mean writing custom-styled or custom widgets rather than getting it for free.

## 2. `iced` (Elm-style retained-mode)

**Identity and maintenance.** Per crates.io (https://crates.io/api/v1/crates/iced), `iced` is "A cross-platform GUI library inspired by Elm," newest version **0.14.0**, MIT, created 2019-05-29, last published 2025-12-07 (crates.io), 2,635,308 downloads. The GitHub API (`api.github.com/repos/iced-rs/iced`) shows `pushed_at: 2026-09-01`, 31,412 stars, 1,655 forks, 490 open issues — so the crates.io publish cadence trails the very active repository by roughly nine months at research time, a smaller version of the split noted for `cursive` in the TUI precedent, though not nearly as stale.

**Architecture — particular attention per the ticket.** iced documents an `Application`/`Program` model built directly on the Elm Architecture: a `State` struct, an `update(&mut State, Message)` function, and a `view(&State) -> Element<Message>` function (docs.rs, https://docs.rs/iced/latest/iced/). Async work is handled via `Task<Message>` (iced's evolution of Elm's `Command`) — `update` can return a `Task` built from `Task::perform()` (runs a future, maps its result to a `Message`), with `.map()`/`.chain()`/`.batch()` composition. A third, optional `subscription(&State) -> Subscription<Message>` function provides "a declarative builder of streams" for passive/streaming event sources (ticks, keyboard, window events) that persist across updates rather than terminating like a `Task`. This is a very close structural match to ADR-0003's own top-level `Action`/`Message` enum plus per-screen `Model`/`update`/`view`: iced's `Task` and `Subscription` are the framework-native equivalent of ADR-0003's `tokio::select!` multiplexing of tick/render/input/background-channel events, just expressed as first-class framework types rather than hand-rolled in the event loop. Composing multiple screens behind one top-level `Message` enum (ADR-0003's actual shape) is a directly documented, idiomatic iced pattern rather than a combination the framework's own docs don't cover (which was the caveat ADR-0003 raised about ratatui).

**Charts.** No chart type is built into `iced` itself. Three extension paths exist: (1) `plotters-iced` (https://crates.io/api/v1/crates/plotters-iced, "Iced backend for Plotters," v0.11.0, MIT, **last published 2024-09-18** — roughly two years stale at research time, 102,953 downloads) lets `plotters` (see §5) render into an iced `Canvas`, which would bring plotters' native `CandleStick` and `Pie`/donut support (see §5) into iced, subject to plotters' own staleness caveat below; a fork `plotters-iced2` was found on crates.io but not independently vetted here. (2) `iced_plot` (https://crates.io/api/v1/crates/iced_plot, "A GPU-accelerated plotting widget for Iced," v0.5.0, published 2026-06-27, MIT) is actively maintained and handles "up to millions of points" with axes/legends/tooltips/crosshairs, but its documented API (`Series::circles`, README) is scatter/line-oriented — no candlestick or pie/doughnut item type is documented. (3) `iced_aksel` (https://crates.io/api/v1/crates/iced_aksel, v0.3.0, published 2026-04-03, MIT) is explicitly a "WIP, batteries not included" charting crate with a canvas-like `PlotData`/`Shape` extension API (its own README's warning: "still pretty early in development. Breaking changes will occur") — usable as a drawing-primitive layer for custom chart types, similar in spirit to ratatui's `Canvas`, but not a source of ready-made chart types itself.

**Tables.** `iced_table` (https://crates.io/api/v1/crates/iced_table, "A table widget for iced," v0.14.0, published 2026-05-19, MIT, 12,149 downloads) is a dedicated, actively-maintained table widget; its docs.rs landing page confirms a `Catalog` styling trait and column-based rendering, but sorting/resizing specifics were not confirmed beyond the README/module-level description reviewed.

**Cross-platform and native look.** iced's own GitHub material states it uses `wgpu` (Vulkan/Metal/DX12) as its default native renderer with `tiny-skia` as a software fallback — like egui, it draws its own widgets rather than delegating to an OS toolkit, so it is visually consistent across Linux/macOS/Windows but not native-looking by default; theming is customizable (`theme::Custom::with_fn`) rather than OS-matching automatically.

## 3. `Tauri` (Rust backend + system web-view frontend)

**Identity and maintenance.** Per crates.io (https://crates.io/api/v1/crates/tauri), newest version **2.11.5**, dual Apache-2.0/MIT, created 2019-11-27, last published 2026-07-01, 28,510,259 downloads. The GitHub API (`api.github.com/repos/tauri-apps/tauri`) shows 110,741 stars, 3,911 forks, 1,462 open issues, `pushed_at: 2026-09-02` — by far the largest community of the surveyed candidates, and very actively maintained.

**Architecture.** Tauri's own architecture docs (https://tauri.app/concept/architecture/) describe a compiled Rust backend (no separate runtime shipped) communicating with an OS-native webview frontend via message-passing "commands" (Rust functions callable from the frontend) and "events" (backend-to-frontend notifications), built on TAO (windowing) and WRY (webview abstraction). Crucially, **Tauri is framework-agnostic on the frontend**: its docs list official support/templates for Leptos, Next.js, Nuxt, Qwik, SvelteKit, Trunk, and Vite, alongside "any number of pieces of an optional JS API." This means charts and tables are not a Tauri-specific question at all — the frontend is ordinary web content, so any JavaScript/TypeScript charting library (Chart.js, ECharts, ApexCharts, etc., not surveyed further here as they are outside the "Rust crate" framing of this ticket) or any JS/WASM grid component natively covers line, doughnut, candlestick, and diverging-bar charts and full-featured sortable tables — this is the one candidate where "does it support chart type X" is trivially yes by construction, not a framework capability gap.

**ADR-0003 compatibility — the double-edged part.** Because application state and rendering live in the frontend (JS, or a Rust-to-WASM framework like Leptos if chosen), Tauri's own Rust side has no natural place for ADR-0003's Model/Message/update/view loop — that pattern would need to live in whichever frontend framework is chosen (e.g. Leptos's own signal-based reactivity, which is not Elm/TEA-shaped), not in the Tauri-facing Rust code, which is reduced to command/event handlers. Reusing ADR-0003 as written (a Rust `tokio::select!`-driven TEA loop) is not directly meaningful on the Tauri side; it would only carry over if the specific frontend framework chosen for Tauri happens to be TEA-shaped, which is a downstream choice Tauri itself does not make.

**Cross-platform and native-look caveats.** Per Tauri's official prerequisites (https://v2.tauri.app/start/prerequisites/) and webview-versions docs, Tauri uses WRY to defer to the **system** webview: WebView2 on Windows (supported Windows 7+, preinstalled on Windows 11, self-updating), WebKitGTK on Linux (v2 requires webkit2gtk 4.1, e.g. Ubuntu 22.04+), and the OS-bundled WKWebView on macOS (10.15+). This means rendering fidelity is not identical across platforms — it depends on each OS's webview engine version, which is not fully within the app's control (particularly older Linux distributions shipping an older WebKitGTK), unlike egui/iced/Slint where the app ships its own renderer.

## 4. `Slint` (declarative, native-looking)

**Identity and maintenance.** Per crates.io (https://crates.io/api/v1/crates/slint), newest version **1.17.1**, created 2022-02-01, last published 2026-07-07, 1,591,624 downloads. The GitHub API (`api.github.com/repos/slint-ui/slint`) shows 23,670 stars, 984 forks, 827 open issues, `pushed_at: 2026-09-02`.

**Licensing — the standout complexity.** crates.io's own version metadata reports the license expression as `GPL-3.0-only OR LicenseRef-Slint-Royalty-free-2.0 OR LicenseRef-Slint-Software-3.0` — a **triple-license** choice unique among the surveyed candidates (all others are permissive MIT/Apache-2.0, or GPL/LGPL for GTK). Per Slint's own pricing page (https://slint.dev/pricing): the GPLv3 option is free but requires the whole application's source to be disclosed on distribution; the "Royalty-free" license permits proprietary desktop/mobile applications without royalties, but explicitly excludes embedded-systems use (embedded needs a paid tier, with royalties from $1.00/device); paid tiers (Startup & Individual, Small Enterprise, Enterprise) drop the GPL disclosure requirement entirely. For a proprietary (closed-source) desktop app specifically, the "Royalty-free" tier is the relevant free option — but this is a materially different (and more commercially involved) licensing posture than every other surveyed framework's permissive-license default.

**Architecture.** Slint UIs are authored in a separate declarative `.slint` markup language (property bindings, not a Rust trait-based widget tree), with Rust used for backing logic and callbacks. This is architecturally the furthest from ADR-0003 of all six main candidates: there is no Model/Message/update/view convention exposed by the framework — application state is exposed to the `.slint` markup via properties/callbacks, and the framework's own reactive property-binding model (not message-passing) drives UI updates. Adopting ADR-0003's hybrid TEA pattern on top of Slint would be an application-level convention layered on top of callback/property wiring, not something the framework provides scaffolding for, similar to egui's situation.

**Charts.** No dedicated chart widget was found in Slint's standard widgets library or via web search (search for "Slint chart widget line bar pie candlestick" returned no Slint-specific charting library hits). Slint does provide a `Path` element (https://docs.slint.dev/latest/docs/slint/reference/elements/path/) supporting SVG-like path commands (`ArcTo`, `CubicTo`, `QuadraticTo`) with fill/stroke — the primitive layer any custom line, doughnut, candlestick, or diverging-bar rendering in Slint would be built on, directly analogous to ratatui's `Canvas` or iced's `Canvas`/`iced_aksel` shape API.

**Tables.** `StandardTableView` (per Slint's reference docs and gallery example, `examples/gallery/ui/pages/table_view_page.slint`) supports per-column `min_width`/`width`/`horizontal_stretch`, and a `sort-ascending(int)`/`sort-descending(int)` callback pair plus a `sort_order` (`SortOrder`: unsorted/ascending/descending) property — i.e. **the widget signals sort intent but the application must actually reorder the backing model**, a middle ground between ratatui's `Table` (no sort at all) and GTK4's `ColumnView` (fully native `Sorter`-driven sort, see §5).

**Cross-platform and native look.** Slint ships its own renderer (not an OS-toolkit wrapper) across Linux/macOS/Windows, with selectable style themes (its docs and examples reference Fluent/Cupertino/Material-styled widget sets aimed at approximating each OS's native look) rather than delegating to the OS toolkit directly — a middle ground between egui/iced's "one custom look everywhere" and gtk-rs's literal native widgets.

## 5. `gtk-rs` / `relm4` (native GTK bindings)

**Identity and maintenance.** `gtk4` bindings (https://crates.io/api/v1/crates/gtk4): newest version **0.11.4**, MIT, published 2026-06-29, 3,709,823 downloads. GitHub (`gtk-rs/gtk4-rs`): 2,337 stars, 215 forks, 75 open issues, `pushed_at: 2026-08-31`. `relm4` (https://crates.io/api/v1/crates/relm4, "An idiomatic GUI library inspired by Elm and based on gtk4-rs"): newest version **0.11.0**, dual Apache-2.0/MIT, published 2026-04-08, 609,607 downloads. GitHub (`Relm4/Relm4`): 1,973 stars, 100 forks, 73 open issues, `pushed_at: 2026-08-24`. Both are smaller communities than egui/iced/Tauri/Slint by star count, but both show recent push activity and recent crates.io publishes. Note: the `gtk4` crate license (MIT, bindings only) covers the Rust wrapper; the underlying native GTK4 library itself is LGPL-2.1+ (well-established, not independently re-verified against a primary source in this pass beyond the bindings' own license field) — a materially different (and less restrictive for proprietary apps) licensing shape than Slint's triple license, since LGPL permits proprietary linking without source disclosure.

**Platform requirements — real setup cost.** Per the official gtk-rs installation book (https://gtk-rs.org/gtk4-rs book, macOS and Windows install pages) and Relm4's own site (https://relm4.org, "All platforms supported by GTK4 are available for Relm4 as well: Linux, Windows, and macOS"): Linux typically has GTK4 available via system package managers; **macOS requires `brew install gtk4 libadwaita meson desktop-file-utils`**; **Windows requires choosing between MSVC or GNU toolchains**, with GTK4 built via `gvsbuild` (MSVC) or installed as pre-built packages — meaningfully more native-toolchain setup than egui/iced/Tauri/Slint, which all ship self-contained renderers requiring no separate system GUI library install (Tauri's webview dependency in §3 is the closest analogue, but is normally already present on-OS).

**Architecture — `relm4` given particular attention alongside `iced`.** `relm4`'s `Component`/`AsyncComponent` traits (docs.rs `relm4::component::AsyncComponent`, and the Relm4 book's async/component pages) define associated types `Model`, `Input` (its `Message` equivalent), `Output`, `Init`, and **`CommandOutput`** — a message variant specifically for async work, populated by `sender.command()` spawning a cancellable background future and routing its result through a dedicated `update_cmd` handler, functionally equivalent to iced's `Task`. The Relm4 book's components documentation describes a documented **parent-child composition pattern**: parent components hold children as `Controller<ChildModel>`, forward child `Output` messages into the parent's own `Input` via `.forward()`, and the book's own worked example has a top-level app component switching over an `AppMode` enum (View/Edit/Export) to decide which child to show — i.e. almost exactly ADR-0003's "top-level `App` owns which screen is active, delegates `update`/`view` to a per-screen `Model`" shape, arrived at independently and demonstrated in relm4's own official documentation rather than needing to be assembled from primitives the way ADR-0003 had to for ratatui. Alongside iced, this makes relm4 one of the two candidates whose native architecture is closest to ADR-0003's own.

**Charts.** Neither `gtk4` nor `relm4` ships chart widgets. The bridge is `plotters-cairo` (https://crates.io/api/v1/crates/plotters-cairo, "Plotters Cairo backend," v0.9.0, MIT, published 2026-05-20, 120,408 downloads — actively maintained) rendering `plotters` output into a GTK `DrawingArea` (GTK4 draws via Cairo), or the more direct `plotters-gtk4` (https://crates.io/api/v1/crates/plotters-gtk4, "Plotters GTK4 Backend," v0.6.0, MIT, **last published 2025-08-25** — over a year stale at research time, 13,415 downloads). Either path inherits `plotters`' own chart-type catalogue (see below) — including native candlestick and doughnut support — subject to `plotters`' own staleness caveat.

**On `plotters` itself (relevant across §2, §5, §6).** Because `plotters` backends recur across iced, gtk-rs/relm4, Dioxus, and Freya, its own status matters generally: per crates.io (https://crates.io/api/v1/crates/plotters), the core `plotters` crate's newest version is **0.3.7**, MIT, 216,539,053 downloads, but **last published 2024-09-08** — roughly two years stale relative to this research date. The GitHub API (`plotters-rs/plotters`) shows `pushed_at: 2026-04-13`, 4,619 stars, 184 open issues — i.e. the same "stale published crate, still-somewhat-active repo" split flagged for `cursive` in the TUI precedent, though less extreme (a 2026-04 push vs. a 2024-09 crates.io release). On chart-type coverage specifically: docs.rs's `plotters::element` module (https://docs.rs/plotters/latest/plotters/element/index.html) confirms both a **`CandleStick`** element ("The candlestick data point element") and a **`Pie`** element ("A Pie Graph") with a documented `donut_hole(hole_radius: f64)` method — "Enables creating a donut chart with a hole of the specified radius" — i.e. `plotters` is the **only surveyed charting layer, across every framework in this document, with native, out-of-the-box doughnut support**; the `plotters::series` module additionally provides `LineSeries`, `AreaSeries`, `PointSeries`, and `Histogram` (bar-family), covering line and (with manual positive/negative layering, as ratatui's ecosystem would also require) diverging-bar needs. This makes `plotters` itself — independent of which GUI framework hosts it — the single most chart-type-complete building block found in this entire survey, at the cost of its own crates.io staleness and needing a framework-specific backend crate (of varying freshness, per framework) to actually render into that framework's canvas.

**Tables.** GTK4's native `ColumnView` (per gtk-rs docs, https://gtk-rs.org/gtk4-rs/git/docs/gtk4/struct.ColumnView.html) supports full native, click-to-sort column headers: a `Sorter` attached via `ColumnViewColumn::set_sorter()`, wrapped in a `SortListModel`, with `sort_by_column()` to set the initial order — the most complete native table/sort story of any candidate surveyed (the older `TreeSortable`/`TreeView` API is explicitly documented as deprecated since GTK 4.10 in favour of `ColumnView`/`SortListModel`).

**Cross-platform and native look.** Because GTK4 is a real native toolkit, apps get genuinely native-rendered widgets on Linux (GTK is the native toolkit there) and reasonable-but-visibly-GTK rendering on macOS/Windows (GTK's own theme engine, not the OS's native widget set) — a different trade-off from Slint/egui/iced's own-renderer approach: GTK4 looks "native" on its home platform and "cross-platform GTK-styled" elsewhere, rather than one consistent custom look everywhere.

## 6. Other candidates: `Dioxus` (desktop target) and `Freya`

**`Dioxus`.** Per crates.io (https://crates.io/api/v1/crates/dioxus): latest **stable** version 0.7.10 (published 2026-07-30 per docs.rs), newest listed version 0.8.0-alpha.1 (published 2026-07-31), dual MIT/Apache-2.0, 2,504,269 downloads. GitHub (`DioxusLabs/dioxus`): 38,942 stars, 1,863 forks, 761 open issues, `pushed_at: 2026-09-01` — very actively maintained, and by star count the largest of the non-Tauri candidates. Architecture is React-style: hooks (`use_signal` for reactive state) and a virtual-DOM-like component model rather than TEA's Model/Message split — its docs.rs summary states it can "render using web-sys, webview, server-side-rendering, liveview, or even" an experimental WGPU-based renderer, so desktop specifically can go through a system webview (architecturally similar to Tauri's webview dependency) or an experimental non-webview renderer. This hooks/signals model is a similar mismatch to egui/Slint versus ADR-0003 — no native Model/Message/update/view scaffolding — and async is handled via Dioxus's own coroutine/`use_future`-style hooks rather than a `tokio::select!`-shaped loop, so adopting ADR-0003 on Dioxus would again be an app-level convention rather than something the framework hands you. Charting options found: `dioxus-charts` (https://crates.io/api/v1/crates/dioxus-charts, "Chart components library for Dioxus," updated 2026-01-06), `trading-charts`/`trading-charts-dioxus` (Rust bindings of the JS "Lightweight Charts" library with a Dioxus adapter, updated 2026-03-22 — notable as a JS-charting-library bridge, similar in spirit to what Tauri gets for free), and `plotters-dioxus` (a `plotters` component for Dioxus, but **last updated 2024-02-26** — over two and a half years stale at research time). No dedicated Dioxus table widget was identified in this pass; webview-mode desktop apps could use plain HTML tables or any JS grid, matching Tauri's situation when Dioxus runs over a webview.

**`Freya`.** Per crates.io (https://crates.io/api/v1/crates/freya): newest version 0.4.3, MIT, published 2026-08-30, but only 39,593 total downloads — much smaller adoption than every other candidate surveyed. GitHub (`marc2332/freya`): 3,123 stars, 136 forks, 66 open issues, `pushed_at: 2026-09-01`. Freya is built on Dioxus's component/hooks model but renders via Skia directly (its own crate description: "Cross-platform and non-web GUI Library powered by Skia") rather than a system webview — this is architecturally notable as the one candidate that gives Dioxus's React-style programming model *without* Tauri/Dioxus-webview's system-webview-version dependency, at the cost of being a much smaller, younger project. It carries an optional `plot` feature that directly re-exports the `plotters` crate and its Skia-compatible backend, so Freya inherits `plotters`' full chart-type catalogue (including native doughnut and candlestick support, §5) more directly than Dioxus's stale `plotters-dioxus` bridge — but still subject to `plotters`' own staleness caveat. No dedicated table/grid widget was found in the Freya docs reviewed; Freya's own component set (Button, Input, ScrollView, per docs.rs) is lower-level than a ready-made data-grid. Cross-platform support targets Linux/macOS/Windows via `winit` (default) plus Vulkan rendering support (per docs.rs). Architecturally it shares Dioxus's hooks-based mismatch with ADR-0003.

**Other names considered and set aside.** No other Rust desktop GUI framework with comparable maintenance activity or a documented charting/table story was found in the course of this research (e.g. no evidence of a currently-competitive alternative beyond the six covered above and their close derivatives).
