# Research: How to use Archify in Personal Ledger

**Question.** Archify was added in [issue #663](https://github.com/IanTeda/Personal-Ledger/issues/663) (commit `15907b2`) as a project skill for diagrams in reviews, ADRs and Wayfinder maps. What is the best way to use it in this repo's agent-driven workflow: which diagram types fit which artefacts, what the end-to-end authoring and rendering workflow should be, how to keep diagrams in step with a fast-changing concept-stage codebase, what friction the current setup has, and which anti-patterns to avoid?

Research was done by reading the vendored skill at `.claude/skills/archify/` (`SKILL.md`, `references/`, `schemas/`, `bin/*.mjs`, `delta/architecture-delta.mjs`, `renderers/shared/repository-evidence.mjs`), by running its CLI locally (`doctor`, `render`, `validate`, `compare`) against the committed diagram with output to a scratch folder, by reading Archify's upstream repository and release manifest through `gh api`, and by reading this repo's own conventions (`docs/agents/issue-tracker.md`, `CLAUDE.md`, `.gitignore`, `mise.toml`, `book.toml`, `.github/workflows/build-publish-documentation.yaml`) and the one existing diagram, `docs/diagrams/desktop-architecture.json`. Sections 1–3 are verified facts; sections 4–8 are recommendations built on them.

## 1. What Archify v3.1.0 actually is (verified)

### 1.1 The vendored copy

- **Identity.** `package.json` and `skill-release.json` both say version `3.1.0`, and `skill-release.json` names the source as `https://github.com/tt-a1i/archify` with an update manifest at `https://tt-a1i.github.io/archify/skill-updates/archify/stable.json` (`.claude/skills/archify/skill-release.json:5-9`).
- **Fidelity to the tag.** Comparing every blob in the upstream tree `v3.1.0:archify` (157 files, via `gh api repos/tt-a1i/archify/git/trees/v3.1.0:archify?recursive=1`) with `git ls-tree HEAD .claude/skills/archify` (142 files) shows identical blob SHAs for every shared path. The only difference is the 15 `examples/*-rendered.html` / `examples/*.html` files, which commit `9632d1e` ("remove the Archify skill's rendered example diagrams") deleted. The copy is otherwise byte-for-byte the tag.
- **Runtime.** The CLI is plain Node ESM with only built-in imports (`bin/archify.mjs:3-8`); `package.json` lists only `devDependencies` (`ajv`, `simple-icons`) used by Archify's own generators (`package.json:30-33`), and `engines.node` is `>=18` (`package.json:9-11`). The delivery contract calls it "zero-dependency" and requires the preview runtime to work without `node_modules` (`references/delivery-contract.md:426`, `:577`). This repo pins `node = "26.7.0"` (`mise.toml:11`), and `node .claude/skills/archify/bin/archify.mjs doctor` reports every renderer, schema and runtime as `[ok]` on that Node.
- **Browser dependency.** `browser-check` and `visual-check` drive Chrome/Chromium over the DevTools pipe, found on `PATH` as `chrome`, `google-chrome`, `google-chrome-stable`, `chromium` or `chromium-browser`, or through `ARCHIFY_CHROME` (`bin/visual-check.mjs:1315-1336`). Without one the browser stage exits 2 with `status: "skipped"` (`references/delivery-contract.md:458`), and `finalize` "stops at the first failed or skipped stage" (`references/delivery-contract.md:265`), so a full `finalize` needs a local Chrome.

### 1.2 Commands

`archify --help` lists `render`, `compare`, `deliver`, `finalize`, `preview`, `validate`, `migrate`, `inspect`, `check`, `browser-check`, `visual-check`, `guide`, `brands`, `examples`, `doctor` and `demo`. What each relevant one does:

- **`finalize <type> <in.json> <out.html> [--repo-root] [--quality] [--out-dir] [--json]`** is the normal path. It runs showcase validation, `deliver`, strict `check --require-provenance` and `browser-check --require-provenance`, stops at the first non-passing gate, prints a compact JSON summary and writes `<stem>.finalize.json`, `<stem>.finalize-summary.json` and `<stem>.browser-check.json` (`SKILL.md:31-39`; `references/delivery-contract.md:262-276`). A pass means four automated gates passed, not that anyone looked at it: it reports `visualReview: "not-requested"` (`SKILL.md:83`).
- **`deliver`** renders a private snapshot of the exact input bytes, runs the artifact checker and only then replaces the target, recording SHA-256 and byte counts for both specification and artifact in `<stem>.delivery.json` (`references/delivery-contract.md:26-30`, `:255`).
- **`render`** is the lower-level renderer with no `--json` receipt (`references/delivery-contract.md:17-22`).
- **`validate --json [--layout-json]`** is for focused diagnosis only; `finalize` already includes it (`SKILL.md:39`; `references/delivery-contract.md:13`).
- **`visual-check --summary --require-provenance [--out-dir]`** is optional. It adds four viewport screenshots and a contact sheet; capture is not perceptual approval (`references/delivery-contract.md:480-495`). Archify separates four claims (deterministic checks, browser evidence, captures, perceptual review) and says passing one never implies another (`references/delivery-contract.md:389-396`).
- **`preview`** is a loopback live-reload loop for an active desktop session only: "Never start it by default. Do not use it for CI, unattended agents…" (`references/delivery-contract.md:567-579`).
- **`compare architecture <base.json> <head.json> [out.html]`** is the only delta feature (section 1.5).
- **`migrate workflow … --to-schema 2`** upgrades Workflow v1 JSON (`references/delivery-contract.md:234-238`).

### 1.3 Diagram types and quality levels

- **Ten types:** `architecture`, `workflow`, `sequence`, `dataflow`, `lifecycle`, `erd`, `tree`, `class`, `timeline`, `waterfall`, each with a schema in `schemas/` and an example in `examples/` (`SKILL.md:50-63`). `guide "<scenario>" --json` helps when the type is ambiguous (`SKILL.md:65`). Archify is "Not for numeric charts or dashboards" (`SKILL.md:3`).
- **Two quality profiles:** `standard` and `showcase` (`schemas/common.schema.json:28`). Authors set `meta.quality_profile: "showcase"` unless a dense `standard` is wanted, and pass the matching `--quality` (`SKILL.md:30`, `:37`). Showcase adds route-rhythm, detour, collinear-overlap and boundary-encloses-non-member failures that standard does not (`references/authoring-contract.md:159-161`, `:286`, `:322`). A showcase pass needs all nine artifact checks with zero composition errors and zero warnings (`references/delivery-contract.md:5`).
- **Type-specific limits that matter here:** an ERD over roughly 8 tables or 50 fields is a "dense full-schema map" and should start at `standard`, listing every physical column with its SQL type and key roles (`SKILL.md:30`; `references/authoring-contract.md:340-350`). Sequence has no self-message loops; internal actions go in notes (`references/authoring-defaults.md:43`). Lifecycle uses schema v3 with a `mainPath`, and concurrent regions have no lifecycle form, so draw one lifecycle per region (`references/authoring-defaults.md:51`; `references/authoring-contract.md:531-532`). Timeline needs `meta.evidence` (`observed` or `illustrative`) and offset-qualified timestamps; Waterfall needs `measured` or `illustrative`, and "Never infer a duration from code structure" (`references/authoring-contract.md:462-490`).

### 1.4 Repository evidence

- **What is cited.** Only primary elements carry `sources`, at most three ranges each: Architecture components, Workflow/Dataflow/Tree nodes, Sequence participants, Lifecycle states, ERD entities, Class types, Timeline events and Waterfall spans; relationships carry none, so the call or write site is cited on the element that owns it (`references/repository-authoring.md:76-90`; `schemas/common.schema.json:148-160`).
- **How it is verified.** `meta.repository` pins a credential-free origin URL and a full 40-character `revision` (`references/repository-authoring.md:10-25`). With `--repo-root`, Archify checks that the root is the Git top level, that `origin` matches the declared URL, that the revision exists, and that each cited path is a blob at that revision with the cited lines in range, reading objects with `git cat-file`/`git show` and ignoring replacement refs (`renderers/shared/repository-evidence.mjs:215-247`, `:300-350`). It "reads blobs at that commit, independently of working-tree edits" and makes no remote requests (`references/authoring-contract.md:550-556`). Without `--repo-root`, a diagram with sources fails with `repository-evidence/root-required` (observed running `validate` without it).
- **What it does not verify.** It proves the cited lines existed at the pinned commit. It does not compare that commit with `HEAD`, and nothing in `bin/archify.mjs` or `repository-evidence.mjs` detects drift since the pin. A diagram pinned at an old commit keeps passing forever.
- **Links.** For GitHub HTTPS origins with `link_mode: "web"`, source references become revision-pinned `github.com/<owner>/<repo>/blob/<sha>/<path>#L…` links (`references/authoring-contract.md:559-561`). They resolve only once that commit is pushed.

### 1.5 Delta and update

- **`compare` is Architecture-only.** It needs `schema_version: 1` and `diagram_type: "architecture"` on both sides (`delta/architecture-delta.mjs:109-116`), authored `id`s on every component and connection (`:118-145`, `:265-266`), and at least one shared component id, or it fails with `delta/no-shared-component-id` (`:262-268`). Boundaries match on `kind + label` (`:336-340`).
- **What it reports.** Components are `added`, `removed`, `changed` (type/label/sublabel/tag/icon), `evidence-changed` (sources only) or `moved` (geometry); connections are `added`, `removed`, `changed` or `rerouted` (`delta/architecture-delta.mjs:183-200`). `proofLevel` is `revision-pinned` only when both sides carry verified 40-character revisions, else `authored` (`:278-283`). Its stated limits: "Authored Architecture IR only; no runtime impact, causality, risk, or mergeability is inferred" (`:340-343`). It writes an HTML base/delta/head view plus a `<stem>.receipt.json`. Run locally against a copy of `desktop-architecture.json` with one label edited, it reported `proofLevel: "revision-pinned"` and exactly one `changed` component.
- **No other update path.** There is no command that refreshes an existing diagram from code, re-pins a revision or flags stale sources. "Update" in Archify means editing the JSON and running `finalize` again; after an edit, give the rerun a fresh `--out-dir` because "Browser evidence belongs to exact artifact bytes" (`references/delivery-contract.md:544-553`; `SKILL.md:41`).
- **Rendering is deterministic.** Rendering `docs/diagrams/desktop-architecture.json` twice with `render --quality showcase --repo-root .` gave byte-identical HTML both times, matching the committed file's SHA-256 (`5389420…52da`, also recorded in `desktop-architecture.finalize-summary.json`). The HTML carries `<meta name="generator" content="archify 3.1.0">`.

### 1.6 Update awareness

`finalize` and `deliver` run a bounded update check (1 s deadline, `bin/delivery-update.mjs:6`) that `ARCHIFY_UPDATE_CHECK_DISABLED=1` turns off (`:51`). When it finds a newer release, the agent shows one line and must "never install or update on your own initiative" (`SKILL.md:43-45`; `references/update-awareness.md`). The committed diagram's receipt shows `status: "unavailable"`, `reason: "cache-unavailable"`, so the check never ran from the sandbox.

## 3. Current state in this repository (verified)

- **Convention.** `docs/agents/issue-tracker.md:18-24` says: a diagram is optional, expected for a flow across three or more components or a migration's halfway state; inside an issue body it is Mermaid; richer diagrams (reviews, ADRs, a map's destination) are Archify, committed flat as `docs/diagrams/<slug>.json` plus `<slug>.html`, with the kind only in the JSON and ADR/review-owned slugs prefixed (`adr-0030-…`); render from the repo root with `finalize … --repo-root . --quality showcase --json`; receipts are gitignored; upgrading means copying a newer tag over `.claude/skills/archify/`; issues link to the repo path. `CLAUDE.md:79` points `/archify` at that section.
- **Receipts.** `.gitignore:182-187` ignores `docs/diagrams/*.finalize.json`, `*.finalize-summary.json`, `*.browser-check.json`, `*.delivery.json` and `*.delivery-pending.json`. The directory lock `.archify-delivery-lock.json`, the `.archify-remove-*` recovery folders and the skill's default `.archify/` work folders (`SKILL.md:14`) are all covered by the blanket `.*` rule (`.gitignore:11`). Receipts hold absolute local paths (`"path": "/home/ian/Projects/…"` in `desktop-architecture.finalize-summary.json`), which is a good reason to keep ignoring them.
- **mdBook.** `book.toml:5` sets `src = "docs"`. A scratch `mdbook build -d <scratch>` copied `docs/diagrams/desktop-architecture.html` byte-identical into `diagrams/`, and also copied the four local receipt JSONs, because mdBook copies non-Markdown files from `src`. CI builds from a clean checkout, so receipts never reach Pages there. Pages deploys only on a GitHub Release or a manual dispatch (`.github/workflows/build-publish-documentation.yaml:14-17`). `docs/SUMMARY.md` links no diagram.
- **The one diagram.** `docs/diagrams/desktop-architecture.json` is a showcase Architecture of `bin-desktop` with 12 components, 13 connections, 2 boundaries and 3 cards, every component cited at `ad9b4b7` with `link_mode: "web"`. Every component and connection has an `id`, so `compare` works on it. Its `finalize` passed all four gates with zero diagnostics, and #663's closing comment says "nobody has looked at it visually yet".
- **It is already drifting.** `HEAD` (`51f2641`) is 14 commits past the pin. Of the 17 distinct files it cites, 8 changed between `ad9b4b7` and `HEAD` (`lib.rs`, `app.rs`, `persistence.rs`, `view/active.rs`, `ledger_store.rs`, `lib-ledger/src/lib.rs`, `lib-ledger/src/change.rs` among them), and the working tree on `concept` stages the deletion of `crates/bins/bin-desktop/src/payees/store.rs`, which the "Domain stores" component cites. The diagram still validates because evidence is checked at the pin.
- **Nothing links to it.** No Markdown file in the repo references `desktop-architecture` or a `docs/diagrams/` file other than `issue-tracker.md` itself, and `gh search issues "docs/diagrams"` finds only #663 and #523.
- **Hand-built predecessors.** The architecture reviews `docs/development/desktop-structure-2026-10-08.html` and `-10-12.html` are hand-coded HTML diagrams; #663 lists redrawing them as out of scope.
- **Size.** The rendered HTML is 838,699 bytes (about 210 KB gzipped), almost all of it the inlined viewer template (`assets/template.html` is 784,815 bytes). Each re-render that changes the HTML adds a new blob of that size to Git history.

## 4. Which diagram type fits which artefact

| Artefact in this repo | Archify type | Evidence | Notes |
| --- | --- | --- | --- |
| Desktop Chrome / View / store Entity structure, Sync Server listener (`UtilitiesService`, `SyncService` behind `AuthInterceptor`, `auth` routes) | `architecture` | Repo-backed, `link_mode: "web"` | Keep one box per module or crate, as #663 asked. Give every component and connection a stable `id` so `compare` can diff later versions. |
| ADR "decision" diagrams (e.g. ADR-0038 Ledger aggregate, ADR-0039 store-wide repository) | `architecture`, or `class` when the decision is a type contract | Repo-backed if the code exists, plain-language otherwise | Prefix the slug `adr-00NN-`. For an ADR proposing code that doesn't exist yet, omit `meta.repository` rather than citing the old code as if it were the new design. |
| Code review of a parent ticket | `compare architecture` between the base and head JSON | Both sides revision-pinned | Gives an added/changed/removed view with `proofLevel: "revision-pinned"`. Only possible when the subject has an Architecture diagram with stable ids. |
| Wayfinder map destination | `architecture` (target structure) or `workflow` (target process) | Usually plain-language: the destination isn't built | Mark it as the target in the title (Archify asks for narrower scopes to be named in the title, `references/authoring-defaults.md:7`). |
| Migration halfway state ("Seams to decide") | Two `architecture` diagrams, current and halfway, with shared ids, plus `compare` | Current side repo-backed, halfway side authored | `compare` makes the halfway delta explicit. Inline Mermaid in the ticket is still the primary view. |
| Sync protocol flows (`Push`/`Pull`, `/authorize` → `/token`, PKCE) | `sequence` | Repo-backed: cite `lib-rpc/src/sync/push.rs`, `pull.rs`, `bin-sync-server/src/auth/interceptor.rs` on the participants | Put internal steps in notes, as there are no self-messages. |
| Change Set flow between Clients and Server | `dataflow` | Repo-backed | Every flow needs a label; use `security` variant only where the source shows auth or PII handling (`references/authoring-defaults.md:49`). |
| Ledger SQLite schema (`crates/libs/lib-database/migrations/client/`, 8 tables; `sync-server/`, 2 tables) | `erd` | Repo-backed: cite each `create_<table>_table.sql` on its entity | Eight tables sits at Archify's dense threshold, so start at `--quality standard` and group tables into domain `tag`s laid out in grid rectangles (`SKILL.md:30`). The `SQL_TYPE｜中文备注` comment convention in `references/authoring-contract.md:346-347` is Archify's Chinese-comment default; put the SQL type alone, since these migrations carry no column comments in that form. |
| Domain model types (`lib-core` `RowID`, `Money`; a domain crate's model) | `class` | Repo-backed | Three columns, four at most (`references/authoring-defaults.md:53`). |
| Navigation modes and pending-chord states (`docs/navigation-design.md`), Toast lifecycle, ticket `state:` flow | `lifecycle` | Repo-backed for code states, authored for process states | One lifecycle per concurrent region; `mainPath` is the happy path. |
| Crate/workspace layout, `bin-desktop` module tree | `tree` with `layout.direction: "right"` | Repo-backed: each folder node cites its `mod.rs`/`lib.rs` | `references/authoring-defaults.md:55`. |
| Ticket or map history, release history | `timeline` with `meta.evidence: "observed"` | Events cite a file at the pinned revision; times from commits or tags | `references/repository-authoring.md:84-88`. |
| Startup or `LedgerStore::apply` timing | `waterfall` | `measured` only from a real `lib-tracing` trace; else `illustrative` | Don't time the app just to draw it (`references/repository-authoring.md:88-90`). |
| Inline diagram in an issue body | Mermaid, not Archify | — | GitHub renders Mermaid in issues; it doesn't render the HTML (`docs/agents/issue-tracker.md:21`, `:24`). |

## 5. Recommended end-to-end workflow

1. **Decide whether a diagram is needed** by the existing rule: three or more components, or a migration halfway state (`docs/agents/issue-tracker.md:20`). Write the Mermaid in the issue body first; it is what readers on GitHub see.
2. **Pick the type** from section 4 (or `archify guide "<scenario>" --json`) and the slug: subject-named, `adr-00NN-` or review-prefixed when owned.
3. **Author the JSON from the right input.** From Mermaid, read it for topology and meaning and write fresh Archify JSON rather than transcribing styling (`SKILL.md:69-77`). From code, follow `references/repository-authoring.md`: freeze `git rev-parse HEAD` and the credential-free origin, orient with `graphify query`, then read the connected slice with line numbers and cite only what each range shows (`references/repository-authoring.md:10-74`). Pin `meta.repository.revision` to a **committed and pushed** commit, because evidence is read from committed blobs and the web links point at GitHub. A dirty tree is not evidence; note the dirty paths in the reply instead (`references/repository-authoring.md:21-25`).
4. **Author into a scratch folder, then publish to `docs/diagrams/`.** Work in the skill's default `.archify/<type>-<slug>-<timestamp>/` folder (`SKILL.md:14`), which `.gitignore:11` already ignores, so repair reruns and `--out-dir review-<n>` evidence never land in `docs/`. Once it passes, copy the JSON to `docs/diagrams/<slug>.json`, set `meta.output` to `docs/diagrams/<slug>.html`, and run the canonical command from the repo root: `node .claude/skills/archify/bin/archify.mjs finalize <type> docs/diagrams/<slug>.json docs/diagrams/<slug>.html --repo-root . --quality showcase --json` (`docs/agents/issue-tracker.md:23`). Use `--quality standard` for a first dense ERD.
5. **Repair from receipts, not guesses.** A non-zero exit is never success; read the compact summary, fix the named neighbourhood and rerun the whole `finalize` (`SKILL.md:41`). For a repaired candidate whose HTML already has browser evidence, pass `--out-dir .archify/<slug>/review-<n>` rather than a folder under `docs/diagrams/`, which the receipt globs in `.gitignore:183-187` don't cover.
6. **Look at it once.** Run `visual-check --summary --require-provenance --out-dir .archify/<slug>/visual` and inspect the contact sheet, or open the HTML, before using it in an ADR or a review. Report it as "automated checks passed; not visually reviewed" until someone has (`SKILL.md:123`).
7. **Commit the JSON and HTML together** in their own commit after the code they describe (`docs: add the <subject> diagram`), never the receipts. The JSON is the source; the HTML is a deterministic build of it.
8. **Link it.** In the issue, keep the Mermaid and add the repo path `docs/diagrams/<slug>.html`. In an ADR or a `docs/*.md` page, link it relatively (`../diagrams/<slug>.html`) so `mise run docs-serve` and the Pages book both open it.

## 6. Keeping diagrams in sync

Archify has no drift detection (section 1.4) and only Architecture has a delta (section 1.5), so staleness has to be managed by the repo.

### 6.1 When to redraw

- **Redraw on a seam, not on every commit.** A diagram is a snapshot at its pinned revision. Redraw when a parent ticket or Wayfinder map closes, when an ADR is accepted, or when a refactor moves a cited module (for example the payees move from `src/payees/` to `src/settings/payees/` now in the working tree). This matches the repo's "full suites and review at parent-ticket close only" rhythm in `CLAUDE.md`.
- **Re-pin when only lines moved.** If the structure is unchanged, update `meta.repository.revision` and the cited line ranges, rerun `finalize`, and let `compare` confirm that only `evidence-changed` entries appear.
- **Redraw as a new kind under the same slug** when the question changes; the flat folder exists so links survive that (`docs/agents/issue-tracker.md:22`).
- **Use `compare` for reviews of Architecture changes**: `git show <base>:docs/diagrams/<slug>.json > base.json`, then `compare architecture base.json docs/diagrams/<slug>.json .archify/<slug>/delta.html --repo-root . --json`. Keep the delta HTML out of the repo unless the review page needs it.

### 6.2 A staleness check that uses only real behaviour

A `mise` task can report drift without inventing Archify features, because the JSON already lists every cited path and the pinned revision:

- **Cited-file drift:** for each `docs/diagrams/*.json`, read `meta.repository.revision` and every `sources[].path`, then run `git diff --quiet <revision> HEAD -- <paths>` and `git cat-file -e HEAD:<path>`. List the diagrams whose cited files changed or vanished, with the commit count since the pin (`git rev-list --count <revision>..HEAD`). This is advisory: a changed file doesn't mean the diagram is wrong.
- **JSON/HTML pairing:** because rendering is deterministic, `render <type> <json> <scratch.html> --quality <profile> --repo-root .` followed by a hash compare with the committed HTML detects an HTML that was hand-edited or not re-rendered after a JSON edit. This needs Node and Git but no Chrome. Read `diagram_type` from the JSON for `<type>` (the folder deliberately doesn't encode it).
- **Where to run it:** as a `mise run diagrams-check` task run by hand at parent-ticket close and in `/code-review`, not in the pre-push hook or CI. Drift is expected in a concept-stage codebase, and a failing gate would push agents to re-pin without re-reading the code, which is worse than a visibly stale diagram.

## 7. Gaps, friction and low-cost improvements

1. **The existing diagram is unlinked and stale.** Link `desktop-architecture.html` from the place that needs it (the Desktop developer docs or the next structure review), and redraw it after the payees and settings refactor in the working tree lands. As a first use of the workflow above, it is also the natural `compare` base.
2. **Upgrade path.** `issue-tracker.md:23` says to copy a newer tag over `.claude/skills/archify/`, which would bring back the rendered example HTML that `9632d1e` removed. Record the upgrade recipe in one place: copy `archify/` from the tag, delete `examples/*-rendered.html` and the other rendered examples, compare blob SHAs against the upstream tree (as in section 1.1), run `doctor`, then re-render every `docs/diagrams/*.json` and commit the changed HTML in the same commit, so the `generator` meta in every HTML matches the vendored version. No upgrade is due today (section 2).
3. **Update notices can't reach the agent from the sandbox.** The receipt reports `cache-unavailable`, and the manifest host is blocked by the sandbox proxy. Since upgrades are deliberate copies, set `ARCHIFY_UPDATE_CHECK_DISABLED=1` in the render command or task, and check `gh release list --repo tt-a1i/archify` when upgrading instead.
4. **Chrome isn't pinned.** `finalize` needs Chrome/Chromium, which `mise.toml` doesn't provide. Document `ARCHIFY_CHROME` in the Diagrams section for machines without a `PATH` Chrome. The staleness check in 6.2 deliberately avoids needing it.
5. **Review evidence can leak into `docs/`.** The `.gitignore` globs only cover receipts directly in `docs/diagrams/`. Either always use `.archify/` for `--out-dir`, as section 5 recommends, or add `docs/diagrams/*/` to `.gitignore`.
6. **Local docs builds publish receipts.** `mise run docs-serve` copies the local receipts, with absolute home paths, into the served book. This is harmless locally and CI is unaffected, but `mdbook build` doesn't exclude them. Accept it, or delete receipts after a passing `finalize`; they aren't needed once the HTML is committed.
7. **GitHub doesn't render the HTML.** The Mermaid-plus-link split already covers this. The link is only one click for someone with the repo cloned or the book served; Pages updates only on release. Exported PNG/SVG from the viewer menu (`references/viewer-runtime.md`, Canonical exports) could be attached to an issue when a static picture is enough, but don't commit exports beside the source: they would drift with no check.
8. **History weight.** Each re-render adds about 840 KB (210 KB compressed) to history. At concept-stage redraw frequency that is acceptable, but it is another reason to redraw on seams rather than on every commit.
9. **ADRs don't say how to own a diagram.** The `adr-00NN-` prefix rule exists, but the ADR template and the domain docs (`docs/agents/domain.md`) don't mention diagrams. A one-line pointer there would make agents writing ADRs find the convention.

## 8. Anti-patterns

- **Citing the working tree.** Evidence is verified at the pinned commit, so citing lines you see in an uncommitted file either fails or, worse, passes against different bytes at `HEAD`. Commit first, then pin.
- **Re-pinning without re-reading.** Bumping `revision` until `finalize` passes turns a stale diagram into a wrong one with fresh-looking provenance. When a cited file changed, re-read the range.
- **Treating a passing receipt as visual review.** `finalize` proves four automated gates; it says `visualReview: "not-requested"`. Don't call a diagram reviewed in an ADR or a PR until someone has looked at it.
- **Editing the HTML.** The HTML is a deterministic build of the JSON, like `lib-rpc/src/generated/*.rs`. Edit the JSON and re-render.
- **Committing receipts, `.archify/` work folders, `review-<n>` folders or delta HTML.** They are local build evidence with absolute paths.
- **Encoding the kind in the slug or folder** (`docs/diagrams/sequence/…`). The flat folder exists so a redraw as another kind keeps its links.
- **Archify in issue bodies instead of Mermaid.** GitHub shows Mermaid; the HTML is the deep view.
- **Mechanically converting Mermaid.** Archify asks for fresh JSON from the Mermaid's meaning, not its styling (`SKILL.md:71`).
- **Inventing measurements.** A Waterfall or Timeline marked `measured`/`observed` must come from a real trace, log or Git history; otherwise mark it `illustrative`.
- **Over-detailed overviews.** Archify warns that "No node, relationship, source, view, card, or boundary count is a target" (`SKILL.md:30`). One box per module or crate, a narrower diagram for a mechanism.
- **Architecture without stable ids.** Without `id` on components and connections, the one delta feature (`compare`) can't run later.
- **Starting `preview` in an agent session.** It is a desktop live-reload loop the skill forbids for unattended agents.
- **Auto-upgrading the skill.** The update notice is information, not permission (`references/update-awareness.md:12`). Upgrades are a deliberate copy and re-render, under their own ticket.

## 9. Unverified

- **Visual quality of `desktop-architecture.html`.** No `visual-check` or human review was run for this note.
- **`finalize` end-to-end in this session.** `render`, `validate` and `compare` were run against scratch output; `finalize` and `browser-check` were not re-run, so Chrome availability on this machine was not checked. The committed receipts show they passed on 15 October 2026.
- **How GitHub presents an `.html` file in the web UI.** The claim that GitHub doesn't render committed HTML comes from this repo's own convention (`docs/agents/issue-tracker.md:21`, `:24`), not from GitHub documentation checked for this note.
- **mdBook's non-Markdown copy rule** was observed from a scratch build with mdBook 0.5.4, not read from mdBook's documentation.
- **The live update manifest.** The GitHub Pages URL was blocked by the sandbox; the manifest was read from the upstream repository's `docs/skill-updates/archify/stable.json` instead, which should be the source Pages serves.
- **The staleness task in section 6.2** is a design, not a tested script.
