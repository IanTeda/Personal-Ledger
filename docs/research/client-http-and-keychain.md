# Research: HTTP requests and the OS keychain in the Clients

**Snapshot date:** 2026-11-23.

**Question** ([#1369](https://github.com/IanTeda/Personal-Ledger/issues/1369), for the map [#1367](https://github.com/IanTeda/Personal-Ledger/issues/1367)). How can the Clients make HTTP requests and reach the OS keychain? Which HTTP client fits both the Desktop (gpui's executor) and the TUI (its loop) without a second runtime fighting the first, with which TLS backend, under what `deny.toml` allows? How does the `keyring` crate behave on Linux Secret Service, the macOS Keychain and the Windows Credential Manager: blocking or async, what comes back on a machine with no keychain, can that be detected up front, and how are entries named? What does either add to the dependency policy?

**Method.** Read from primary sources only: the crate sources as published on crates.io (downloaded with the crates.io API, versions named below), their docs.rs pages, gpui 0.2.2's own source from the cargo registry, Zed's `reqwest_client` source on GitHub, the workspace's `Cargo.lock`, `deny.toml` and bin manifests on `concept` at `ed20ab1`, and the RustSec advisory database the repo's `cargo deny` already fetched (`target/advisory-dbs`). Nothing here was run on macOS or Windows; claims marked **(unverified)** come from general platform knowledge rather than a source read for this note.

## Summary

- **HTTP:** use `reqwest` (async, Tokio) behind a port, with rustls on the *ring* provider. Both Clients already run a Tokio runtime from `#[tokio::main]`, so neither needs a second one: the TUI awaits `reqwest` in its own loop, and the Desktop spawns each request on the Tokio handle and awaits the `JoinHandle` from a gpui task, which is exactly what Zed does. A blocking `ureq` on a thread is the credible fallback and the smaller dependency, but adds a crate the tree does not have; `reqwest`'s whole stack (hyper, hyper-rustls, rustls with ring, tokio) is already in `Cargo.lock`.
- **TLS:** rustls with *ring* and the Mozilla roots (`webpki-roots`) is what the lock already holds (rustls 0.23.46, ring 0.17.14, webpki-roots 1.0.10), all past every advisory in the local RustSec copy. `reqwest` 0.13's default would switch the provider to *aws-lc-rs* and add `rustls-platform-verifier`; that passes the licence list too, but adds a C build and new crates, so it is a choice, not a free upgrade.
- **Keychain:** `keyring` is now 4.x, a thin wrapper over `keyring-core` 1.x plus one crate per store. Its default `v1` feature picks Keychain (macOS), Credential Manager (Windows) and Secret Service over zbus (Linux and BSD) automatically. The API is **blocking**. With no Secret Service, store set-up fails once and `Entry::new` returns `Error::NoDefaultStore`; `keyring::Entry::store_status()` answers that **up front**, before any key is read. Entries are named by a `(service, user)` pair.
- **gpui's own credentials and HTTP APIs don't fit:** `App::write_credentials` and friends are Desktop-only, hard-code Zed's names (`zed-github-account`, `zed:url=…`), and key by URL; `App::http_client` is a `NullHttpClient` until the app supplies one.
- **Policy:** every crate added is `MIT OR Apache-2.0` (aws-lc's mix is also all on the allow list); none has an open RustSec advisory; everything comes from crates.io. The only policy change worth making is a `deny.toml` ban keeping `reqwest` and `keyring` out of the I/O-free libs.

## 1. What the workspace already has

- **Runtimes.** Both bins start on `#[tokio::main]` with the workspace's `tokio = { version = "1.48.0", features = ["full"] }` (`Cargo.lock`: tokio 1.54.1). The TUI's loop is a `tokio::select!` over an `mpsc` channel (`crates/bins/bin-tui/src/event.rs`, `shell.rs`, ADR-0003). The Desktop's `main` is `#[tokio::main] async fn main` that then calls `bin_desktop::run`, so gpui's `Application::run` blocks the main thread *inside* a live multi-thread Tokio runtime (`crates/bins/bin-desktop/src/main.rs`); its `log_feed.rs` already uses `tokio::sync::Notify`. `lib-database`'s `writer.rs` sets the other precedent: a dedicated thread owning a `new_current_thread` Tokio runtime and driving `sqlx` with `block_on` (ADR-0046).
- **HTTP in the lock.** `reqwest` 0.12.28 is a dev-dependency of `bin-sync-server` only, as `default-features = false, features = ["json", "rustls-tls"]`. gpui 0.2.2 pulls `gpui_http_client` 0.2.2, which pulls `zed-reqwest` 0.12.15-zed (Zed's fork), so hyper 1.11.1, hyper-util 0.1.20, hyper-rustls 0.27.9, tokio-rustls 0.26.5, rustls 0.23.46 and webpki-roots 1.0.10 are already compiled into the shipped Desktop. The lock's rustls depends on `ring` (0.17.14), not `aws-lc-rs`, which is absent from the lock. `ureq` is absent.
- **Keychain plumbing in the lock.** gpui depends on `oo7` 0.5.0 (a Secret Service client) on Linux and FreeBSD, and on zbus 5.19.0 through `oo7` and `ashpd`; `security-framework` 3.7.0 and `windows-sys` 0.61.2 are in the lock too. `keyring` and `secret-service` are absent.
- **Policy** (`deny.toml`): licences limited to permissive and MPL-2.0 (MIT, Apache-2.0, ISC, BSD, Zlib, Unicode-3.0, …); `sources` allow crates.io only, no git; `bans.multiple-versions = "warn"`; the `bans.deny` list keeps UI toolkits and `lib_database` to their bins; advisories `yanked = "deny"`, `unmaintained = "workspace"`.

## 2. HTTP client options

### 2.1 What gpui offers

- `gpui::App::http_client()` returns an `Arc<dyn HttpClient>`, and `set_http_client` / `Application::with_http_client` replace it (gpui 0.2.2 `src/app.rs` lines 139–167, 1166–1172). The default is `NullHttpClient`, whose `send` returns `anyhow::bail!("No HttpClient available")` (`src/app.rs` 2345–2357). `gpui_http_client`'s `HttpClient` trait (`src/http_client.rs` 60) is only the seam; it ships no transport.
- Zed's real transport is its own `reqwest_client` crate (not in the lock, not published as a gpui companion). It keeps a `static RUNTIME: OnceLock<tokio::runtime::Runtime>` built with `.worker_threads(1)`, takes `tokio::runtime::Handle::try_current()` and falls back to that runtime, and in `send` does `handle.spawn(async { request.send().await })`, aborts the task on drop, and awaits the `JoinHandle`, "which works from any executor" ([zed `crates/reqwest_client/src/reqwest_client.rs`](https://github.com/zed-industries/zed/blob/main/crates/reqwest_client/src/reqwest_client.rs)).
- Using gpui's trait would tie fetching to `bin-desktop` (`deny.toml` lets only it reach gpui), so the TUI could not share it. Not a fit for a cross-Client port.

### 2.2 `reqwest` (async, Tokio)

- `reqwest::Client` "is asynchronous (requiring Tokio)" (`reqwest` 0.13.5 `src/lib.rs`). Its futures need a Tokio reactor; polled on gpui's executor directly they fail with Tokio's "no reactor running" panic **(unverified here: standard Tokio behaviour, and the reason Zed's client spawns onto a handle)**.
- **TUI:** native fit. Spawn the request with `tokio::spawn` and send the result back as an action on the existing `mpsc` channel.
- **Desktop:** capture `tokio::runtime::Handle::current()` in `main` (or inside `run`, which is already on the runtime) and hand it to the adapter; each fetch is `handle.spawn(...)` with the `JoinHandle` awaited from `cx.background_executor().spawn(...)` or `cx.spawn(...)`. One runtime, no fight: Tokio owns sockets and timers, gpui owns the UI thread. This is Zed's pattern in §2.1.
- **Executor-independent alternative:** an adapter that, like `writer.rs`, owns one thread with a current-thread runtime and takes requests over a channel. It needs no handle from either bin and works identically in tests, at the cost of one more thread.
- `reqwest::blocking` must *not* run inside an async runtime: "it will panic when attempting to block" (`reqwest` 0.13.5 `src/blocking/mod.rs`). Not useful here, since both bins are inside one.

### 2.3 `ureq` (blocking, no runtime)

- `ureq` 3.5.2 "uses blocking I/O instead of async I/O" (`src/lib.rs` line 27); it has no runtime of its own. Default features are `rustls` (with `_ring`, `rustls-webpki-roots`) and `gzip`; `json`, `platform-verifier` and `native-tls` are opt-in (`Cargo.toml` `[features]`). Licence `MIT OR Apache-2.0`.
- Call it from `tokio::task::spawn_blocking` in the TUI and from a gpui background task or a plain thread in the Desktop. A Price Source fetch is a handful of small GETs a week (ADR-0052), so blocking a pool thread costs nothing that matters.
- It adds `ureq`, `ureq-proto` and friends to a tree that already has the whole `reqwest` stack, so it is *more* new code, not less, for this workspace. Its advantage is independence from Tokio: if a Client ever drops `#[tokio::main]`, `ureq` doesn't care.

### 2.4 Versions and TLS

- `reqwest` 0.13.5 (2026-09-08) is the current line. Its `default-tls` is now `rustls`, and `rustls` means `__rustls-aws-lc-rs` plus `rustls-platform-verifier` (`Cargo.toml` `[features]`). `rustls-no-provider` keeps rustls and the platform verifier but leaves the crypto provider to the app, which would then install ring with `rustls::crypto::ring::default_provider().install_default()` **(unverified: rustls API, not exercised here)**. `native-tls` remains available.
- `reqwest` 0.12's `rustls-tls` feature, as the Sync Server's tests use it, resolves to rustls with ring and `webpki-roots`, matching the lock exactly (`Cargo.lock` `reqwest` 0.12.28 depends on `hyper-rustls`, `rustls`, `webpki-roots 1.0.10`; `rustls` depends on `ring`). Adding it to the bins adds no new transitive crate.
- **aws-lc-rs:** `aws-lc-rs` 1.19.0 is `ISC AND (Apache-2.0 OR ISC)`, `aws-lc-sys` 0.47.0 is `ISC AND (Apache-2.0 OR ISC) AND Apache-2.0 AND MIT AND BSD-3-Clause AND …` (crates.io API), all on the allow list. It builds C (and needs CMake or a prebuilt on some targets) **(unverified: aws-lc-sys build docs not read)**, and five `aws-lc-sys` advisories from 2026 (RUSTSEC-2026-0044 to -0048) show it is a live target. *ring* is already built for every target the bins ship.
- **Roots:** `webpki-roots` bundles Mozilla's roots, so a stale binary trusts stale roots (RUSTSEC-2026-0381, distrusted emSign intermediates, patched in 1.0.10, which the lock has). `rustls-platform-verifier` 0.7.1 (`MIT OR Apache-2.0`) uses the OS trust store instead, which follows OS updates and corporate CAs. For three public APIs (CoinGecko, Yahoo Finance, Frankfurter) either works; the platform verifier is the better default for a desktop app that may outlive a release.
- **Advisories in the lock:** rustls 0.23.46 is at or past the patched versions of RUSTSEC-2026-0285, -0346, -0347, -0348 and -0349; ring 0.17.14 is past RUSTSEC-2025-0009; RUSTSEC-2025-0010 (ring < 0.17 unmaintained) does not apply.

## 3. The OS keychain

### 3.1 `keyring` is now 4.x: a wrapper over `keyring-core` and store crates

- `keyring` 4.2.0 (2026-08-29, `MIT OR Apache-2.0`) "operates in one of two modes", `v1` (default) or `cli` ([docs.rs](https://docs.rs/keyring/latest/keyring/)). The library moved into `keyring-core` 1.1.0 and "each credential store now lives in its own crate" ([keyring-rs README](https://github.com/open-source-cooperative/keyring-rs)). Applications that want to choose stores "should instead be linking to the keyring-core library and any specific credential stores they want to use".
- `v1` = `apple-native-keyring-store/keychain`, `windows-native-keyring-store`, `zbus-secret-service-keyring-store` (`keyring` 4.2.0 `Cargo.toml`). Its `Entry` wraps `keyring_core::Entry` and on first use runs `set_credential_store` once (a `LazyLock`): `apple_native_keyring_store::keychain::Store::new()` on macOS, `windows_native_keyring_store::Store::new()` on Windows, `zbus_secret_service_keyring_store::Store::new()` on other Unix, then `keyring_core::set_default_store(store)` (`src/v1.rs` 107–124). On Linux `zbus-secret-service-keyring-store` is pulled with `crypto-rust`, so no OpenSSL.
- The other Linux stores (`dbus-secret-service-keyring-store` with vendored libdbus, `linux-keyutils-keyring-store` for the kernel keyring) are reachable only through `cli` or by depending on `keyring-core` directly. The kernel keyring does not survive a reboot **(unverified: from keyutils semantics, not read here)**, so it is no substitute for a persistent key store.
- Versions read: `keyring-core` 1.1.0, `apple-native-keyring-store` 1.0.3, `windows-native-keyring-store` 1.1.0, `zbus-secret-service-keyring-store` 1.0.1 (on `secret-service` 5.x, latest 5.2.0), `dbus-secret-service-keyring-store` 1.0.1, `linux-keyutils-keyring-store` 1.0.0. All `MIT OR Apache-2.0`.

### 3.2 Blocking, not async

- `keyring_core::Entry` methods return `Result` directly: `new(service: &str, user: &str) -> Result<Entry>`, `set_password(&self, &str) -> Result<()>`, `get_password(&self) -> Result<String>`, `set_secret`/`get_secret` for bytes, `delete_credential(&self) -> Result<()>` ([docs.rs `Entry`](https://docs.rs/keyring-core/latest/keyring_core/struct.Entry.html)).
- On Linux the store is built on `secret_service::blocking::SecretService` (`zbus-secret-service-keyring-store` `src/service.rs` line 13), which wraps the async API in `block_on` (`secret-service` 5.2.0 `src/blocking/mod.rs`). zbus comes with its default (async-io) runtime, so it is safe to call from any plain thread, but each call blocks its caller on a D-Bus round trip, and an unlock may wait on a user prompt (`ServiceError::Prompt` is mapped below).
- So neither Client should call it on its UI thread or a Tokio worker: `tokio::task::spawn_blocking` in the TUI, `cx.background_executor().spawn(...)` in the Desktop.
- `keyring-core` is thread-safe, but "the underlying credential stores may not handle access to a single credential from different threads reliably" ([docs.rs keyring-core](https://docs.rs/keyring-core/latest/keyring_core/)): keep one key's reads and writes on one path.

### 3.3 Per platform

- **Linux, Secret Service (gnome-keyring, KWallet, KeePassXC…).** Items are searched by `service` and `username` attributes across all collections and created in the `default` (login) collection; a `target` modifier puts them in a named collection. New items are labelled `keyring:{user}@{service}` unless a `label` modifier is given (`zbus-secret-service-keyring-store` `src/lib.rs`). KWallet's Secret Service API is UTF-8 only, so binary secrets need encoding; API keys are text, so this does not bite. Under WSL there is no `default` collection, so every entry needs a non-default `target` (same source). A locked collection is unlocked on search (`service.rs` `find_matching_items` calls `unlock_all`), which can raise the provider's unlock prompt.
- **macOS, Keychain.** A generic password in the login keychain, `service` attribute = service, `account` attribute = user; unambiguous within a keychain; neither may be empty; shown in Keychain Access under Passwords with *where* and *name* both the service (`apple-native-keyring-store` 1.0.3 `src/keychain.rs`). The item's access list is tied to the writing app's code signature, so an unsigned binary (ADR-0004: no signing yet) is likely to raise an "allow access" prompt after each rebuild or update **(unverified: Keychain ACL behaviour from Apple's model, not tested)**.
- **Windows, Credential Manager.** A generic credential whose `target_name` defaults to `{user}.{service}` (empty prefix and suffix, `.` delimiter), so `("a.b", "c")` and `("b", "c.a")`-style collisions are possible unless the store forbids the delimiter in the service. Default persistence is `Enterprise` (roams with a domain profile); `Session` and `Local` are available as a `persistence` modifier (`windows-native-keyring-store` 1.1.0 `src/lib.rs`). The blob limit is 2,560 bytes **(unverified: `CRED_MAX_CREDENTIAL_BLOB_SIZE` from Microsoft's docs)**, ample for an API key.

### 3.4 No keychain: the error, and detecting it up front

- `keyring_core::Error` has eleven variants ([docs.rs](https://docs.rs/keyring-core/latest/keyring_core/error/enum.Error.html)); the ones a Client meets are `NoEntry` (never set or deleted), `NoStorageAccess(_)` (store exists but can't be reached, "often because of a platform access rule such as a locked credential store"), `PlatformFailure(_)` (the store failed at runtime), `NoDefaultStore` (no store set, so no entry can be built), `Ambiguous(_)` (several items match) and `Invalid(_, _)`.
- On Linux the Secret Service store connects in its constructor: `Service::new()` calls `SecretService::connect(EncryptionType::Dh)` and maps failure to `PlatformFailure` (`service.rs` 24–27). `connect` opens the session bus and then an encrypted session with `org.freedesktop.secrets` (`secret-service` 5.2.0 `src/lib.rs` 172–198); no bus, no address, or no provider becomes `secret_service::Error::Unavailable`, "no secret service provider or dbus session found" (`src/util.rs` 151–159, `src/error.rs`). `Locked`, `NoResult` and `Prompt` map to `NoStorageAccess`; everything else to `PlatformFailure` (`zbus-secret-service-keyring-store` `src/errors.rs`).
- Through `keyring`'s `v1`, that construction failure is remembered and every `Entry::new` then returns `Error::NoDefaultStore`. **Detecting it ahead of time is supported:** `keyring::Entry::store_status() -> &'static Result<()>` runs the one-time initialisation and returns its result, `Ok(())` when a store is available, `Invalid("platform", _)` on an unsupported OS, or the store's own error (`src/v1.rs` 55–68: "if you want to do runtime checking of credential store initialization without first creating an entry, you can just call this function before `Entry::new`").
- Caveat: `v1` caches that result for the process, so a user who starts or installs a keyring after launch must restart the Client. Depending on `keyring-core` and the store crates directly lets the Client retry `Store::new()` itself, for example each time the key field opens.
- Caveat: a provider that is D-Bus-activatable is started by the connect call rather than reported missing **(unverified: standard D-Bus activation, not tested)**, so "available" can mean "just launched gnome-keyring", and a locked login keyring still fails later with `NoStorageAccess` or raises a prompt. Up-front detection answers "is there a Secret Service", not "can I read without a prompt".
- The crate's own headless advice is to start gnome-keyring unlocked with a known password, as its CI does (`zbus-secret-service-keyring-store` `src/lib.rs`, "Headless usage"). That is a user workaround, not something a Client can do for them; ADR-0043's "the key field says so and stores nothing" stands.

### 3.5 Naming entries

- An entry is `(service, user)`, both non-empty. The amendment to ADR-0043 says each Client keeps its own key; one service name for both bins lets the Desktop and the TUI on one machine share a key, two names keep them apart. That is a decision for the API key entry ticket, not this note.
- A reverse-DNS service matches the packaging identifiers already in use (`au.id.teda.personal-ledger.desktop`, `au.id.teda.personal-ledger.tui`; a shared `au.id.teda.personal-ledger` would serve both) and avoids `.`-collisions on Windows only if the user part carries no `.` either, since Windows joins them as `{user}.{service}`.
- The user part names the key: a built-in Price Source has a stable `const` id (ADR-0043), but a Custom source is a Ledger row, and two Ledgers on one machine can hold the same row id. So a Custom source's key needs something Ledger-unique in its name (a Ledger id, or a UUID stored on the source), or two Ledgers will overwrite each other's keys. Flagged for the decision ticket.

### 3.6 gpui's own credentials API

- gpui 0.2.2 has `App::write_credentials(url, username, password)`, `read_credentials(url)` and `delete_credentials(url)`, each returning a gpui `Task` (async) (`src/app.rs` 1057–1076). Linux uses `oo7` on the background executor, macOS `SecItem*` with `kSecClassInternetPassword` keyed on `kSecAttrServer = url`, Windows `CredWriteW` on the foreground executor with `CRED_PERSIST_LOCAL_MACHINE` (`src/platform/{linux,mac,windows}/platform.rs`); the test platform stores nothing (`src/platform/test/platform.rs` 415–425).
- It is not usable here: it is reachable only from `bin-desktop`, so the TUI would need a second mechanism; its names are Zed's (`KEYRING_LABEL = "zed-github-account"` on Linux, target `zed:url={url}` on Windows); and because it keys by URL and uses a different item class on macOS, a key written through it is invisible to `keyring` and vice versa.

## 4. Dependency policy

- **Licences.** `keyring`, `keyring-core`, every store crate, `secret-service`, `reqwest`, `ureq`, `rustls-platform-verifier`: `MIT OR Apache-2.0`. zbus (already in the lock) passes today. `aws-lc-rs`/`aws-lc-sys` (only if `reqwest` 0.13's default provider is taken): every licence in their expressions is on the allow list. No `deny.toml` licence change is needed.
- **Advisories.** The local RustSec copy has no advisory for `keyring`, `keyring-core`, `secret-service`, `zbus`, `oo7`, `reqwest` or `ureq`; the rustls, ring and webpki-roots advisories are all patched in the lock's versions (§2.4); `security-framework` has only RUSTSEC-2017-0003, against a long-gone version. `unmaintained = "workspace"` would flag a direct dependency that goes unmaintained; `keyring`'s 4.x rewrite under an active maintainer suggests that is not near.
- **Sources.** All on crates.io; nothing needs `allow-git`.
- **Duplicates.** `reqwest` 0.12 beside gpui's `zed-reqwest` shares every transitive crate. `reqwest` 0.13 would sit beside 0.12 (Sync Server tests) and the fork, warned under `multiple-versions = "warn"` but not failed; bumping the Sync Server's dev-dependency at the same time removes one duplicate.
- **VIPER.** `reqwest` and `keyring` are I/O, so they belong in adapters the bins own, never in a domain or feature crate. `deny.toml`'s `bans.deny` could gain `{ crate = "reqwest", wrappers = [...] }` and `{ crate = "keyring", wrappers = [...] }` (or `keyring-core`) naming only the adapter that implements the fetch and key ports, as it does for `lib_database`; `viper_dependencies.rs` would then catch a domain crate reaching for either.

## 5. Recommendation

- **HTTP:** `reqwest` (async) on the Tokio runtime both bins already run, behind a port the price-fetching module owns, implemented once and used by both Clients. Rustls with ring, matching the lock: either `reqwest` 0.12 with `rustls-tls` (zero new transitive crates), or 0.13 with `rustls-no-provider` plus an explicit ring provider (adds `rustls-platform-verifier`, for OS roots). The Desktop drives requests by spawning on a Tokio handle and awaiting the `JoinHandle` from gpui (Zed's pattern), or the adapter owns its own thread and current-thread runtime as `writer.rs` does. `ureq` on a thread is the fallback if a Client ever leaves Tokio.
- **Keychain:** `keyring` 4.x through `keyring-core` and the three native stores (Apple Keychain, Windows Credential Manager, zbus Secret Service with `crypto-rust`), not gpui's credentials API. Call it off the UI thread. Detect a missing store up front with `Store::new()` (or `keyring::Entry::store_status()` if the `v1` wrapper is enough and a restart to pick up a newly started keyring is acceptable), and show ADR-0043's "no keychain" state from that. Name entries with one reverse-DNS service and a user part that is unique across Ledgers for Custom sources.
