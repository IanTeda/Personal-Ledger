# Research: detecting the system light/dark setting

**Question.** GitHub issue [#296](https://github.com/IanTeda/Personal-Ledger/issues/296) ("Colour Themes: detecting the system light/dark setting"), a child of the [Colour Themes for the Desktop and TUI](https://github.com/IanTeda/Personal-Ledger/issues/292) Wayfinder map (#292), asks how each Client can learn the operating system's light/dark setting, both at start-up and live while running. For the Desktop that means `gpui`'s `Window::appearance()` / `observe_window_appearance` and `gpui-component`'s system-appearance sync, and what they rely on per OS (the XDG desktop portal's `org.freedesktop.appearance` `color-scheme` on Linux, including Hyprland/Omarchy; macOS; Windows). For the TUI it means OS-level crates such as `dark-light`, querying the terminal's background with OSC 11 (support, latency, tmux), and live change notifications (mode 2031 and the `CSI ? 996 n` / `CSI ? 997 ; Ps n` reports). This note is primary-source research only: it presents facts and options and decides nothing, matching the map's "planning only" scope. It feeds the decision tickets it blocks, [#299](https://github.com/IanTeda/Personal-Ledger/issues/299) "TUI terminal theme or Colour Theme" and [#302](https://github.com/IanTeda/Personal-Ledger/issues/302) "code architecture". Already settled at charting: every built-in Colour Theme has paired light and dark Colour Variants, the Colour Appearance (Light / Dark / System) picks the Colour Variant, and following an OS light/dark change while running is in scope. `CONTEXT.md` defines System as following "the operating system's (or terminal's) own light/dark setting", which is exactly the ambiguity this note unpacks for the TUI. Research was carried out on 2026-09-26.

Vocabulary note, per `CONTEXT.md` and the map: **Colour Theme**, **Colour Role**, **Colour Variant** and **Colour Appearance** are ours; other programs' own words ("theme", "color scheme", "appearance", `ThemeMode`, `WindowAppearance`) are kept when describing those programs, and API identifiers keep their US spelling. The sibling notes [`gpui-component-theming.md`](https://github.com/IanTeda/Personal-Ledger/blob/research/gpui-component-theming/docs/research/gpui-component-theming.md) (#297) and [`tui-terminal-vs-rgb-colour.md`](https://github.com/IanTeda/Personal-Ledger/blob/research/tui-terminal-vs-rgb-colour/docs/research/tui-terminal-vs-rgb-colour.md) (#295) already cover `ThemeMode`/`Theme::change` and the ANSI-vs-RGB question; this note only repeats what it needs.

## 2. What each OS exposes

**Linux / BSD: the XDG desktop portal Settings interface.** The spec defines `org.freedesktop.appearance` `color-scheme` (`u`): `0` no preference, `1` prefer dark, `2` prefer light; and `org.freedesktop.appearance` `contrast` (`u`): `0` no preference, `1` higher contrast. `ReadOne(namespace, key)` "was added in version 2" of the interface; the older `Read` is deprecated because it returns the value inside two layers of variant instead of one. The `SettingChanged(namespace, key, value)` signal is "emitted when a setting changes" ([Settings spec](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Settings.html)). The frontend (`org.freedesktop.portal.Desktop` on the session bus) forwards to whichever backend implements `org.freedesktop.impl.portal.Settings`; the backend decides where the value comes from. There is no portal-free standard: without a Settings backend, a Linux app has no portable way to learn the setting.

**macOS.** AppKit exposes an `effectiveAppearance` on `NSApplication`, `NSWindow` and `NSView`, whose `name` is one of `NSAppearanceNameAqua`, `NSAppearanceNameDarkAqua`, and the vibrant variants; `NSView` receives `viewDidChangeEffectiveAppearance` when it changes. (Taken from how `gpui` and `mundy` use these APIs, §3 and §6; Apple's own reference pages were not fetched, see §11.)

**Windows.** Microsoft's guidance, as cited in `gpui`'s source, is to read `Windows.UI.ViewManagement.UISettings.GetColorValue(UIColorType::Foreground)` and classify a light foreground as dark mode ([apply-windows-themes](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/apply-windows-themes)). A change is announced to top-level windows as `WM_SETTINGCHANGE` with the string parameter `ImmersiveColorSet`. The other common route, used by `dark-light`, is the registry value `HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize\AppsUseLightTheme`, watched with `RegNotifyChangeKeyValue`.

## 3. Desktop: what `gpui` 0.2.2 does per OS

**The public surface.** Three calls matter:

- `App::window_appearance()` (`gpui-0.2.2/src/app.rs:1029-1031`) asks the platform directly (`self.platform.window_appearance()`), with no window needed.
- `Window::appearance()` (`src/window.rs:1711-1713`) returns a cached `self.appearance`, seeded from `platform_window.appearance()` when the window is created (`window.rs:987`) and refreshed in `Window::appearance_changed` (`window.rs:1702-1708`), which also runs every registered appearance observer.
- `Window::observe_window_appearance(callback)` (`window.rs:1321`) and its `Context<T>` form `cx.observe_window_appearance(window, callback)` (`src/app/context.rs:465-469`) register those observers and return a `Subscription`. The platform window's `on_appearance_changed` callback is wired to `Window::appearance_changed` at window creation (`window.rs:1084-1090`).

`WindowAppearance` has four values, `Light`, `Dark`, `VibrantLight`, `VibrantDark` (`src/platform.rs:1279`); the vibrant ones only occur on macOS.

**Linux (Wayland and X11): the portal via `ashpd`, with live `SettingChanged`.** Both the `wayland` and `x11` features (both in `gpui`'s `default` feature set, `Cargo.toml:38-43`) enable the optional `ashpd` dependency (`Cargo.toml:65-100`). `src/platform/linux/xdg_desktop_portal.rs` ([zed@69e2130](https://github.com/zed-industries/zed/blob/69e2130295c2649963eb639fc70b4f2ee8ea1624/crates/gpui/src/platform/linux/xdg_desktop_portal.rs)) spawns a background task that:

- creates an `ashpd::desktop::settings::Settings` proxy (`:32`);
- reads the initial value with `settings.color_scheme()` (`:34-38`), which in `ashpd` 0.11.1 is `read::<ColorScheme>("org.freedesktop.appearance", "color-scheme")` (`ashpd-0.11.1/src/desktop/settings.rs:245-247`), and `read` calls the deprecated `Read` method and unwraps the extra variant layer (`settings.rs:224-235`), not `ReadOne`;
- then subscribes with `settings.receive_color_scheme_changed()` (`:92-97`), a `SettingChanged` stream filtered by D-Bus match args to that namespace and key (`settings.rs:257-262`, `:330`);
- maps `PreferDark → Dark`, `PreferLight → Light` and `NoPreference → Light` (`:158-165`).

The events arrive on the calloop main loop. The Wayland client (`src/platform/linux/wayland/client.rs:523-536`) and X11 client (`src/platform/linux/x11/client.rs:455-469`) both store the value in `LinuxCommon::appearance` and call `set_appearance` on every open window, which fires that window's `appearance_changed` callback (`wayland/window.rs:751-758`, `x11/window.rs:1135-1145`). So on Linux `gpui` does follow the OS live, as long as a portal Settings backend answers.

Three Linux details matter for Personal Ledger:

- **Start-up race.** `LinuxCommon::new` initialises `appearance: WindowAppearance::Light` (`src/platform/linux/platform.rs:122-131`), and the first portal read is asynchronous. Until that D-Bus round-trip lands, `App::window_appearance()` returns `Light` whatever the OS says, and a window created in that gap is seeded `Light` and then corrected by an `appearance_changed` call. Code that reads the appearance once at start-up and never again will be wrong on a dark Linux desktop if it reads too early (see §4 for where `bin-desktop` reads it).
- **No portal, no signal.** If `Settings::new()` or the reads fail (no portal, no Settings backend) the task simply ends (`?` on `:32` and `:92`); the value stays `Light` for the life of the process and nothing is logged by this code path.
- **Spurious callbacks.** On Wayland the same `appearance_changed` callback is also fired when the compositor switches between server- and client-side decorations (`wayland/window.rs:442-460`), with no colour-scheme change. Observers therefore need to be idempotent (compare old and new before acting).

**macOS: `effectiveAppearance`, with a view callback rather than KVO.** `MacPlatform::window_appearance` reads `NSApplication.sharedApplication.effectiveAppearance` synchronously (`src/platform/mac/platform.rs:639-645`); `MacWindow::appearance` reads the native window's `effectiveAppearance` (`mac/window.rs:1048-1050`). Change detection is the view class overriding `viewDidChangeEffectiveAppearance` (`mac/window.rs:233`, handler `view_did_change_effective_appearance` at `:2328-2338`), which calls the window's `appearance_changed` callback; there is no key-value observation. `WindowAppearance::from_native` maps `NSAppearanceNameAqua`/`DarkAqua`/`VibrantLight`/`VibrantDark` and falls back to `Light` for an unknown name after a `println!` (`mac/window_appearance.rs:10-30`).

**Windows: `UISettings` plus `WM_SETTINGCHANGE`.** `system_appearance()` (`src/platform/windows/util.rs:175-187`) reads `UISettings::GetColorValue(UIColorType::Foreground)` and returns `Dark` when that colour is light, citing the Microsoft page above. It is called synchronously for `window_appearance()` (`windows/platform.rs:420-421`) and at window creation (`windows/window.rs:420`). Live change: `WM_SETTINGCHANGE` (`windows/events.rs:105`) whose parameter string is `ImmersiveColorSet` re-reads `system_appearance()`, and only if the value differs updates state, fires `appearance_changed`, and re-applies the DWM dark title bar (`events.rs:1141-1164`).

## 4. Desktop: `gpui-component` 0.5.1 and `bin-desktop` today

`Theme::sync_system_appearance(window, cx)` ([`crates/ui/src/theme/mod.rs:128-138`](https://github.com/longbridge/gpui-component/blob/0f0ab35233212f8f3277028995caf0c41e13ee6c/crates/ui/src/theme/mod.rs#L128-L138)) takes `window.appearance()` when a window is given, else `cx.window_appearance()`, and passes it to `Theme::change`. The in-code comment says "Better use window.appearance() for avoid error on Linux" and links [gpui-component#104](https://github.com/longbridge/gpui-component/issues/104), a closed Linux `BorrowMutError` panic in `gpui`'s Wayland client. `gpui_component::init` calls `Theme::sync_system_appearance(None, cx)` exactly once (`theme/mod.rs:21-26`). A repository-wide grep of `gpui-component-0.5.1/` finds no `observe_window_appearance` call: the crate never re-syncs on its own, as the #297 note also found (its §3).

In `bin-desktop` on `concept`, `main.rs:95` calls `gpui_component::init(cx)` inside `Application::run`, before any window is opened, so the one sync that happens uses `cx.window_appearance()`. Nothing in `crates/bins/bin-desktop/src` calls `observe_window_appearance`, `sync_system_appearance`, `Theme::change` or `window.appearance()` (grep for `appearance`, `ThemeMode`, `Theme::change` and `sync_system_appearance` finds nothing). Combining that with §3's start-up race: on Linux the seeded `ThemeMode` is very probably always `Light` today, whatever the portal says, because the async portal read is unlikely to have completed by the time `init` runs (inferred from source, not tested; §11). On macOS and Windows the read is synchronous and correct at start-up. On every OS a later OS change is not followed. `bin-desktop`'s own chrome colours (`src/theme.rs`) are compile-time constants with no dark Colour Variant (its module comment, lines 3-5), so only the `gpui-component` chart/table widgets would react in any case.

The mechanism needed for "System" is therefore already in the pinned `gpui`: per window, `cx.observe_window_appearance(window, …)` on the root view, reading `window.appearance()` in the callback and at first render, and re-resolving the Colour Variant (and calling `Theme::change` for `gpui-component`) only when the value differs. This is what the `gpui-component` comment implies but does not do itself.

## 5. Linux on Hyprland / Omarchy

**Which backend answers.** `xdg-desktop-portal` picks backends by `$XDG_CURRENT_DESKTOP` using `<desktop>-portals.conf`. Local observations on this machine (`XDG_CURRENT_DESKTOP=Hyprland`):

- `/usr/share/xdg-desktop-portal/hyprland-portals.conf` is `[preferred] default=hyprland;gtk`.
- `hyprland.portal` lists only `Screenshot`, `ScreenCast`, `GlobalShortcuts` and `InputCapture`, no `Settings` (the same file upstream: [`hyprland.portal`](https://github.com/hyprwm/xdg-desktop-portal-hyprland/blob/e87ae7823e7bf0601385220c69b5a3b245123fc5/hyprland.portal)). So `xdg-desktop-portal-hyprland` does not implement Settings, and the `gtk` fallback serves it.
- `gtk.portal` lists `org.freedesktop.impl.portal.Settings` among its interfaces.

**What `xdg-desktop-portal-gtk` reports.** Its `get_color_scheme()` reads the GSettings enum `org.gnome.desktop.interface` `color-scheme` (`src/settings.c:94-104` at [1.15.3](https://github.com/flatpak/xdg-desktop-portal-gtk/blob/1.15.3/src/settings.c#L94-L104)), and when GSettings reports a change to that key it emits `SettingChanged` in the `org.freedesktop.appearance` namespace (`settings.c:281-286`). So on Hyprland the portal value is exactly the GNOME GSettings key, live.

**What Omarchy sets.** `omarchy-theme-set` runs `omarchy-theme-set-gnome` among its reload steps (`/usr/bin/omarchy-theme-set:326`, local). That script resolves the theme's mode (`omarchy-theme-color … mode`, from `colors.toml`'s `mode`, a legacy `light.mode` file, or background luminance) and runs `gsettings set org.gnome.desktop.interface color-scheme "prefer-light"` or `"prefer-dark"` (plus the matching Adwaita `gtk-theme`) (`/usr/bin/omarchy-theme-set-gnome:19-26`, local). It exits early if `DBUS_SESSION_BUS_ADDRESS` is unset.

**Observed end to end.** `gdbus call --session --dest org.freedesktop.portal.Desktop --object-path /org/freedesktop/portal/desktop --method org.freedesktop.portal.Settings.ReadOne org.freedesktop.appearance color-scheme` returned `(<uint32 2>,)` (prefer light), and `gsettings get org.gnome.desktop.interface color-scheme` returned `'prefer-light'` at the same time (local observation, 2026-09-26). The chain Omarchy theme switch → GSettings → portal-gtk `SettingChanged` → `ashpd` stream → `gpui` `appearance_changed` is therefore complete on this install. A live switch was not performed during this research (§11).

**Where it breaks.** On a Hyprland (or other wlroots) session without `xdg-desktop-portal-gtk` (or `-gnome`/`-kde`) installed there is no Settings backend, and per §3 `gpui` silently stays `Light`. `xdg-desktop-portal-gtk` also needs the GNOME `org.gnome.desktop.interface` schema installed to have a `color-scheme` key (`settings.c:99`). Omarchy ships both, per the local package list.

## 6. TUI option 1: ask the OS (`dark-light`, `mundy`)

These crates answer the same question as §3, without `gpui`.

**`dark-light` 3.0.0** (MIT OR Apache-2.0; [rust-dark-light/dark-light](https://github.com/rust-dark-light/dark-light), released 2026-08-12, repository last pushed 2026-08-13, 2 open issues, MSRV 1.78). `detect() -> Result<Mode, Error>` with `Mode::{Dark, Light, Unspecified}`, plus `subscribe()` (blocking iterator) and, with the default `async-io` or the `tokio` feature, `stream()` (README). Per platform (`src/platforms/`):

- Linux/BSD: a `zbus` 5.19 blocking proxy on `org.freedesktop.portal.Settings`, `ReadOne("org.freedesktop.appearance", "color-scheme")` for `detect`, and a thread over `SettingChanged` filtered to that key, de-duplicated, for `subscribe` (`freedesktop.rs:12-87`). `zbus` 5.19.0 is already in this workspace's `Cargo.lock`.
- macOS: reads `NSUserDefaults` `AppleInterfaceStyle` (`macos.rs:17`) and detects changes by polling once per second (`POLL_INTERVAL`, `macos.rs:30-61`); the README says this is because its `objc2` bindings do not yet expose a safe distributed-notification observer.
- Windows: registry `AppsUseLightTheme`, watched with `RegNotifyChangeKeyValue` (`windows.rs:5-61`).

**`mundy` 0.2.3** (Apache-2.0; [tautropfli/mundy](https://github.com/tautropfli/mundy), released 2026-04-30, last push 2026-05-02, 3 open issues, MSRV 1.80), by the author of `terminal-colorsaurus`. Reads colour scheme, contrast, accent colour, reduced motion/transparency and more, as a de-duplicated async stream (`Preferences::stream(Interest::…)`, readme). Linux: portal `SettingChanged` (`src/freedesktop/mod.rs:302-307`); macOS: observes `effectiveAppearance` (`src/macos/observer.rs:57`); Windows: `UISettings` plus a `WM_SETTINGCHANGE` hook (`src/windows/mod.rs:30-39,152`). Its `contrast` preference is also relevant to the map's high-contrast Colour Theme.

**What the OS answer means for a TUI.** Both report the setting of the machine the TUI process runs on, through that machine's session bus or APIs. That is the right answer when the TUI runs locally in a terminal that itself follows the OS. It is the wrong or no answer when: the TUI runs over SSH (the remote host usually has no session bus or portal for that user, so the Linux path errors; and if it answers, it is the server's setting, not the viewer's); the terminal's own colours do not follow the OS (a user with a dark terminal on a light desktop, or foot, whose light/dark switch is separate from the OS, §8); or inside a Flatpak/containers without portal access. The cost is a `zbus` connection (Linux) or native bindings, which is small but new to `bin-tui`.

## 7. TUI option 2: ask the terminal (OSC 10/11)

**The query.** xterm's `OSC 10` / `OSC 11` set the "VT100 text foreground/background color"; "if Pt is a '?', the control sequence elicits a response which consists of the control sequence which would set the corresponding value", i.e. `ESC ] 11 ; rgb:RRRR/GGGG/BBBB ST` ([ctlseqs](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html)). The app then classifies the colour by lightness. This answers "is the surface I am drawing on light or dark", which is the terminal's reality rather than the OS setting, and works over SSH because it travels in-band.

**Support.** `terminal-colorsaurus`'s own tested survey (`doc/terminal-survey.md`, 1.0.3) lists `OSC 10`/`OSC 11` support in Alacritty (0.13.1), Contour, foot (1.16.1), Ghostty (1.0.0), iTerm2, kitty (0.31.0), Konsole, VTE terminals (GNOME Terminal/Console etc.), macOS Terminal, mintty, Rio, urxvt (with a terminator bug), WezTerm, xterm, VS Code/xterm.js, Windows Terminal (listed as `>= v1.22` in the summary), and tmux ("next-3.4"). It lists no support in the Linux console, GNU Screen, PuTTY, mosh, ConEmu and a handful of others. Alacritty's own escape table at master marks `OSC 10`, `OSC 11` and `OSC 111` "Implemented" ([alacritty-escapes.7.scd:230-252](https://github.com/alacritty/alacritty/blob/d692748d3f61253ebe9f5094320120d22f6a046f/extra/man/alacritty-escapes.7.scd#L230-L252)).

**Latency and the "no answer" problem.** A terminal that does not support the query stays silent, so a naive reader waits for its timeout. `terminal-colorsaurus` sends `OSC 11` followed by `DA1` (`CSI c`, answered by nearly every terminal); because replies come back in order, a `DA1` reply arriving first means "unsupported" without waiting (`src/xterm.rs:93-141`). Its default timeout is 1 s and its docs recommend leaving it high for SSH (`src/lib.rs:136-149`); it also refuses up front for `TERM=dumb`, `screen*` and `Eterm` (`src/quirks.rs:12-60`) and uses a `BEL` terminator to cope with urxvt (`quirks.rs:74-88`). `terminal-light` sends `OSC 11` with a 100 ms timeout (`src/xterm.rs:25`; its crate docs still say 20 ms) and falls back to `$COLORFGBG`. The crate's `doc/latency-rustdoc.md` benchmarks are charts only and were not transcribed (§11).

**tmux.** Since 3.4 tmux answers `OSC 10`/`OSC 11` queries itself: "Query the client terminal for foreground and background colours and if OSC 10 or 11 is received but no colour has been set inside tmux, return the colour from the first attached client" ([CHANGES, 3.3a→3.4](https://github.com/tmux/tmux/blob/94796f6b1182507efac8a272fc309a79e22e58a5/CHANGES)). So no passthrough wrapping is needed on 3.4+; `termbg` still wraps its query in `DCS tmux; … ST` passthrough when `$TMUX` is set (`termbg-0.6.2/src/lib.rs:99,315`), which depends on tmux's off-by-default `allow-passthrough`. Omarchy's `omarchy-theme-set-tmux` sets tmux's `window-style` background and writes the theme's `OSC 10/11/4` sequences into every pane (`/usr/bin/omarchy-theme-set-tmux:59-92`, local), so inside Omarchy's tmux a later `OSC 11` query returns the new theme's background.

**Clash with `crossterm`'s reader.** `bin-tui` reads input through `crossterm::event::EventStream` in a Tokio task (`src/event.rs:40-41`) after `Tui::new` enters raw mode (`src/tui.rs:67-73`). `crossterm` 0.29 has no API to send an `OSC 11` query or parse its reply: an `ESC ]` sequence falls through `parse_event`'s `_ =>` arm, which re-parses the rest as an Alt-modified key (`parse.rs:78-88`), so a reply read by `EventStream` becomes spurious key events (inferred from source). Requests for an API are open ([crossterm#1037](https://github.com/crossterm-rs/crossterm/issues/1037), opened 2026-02-25); a "Color palette querying and change detection" PR ([crossterm#1045](https://github.com/crossterm-rs/crossterm/pull/1045)) was closed unmerged on 2026-04-28. `crossterm`'s latest release is still 0.29.0 (crates.io). In practice the query has to happen before `EventHandler::new` starts reading (as `supports_keyboard_enhancement()` already does inside `Tui::new`), or be done by a crate that opens the tty itself while `crossterm`'s reader is not running.

**Crates.**

- **`terminal-colorsaurus` 1.0.3** (MIT OR Apache-2.0; [tautropfli/terminal-colorsaurus](https://github.com/tautropfli/terminal-colorsaurus), released 2025-12-28, last push 2026-05-06, 4 open issues, MSRV 1.74; ~1.13 M recent downloads). `theme_mode(QueryOptions) -> Result<ThemeMode>`, `color_palette`, `foreground_color`, `background_color` (`src/lib.rs:157-179`). Opens the terminal itself and restores raw mode even on panic (`lib.rs:13`). No `crossterm` dependency. No mode-2031 support.
- **`terminal-light` 1.9.1** (MIT; [Canop/terminal-light](https://github.com/Canop/terminal-light), released 2026-08-23, 0 open issues). `luma()`/`background_color()`; OSC 11 then `$COLORFGBG` (`src/lib.rs:99-112`); depends on `crossterm` 0.29 (the same version as `bin-tui`). Its docs note waiting with a timeout is not implemented on Windows.

Oldest release of the three.

## 8. Live change in the terminal: mode 2031

**The protocol.** Contour's spec: the app sends `CSI ? 996 n` to query, and the terminal replies `CSI ? 997 ; 1 n` (dark) or `CSI ? 997 ; 2 n` (light). `CSI ? 2031 h` enables, and `CSI ? 2031 l` disables, unsolicited reports of the same form, sent "when the color palette updates due to theme changes initiated by the operating system or when users modify terminal profiles or color schemes" ([spec](https://contour-terminal.org/vt-extensions/color-palette-update-notifications/)). The spec does not itself describe DECRQM, but foot answers `CSI ? 2031 $ p` (`csi.c:672`), so support can be probed that way in at least foot.

**Who implements it.** The spec's adoption table lists Contour (0.4.0), Ghostty (1.0.0), Kitty (0.38.1), VTE (0.82.0), tmux ([tmux#4269](https://github.com/tmux/tmux/issues/4269), closed), Zellij (0.44.2) and, as consumers, Neovim, Helix and Yazi; WezTerm is still open ([wezterm#6454](https://github.com/wezterm/wezterm/issues/6454)). foot added it in 1.23.0 ("Support for private mode 2031 - Dark and Light Mode Detection", [CHANGELOG](https://codeberg.org/dnkl/foot/src/branch/master/CHANGELOG.md)). Alacritty does not: 2031 is absent from its supported `CSI ? h` modes list at master (`alacritty-escapes.7.scd:127`, modes `1 … 2026`). iTerm2 and Windows Terminal were not checked (§11).

**What "dark" means differs per terminal.** foot's reply is not measured from the background: `CSI ? 996 n` answers from `term->colors.active_theme` (`csi.c:1584-1600`, whose comment says "In foot, the themes aren't necessarily light/dark, but by convention, the primary theme is dark"), and the unsolicited `997` is sent only by `term_theme_switch_to_dark`/`_to_light`/`_toggle`, i.e. switching between foot's `[colors-dark]` and `[colors-light]` sections (`terminal.c:4783-4844`). `osc.c` has no 997 path, so a colour change written with `OSC 11` does not trigger a report. tmux 3.6 added 2031 and "will guess the theme from the background colour on terminals which do not themselves support the escape sequence"; the unreleased 3.8 changes this so that "the terminal's own theme is reported to panes instead of being guessed from the background" and "Do not send theme unless it has changed" (tmux `CHANGES`, 3.5a→3.6 and 3.7c→3.8; 3.8-rc2 was tagged 2026-09-09).

**Omarchy's theme switch versus 2031 (local observation).** Omarchy re-themes foot by writing `OSC 10/11/12/17/19/4` sequences from `omarchy-theme-osc` straight to each foot child's pty (`/usr/bin/omarchy-theme-set-foot:15-21`), not by switching foot's light/dark slot. Per the foot source above, that recolours the terminal without a 2031 notification, and a later `CSI ? 996 n` still reports foot's slot (normally "dark"), while `OSC 11` would return the new, possibly light, background. Inside tmux, Omarchy additionally sets `COLORFGBG` (`15;0` or `0;15`) in the tmux environment (`omarchy-theme-set-tmux:39-49`, affects new panes only), writes the OSC sequences into each pane, sends `SIGWINCH` to each pane's foreground process group (`:94-103`) and refreshes clients. A crossterm TUI would see that `SIGWINCH` as a `Resize` event (`bin-tui` already forwards it as `Event::Resize`, `event.rs`), which is a usable, if indirect, cue to re-query `OSC 11`; this was read from the scripts, not exercised (§11). Ghostty and Kitty, which Omarchy reloads by signal (per #295's note), were not tested for whether a signal-driven config reload emits 2031.

**`crossterm` and 2031.** In `crossterm` 0.29 a `CSI ? … n` report is not parsed: the `b'?'` arm only handles final bytes `u` and `c` and otherwise yields `Ok(None)` (`parse.rs:180-184`), which the reader treats as "incomplete, keep buffering" (`source/unix/mio.rs:209-212`). The open issue [crossterm#1104](https://github.com/crossterm-rs/crossterm/issues/1104) (2026-08-07) describes the consequence: once a terminal sends `CSI ? 997 ; 1 n`, "from that moment `read()` returns nothing for anything the user types" until a stray `u` or `c` clears the buffer. So enabling mode 2031 in `bin-tui` on the pinned `crossterm` would wedge keyboard input on the first light/dark flip. Using 2031 requires a `crossterm` fix or a different input layer (Helix, for example, moved to its own `termina` backend, per #295's note).

## 10. Summary and options for the decision tickets

| Client / context | Start-up signal | Live signal | Available today in pinned deps | Main caveat |
| --- | --- | --- | --- | --- |
| Desktop, Linux (Hyprland/Omarchy) | portal `color-scheme` via `ashpd` in `gpui` | portal `SettingChanged` → `observe_window_appearance` | yes | async first read races start-up (defaults `Light`); needs a Settings backend (gtk on Hyprland) |
| Desktop, macOS | `effectiveAppearance` | `viewDidChangeEffectiveAppearance` → `observe_window_appearance` | yes | none found |
| Desktop, Windows | `UISettings` foreground | `WM_SETTINGCHANGE` `ImmersiveColorSet` → `observe_window_appearance` | yes | none found |
| TUI, OS setting | `dark-light`/`mundy` | their subscribe/stream | new crate (+`zbus`) | wrong over SSH or when the terminal ignores the OS |
| TUI, terminal background | OSC 11 query | none (re-query on a cue, e.g. `SIGWINCH`/focus) | no (`crossterm` cannot parse replies) | must run before `EventStream`; timeout on silent terminals |
| TUI, terminal mode report | `CSI ? 996 n` | mode 2031 `CSI ? 997 ; Ps n` | no (breaks `crossterm` 0.29 input) | not in Alacritty/WezTerm; foot reports its slot, not its background |

These are the shapes the evidence supports for #302 (code architecture) and #299 (TUI approach); this note does not choose.

**Desktop.** The platform work is done by `gpui`; the open choices are where the listener lives and what it feeds.

- **D1. Follow `gpui` per window.** Subscribe with `cx.observe_window_appearance` in each window's root view, re-resolve the Colour Variant when Colour Appearance is System and the value changed, and push `Theme::change` for `gpui-component`. For: no new dependency, correct on all three OSes, live. Against: must avoid the Linux start-up race (read `window.appearance()` after the window exists, or rely on the first `appearance_changed`), and observers must ignore Wayland's decoration-triggered no-op callbacks.
- **D2. Use an OS crate (`mundy`/`dark-light`) in the Desktop too, sharing code with the TUI.** For: one detection path for both Clients; `mundy` also exposes contrast and accent colour. Against: duplicates what `gpui` already delivers, adds a second D-Bus connection on Linux and (for `dark-light`) 1 s polling on macOS.

**TUI.** The deeper choice is what "System" means for the TUI, which `CONTEXT.md` already hedges ("operating system's (or terminal's)").

- **T1. OS setting** (`dark-light` or `mundy`). For: matches the Desktop's meaning of System; live on all OSes; independent of `crossterm`. Against: answers for the wrong machine over SSH, and is wrong whenever the terminal's colours do not track the OS (for example foot's own light/dark slots, or a user's fixed dark terminal on a light desktop).
- **T2. Terminal background via OSC 11 at start-up** (`terminal-colorsaurus`-style, before `EventStream` starts). For: describes the surface actually being drawn on, works over SSH and inside tmux 3.4+, and on Omarchy returns the current theme's background even after an OSC-driven re-theme. Against: one-shot; live following needs a trigger to re-query plus a way to read the reply past `crossterm` (pause the reader, or own the tty), and up to the timeout on silent terminals.
- **T3. Mode 2031 for live change**, with `CSI ? 996 n` at start-up. For: the protocol designed for exactly this; tmux forwards it. Against: blocked on `crossterm` (#1104 wedges input); missing in Alacritty and WezTerm; foot's answer can disagree with its actual background under Omarchy's OSC-based re-theming.
- **T4. Layered.** For example: OSC 11 at start-up, falling back to the OS crate, then to a stored default; re-query on `Resize`/focus-gained; adopt 2031 later if `crossterm` gains support. For: best coverage. Against: most code and the most cases to test.
- **Interaction with #299.** If #299 keeps an ANSI "terminal" Colour Theme (its option A or C), System detection matters only for RGB Colour Themes, because the terminal already supplies light or dark for ANSI colours; the TUI could then treat System as "use the terminal's own colours". If #299 chooses app-controlled RGB throughout (its option B), a correct System answer becomes necessary for every user who leaves Colour Appearance on System, and the SSH and foot cases above decide how often it is wrong.
