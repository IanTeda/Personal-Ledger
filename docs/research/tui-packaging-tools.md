# Research: Cross-platform packaging tools for a non-root Rust TUI installer

**Question.** Personal Ledger's planned TUI binary will need cross-platform release packaging, and `docs/product-requirements.md` sets two constraints that shape the evaluation: NFR.2, "The app never requires root/administrator privileges to run," and NFR.6, "The app builds and runs on Linux, macOS, and Windows." This note surveys four candidate packaging approaches — `cargo-dist`, `cargo-packager`, `cargo-bundle`, and hand-rolled GitHub Actions scripting — against three required release outputs: (1) a portable Windows `.exe`/archive needing no installer or UAC elevation, (2) a macOS `.dmg`/`.app` installable to user space without `sudo`, and (3) a Linux `.deb` and/or AppImage installable without root. This is research input for decision ticket #12 ("Decide packaging tool and record ADR"); it does not make the decision. All claims below are cited to primary sources — the tools' own GitHub repos (README, docs source, config/API reference, CI workflow files, issue tracker), crates.io/GitHub API metadata, and official platform documentation (Apple, Microsoft, Debian, AppImage.org) — rather than blog posts or tutorials.

Research was done by reading each tool's README and documentation source directly from its GitHub repository (via the `gh` CLI and `WebFetch` against `axodotdev/cargo-dist`, `crabnebula-dev/cargo-packager`, and `burtonageo/cargo-bundle`, including their `book/src/**`/docs-source Markdown and `docs.rs` API reference pages), cross-checking release/version/star/issue metadata via the GitHub REST API and the crates.io API, and consulting Apple's Platform Security Guide and Mac User Guide, Microsoft Learn's Defender SmartScreen docs, the Debian Policy Manual, and appimage.org for the platform-level Gatekeeper/SmartScreen/`.deb`/AppImage facts.

## 2. cargo-dist

**Output-type support.** cargo-dist's core output is an archive (`.zip` on Windows, `.tar.xz` elsewhere by default, configurable) containing the prebuilt binary — "Archives are the primary output of dist: a single file (zip or tarball) containing prebuilt executables/binaries for an app" (cargo-dist docs, `book/src/artifacts/archives.md`, https://axodotdev.github.io/cargo-dist/book/artifacts/archives.html). On top of archives it currently ships five "installers," of which only `msi` (Windows) is a self-contained "bundling" installer; `shell`, `powershell`, `npm`, and `homebrew` are "fetching" installers that download the archive at install time (cargo-dist docs, `book/src/installers/index.md`, https://axodotdev.github.io/cargo-dist/book/installers/). Read directly from the docs source tree, the installer pages present are exactly `homebrew.md`, `index.md`, `msi.md`, `npm.md`, `other.md`, `powershell.md`, `shell.md`, `updater.md`, `usage.md` — there is no `dmg.md`, `deb.md`, or `appimage.md` (https://github.com/axodotdev/cargo-dist/tree/main/book/src/installers). The docs are explicit that macOS and Linux packaging formats are *not yet implemented*: "The following installers have been requested, and we're open to supporting them, but we have no specific timeline for when they will be implemented," listing "macOS dmg / app" (tracked at https://github.com/axodotdev/cargo-dist/issues/24), "linux flatpak" (https://github.com/axodotdev/cargo-dist/issues/25), and a "linux docker image containing binaries" (https://github.com/axodotdev/cargo-dist/issues/365) — notably, `.deb` and AppImage are not even on that future-work list, i.e. not requested/tracked at all as of this research (cargo-dist docs, `book/src/installers/index.md`). Consistent with this, the docs source has a Windows-only signing guide (`book/src/supplychain-security/signing/windows.md`) and no macOS-signing/notarization guide directory exists under `supplychain-security/signing/` at all (https://github.com/axodotdev/cargo-dist/tree/main/book/src/supplychain-security/signing).

**Config format.** Config now lives in `dist-workspace.toml` / `dist.toml` (the tool itself was renamed from `cargo-dist` to `dist`, README: "`dist` (formerly known as `cargo-dist`)", https://github.com/axodotdev/cargo-dist/blob/main/README.md); the older `[workspace.metadata.dist]` / `[package.metadata.dist]` sections in `Cargo.toml` are still supported for existing Rust users during "a major config migration" (cargo-dist docs, `book/src/reference/config.md`, https://axodotdev.github.io/cargo-dist/book/reference/config.html, referencing https://github.com/axodotdev/cargo-dist/pull/1247). The crates.io package name remains `cargo-dist`.

**GitHub Actions integration.** This is cargo-dist's standout feature: "dist enables CI for you by default the first time you `dist init`" and generates a complete GitHub Actions `release.yml` implementing a plan → build-local-artifacts → build-global-artifacts → host → publish → announce pipeline that uploads to GitHub Releases (cargo-dist docs, `book/src/ci/`, https://axodotdev.github.io/cargo-dist/book/ci/). GitHub Actions is presently the only supported CI backend ("github: uses GitHub Actions and uploads to GitHub Releases"); GitLab and Travis CI are requested but unimplemented.

**Maintenance activity.** Maintained by **Axo** (axo.dev), a company — the GitHub org `axodotdev`'s profile links to https://axo.dev. Latest GitHub release is `v0.32.0`, "Version 0.32.0 (2026-05-21)," published 2026-05-22 (GitHub Releases API, `axodotdev/cargo-dist`). crates.io shows 173,897 total downloads and 19,680 recent downloads for `cargo-dist` (crates.io API, https://crates.io/api/v1/crates/cargo-dist). The GitHub repo has 2,107 stars, 146 forks, and 331 open issues (GitHub REST API, `axodotdev/cargo-dist`), and is licensed Apache-2.0/MIT.

**Windows signing/SmartScreen.** cargo-dist has a first-party, opt-in Windows code-signing integration: the `ssldotcom-windows-sign` config key — "If you wish to sign your Windows artifacts ([EXEs] and [MSIs]) such that Windows SmartScreen won't complain about them, this is the feature for you," supporting SSL.com's "prod" or "test" signing environments via their GitHub Action (cargo-dist docs, `book/src/reference/config.md`, https://axodotdev.github.io/cargo-dist/book/reference/config.html#ssldotcom-windows-sign). Signing is explicitly optional — the config field is unset by default.

**Bottom line.** cargo-dist is the strongest tool here for automated, zero-maintenance Windows portable-archive + Windows-signing CI, and for generating the release pipeline itself — but as of this research it has **no native path to the macOS `.dmg`/`.app` or Linux `.deb`/AppImage outputs the PRD requires**; those would have to be hand-rolled alongside it (or produced by a second tool), which materially changes its value proposition for this project.

## 3. cargo-packager

**Output-type support.** cargo-packager's own README states its supported package set directly: "macOS — DMG (.dmg), Bundle (.app); Linux — Debian package (.deb), AppImage (.AppImage), Pacman (.tar.gz and PKGBUILD); Windows — NSIS (.exe), MSI using WiX Toolset (.msi)" (cargo-packager README, https://github.com/crabnebula-dev/cargo-packager/blob/main/README.md). This is the only one of the three dedicated packaging crates that natively covers *all three* required output categories in one tool. For Windows, the NSIS installer's `install_mode` field defaults to `NSISInstallerMode::CurrentUser`, documented as: "Default mode for the installer. Install the app by default in a directory that doesn't require Administrator access. Installer metadata will be saved under the `HKCU` registry path" — versus `PerMachine` ("requires Administrator access") and `Both` ("this mode will require Administrator access even if the user wants to install it for the current user only") (docs.rs, `cargo_packager::config::NSISInstallerMode`, https://docs.rs/cargo-packager/latest/cargo_packager/config/enum.NSISInstallerMode.html). This satisfies "no elevation" but produces an *installer* `.exe`, not a bare portable single-file executable — the PRD's "portable single .exe with no installer" wording is not literally met by cargo-packager's Windows output; a genuinely installer-free portable `.exe` would just be the raw `cargo build` output, zipped separately.

**Config format.** `Packager.toml`, `packager.json`, or a `[package.metadata.packager]` table in `Cargo.toml`; full schema documented at `cargo_packager::config::Config` on docs.rs (https://docs.rs/cargo-packager/latest/cargo_packager/config/struct.Config.html), with a JSON Schema also shipped in-repo for editor autocomplete (cargo-packager README).

**GitHub Actions integration.** No official reusable GitHub Action was found in the `crabnebula-dev` GitHub org (checked via the GitHub API — the org's public repos include `cargo-packager`, `wry`, `devtools`, `cloud-release` (a CrabNebula Cloud-specific action), but no `cargo-packager-action`). Usage is CLI-only: `cargo install cargo-packager --locked` then `cargo packager --release` as documented in the README — a documented CLI recipe to script into a workflow yourself, not a drop-in Action. The project's own CI (`.github/workflows/integration-tests.yml` in the repo) demonstrates cross-platform invocation but is not packaged for reuse by consumers.

**Maintenance activity.** Maintained by **CrabNebula**, a company (GitHub org `crabnebula-dev`; repo homepage https://docs.crabnebula.dev/packager/; CrabNebula is also the org behind Tauri-adjacent tooling like `devtools` and `wry` in the same org). Latest release `@crabnebula/packager v0.11.8`, published 2025-11-27 (GitHub Releases API, `crabnebula-dev/cargo-packager`), matching crates.io's `max_stable_version: 0.11.8` (crates.io API). crates.io shows 172,669 total downloads and 44,343 recent downloads — the highest recent-download figure of the three crates checked. GitHub: 470 stars, 48 forks, 66 open issues. Licensed MIT/Apache-2.0.

**macOS signing/notarization support.** `MacOsConfig` exposes `signing_identity` ("typically of the form: `\"Developer ID Application: TEAM_NAME (TEAM_ID)\"`"), `signing_certificate`/`signing_certificate_password` (explicitly noted as unable to be set via config file — env/CLI only), `notarization_credentials`, and `entitlements` (docs.rs, `cargo_packager::config::MacOsConfig`, https://docs.rs/cargo-packager/latest/cargo_packager/config/struct.MacOsConfig.html) — all `Option` fields, i.e. signing/notarization is fully optional and cargo-packager can produce an unsigned `.dmg`/`.app` if these are left unset.

**Bottom line.** cargo-packager is the only dedicated tool that natively hits all three required output categories in one config, but pays for that breadth with weaker CI ergonomics (no generated workflow) than cargo-dist, and its Windows output is an installer rather than a bare portable exe.

## 4. cargo-bundle

**Output-type support.** Directly from the current README: "`cargo-bundle` is a tool used to generate installers or app bundles for GUI executables built with `cargo`. It can create `.app` bundles for Mac OS X and iOS, `.deb` packages and `.AppImage` bundles for Linux, and `.msi` installers for Windows (note however that iOS and Windows support is still experimental). Support for creating `.rpm` packages (for Linux) and `.apk` packages (for Android) is still pending" (cargo-bundle README, https://github.com/burtonageo/cargo-bundle/blob/master/Readme.md). The `-f/--format` CLI flag lists possible values `deb, ios, msi, wxsmsi, osx, rpm, appimage`, confirming AppImage and `.deb` are implemented today, not aspirational. macOS-specific config includes `osx_dmg_background` for a custom Finder-window DMG background, confirming DMG generation (not just raw `.app`) is supported. AppImage-specific settings (`appimage_runtime_path`, `appimage_runtime_url`, `appimage_metainfo_path`, `appimage_compression`) exist, but the README flags a real limitation: "Shared libraries are **not** auto-collected (unlike tools that wrap `linuxdeploy` / `appimagetool`). Dynamically linked GUI apps may need matching system libraries on the target machine, or you can stage libs under `usr/lib` in the AppDir yourself" — for a TUI binary with few dynamic dependencies this is a smaller risk than for a GUI app, but it's a real gap versus `linuxdeploy`-based hand-rolled AppImage builds.

**Config format.** `[package.metadata.bundle]` in `Cargo.toml`, with per-binary overrides via `[package.metadata.bundle.bin.<name>]` (cargo-bundle README).

**GitHub Actions integration.** No CI-generation feature exists. The only related guidance in the README is a passing note: "Github Actions and Bitbucket Pipelines both have Apple MacOS build runners/containers available to use for free" — i.e., an aside about runner availability, not a documented recipe or action.

**Maintenance activity.** Individually maintained by George Burton (`burtonageo`), not a company. The README's own status line still reads: "Very early alpha. Expect the format of the `[package.metadata.bundle]` section to change, and there is no guarantee of stability" (cargo-bundle README, "Status" section). Despite that framing, the project is not dormant: crates.io lists `0.11.0` as the current max version, published 2026-05-30 (crates.io API, version-specific endpoint), and the GitHub repo shows a last-`pushed` timestamp of 2026-08-23 — i.e., commits within the last two weeks of this research. GitHub: 1,371 stars, 101 forks, 76 open issues, not archived. Dual-licensed MIT/Apache-2.0 (`license = "MIT OR Apache-2.0"` in `Cargo.toml`).

**Bottom line.** cargo-bundle is the closest single-maintainer analogue to cargo-packager's output-type breadth (it also natively covers all three required categories, `.deb`+AppImage on Linux and `.app`/DMG on macOS, plus experimental `.msi`), and is being actively developed despite its own "alpha/no stability guarantee" self-assessment — but the explicit config-format-instability warning, the AppImage shared-library caveat, the bus-factor of a single named maintainer, and the complete absence of any CI-generation or GitHub Actions guidance are real risks a decision-maker should weigh.

## 5. Hand-rolled GitHub Actions packaging

**Mechanism.** No dedicated crate; the release workflow is built directly from OS-native tools run as steps on the three GitHub-hosted runner families. GitHub's own `runner-images` documentation confirms Ubuntu, Windows, and macOS images are all available as GitHub-hosted runners (`actions/runner-images`, https://github.com/actions/runner-images) — e.g. `ubuntu-latest`/`ubuntu-24.04`, `windows-latest`/`windows-2025`, `macos-latest`/`macos-26`, each migrated forward over time, with GitHub recommending pinning a specific OS version if workflow stability matters.

- **Windows:** the compiled `.exe` from `cargo build --release` is already a portable, non-elevated single file; wrapping it in a `.zip` (PowerShell `Compress-Archive`, or `zip`) needs no dedicated tool at all.
- **macOS:** assembling a `.app` bundle by hand (Info.plist + binary + `Contents/MacOS/`) and then packaging a `.dmg` via Apple's own `hdiutil` command-line tool, or the popular third-party `create-dmg` shell-script wrapper around it (2,619 GitHub stars, `create-dmg/create-dmg`, https://github.com/create-dmg/create-dmg) named explicitly in this research's brief.
- **Linux `.deb`:** `dpkg-deb --build` against a hand-assembled package tree; this is the same primitive cargo-bundle/cargo-packager wrap, so hand-rolling buys no functional difference here beyond direct control of the `control` file and lack of Rust tooling dependency.
- **Linux AppImage:** `AppImage/appimagetool` (a "low-level tool to generate an AppImage from an existing AppDir," 425 stars, https://github.com/AppImage/appimagetool) and/or `linuxdeploy` ("AppDir creation and maintenance tool. Featuring flexible plugin system," 816 stars, https://github.com/linuxdeploy/linuxdeploy) — `linuxdeploy` specifically addresses the shared-library-collection gap noted above in cargo-bundle.

**GitHub Actions integration.** None of these tools ship a workflow generator; every step must be written and maintained by hand, across three separate runner OSes, with per-tool installation steps (`appimagetool`/`linuxdeploy` are not preinstalled on `ubuntu-latest`; `dpkg-deb` is; `hdiutil` is preinstalled on `macos-latest`). This is the most labor-intensive and highest-ongoing-maintenance option of the four, but also the most flexible — it can hit all three required outputs exactly as specified (a true bare portable `.exe`, an unsigned `.dmg`, a `.deb`, and/or an AppImage) with no dependency on any third-party crate's release cadence or design choices.

**Maintenance activity.** Not applicable to "hand-rolled" as a whole — the risk is distributed across whichever underlying tools get scripted in (`dpkg-deb` ships with `dpkg` itself; `appimagetool` and `linuxdeploy` are separately maintained open-source projects with their own star counts/issue trackers noted above; `create-dmg` is a third-party shell script, not an Apple tool).

## 6. Gotchas for non-root / portable / unsigned builds

**macOS Gatekeeper.** Apple's Platform Security Guide states: "by default, Gatekeeper helps ensure that all downloaded software has been signed by the App Store or signed by a registered developer and notarized by Apple" (Apple Support, "Gatekeeper and runtime protection," https://support.apple.com/guide/security/gatekeeper-and-runtime-protection-sec5599b66df/web) — i.e. notarization is the *default-enforced* path for internet-downloaded software, not merely a nicety. Apple's own Mac User Guide describes the resulting user-facing friction for software that isn't from an "identified developer": "If you try to open an app that isn't registered with Apple by a known developer, you get a warning dialog," and the documented recovery path is System Settings → Privacy & Security → Security → "Open Anyway," entering the login password to confirm (Apple Support, "Open a Mac app from an unidentified developer," https://support.apple.com/guide/mac-help/mh40616/mac) — Apple itself frames this override as risky, noting "overriding security settings to open an app is the most common way that a Mac gets infected with malware." Concretely, this means an unsigned/unnotarized `.dmg`/`.app` from any of the four packaging approaches will trigger this warning and manual override step on every fresh download unless the app is code-signed and notarized — notarization is "effectively necessary for a good UX" even though it is not a hard technical requirement to produce the artifact itself. Of the three dedicated tools, only cargo-packager exposes first-party signing/notarization config fields (`signing_identity`, `notarization_credentials`, §3); cargo-dist has no macOS signing guide at all (§2); cargo-bundle's README does not document a signing workflow either.

**Windows SmartScreen.** Microsoft's own documentation frames SmartScreen as reputation-based: it "provides reputation checks for apps, checking downloaded programs and the digital signature used to sign a file. If a URL, a file, an app, or a certificate has an established reputation, users don't see any warnings. If there's no reputation, the item is marked as a higher risk and presents a warning to the user" (Microsoft Learn, "Microsoft Defender SmartScreen overview," https://learn.microsoft.com/en-us/windows/security/operating-system-security/virus-and-threat-protection/microsoft-defender-smartscreen/). This means a new, low-download-count unsigned `.exe` — exactly the profile of an early-stage OSS release — is likely to trigger the familiar "Windows protected your PC" prompt regardless of which packaging tool built it, because the block is driven by file/certificate reputation rather than by signature presence alone; a newly-issued signing certificate does not immediately grant a "trusted" reputation either. Only cargo-dist documents a concrete, ready-made mitigation (`ssldotcom-windows-sign`, §2); code signing is optional for all four approaches but is the only lever any of them exposes against SmartScreen.

**Linux `.deb` vs. root.** The Debian Policy Manual requires installed package files to be "owned by `root:root`... mode 644 or 755" and to live under `/usr` (not `/bin`, `/lib`, `/sbin` directly) (Debian Policy Manual, "Files," https://www.debian.org/doc/debian-policy/ch-files.html) — this is the conventional, root-owned, system-wide install model that `dpkg -i`/`apt install` assume, and it is in real tension with NFR.2's "never requires root." None of the four approaches changes this fact: a `.deb` built by cargo-packager, cargo-bundle, or hand-rolled `dpkg-deb` is still, by Debian convention, a root-installed artifact. A `.deb` is not inherently a non-root-friendly format; it would need a non-standard, user-prefix-only install flow to satisfy NFR.2, which pushes against the packaging ecosystem's own conventions.

**AppImage sidesteps root by design.** appimage.org states plainly: "AppImages can be downloaded and run without installation or the need for root rights," because "the key idea of the AppImage format is one app = one file. Every AppImage contains an app and all the files the app needs to run," and the only setup step is `chmod a+x` to set the executable bit before running it directly (AppImage.org, https://appimage.org/). This makes AppImage — supported natively by both cargo-packager and cargo-bundle, and buildable by hand via `appimagetool`/`linuxdeploy` — the Linux format that actually satisfies NFR.2 without qualification, unlike `.deb`.

## Summary for the decision ticket

No single dedicated tool cleanly wins all three required outputs. **cargo-dist** has by far the strongest CI story (self-generating GitHub Actions release pipeline, optional built-in Windows SmartScreen signing) and fully nails the Windows portable-archive requirement, but as of this research it has **no native macOS `.dmg`/`.app` or Linux `.deb`/AppImage support at all** — those categories aren't even on its public future-work list — so adopting it alone would leave two of the three required outputs unmet. **cargo-packager** is the only dedicated tool natively covering all three categories in one config (macOS DMG/`.app`, Linux `.deb`+AppImage, Windows NSIS with a non-elevated default install mode), backed by a company (CrabNebula) with a real release cadence, but requires hand-writing your own GitHub Actions workflow around its CLI, and its Windows artifact is an installer rather than a bare portable exe. **cargo-bundle** covers the same three categories as cargo-packager and is more actively committed-to than its "very early alpha" self-description suggests, but carries single-maintainer bus-factor risk, an explicitly unstable config format, no CI-generation help at all, and a known AppImage shared-library gap. **Hand-rolled GitHub Actions scripting** can satisfy all three required outputs exactly as specified (including a truly bare portable Windows exe and an AppImage built via `linuxdeploy`, which handles shared-library collection cargo-bundle doesn't), at the cost of writing and maintaining the most CI code with the least upstream leverage.

The open questions for whoever resolves #12: (1) whether cargo-dist's CI-generation strength is worth pairing it with a second tool (or hand-rolled steps) just for the macOS/Linux outputs it doesn't produce, versus adopting cargo-packager or cargo-bundle as a single tool for all three platforms at the cost of writing the CI workflow by hand; (2) whether the `.deb` vs. non-root tension is acceptable to ship as a secondary/best-effort Linux artifact alongside a primary AppImage (which is the format that actually satisfies NFR.2 unmodified); and (3) whether unsigned macOS/Windows artifacts are acceptable for an initial release given that Gatekeeper and SmartScreen will both present real friction (manual override dialogs) to every first-time downloader regardless of which of the four tools produced the artifact — code signing/notarization is optional to build but not optional for a smooth first-run UX on either platform.
