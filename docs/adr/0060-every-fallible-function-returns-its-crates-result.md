# Every fallible function returns its crate's Result

The [error.rs convention](https://github.com/IanTeda/Personal-Ledger/issues/1274) gave every library crate a private `error.rs` exporting `Error` and `Result<T>`, but it only required the alias to exist, not to be used. Functions still returned `std::result::Result<T, X>`, `io::Result`, another crate's `Result`, per-function error types (`OpenFailure`, `PathRefusal`, `CreationFailure`, `SyncError`, `TokenError`) and `Result<_, String>`, so a caller couldn't tell from a signature which failures it had to handle, and a library error could reach a bin's Message as English text. The [Result map](https://github.com/IanTeda/Personal-Ledger/issues/1309) fixed the rule for every library crate (`crates/libs/*`, `lib-shell` included) and every bin crate (`crates/bins/*`), with no crate exemptions.

We're holding every crate to its own `Result`:

- **The rule.** Every crate, library or bin, has a private `error.rs` exporting `Error` and `pub type Result<T, E = Error> = std::result::Result<T, E>;`, and every fallible function, public or private, returns that `Result`. The only `std::result::Result` left is in the alias's definition. A lookup that may find nothing still returns `Option`.
- **Another crate's error is wrapped, never passed through.** A crate never returns another crate's `Result` or `Error`. Where one of its workflows carries a library error up with `?`, its `Error` holds a `#[from]` variant for it, as `lib-bill-payments` wraps `lib_bills::Error`. A crate may still import another crate's `Error` to match on it, map it or implement its port. An error is never flattened into a string: an infrastructure library (`lib-database`, `lib-rpc`, `lib-locale`, `lib-locale-build`, `lib-tracing`) may keep a `Generic(String)` for its own failures, but it never carries another error's text.
- **Value errors are the one named exception** ([#1310](https://github.com/IanTeda/Personal-Ledger/issues/1310#issuecomment-7070198116)). A **value error** is an enum declared beside one value type, naming only the ways a text or number fails to become that value; it reads no port and does no I/O. A value type's parse or validate function returns `Result<T, ItsValueError>` through its crate's alias, so a caller matches exactly the failures that function can produce. Value errors are part of their value's vocabulary, so any crate may name another crate's value error in a signature; the ban on another crate's `Result` or `Error` does not reach them. A crate's `Error` wraps a value error with `#[from]` only where one of its workflows carries it up with `?`. A refusal that reads ports or the disk (`PathRefusal`) or a port's failure (`CreationFailure`) is not a value error and folds into its crate's `Error`.
- **A port that has to fail returns its feature crate's `Result`.** Ports stay infallible by default ([ADR-0046](0046-per-domain-adapters-hold-rows-in-memory-behind-one-shared-writer.md)); where one can fail, as `LedgerCreation` does, it returns the feature crate's `Result<T>` and the `lib-database` adapter converts its own errors into that crate's `Error`.
- **A bin's `Error` is typed only** ([#1312](https://github.com/IanTeda/Personal-Ledger/issues/1312#issuecomment-7070281723)). It has no `Generic`, and holds the bin's fatal failures (start-up and shutdown) and the typed failures its own functions return, wrapping a library error with `#[from]` only where one of its functions carries it up. The Sync Server has one `Error`, mapped to `tonic::Status` and `IntoResponse` at its boundary.
- **Where a library error stops.** Before the UI runs and after it quits, a library error goes up with `?` to `main`, which returns the bin's `Result<()>`. While the UI runs no caller sits above an event handler, so the error is handled where it's received: its text is logged with `tracing`, and the person sees a Message (an Error Toast, or the status line for a Refusal) chosen by matching on its variant. An error's `Display` text never goes into a Message.
- **Signatures fixed from outside are exempt**, recognised by their syntax with no marker: a method inside an `impl Trait for Type` block (`FromStr`, `TryFrom`, serde, sqlx `Decode` and `Type`, tonic handlers), an error that is an associated type of a generic parameter (`D::Error`), `fmt::Result`, and an error that is the function's or impl's own generic parameter.
- **A convention test enforces it** ([#1313](https://github.com/IanTeda/Personal-Ledger/issues/1313#issuecomment-7070352589)). `lib-database`'s `tests/error_convention.rs` parses every library and bin crate with `syn`, private functions included and test, build, bench, example and generated code skipped. A `Result` in a return type fails if its second argument isn't on the test's `VALUE_ERRORS` list (so `Result<T, Error>` fails even with the crate's own `Error`), and a path-qualified `Result` fails unless it is `crate::Result`. A `use` that imports another crate's `Result` under any name fails. Adding a value error to `VALUE_ERRORS` is a reviewed edit, judged against the definition above. `mise run lint` and CI's lint job run the test.

## Considered options

- **Per-function or per-entity error types.** Rejected: they split one crate's failures across types a caller has to learn one by one, and a Presenter loses the one enum it matches to pick a Message. Value errors are the exception because their callers match exhaustively on the narrow type, and nesting them in the crate's `Error` would force a `_ =>` arm that swallows new variants.
- **Letting a crate return another crate's `Result`.** Rejected: the caller's signature then speaks for a crate it doesn't own, can't grow a failure of its own without changing type, and passes the other crate's errors further up than anything meant to handle them.
- **No ADR, as the error.rs convention chose.** Rejected now: "have the alias" needed no reasons, but "use the alias" carries exemptions (value errors, fixed signatures) that read as arbitrary without the trade-offs behind them.
- **A dylint compiler lint, or ast-grep, for enforcement.** Rejected: a dylint lint is too heavy to keep, and ast-grep is a new tool with no more type information than `syn`.

## Consequences

- The convention test lands before the crates are fixed, with a `PENDING` list of the crates that fail today; the return-type and import rules are off for those crates, and a listed crate that passes fails the test as a stale entry, so the list only shrinks. Until it is empty, code in a `PENDING` crate may still break this rule.
- `syn` sees syntax, not resolved names, so the test checks how a signature is spelt rather than what it resolves to, which is why it also polices `use` of another crate's `Result`; a function written inside a `macro_rules!` body slips past it.
- Error text that reaches a Message today breaks the stopping rule and is fixed in its own ticket, since fixing it changes a Message: the TUI's save-failed Toast ([#1319](https://github.com/IanTeda/Personal-Ledger/issues/1319)), the TUI's configuration-write status line ([#1320](https://github.com/IanTeda/Personal-Ledger/issues/1320)) and the Desktop's Budget history export Toast ([#1321](https://github.com/IanTeda/Personal-Ledger/issues/1321)). `lib-locale` formatting an ICU error into `Generic` is tracked in [#1322](https://github.com/IanTeda/Personal-Ledger/issues/1322), with its `Format(String)` sites.
- `main` still reports a failure in std's `Debug` form; a cleaner report is a behaviour change for its own ticket.
