# Price fetching lives in lib-units behind a transport port, and adapter crates hold the I/O

Units that price themselves ([CORE: Units price themselves from their Price Sources](https://github.com/IanTeda/Personal-Ledger/issues/1367)) need HTTP, and every feature crate is I/O-free ([viper architecture](../development/viper-architecture.md)). [CORE: which crates own the price fetch port, its HTTP adapter and the API key port](https://github.com/IanTeda/Personal-Ledger/issues/1378) decided that `lib-units` owns every fetching rule and that the HTTP itself runs in a new crate, `lib-price-feed`, the second **adapter crate** after `lib-database`.

- **`lib-units` owns fetching.** Fetching writes only to the Units domain, so it needs no feature crate of its own. The Interactors (scheduled rounds, fetch now, backfill, test, Daily and Hourly requests), a read port for the Accounts' Opened dates (answered by a `Stored…Reads` in `lib-database`) and the transport port all live there.
- **The port is plain transport.** `lib-units` builds a `PriceRequest` (method, URL, headers) from a Price Source, its symbols and its key, and sends it without waiting (`send(id, request)`). Every piece of provider knowledge (placeholders, history and batch requests, `Endpoint` headers, parsing, the seven failure reasons, a test's response) stays in `lib-units`, tested on fake responses with no HTTP.
- **Responses come back as an input.** The bin sends `lib_units::PriceResponse { request, outcome }` through the same door as a key press; `lib-units` matches it to its request, parses it, and writes a round through `RecordFetchedPrices` as one commit.
- **Fetching state is one struct, `PriceFetching`**, in `lib-units`: in-flight rounds, back-off, held failures, the call budget and the Daily and Hourly cache. Each Client keeps one per open Ledger, next to `LedgerPorts`, never persisted; the adapter holds none of it.
- **API keys:** `lib-units` declares `PriceSourceKeys::key(source) -> Option<SecretString>`, `None` meaning missing or undecryptable. `lib-database` answers it, decrypting with the API key secret the bin passes into `LedgerPorts::new`.
- **`lib-price-feed`** implements the transport port over async `reqwest` (rustls on ring) on the Tokio handle the bin gives it, with a request timeout, returning status and body, or a transport error, over a channel the bin polls. It knows nothing about providers. Only the bins build it, and they hold it beside `LedgerPorts`, not inside it, since it holds no stores.

## The dependency rule

`viper_dependencies.rs` gains an `ADAPTER_CRATES` list (`lib_database`, `lib_price_feed`): no crate in `FEATURE_CRATES` or `SHARED_CRATES` may depend on one, and `lib_price_feed` may depend on no feature crate but `lib_units`. `deny.toml` lets only `lib_price_feed` and `bin_sync_server` (its test-only use) wrap `reqwest`, and only `bin_desktop` and `bin_tui` wrap `lib_price_feed`. A future crate doing I/O for a feature crate joins `ADAPTER_CRATES`.

## Considered Options

- **Fold the adapter into `lib-units`, behind a Cargo feature.** Rejected: `reqwest`, rustls and `tokio` would compile into everything that depends on `lib-units`, and feature unification turns the feature on anyway.
- **Put the HTTP adapter in `lib-database`.** Rejected: it holds no stores, and `lib-database` would grow a network stack unrelated to persistence.
- **A smart port that takes a Price Source and returns prices.** Rejected: provider knowledge would move into the adapter, out of reach of `lib-units`' tests, and Test would need a second path to show the raw response.
- **A feature crate of its own for fetching.** Rejected: fetching writes only Units, so it is not a cross-domain workflow.

## Consequences

- `lib-units` stays I/O-free and its fetching rules are tested with no network.
- Both Clients get fetching from the same Interactors; each only runs the minute timer, polls the response channel and hands responses to the door.
- `keyring` is not a dependency.

## Amendment: a response lands through one call, and fetching never writes

Settled by [#1411](https://github.com/IanTeda/Personal-Ledger/issues/1411) on the [deepening map](https://github.com/IanTeda/Personal-Ledger/issues/1410). After #1406 split `PriceFetching` into private parts, its caller still asked which kind a response was and drove each part's landing, history reading and bookkeeping by hand. Now every response, whether a test, finer prices, history or a round, lands through one `PriceFetching::land`, which is lent the Units read-only. Inside it, fetching checks that each Unit is still active and on the same link, reads and folds history, and keeps all of its own bookkeeping (backoffs, 429 holds, empty and failed weeks, the next history request). It hands back a `Landing`: nothing, a test's result, a round's prices (with a round outcome only for a Fetch now, whose priced Units fetching has already queued to backfill), or a Unit's history weeks.

Fetching never writes the Ledger. `RecordFetchedPrices` and `RecordPriceHistory` remain the Interactors that write and log ([ADR-0047](0047-interactors-log-ledger-changes-and-presenters-never-log.md)), taking only what the `Landing` names, and the Presenter tells. Letting fetching write through the Units ports was rejected because it would make fetching a Ledger writer that logs changes outside an Interactor. Lending it the Units read-only is what breaks the old loop, where the writer called back into fetching to note how each Unit fared.

Backfill is planned the same way, settled by [#1412](https://github.com/IanTeda/Personal-Ledger/issues/1412). One `PriceFetching::backfill` is lent the Units ports read-only and applies every planning rule from ADR-0043's backfill amendment inside it: which Units want history, the floor, the source's depth, the weeks a provider answered with nothing, the retry rule, Key missing, and oldest gap first. Backfilling writes nothing to the Ledger, so there is no Interactor for it and the Presenter calls fetching directly. The scheduled check is planned inside fetching too, by the rule below, and asks one `due` question per Unit rather than piecing together its in-flight, backoff and relink state.

Which planners are fetching's is settled by [#1429](https://github.com/IanTeda/Personal-Ledger/issues/1429). Price fetching has an Interactor only for a write to the Ledger (`RecordFetchedPrices`, `RecordPriceHistory`) or for a fetch a person asks for by name: Fetch now, Fetch source, Fetch all and a Price Source test. This keeps the architecture's one Interactor per user intent. Every other planner writes nothing and is started by the clock, a Ledger open, a landed response or a view's state, so it lives inside `PriceFetching`: the scheduled check, the backfill on open, a Fetch now's follow-on backfill and the finer prices a Unit prices view asks for. Fetching is lent the full Units ports, which are read-only by type because every write needs `&mut`, so each planner reads for itself rather than taking what its caller pieced together. A Presenter holds no planning rule. It keeps only its view's state (the window and the grain, whether a test can run) and passes it to one fetching call. Keeping the scheduled check as an Interactor beside Fetch now was rejected: it is no one's intent and writes nothing, the same shape as the `Backfill` Interactor deleted by #1412.

Fetching's facade is settled by [#1430](https://github.com/IanTeda/Personal-Ledger/issues/1430). The rest of the crate starts or lands work through its doors: `ask_round` (Fetch now and Fetch source, always asked), `send_test` (a Price Source test, handed the test's facts, which builds its requests itself), `land`, `check`, `backfill` (the backfill on Ledger open), `ask_fine`, `release`, `drop_test` and `key_stored`. It draws from its queries: `fine_state` (asked by Unit, grain and window, like `ask_fine`), `testing`, `source_testing`, `test_result`, `wait_begun`, `source_in_flight` and the public reads of in-flight and last-fetch state. Everything else in `fetching/`, including requests, fetching keys and the backfill's planner variants, is private to it. Whether a price is out of date is a question about the Unit, so it lives on the Unit model, not in fetching.

Both Clients host fetching through one module, settled by [#1413](https://github.com/IanTeda/Personal-Ledger/issues/1413). A Client holds one `LedgerPrices` per Open Ledger. It owns the shared fetching and the feed's response channel, and its interface spells out the hosting rules that used to live only in doc prose: `open` runs the open check and backfill, `check` runs on each tick of the Client's minute timer, `land_next` lands one response per input, and `pump` sends the queued calls. The Consequence above that each Client "runs the minute timer, polls the response channel and hands responses to the door" now reads: each Client runs the minute timer and, on its poll, calls `land_next` once per response as one input, then `pump`. It never builds `PriceFetching` or reads the channel itself. Each Client keeps its own timer, its own clock and the way it commits and passes on notices.

A Price Source test has one home, settled by [#1414](https://github.com/IanTeda/Personal-Ledger/issues/1414). The presenter module `PriceSourceTest` is the only caller of the `TestPriceSource` Interactor. It owns the test's lifecycle: sending it, the last test's request, dropping that request on a retest or when its form closes, and turning a landed result into the form's view or into the Toast for `t` on a row. The form holds one `PriceSourceTest` and keeps only what depends on its fields: whether a test can run and why not. The Units page's `t` is a one-shot `PriceSourceTest::in_background`. Results are pulled, not pushed: a form's test lands as `Landing::Nothing` and stays held in fetching's `PriceTests` until the form reads it, and only a test answered by a Toast returns `Landing::Test`. Pushing results to the form was rejected because `LedgerPrices` would then have to keep a registry of open forms that nothing else needs. `PriceTests` stays inside fetching, and the facade does not grow.
