# One generic Entity hosts each Presenter, through `lib-viper`'s Presenter contract

Every Presenter already has `handle(event, router)` and `view_model()`, but nothing named that contract, so the Desktop hosted each Presenter in gpui by hand. Each domain copied one template: a page Entity with its own take, send, handle and `dialog_landed`, the same forwards from `module_key` and `module_command` to its keymap, and a Dialog Entity whose `HostedDialog` impl repeated `presenter.handle(Event::Input(input), &mut router); self.closed(router)` (22 impls, 17 with that body). Five modules held an enum of Presenters in one Dialog Entity only because each module had one Entity type, and the bin built each Dialog's hints while page hints came from the view model. Decided in the [#1077](https://github.com/IanTeda/Personal-Ledger/issues/1077) grilling on the [#1075](https://github.com/IanTeda/Personal-Ledger/issues/1075) route; ADR-0055 had already moved write tracking and announcing into the commit and `send`.

## Decision

- **`lib-viper` names the contract.** `Presenter` has associated types `Event`, `ViewModel` and `Router: ?Sized` (`dyn TagsRouter`, `dyn DialogRouter<TagsOutcome>`), and `handle`, `view_model` and `takes` (default `true`). Associated types, not generics: each Presenter has exactly one of each.
- **A page Presenter** (`PagePresenter`) adds its `Outcome`, `dialog_closed(Option<Outcome>) -> Event` and `keymap()`. The Presenter owns its keymap, so the host turns a chord or a palette command into an event through it. A Dialog from another module maps its outcome into the page's `Outcome` at open.
- **A Dialog Presenter** (`DialogPresenter`) adds its `Outcome`, builds its Input, Confirm and Cancel events, and answers `can_confirm`, `close_open_select` and `steps_list`. A Dialog confirms only through `handle(Confirm)`; no Presenter has a separate `confirm(router)`. A Dialog's hints are in its view model, built from a `lib-viper` `DialogKeys` value (the chords of the Dialog command names `lib-viper` owns) that its Router hands it at open, as a page's hints already are. The shared hint Messages are `lib-locale`'s.
- **The trait methods are the only methods.** The inherent `handle`, `view_model`, `takes` and `confirm` go, so a Presenter is called one way, by both Clients and its tests.
- **One generic Entity each.** The Desktop hosts every page Presenter in `ModulePage<P>` and every Dialog Presenter in `ModuleDialog<P>`. The page Entity owns the Presenter, its focus flag, its `notify_on` subscriptions and the take, send and handle path; it never counts or announces a write (ADR-0055). A domain implements `PageView` on its Presenter type (its `Setup`, the `Domain`s it repaints on, how its Router is built, `render`, and optionally `heading_meta`, `side_pane` and `reveal`) and `DialogView` on each Dialog Presenter (`render`, `readback`, `kind`), and keeps its Router.
- **One Presenter per hosted Dialog.** A module with several Dialogs hosts each Presenter in its own `ModuleDialog<P>`; there is no enum of Presenters.
- **Main Views and Settings pages share the page Entity.** It implements today's `Page` and the main-View methods `ActiveViewEntity` forwards to, and carries none of the pre-module key paths (`handle_key`, `key_ahead`, `search_key`). Joining those two hosting interfaces is [#1079](https://github.com/IanTeda/Personal-Ledger/issues/1079)'s.
- **Migration.** `ModuleDialog<P>` implements `HostedDialog` and `ModulePage<P>` implements `Page`, so the Dialog host and `route_key` are unchanged while generic and hand-written Entities live side by side. Tags and Tag Removal set the pattern; once the last Dialog moves, `HostedDialog` has no other implementation and is deleted. Inventory, Display and Units keep hand-written pages until #1079 retires the key paths they still use, though their Dialogs move.

## Considered Options

- **Keep a hand-written Entity per domain**, as ADR-0037 set up. Rejected: with the commit announcing writes (ADR-0055), what was left in each Entity was the same plumbing, copied into every new module.
- **Generic type parameters on the traits** (`Presenter<E, V, R>`). Rejected: a Presenter has one event, view model and Router, so associated types say so and keep the bounds short.
- **One Dialog Entity per module, holding an enum of Presenters.** Rejected: the enum is chosen at open and never changes, so it only existed to give each module one type; the generic host makes it unnecessary.
- **Hosting hooks for the pre-module key paths on the generic page.** Rejected: it would carry into the new type the paths #1079 retires.

## Consequences

- A new module writes its Presenters, a `PageView` and a `DialogView` per Dialog, and its Router; no Entity, take, send, handle or `HostedDialog` impl.
- Pages and Dialogs that hold view-only state beside their Presenter (scroll handles, a select's list window, a row menu's position, a popover's left edge) need it held by the generic Entity; how is settled in the first ticket.
  - Settled in [#1087](https://github.com/IanTeda/Personal-Ledger/issues/1087): `PageView` and `DialogView` each have `type Widgets: Default`, which the generic Entity owns and passes `&mut` to `render`, and to an optional `PageView::menu_at` that records where a row's menu was opened. The Presenter never sees it. Merge tags' two list windows are its `Widgets` (`ListWindows`), so it needs no enum variant to carry them; a View with none uses `()`.
- The Router is a generic associated type, `type Router<'r>: ?Sized` (`dyn TagsRouter + 'r`), not `type Router: ?Sized`: a trait object in an associated type defaults to `'static`, and the Desktop's Routers borrow the call's gpui `Context`, so `DialogPresenter` bounds it as `for<'r> Presenter<Router<'r> = dyn DialogRouter<Self::Outcome> + 'r>` and `PageView::with_router` lends the Router to a closure ([#1087](https://github.com/IanTeda/Personal-Ledger/issues/1087)).
- The generic Entities read what the status line shows through the bin traits too: `PageView::status` gives a page's hints and right-hand text, and `DialogView::hints` a Dialog's, both from the view model.
- The Categories Dialog's confirm takes its Category budget ports as an argument, so it moves only once [#1078](https://github.com/IanTeda/Personal-Ledger/issues/1078) puts that write behind a port the Presenter holds.
- The UI tests don't change: `DialogReadback` is filled from `DialogView::readback`, and the `PageSnapshot` types read `view_model()` through the generic page. Shrinking the harness is [#1080](https://github.com/IanTeda/Personal-Ledger/issues/1080)'s.
