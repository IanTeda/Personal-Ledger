# Payee as a first-class entity, with rename aliases, not a free-text field

`CONTEXT.md` and `docs/product-requirements.md`'s Constraints originally decided Payee was not a separate entity in V1: `Transactions.payee` was a plain nullable `TEXT` column, matched by exact text only, with no normalisation. Building CC-TUI-007's suggestion UI (issue #71) surfaced a case that decision didn't cover well: renaming a payee (e.g. a shop trading as "Kmart" starts appearing as "Kmart AU" on bank feeds) had no way to reconcile old and new spellings — every past Transaction would keep saying "Kmart" forever, and typing "Kmart" again wouldn't surface "Kmart AU" as a suggestion, defeating the point of totalling spend by payee.

We reversed the original decision: Payee is now a first-class entity (`payees`: `id`, `name` — case-insensitively unique, `is_active`, `updated_on`), and `transactions.payee_id` is a nullable foreign key to it, replacing the free-text column. Renaming a Payee changes exactly one row and is reflected everywhere it's referenced via the join, with no bulk `UPDATE` of Transactions needed — the alternative (keeping free text and bulk-rewriting every matching Transaction on rename) was rejected as a heavier, easier-to-get-wrong operation for the same result. A `payee_aliases` table (`id`, `payee_id`, `pattern`) records the prior name whenever a rename happens, so a suggestion typed against an old name still resolves to the current Payee; a Payee not yet seen is auto-created the first time its name is entered on a Transaction, keeping payee creation invisible in the common case. `pattern` is stored as a regex — though V1 only ever auto-generates an exact-match pattern from the literal old name — so a future cycle can let a pattern be hand-broadened (e.g. to catch several old variants at once) without a schema change.

The existing `transactions` table (shipped in the Transactions build ticket, #70) is rebuilt by a new migration rather than edited in place, backfilling a canonical Payee for every distinct existing `Transactions.payee` value and pointing each Transaction's new `payee_id` at it. Payee keeps the same lifecycle as Unit/Category/Account: `is_active` toggling only, no hard delete once a Transaction references it (enforced by the FK-enforcement pragma added in #69).
