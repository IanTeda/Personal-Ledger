# Payee as a first-class entity, with rename aliases, not a free-text field

`CONTEXT.md` and `docs/product-requirements.md`'s Constraints originally decided Payee was not a separate entity in V1: `Transactions.payee` was a plain nullable `TEXT` column, matched by exact text only, with no normalisation. Building CC-TUI-007's suggestion UI (issue #71) surfaced a case that decision didn't cover well: renaming a payee (e.g. a shop trading as "Kmart" starts appearing as "Kmart AU" on bank feeds) had no way to reconcile old and new spellings — every past Transaction would keep saying "Kmart" forever, and typing "Kmart" again wouldn't surface "Kmart AU" as a suggestion, defeating the point of totalling spend by payee.

We reversed the original decision: Payee is now a first-class entity (`payees`: `id`, `name` — case-insensitively unique, `is_active`, `created_on`, `updated_on` — the same shape as Units/Categories/Accounts, since a Payee is mutable, unlike a Transaction), and `transactions.payee_id` is a nullable foreign key to it, replacing the free-text column. Renaming a Payee changes exactly one row and is reflected everywhere it's referenced via the join, with no bulk `UPDATE` of Transactions needed — the alternative (keeping free text and bulk-rewriting every matching Transaction on rename) was rejected as a heavier, easier-to-get-wrong operation for the same result. A `payee_aliases` table (`id`, `payee_id`, `pattern`) records the prior name whenever a rename happens, so a suggestion typed against an old name still resolves to the current Payee; a Payee not yet seen is auto-created the first time its name is entered on a Transaction, keeping payee creation invisible in the common case. A `payee_aliases` row is write-once and never updated, so — like Transactions — it carries no separate timestamp column; its `id`'s UUIDv7 stands in for when the rename happened. `pattern` is stored as a regex — though V1 only ever auto-generates an exact-match pattern from the literal old name — so a future cycle can let a pattern be hand-broadened (e.g. to catch several old variants at once) without a schema change.

The existing `transactions` table (shipped in the Transactions build ticket, #70) is rebuilt by a new migration rather than edited in place, backfilling a canonical Payee for every distinct existing `Transactions.payee` value and pointing each Transaction's new `payee_id` at it. Payee keeps the same lifecycle as Unit/Category/Account: `is_active` toggling only, no hard delete once a Transaction references it (enforced by the FK-enforcement pragma added in #69).

## Amendment: hand-authored match rules are Payee Aliases

The Desktop Payees Surface ([#281](https://github.com/IanTeda/Personal-Ledger/issues/281), settled in [#282](https://github.com/IanTeda/Personal-Ledger/issues/282)) adds hand-authored **match rules**: raw bank-statement strings that map a line to a Payee on import. Rather than a second table, a match rule *is* a Payee Alias — the future hand-authored pattern this ADR left room for — and a rename still auto-adds one.

- **One matching test for every alias:** case-insensitive *contains* of the alias against the raw text, whether the alias came from a rename or was typed by hand. There is no kind flag; contains is a superset of the exact match a rename alias used to need. `pattern` keeps its column name but now holds a literal substring, not a regex — nothing compiles or matches a regex.
- **Normalisation:** an alias is stored trimmed and upper-cased (so storage and display agree), deduplicated within its Payee; empty or whitespace-only input is ignored.
- **Unique across Payees:** the same alias cannot sit on two Payees; adding one another Payee owns is rejected with an error naming that Payee. Renaming a Payee to a name that equals another Payee's alias is rejected the same way; renaming it to one of its *own* aliases drops that alias (and the old name becomes a new alias as usual).
- **Which Payee wins:** when several aliases are contained in the raw text, the **longest** matching alias wins, then the Payee name alphabetically as a tie-break — so a short `BP` cannot steal a line a longer alias describes.
- **Editable:** every alias, rename-generated or not, is an ordinary removable chip in the Edit Payee dialog. Removing one never changes past Transactions, which link to the Payee by id. An alias is still write-once — edited only by removing and re-adding.
- **Not a search key:** Transactions search and the payee filter match a Split's current Payee name (or id), not its aliases; aliases resolve raw text (import, typed entry) only.

A Payee also gains an optional **default Category** (a leaf Category) that pre-fills only *new* Splits for that Payee; changing it never touches existing Splits, and a deactivated default Category still stands but is shown as inactive.
