# Built-in Price Sources are code referenced by id, and API keys sync encrypted

*Retitled from "…and API keys never sync" by [CORE: amend ADR-0043 and ADR-0052 for Units that price themselves](https://github.com/IanTeda/Personal-Ledger/issues/1381): the body below records the original decision, and the amendments supersede it where they say so.*

A Price Source is structured rather than one URL: an address, a request template with `{symbol}` and `{quote}` placeholders, a price path (a JSON pointer into the response), its authentication (the key parameter's name only), an update interval and the Unit Kinds it can price. We decided that the built-in sources (CoinGecko, Yahoo Finance and Frankfurter to start) are a `const` table in `lib-units`, always listed on the Units Settings page, and that the Ledger stores only a built-in's id with the user's own name and update interval for it. A built-in can be renamed and retimed but never deleted; only a Custom source, which stores its own address, request, price path and authentication, is added or deleted, and deleting one moves its Units to Manual entry. A Unit's symbol and quote Unit live on the Unit's link to its source, not on the source. API keys are never part of the synced Ledger: each Client keeps its own, as it does for AI Connections ([ADR-0034](0034-ai-connections-are-per-client-and-assistant-access-starts-read-only.md)).

Referencing built-ins by id means an app update that fixes a provider's address or response shape fixes it on every Ledger at once, with no stored copy to migrate or drift. Code rather than data files keeps the table compile-checked and the crate I/O-free.

## Considered Options

- **Copy a built-in's fields into the Ledger when it is added.** Rejected: a provider's API change would leave every existing Ledger holding a broken copy until the user re-entered it.
- **Ship built-ins as data files compiled by `build.rs`, as Colour Themes are.** Deferred, not rejected: worth it only if sources should ship without a Rust change.
- **Sync API keys inside the Ledger.** Rejected: it would spread secrets through the Sync Server's Change Set store.

## Consequences

- The Price Sources table's **+** adds a Custom source only, and a built-in row has no Delete.
- ~~Where a Client stores an API key is still open.~~ Closed: API keys are stored encrypted in the Ledger and sync ("API keys sync, encrypted with the API key secret" below).
- ~~Where fetching runs, and how a fetched last price syncs, are still open; until then Test is not built.~~ Closed: fetching runs in each Client ("where and when fetching runs" below, and [ADR-0062](0062-price-fetching-lives-in-lib-units-behind-a-transport-port-and-adapter-crates-hold-the-io.md) for its crates); a fetched Weekly Price is an ordinary Unit write that syncs whenever Unit writes do ([ADR-0052](0052-units-keep-a-weekly-price-history.md)'s amendment); Test is decided in [CORE: Test price source and Test with symbol](https://github.com/IanTeda/Personal-Ledger/issues/1373). Nothing in this ADR is left open.

## Amendment: API keys default to the OS keychain

Decided in the [VIPER transition grilling](https://github.com/IanTeda/Personal-Ledger/issues/745). A Client keeps each API key in the OS keychain through the `keyring` crate: Keychain on macOS, Credential Manager on Windows, Secret Service (gnome-keyring or KWallet) on Linux. The key never goes into the database, the static config file or the Git backup. A key can't be hashed, since it has to be sent in plain form, and a secret in the config file sits on the same disk as the database it would protect. A password in the UI was rejected: it adds a prompt at every start, and a forgotten password loses every key. On a machine with no keychain, such as a headless Linux machine without Secret Service, the key field says so and stores nothing, and that source's Units stay on Manual entry; an encrypted-file fallback waits until someone needs it. Building this belongs with the Price Source fetching work, since nothing reads a key until fetching exists. The `price_sources` table holds Custom sources only and never a key.

## Amendment: Units keep Weekly Prices

The "last price only" on a Unit's link is superseded by [ADR-0052](0052-units-keep-a-weekly-price-history.md): a Unit keeps a Weekly Price per ISO week, and its last price is the newest one's close.

## Amendment: where and when fetching runs

Decided in [CORE: where and when Unit prices are fetched](https://github.com/IanTeda/Personal-Ledger/issues/1074). Fetching runs in each Client while a Ledger is open: on open, then every minute, whatever View is showing. `lib-units` decides what is due and writes the result; the HTTP request goes through a port, async on the Tokio runtime both bins already start; the Clients only run the timer and hand results back. A Unit is due when it has no Weekly Price for the current week, or when its newest Weekly Price was written longer ago than its source's Updates interval (Daily is 24 hours), so the schedule comes from the Ledger itself with no last-fetched record, and a price another Client fetched and synced counts as fresh. Due Units are fetched together per source. Each Client keeps, in memory only, which sources have a fetch in flight and when each was last tried, and a source that failed waits at least its own interval before it is tried again. A source's round comes back as one input through the same commit door as a key press, writing every fetched Unit at once and skipping any Unit gone, deactivated or relinked since the fetch went out. Units on Manual entry, deactivated Units and Units on a source set to Manual only are never fetched on schedule. A fetched price goes into the week of the Clock's day. (Due-ness amended by the backfill amendment below: "no Weekly Price" became "no Weekly Price for the current week", so a backfilled last week never hides a missing current price.) Daily and Hourly Prices are read through the same port for a View to show, never written, and cached in memory by (Unit, grain, window): a past window for the Ledger's session, the current one for 15 minutes ([CORE: Daily and Hourly Prices a View can ask a Unit for](https://github.com/IanTeda/Personal-Ledger/issues/1376)).

## Amendment: which built-ins stay, and what an Endpoint carries

Decided in [CORE: which built-in price providers stay, given their terms and limits](https://github.com/IanTeda/Personal-Ledger/issues/1375), from what [CORE: what the built-in price providers offer today](https://github.com/IanTeda/Personal-Ledger/issues/1368) found. All three built-ins stay.

- **Yahoo Finance** stays a normal built-in, although its terms forbid automated collection: it is the only keyless source with long equity history, and it is tolerated in practice. Its chart endpoint refuses a request with no `User-Agent`, so an `Endpoint` gains fixed request headers (a name and a value, never secret), which a Custom source can use too; Yahoo's sends `User-Agent: Personal-Ledger/<version>`, our own name rather than a browser's. The Units page says the API is unofficial and may stop working. Demoting it to opt-in and dropping it were rejected.
- **CoinGecko** stays keyless by default, with an optional free Demo key sent in the `x-cg-demo-api-key` header for 100 calls a minute instead of about 5, so `PriceSourceAuth` gains a key that is optional, and a built-in can take a key. "Powered by CoinGecko" shows in its detail pane on Units Settings and in the pane of every Unit it prices. Its terms ask that cached data refresh every 24 hours; a personal Ledger keeps its Weekly Prices anyway, and we accept that.
- **Frankfurter** moves to v2 at `https://api.frankfurter.dev`: request `/v2/rate/{symbol}/{quote}`, price at `/rate`, blended same-day rates for 219 currencies. v1 is ECB only and deprecated. Its Updates stay Daily.
- **Placeholders** gain `{symbol_lower}` and `{quote_lower}`, since CoinGecko keys its response by the lower-case quote; the built-ins stay plain data rather than a case written into code.
- **History:** each built-in gains an optional history request beside its price request, with `{from}` and `{to}` date placeholders and a path to the series: CoinGecko's `market_chart/range` (365 days on the free tiers), Yahoo's chart with `period1`, `period2` and `interval=1d` (daily, changed from `1wk` by the backfill amendment below), and Frankfurter v2's time series. How its rows become Weekly Prices is the backfill amendment below; a Custom source gets one too (see "a Custom source's history request" below).

## Amendment: API keys live in the Ledger, encrypted

Decided in [CORE: which built-in price providers stay, given their terms and limits](https://github.com/IanTeda/Personal-Ledger/issues/1375), superseding "API keys default to the OS keychain" above, to keep things simple: one store on every platform, with no keychain to be missing. A Client's static configuration holds an encryption key, and each API key is stored encrypted with it in the Ledger file. The objections the keychain amendment recorded still stand and are accepted: a copy of the configuration file and the Ledger together reveals every key. Whether the encrypted keys sync, and so whether every device on a Ledger shares one configuration key, how that key is made and what a Client does without one, are open in [CORE: entering and removing a Price Source's API key](https://github.com/IanTeda/Personal-Ledger/issues/1374).

## Amendment: backfilling a Unit's history

Decided in [CORE: backfill rules for a Unit's Weekly Prices](https://github.com/IanTeda/Personal-Ledger/issues/1370). A Unit on a fetching source **backfills** its missing past weeks from its source's history request.

- **Wanted range:** from the week holding the Unit's floor to last week. The floor is the earliest Opened date of the Accounts in the Unit, deactivated ones included, or the Unit's creation date when it has no Accounts. The current week is never backfilled, since the scheduled fetch owns it. A 52-week minimum was rejected.
- **Derived, not triggered:** a Unit needs history when a week in its wanted range has no Weekly Price. Linking, an earlier Account, a quote change (which clears the weeks) and weeks missed while closed all reduce to that one rule, with no bookkeeping.
- **Gaps only:** a backfill never overwrites a week that has a Weekly Price, so a hand-set week survives relinking and a week built from fetches keeps its shape. Weekly Prices gain no provenance column. The write checks again that each week is still empty, so a week synced meanwhile wins.
- **Grain:** every history request asks for daily points (Yahoo's `interval=1wk` becomes `1d`, since its weekly bars don't start on Monday for every market). The adapter returns points dated by the provider's trading day, not UTC, and `lib-units` folds each ISO week: open from the first point (its open, else its close), close from the last, high and low from the extremes. A week with no points stays empty.
- **Provider limits:** a built-in carries a history depth where its provider has one (CoinGecko 365 days), so no request is sent that is bound to be refused. Weeks the provider can't supply stay empty with no error, and each Client remembers in memory which ranges came back empty, not asking again until the Ledger is reopened or the Unit's link changes.
- **When it runs:** on Ledger open (app start, `:open`, `:new`), after each sync completes (a hook for the sync effort), and after a fetch now of that Unit. Never on the minute check: there is no backfill job. An edit that opens a gap waits for one of these.
- **Pacing and retry:** one history request in flight per source, one Unit at a time, oldest gap first, sources in parallel; it shares the source's in-flight and back-off bookkeeping. A Unit whose history request fails, or whose source is rate limited, retries every 10 minutes until last week has a Weekly Price; older gaps wait for the next open or sync.
- **Which Units:** never Manual entry, deactivated Units or the base Unit. A Unit on a source set to Manual only backfills only through fetch now.
- **Writing:** a new `lib-units` Interactor, `RecordPriceHistory`, writes one Unit's weeks in one commit through the usual door, skipping a Unit gone, deactivated or relinked since the request went out. Backfilled weeks carry their real `written_at`, which is why due-ness now asks for a Weekly Price in the current week.
- **Week of a fetched price:** stays the Clock's day, not the provider's as-of date: a Monday fetch of Friday's rate is this week's first price, and reaching back into an ended week would contradict its being final.
- **What shows:** a backfill never Toasts, never sets `fetch failed` and never touches the Last fetch fact. The Unit's Weekly Prices table shows *Fetching history…* while one is in flight, and *History failed · <reason> · tries again in N minutes* after a failure. Rate limited and Offline back off the source for everyone. A fetch a person asks for (fetch now, `units fetch-all`) shows an Info Toast as each source round starts, *Fetching prices from CoinGecko…*, and a status-line message naming the sources still in flight, *Fetching prices from CoinGecko, Yahoo Finance…*, then *Fetching price history for BTC from CoinGecko…* during its backfill, cleared when everything has landed, beside the outcome Toasts already decided. Scheduled rounds and open- or sync-time backfills stay silent apart from the in-place rows.

## Amendment: API keys sync, encrypted with the API key secret

Decided in [CORE: entering and removing a Price Source's API key](https://github.com/IanTeda/Personal-Ledger/issues/1374), settling what the amendment above left open. **The title's "API keys never sync" no longer holds:** a key's ciphertext syncs with the Ledger; only the secret that decrypts it stays on each device. The rejected option "Sync API keys inside the Ledger" is accepted in this form, because the Change Set store now carries ciphertext only.

- **API key secret:** each Client's static configuration holds one, `[Secrets] api_key_secret` (env `PERSONAL_LEDGER_SECRETS__API_KEY_SECRET`), used for every Ledger on that device. A person may put their own string there first; otherwise the Client generates a 256-bit random one (base64url) through `ConfigWriter` the first time a key is saved on a Ledger with no key rows. The encryption key is derived from it with Argon2id, so a weak typed string is still stretched. Every device on a Ledger needs the same secret, which a person copies into each device's configuration by hand: the app never shows it, and Settings › Data & backup shows only its fingerprint (*Encryption key · 3F9A-21C0*, or *Not set*). A Copy action was rejected, since it puts the secret on the clipboard.
- **Table and cipher:** `price_source_keys` (price source id as primary key, built-ins included, with no foreign key, like `units.price_source_id`; nonce, ciphertext, `key_check`, timestamps). XChaCha20-Poly1305 (`chacha20poly1305`), a fresh random nonce on each write, the source id as associated data so a row moved onto another source won't decrypt. `key_check` is a keyed fingerprint of the derived key, not secret. Encryption happens in `lib-database`'s adapter; `lib-units` sees only `SecretString` through its `PriceSourceKeys` port, which `lib-database` answers ([ADR-0062](0062-price-fetching-lives-in-lib-units-behind-a-transport-port-and-adapter-crates-hold-the-io.md)).
- **One secret per Ledger:** a Client writes a key only when its secret's fingerprint matches the `key_check` on the Ledger's rows, or the Ledger has none, and generates a secret only in that second case, so a Ledger never needs two secrets. On a mismatch the key field is off and says the Ledger's keys were saved with another device's secret, to be copied into this device's settings. **Remove all API keys** on Data & backup, behind a confirm Dialog, deletes every row everywhere: the way out when the secret is lost.
- **A key that won't decrypt** (no secret, a different one, or a mismatch) counts as no key: fetches and tests read **Key missing**, CoinGecko's optional key falls back to keyless, Units keep their links and only stop fetching, and the pane's **API key** fact says *Saved, but can't be read on this device*. The row is never deleted on its own.
- **The key field:** always masked, with no reveal. In Edit, a saved key shows as the empty field's placeholder *Key saved · leave blank to keep it*; blank keeps it, typed text replaces it on Save. **Remove key** beside the field clears it, since blank can't mean both. A built-in that takes an optional key (CoinGecko) gets the same field in its Edit Dialog. The pane gains an **API key** fact: *Saved*, *Not set*, or *Saved, but can't be read on this device*. Test with symbol's rules stand: the typed key, else the stored one, else **Key missing**; a test never stores a key.
- **Writes:** the key is written in the Dialog Save's commit; deleting a Custom source, or switching its authentication to None, deletes its key in the same commit; changing only the key's name or placement keeps it. Key writes are never undoable: undoing a Save restores the source and leaves the key. Rows sync last-write-wins per source id like any row, and a delete syncs.
- **Never leaked:** the key is a `secrecy::SecretString` from field to HTTP adapter, exposed only where it goes into the request; the derived key is a zeroized `SecretBox`; `Config`'s `Debug` and trace fields redact the secret; no span records a key, secret, nonce, ciphertext or decrypted value, only the source id and saved or removed; a response shown in a test masks any echo of the key.
- The `keyring` crate is no longer needed.

## Amendment: a Custom source's history request

Decided in [CORE: whether a Custom Price Source gets a history request](https://github.com/IanTeda/Personal-Ledger/issues/1380). A Custom source can have a history request, optional, so it can backfill and offer Daily Prices like a built-in.

- **One type for every source:** the history request is one `HistoryEndpoint` (request, series path, date path, price path and series shape), which the Custom source Dialog edits in its own *History* section under the price request and the built-in table fills in as plain data. CoinGecko and Frankfurter use the shapes a Custom source can; Yahoo's parallel `timestamp` and `close` arrays are a columns shape only the built-in table uses, which the form never offers.
- **Series shapes a person can type:** the series path points at either an array of points, where the date path and price path are JSON pointers relative to each point (CoinGecko's `[ms, price]` pairs are `/prices`, `/0`, `/1`), or an object keyed by date, where an empty date path means the key. The columns shape was rejected for Custom sources: a third set of fields for one provider's layout.
- **Close only:** a Custom series gives each point's close and nothing else; a week's open, high and low fold from the daily closes, as close-only points already do.
- **Dates:** `{from}` and `{to}` fill as ISO dates, and new `{from_unix}` and `{to_unix}` as Unix seconds. A point's date is read without a format field: an ISO date or datetime string gives its date part, and a number is Unix seconds, or milliseconds above 10¹¹.
- **Daily only:** a Custom history request gives Daily Prices, for backfill and the Unit prices view's Day grain, and never Hourly, so `z` skips Hour. Several points on one day fold as a week does, the last being the close.
- **No history depth:** a Custom source declares none. A range that comes back empty is remembered in memory as for the built-ins, so a missing depth costs at most one request per Unit per session.
- **Tested inline:** Test price source and Test with symbol run the history request after the price request passes, asking for the last 14 days and showing *History · 10 points · newest 2026-11-20 · 1.2345*. Its failures are the same seven reasons, an empty series reading as No price, and the collapsed response gains a history part that opens by itself on failure. A test writes nothing.
- **Without one:** a Unit on a Custom source with no history request never backfills: its unfilled past weeks stay empty, it never shows *Fetching history…* or *History failed*, and its Weekly Prices table shows one muted line, *<source> has no history request, so past weeks fill only by hand*. Out of date is unaffected, since it reads only the newest price. The Unit prices view's `z` offers neither Day nor Hour.

## Amendment: batching and throttling

Decided in [CORE: batching price fetches and backing off when a provider throttles](https://github.com/IanTeda/Personal-Ledger/issues/1379).

- **Batching, built-ins only:** a built-in can declare a batch request in code beside its single request, with list placeholders (`{symbols}`, `{quotes}`), the most symbols one call takes and the same price path. CoinGecko batches chunks of `ids` with every quote they need; Frankfurter makes one call per base currency. Yahoo Finance stays one chart call per Unit (its batch endpoint is undocumented), and a Custom source gets no batch request, so its form is unchanged.
- **A round of several calls:** a Unit missing from a batch reply reads Not found or No price. A round-level failure (Offline, Rate limited, Key missing, Key rejected, Source error) stops the round; Units already fetched are still written in its one commit, the source backs off with that reason, and the Units not reached get no failure of their own.
- **429:** reads Rate limited, and the source backs off for the longer of the usual rule and `Retry-After` (60 seconds when absent). Fetch now, Daily and Hourly requests and tests ignore back-off but wait out an unexpired `Retry-After`, saying so in place or in the status line.
- **Call budget:** every call to a source, whatever asked for it, goes through a per-Client budget declared in code (CoinGecko 5 a minute keyless and 30 with a Demo key, Yahoo Finance 30, Frankfurter 60, Custom sources 30). Calls a person asked for go ahead of scheduled rounds and backfill, but never interrupt a call in flight. There is no coordination across devices.
- **Backfill pacing** is unchanged: one history request per source, one Unit at a time, through the same budget, never batched.

## Amendment: where fetching's code lives

Decided in [CORE: which crates own the price fetch port, its HTTP adapter and the API key port](https://github.com/IanTeda/Personal-Ledger/issues/1378) and recorded as [ADR-0062](0062-price-fetching-lives-in-lib-units-behind-a-transport-port-and-adapter-crates-hold-the-io.md): `lib-units` owns every fetching rule behind a plain transport port, and a new adapter crate, `lib-price-feed`, is the only crate that runs HTTP.
