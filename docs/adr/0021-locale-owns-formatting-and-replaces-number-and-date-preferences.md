# The Locale owns number, date and currency formatting, replacing the number-separator and date-format Preferences

[ADR-0014](0014-preferences-table-and-leaner-sync-server-config.md) made date format and decimal/thousands separator Ledger-scoped Preferences, so the desktop and TUI each kept their own enums for them (`lib-core`'s `DateFormat` and `NumberFormat`, and `bin-desktop`'s `DateFormat` and `DecimalSeparator`, which already disagree: `1 234,56` versus `1 234.56`). Localising the UI (see the Locale, Message and Catalogue terms in `CONTEXT.md`) needs one owner of formatting, so we're moving it into the localisation crate, driven by the Locale, and replacing those two Preferences.

The Locale is Configuration, not a Preference: a Client takes it from the operating system, unless a static `lib-config` setting overrides it, falling back to `en-US` when the value is unsupported or unreadable. It is per-Client and never synced, is needed before the database is open, and changes only by editing the config and restarting, so there is no in-app switch and no runtime Locale change to propagate. The number-separator Preference is deleted, because `en-AU`, `en-US` and `en-GB` all use `1,234.56`. The date Preference becomes a nullable date style (short, medium, long or ISO): `null` uses the Locale's default, and ISO overrides the Locale for both display and typed input. Typed date input follows the Locale's short form, also accepts ISO always, and accepts the relative words `today`, `yesterday` and `tomorrow`. Currency amounts split responsibility: the Unit supplies the code and fraction digits, the Locale supplies the presentation (separators, symbol placement, disambiguation such as `A$`). Amounts stay exact (`Money`, never `f64`).

This partly supersedes ADR-0014: the Preferences become the default Unit for new Accounts, colour theme and date style.

## Considered Options

The Locale owning formatting with no overrides was rejected because ISO is unambiguous and already used for typed input, so users need a way to keep it. Keeping both Preferences alongside the Locale was rejected because it leaves two owners of one concern and the existing two definitions have already drifted apart. Making the Locale a synced Preference, with a nullable "follow the OS" state, was rejected: a language is a per-device choice (a laptop and a desktop can reasonably differ), a synced value would let one device switch another, and it would force the Locale to be read from the database before the first frame and propagated to open views at runtime. Static configuration with a restart is far simpler and keeps every lookup a plain read of a value fixed for the life of the process.
