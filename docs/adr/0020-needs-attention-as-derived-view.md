# Needs Attention as a derived view, not a materialized attention-item table

Needs Attention needs to surface four kinds of "this wants action" fact: open Tasks, Flagged Transactions, Transactions that are Cleared but not yet Reconciled, and unresolved Bill Schedule entries due on or before today plus their Bill Plan's Attention Lead — see `CONTEXT.md`. We considered a single persisted "Attention Item" table, auto-populated by a background or on-open scan the same way Bill Schedule entries are materialized ahead of their due date ([ADR-0019](0019-materialized-bill-schedule-transaction-linked.md)), giving every surfaced fact — including the three that aren't manually created — its own dismissible row.

We rejected it. Unlike a Bill Schedule entry, which needs a stable identity for a Transaction to eventually link against, none of the Flagged/Cleared-not-Reconciled/Overdue-Bill facts need a *new* identity: each already lives as a status on an existing row (a Transaction's Flagged marker and Transaction Status, a Bill Schedule entry's own status). Materializing them into a second table would mean detecting "is there already an Attention Item row for this still-unresolved fact" on every scan — an ADR-0019-shaped dedup problem — purely to duplicate state the Ledger already tracks, with the duplicate free to silently drift from the source it mirrors (e.g. a stale Attention Item row surviving after its Transaction is Reconciled, if the cleanup scan hasn't run since).

Instead, only Task — the one Needs Attention entry with no existing home elsewhere in the Ledger — is a real persisted row. Needs Attention itself is a live, on-demand query joining Task with the existing Flagged/Transaction Status/Bill Schedule status fields, recomputed on every view and never cached, so a fact resolves itself off the list the instant its underlying state changes, with nothing to separately dismiss or garbage-collect. The trade-off: Needs Attention can never be queried as its own list-with-history the way Bill Schedule is (see `docs/bills.md`) — there is no stored record of what needed attention last week, only what needs it right now.

**Amended (#366):** the Bill Schedule part of the query is a date predicate, not a status one: an entry counts while unresolved (not Paid or Skipped) and its due date is on or before today plus its Bill Plan's Attention Lead (unset = 0). The earlier "Overdue, or Due within lead" wording never flagged an entry whose lead crossed into the next calendar month, since that entry is still Upcoming. The one predicate drives the Bills Schedule view, the Bills rail badge and the Dashboard alike.
