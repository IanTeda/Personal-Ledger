# Tag as an independent, many-to-many Transaction label, not a grouping over Category/Payee

`CONTEXT.md`'s Category entry previously listed `_Avoid_: Tag, group` — Tag had been weighed as just another word for Category and rejected. Revisiting it for "totals across Categories and Payees" surfaced a genuinely different need: a cross-cutting label that doesn't nest inside the fixed, required, exactly-one Category classification.

We modelled Tag as its own entity: a freeform, globally-unique (case-insensitive) label attached many-to-many directly to Transactions, independent of their Category and Payee — not a grouping layered over Category or Payee themselves. The rejected alternative (tagging Categories/Payees and rolling totals up through them) can't express a Transaction that should count toward a cross-cutting total despite sitting under an untagged Category or Payee (e.g. one stray "Japan Trip 2026" expense filed under "Miscellaneous"), which is exactly the case this feature exists for.

Tag gets the same `is_active` soft-delete lifecycle as Unit/Category/Account/Payee, but — unlike Payee — no rename-alias history: nothing auto-creates a Tag from parsed import text that would later need reconciling under a rename, so a plain in-place rename is enough. A Tag's total only sums across Transactions sharing one Unit; a Tag spanning mixed Units reports per-Unit subtotals rather than ever summing across them, extending the "never silently sum across Units" rule the Accounts design (`docs/ux/tui/accounts/README.md`) already established for type-grouped subtotals.

Scope for now: this ADR settles the domain model and vocabulary only — schema, UI, and reporting are deferred to a future build effort.

## Amendment: an optional colour

Settled in [#352](https://github.com/IanTeda/Personal-Ledger/issues/352), against the original colourless Tag: a Tag gains an **optional colour**, a user-chosen hex value stored as `lib-core`'s `HexColor`, so Tags can be told apart at a glance on busy Transactions. It is the user's data, not a Colour Theme role: it does not change with the Colour Theme or Colour Variant, and its contrast on a Dark Variant is the user's choice. A new Tag has no colour; the picker offers the handoff's six swatches (`#ec3013` `#7a8a6b` `#c9922f` `#4a7c9e` `#8a6bb5` `#9b9797`) as presets plus a free hex field and "none". A colourless Tag shows no swatch. Where set, the colour shows as a small square before the Tag's name on the Tags page, its Add and Edit dialogs, the Transactions tag chips and the Transactions filter builder, in both Clients. Merging one Tag into another keeps the target's colour (or its lack of one); the source's colour is dropped.

## Amendment: removing a Tag

Settled in [#353](https://github.com/IanTeda/Personal-Ledger/issues/353), against the original soft-delete-only lifecycle and unlike Payee's no-hard-delete-once-referenced rule ([ADR-0012](0012-payee-entity-with-rename-aliases.md)): a Tag can **always be hard-deleted**, used or not. Removing a Tag untags every Split carrying it and deletes the Tag; the Transactions and their Splits keep their Amount, Category and Payee, so no money is lost, only the label. It cannot be undone. The confirmation stays neutral (not the destructive red variant): an unused Tag needs only Cancel · Remove tag, while a Tag on any Split states how many Transactions lose it, says it can't be undone, and asks for the Tag's name to be typed. Remove never deactivates instead.

`is_active` stays, as a separate toggle in the Tag's Edit dialog, for retiring a Tag while keeping its history (e.g. "Japan Trip 2026" after the trip). An inactive Tag gets the Payee treatment: it stays on the Tags list dimmed and marked "inactive", can be reactivated from Edit, is left out of the Tag counts, is not offered when tagging a Split, and stays listed (dimmed) in the Transactions filter builder and on existing tag chips so its history remains reachable. Its name stays taken for case-insensitive uniqueness.
