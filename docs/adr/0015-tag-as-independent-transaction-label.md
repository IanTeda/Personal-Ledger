# Tag as an independent, many-to-many Transaction label, not a grouping over Category/Payee

`CONTEXT.md`'s Category entry previously listed `_Avoid_: Tag, group` — Tag had been weighed as just another word for Category and rejected. Revisiting it for "totals across Categories and Payees" surfaced a genuinely different need: a cross-cutting label that doesn't nest inside the fixed, required, exactly-one Category classification.

We modelled Tag as its own entity: a freeform, globally-unique (case-insensitive) label attached many-to-many directly to Transactions, independent of their Category and Payee — not a grouping layered over Category or Payee themselves. The rejected alternative (tagging Categories/Payees and rolling totals up through them) can't express a Transaction that should count toward a cross-cutting total despite sitting under an untagged Category or Payee (e.g. one stray "Japan Trip 2026" expense filed under "Miscellaneous"), which is exactly the case this feature exists for.

Tag gets the same `is_active` soft-delete lifecycle as Unit/Category/Account/Payee, but — unlike Payee — no rename-alias history: nothing auto-creates a Tag from parsed import text that would later need reconciling under a rename, so a plain in-place rename is enough. A Tag's total only sums across Transactions sharing one Unit; a Tag spanning mixed Units reports per-Unit subtotals rather than ever summing across them, extending the "never silently sum across Units" rule the Accounts design (`docs/ux/tui-mockups/02-accounts/README.md`) already established for type-grouped subtotals.

Scope for now: this ADR settles the domain model and vocabulary only — schema, UI, and reporting are deferred to a future build effort.

## Amendment: an optional colour

Settled in [#352](https://github.com/IanTeda/Personal-Ledger/issues/352), against the original colourless Tag: a Tag gains an **optional colour**, a user-chosen hex value stored as `lib-core`'s `HexColor`, so Tags can be told apart at a glance on busy Transactions. It is the user's data, not a Colour Theme role: it does not change with the Colour Theme or Colour Variant, and its contrast on a Dark Variant is the user's choice. A new Tag has no colour; the picker offers the handoff's six swatches (`#ec3013` `#7a8a6b` `#c9922f` `#4a7c9e` `#8a6bb5` `#9b9797`) as presets plus a free hex field and "none". A colourless Tag shows no swatch. Where set, the colour shows as a small square before the Tag's name on the Tags page, its Add and Edit dialogs, the Transactions tag chips and the Transactions filter builder, in both Clients. Merging one Tag into another keeps the target's colour (or its lack of one); the source's colour is dropped.

## Amendment: removing a Tag

Settled in [#353](https://github.com/IanTeda/Personal-Ledger/issues/353), against the original soft-delete-only lifecycle and unlike Payee's no-hard-delete-once-referenced rule ([ADR-0012](0012-payee-entity-with-rename-aliases.md)): a Tag can **always be hard-deleted**, used or not. Removing a Tag untags every Split carrying it and deletes the Tag; the Transactions and their Splits keep their Amount, Category and Payee, so no money is lost, only the label. It cannot be undone. The confirmation stays neutral (not the destructive red variant): an unused Tag needs only Cancel · Remove tag, while a Tag on any Split states how many Transactions lose it, says it can't be undone, and asks for the Tag's name to be typed. Remove never deactivates instead.

`is_active` stays, as a separate toggle in the Tag's Edit dialog, for retiring a Tag while keeping its history (e.g. "Japan Trip 2026" after the trip). An inactive Tag gets the Payee treatment: it stays on the Tags list dimmed and marked "inactive", can be reactivated from Edit, is left out of the Tag counts, is not offered when tagging a Split, and stays listed (dimmed) in the Transactions filter builder and on existing tag chips so its history remains reachable. Its name stays taken for case-insensitive uniqueness.

## Amendment: normalised uniqueness and merge

Settled in [#354](https://github.com/IanTeda/Personal-Ledger/issues/354), against the original case-insensitive-only uniqueness: a Tag's name is unique by its **normalised form**, the name Unicode lower-cased with everything but letters and digits dropped, so `work trip`, `Work-Trip` and `work_trip` are one name and only one can exist. A name must keep at least one letter or digit once normalised. Adding, renaming or typing a Tag whose normalised name another Tag already holds is refused with the plain "name taken" error, as elsewhere; typing an existing Tag's exact name (ignoring case) on a Split still reuses it. Near-spellings beyond that (typos such as `reimburseable`) are not caught, since edit-distance matching would flag real pairs like `gift` / `gifts` or two years' trips.

The Tags page keeps the handoff's likely-duplicate flag as a **safety net** for data that breaks the rule, for example Tags arriving by Sync from another Client: two Tags with the same normalised name are flagged, the page counts them, and the flag leads to Merge. The suggested merge target of such a group is the active Tag, then the one on more Transactions, then the older; every other member is flagged as a duplicate of it. Inactive Tags are flagged and may be merged, as source or target.

**Merge** folds a source Tag into a different target Tag as one operation: every Split carrying the source gains the target (if it lacks it) and loses the source, then the source is deleted (always allowed, per the removal amendment). The target keeps its name, colour and `is_active`; nothing else on the Splits changes, and it cannot be undone. Merge is a general tool, not only for flagged duplicates, reached from the Tags page's duplicate link and flag, a key on the Tags page, and a palette verb. It is described in the Tag glossary entry rather than a separate term, until Payees gain their own merge.

## Amendment: usage figures on the Tags page

Settled in [#355](https://github.com/IanTeda/Personal-Ledger/issues/355), against the Categories and Payees pages' base-Unit-only totals: the Tags page keeps the per-Unit rule above rather than following them. Each Tag's usage covers **all time** and every Transaction, whatever its Account. Its **total** sums every Split carrying the Tag when they share one Unit, with the Unit's code appended when it is not the base Unit (`−812.00 usd`). A Tag spanning several Units shows a muted "mixed units" in the page's single TOTAL cell, the same wording as the Transactions running total, and never a sum; its per-Unit subtotals are reached through the Transactions page filtered by the Tag, and later through Reports. Its **Transaction count** counts distinct Transactions, so a Transaction whose two Splits both carry the Tag counts once (unlike the Payees page, which counts Splits); this is the figure the remove and merge confirmations quote and the page sorts by, descending, ties by name. **Last used** is the newest date of any Transaction carrying the Tag, future-dated ones included, shown in the user's Date Style like every other date. A Tag on no Split shows a count of 0 and "—" for total and last used.
