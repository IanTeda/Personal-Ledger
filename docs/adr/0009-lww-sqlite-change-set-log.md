# Per-field last-write-wins over a SQLite Change Set log for the Sync Server

A primary-source survey (`docs/research/sync-reconciliation-approaches.md`) compared three conflict-resolution strategies for syncing independent local SQLite copies across devices — last-write-wins (LWW), CRDTs, and manual merge — against real precedent (PowerSync, Turso's libSQL offline-sync beta, `cr-sqlite`, Automerge, Apache CouchDB's replication model), and four candidate storage engines for the Sync Server's own durable Change Set log — SQLite via `sqlx`, PostgreSQL, `sled`, and `redb` — against this workspace's actual stack and its Docker-only, single-persistent-volume, homelab-trusted-network deployment model (FC-SYNC-005/006, NFR.6b, §6.1 Assumptions).

We chose **per-field last-write-wins**, backed by a Hybrid-Logical-Clock-style timestamp (physical time plus a monotonic logical counter, not a bare wall-clock value) with the originating Client's stable ID as the tie-breaker on exact-timestamp collisions. This is the smallest strategy that satisfies FC-SYNC-003's actual demonstration bar — basic push/pull sync with offline catch-up, not conflict-free correctness — and it matches the honest state of the art the research found: even Turso's purpose-built offline-sync product ships conflict *detection* without automatic *resolution* today, and PowerSync, the most mature LWW implementation surveyed, still frames plain timestamp-based LWW as a starting point with documented escape hatches rather than a universally sufficient answer. Personal Ledger's own domain shape favours it further: a Transaction's fields (amount, Category, Account, Payee, description, date, Transaction Status, Flagged) are narrow and mostly independent, so most real concurrent edits from one user's own devices — flagging a Transaction on the phone while editing its description on the desktop — won't even collide at the field level. CRDTs (specifically `cr-sqlite`-style per-column registers) were considered and rejected for this cycle: they remove *ambiguity* about which replica's value wins, not *data loss* for an arbitrary field like a Transaction amount, and the per-column CRDT machinery is real additional engineering scope FC-SYNC-003 doesn't need to satisfy — though the domain shape above means it remains a credible upgrade path later if plain LWW's silent-data-loss behaviour proves unacceptable even for a single user's own devices. Manual merge was rejected for this cycle because it needs a conflict-presentation UI that exists in neither the Desktop nor TUI client today, a larger scope addition than this feasibility cycle calls for.

We chose **SQLite via `sqlx`** for the Change Set log's storage engine, reusing `lib-database`'s existing conventions directly: `thiserror`-wrapped errors, `sqlx::migrate!`-driven schema evolution, and the same per-entity `find`/`insert`/`update`/`delete`/`builder`/`model` file split. Every constraint this PRD actually states points the same direction — no separate database server process desired unless justified, a single persistent volume, a Docker-only non-root container — and none of the alternatives earned the operational cost of departing from the incumbent stack. PostgreSQL's durability engineering is mature and not in question, but it demands a second container, its own healthcheck, and version-specific volume-mount discipline (PostgreSQL 18+ namespaces its default data directory by version; 17 and earlier require a specific mount point) for no capability this single-user, homelab-deployed product needs. `sled`'s own README recommends SQLite over itself for reliability-sensitive use, and its published crate is roughly two years stale. `redb` is the most credible embedded-KV alternative — current, well-documented per-transaction durability levels, genuinely crash-safe by its own account — but its synchronous API has no `sqlx`/`tokio` story (every transaction would need `spawn_blocking` plumbing) and no SQL query layer or migration tooling, meaning cursor-range logic and schema evolution would be hand-rolled instead of reusing patterns already proven in this codebase, for a durability guarantee SQLite's WAL mode already provides.

The Change Set schema carries: a stable Change Set ID (this project's own `RowID` — UUIDv7-based, time-ordered, already used project-wide per `crates/libs/lib-domain/src/row_id.rs` and FR.21 — rather than inventing a new ID scheme), the target table/row/field identifiers, the new value, the HLC-style timestamp, the originating Client's stable ID, and a version/parent-version field. That last field is captured from the start even though nothing consumes it under plain LWW, so a future upgrade to CRDT-based or manual-merge conflict handling doesn't require a Change Set log schema migration just to add the metadata it would need.

The Change Set log's retention/pruning policy is deliberately **not decided this cycle**: for a feasibility demo on one self-hoster's own small device fleet, unbounded growth isn't a real operational problem yet, and designing a pruning policy (e.g. pruning a Change Set once every currently-known Client has acked it) without real usage/volume data would be speculative. Every Change Set is kept indefinitely for now; retention is revisited once a later cycle has actual usage data to design against.

This is feasibility-cycle scope, not a generalised, multi-tenant, adversarial-network sync protocol — explicitly out of scope per the PRD's §7 "multi-device sync protocol" future consideration. The decisions above satisfy FC-SYNC-001 and FC-SYNC-003, and unblock [Demonstrate basic push/pull sync with offline catch-up](https://github.com/IanTeda/Personal-Ledger/issues/46) and [Demonstrate docker Compose deployment with persistent volume](https://github.com/IanTeda/Personal-Ledger/issues/49), part of the [Sync Server feasibility](https://github.com/IanTeda/Personal-Ledger/issues/40) map.
