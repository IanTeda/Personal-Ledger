# OS/filesystem-level encryption for data at rest, not SQLCipher

Personal Ledger stores all data locally in SQLite via `sqlx` (`crates/libs/lib-database`), and NFR.2 ("All data is stored locally in SQLite; no data leaves the device by default") makes at-rest encryption worth deciding explicitly rather than leaving implicit. `docs/research/sqlite-encryption.md` (feasibility cycle) surveyed the options against this project's actual stack: SQLCipher (BSD-3-Clause, the most mature encrypted-SQLite implementation), SQLite3 Multiple Ciphers (no usable Rust/`sqlx` integration found), and OS/filesystem-level encryption (LUKS, FileVault, BitLocker). We decided **OS/filesystem-level encryption**, relying on the host platform rather than adding application-level cryptography — confirming and formalising the assumption already stated in `docs/product-requirements.md` §6.1.

`sqlx`'s SQLite driver (`sqlx-sqlite`, `libsqlite3-sys`-based) has no first-party Cargo feature to build/link an SQLCipher-capable SQLite — the only path is a version-fragile Cargo feature-unification trick the `sqlx` maintainer himself described as holding only "so long as the API between the version of `libsqlite3-sys` and `sqlx` doesn't change" (see the research doc, §2–3, citing `sqlx` issues #621/#1436/#2009/#3626), plus a new compiled-in OpenSSL build dependency and fully application-owned key management. Given Personal Ledger's actual profile — single-user, self-hosted, local-first, no cloud dependency (§1.2) — OS-level encryption is commonly already on by default on the platforms this app targets (FileVault/BitLocker out of the box on consumer installs, LUKS a standard Linux-installer option), covers the whole device rather than one file, and avoids taking on SQLCipher's build and key-management cost to defend against a threat model (another local process/user reading the file while the disk is mounted) a genuinely single-user desktop deployment may not need to defend against.

This decision requires no code this cycle: reliably detecting "is this volume encrypted" cross-platform is itself a nontrivial, platform-specific feature nothing in the FRs/NFRs calls for, and an unreliable check would give a false sense of security. NFR.2 now cross-references §6.1 so the posture is stated as a requirement, not left implicit in Assumptions alone.

**Revisit triggers** (from the research's own recommendation): supporting users who won't enable disk encryption themselves; database files backed up or synced to less-trusted storage as a supported feature; or a future shared-machine/multi-profile mode. If any of these materialise, Workaround A from the research doc (the `libsqlite3-sys` `bundled-sqlcipher`/`bundled-sqlcipher-vendored-openssl` Cargo feature-unification trick) is the realistic path — a driver swap to `rusqlite` or a `sqlite3mc` integration are not justified by anything found in that research.
