# Colour Theme and Colour Appearance are nullable Preferences, and `[theme]` overrides only Colour Roles

ADR-0014 made "colour theme" a Ledger-scoped Preference, but the `preferences.colour_theme` column holds a single `HexColor` accent, not a Colour Theme. The Colour Themes map settled that the user picks a Colour Theme and a Colour Appearance, both synced, and that a `[theme]` Configuration section overrides colours on one Client (see Colour Theme, Colour Role, Colour Variant and Colour Appearance in `GLOSSARY.md`). This amends ADR-0014.

We're replacing the `HexColor` column with two nullable Ledger-scoped Preferences: `colour_theme` (a built-in Colour Theme's id, such as `modernist`) and `colour_appearance` (`light`, `dark` or `system`). Null means the default (Modernist; System), and only an explicit choice is stored and synced, as the date style does under ADR-0021. There is no SQL `CHECK` on the id. A Client that does not know a synced id (one added in a later release) draws the default Colour Theme and logs a `warn`, but never writes the default back, so a newer Client still shows the choice.

`[theme]` holds only the seven Colour Role keys from ADR-0022. It cannot name a Colour Theme or a Colour Appearance. An override replaces only the roles it names; the rest come from the resolved Colour Theme. Resolution runs: Colour Theme from the Preference, then the Colour Variant from the Colour Appearance (System follows the OS or terminal), then the `[theme]` roles over it. A bare key applies to both Colour Variants, and a `[theme.light]` or `[theme.dark]` subsection overrides one Colour Variant, with the more specific key winning. Environment variables follow the usual nesting: `PERSONAL_LEDGER_THEME__ACCENT`, `PERSONAL_LEDGER_THEME__DARK__ACCENT`. A value that is not a colour, or an unknown key, is ignored with a `warn` naming the key and value; the Client still starts. `[theme]` is read once at start, so a change needs a restart, while Preference and OS light/dark changes apply live. The Settings pickers stay enabled while roles are overridden, with a note saying how many colours are overridden by Configuration.

## Considered Options

Non-null columns with defaults written at Ledger creation were rejected: they cannot tell "never chosen" from "chose the default", so a changed default would never reach existing Ledgers. Keeping the accent `HexColor` as a third Preference was rejected because a custom accent is now a `[theme]` override, and a synced one would push one machine's colour tweak onto every Client.

Letting `[theme]` also name a Colour Theme and Colour Appearance was rejected to keep one owner per concern: the choice is a Preference picked in Settings, and Configuration only adjusts colours. It also avoids a disabled picker in Settings. Replacing the whole Colour Theme when any role key is set was rejected because a one-line accent change would force writing all seven roles. Bare keys only were rejected because one accent rarely suits both a light and a dark background.

A SQL `CHECK` on the Colour Theme id, or writing the default back on an unknown id, were rejected because either one breaks syncing a Colour Theme added in a newer release. Failing start on a bad `[theme]` value was rejected to match ADR-0022's "never reject an override" rule: one bad colour must not stop the Client. Watching the Configuration file for live changes was rejected, following ADR-0021: Configuration is read once at start.
