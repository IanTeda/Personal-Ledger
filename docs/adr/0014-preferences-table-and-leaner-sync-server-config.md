# User-editable settings become a synced Preferences table; Sync Server keeps a leaner Configuration search

`CONTEXT.md`'s Preference/Configuration split (from [Decide the application Settings / Preference model](https://github.com/IanTeda/Personal-Ledger/issues/63)) drew the line as "edited from inside a running Client" (Preference, database-stored) versus "deployment-time" (Configuration, `lib-config`'s layered INI files/env vars) — but only ever assigned one Preference (the default Unit for new Accounts), leaving colour theme, date format, and decimal/thousands separator classified as Configuration despite the same "user sets this" character, on the reasoning that the user set them once via the config file. Revisiting the approach ahead of CC-TUI-002/CC-DESKTOP-002 building out real Settings screens surfaced that this split needed sharpening, and that the Sync Server — sharing `lib-config` with the Clients today — has a different deployment shape (Docker-only, single persistent volume, homelab network, per ADR-0009) that the Client-oriented multi-directory config search doesn't fit.

We reclassify colour theme, date format, and decimal/thousands separator from Configuration to Preference, joining the default Unit. All four are Ledger-scoped (not Client-scoped): a new typed singleton table in the Ledger's local SQLite file (one row, explicit columns, following `lib-database`'s existing per-entity convention), whose writes emit a Change Set exactly like `units`/`accounts` do — so these settings sync across a user's own Clients through the Sync Server rather than needing to be set separately on each device. We considered a generic key-value settings table instead (no migration needed to add a future Preference) but rejected it: the known set is small, `sqlx`'s compile-time query checking wants fixed columns, and every other entity in `lib-database` is a typed table, not a KV store. Client-scoped (local-only, unsynced) Preferences remain valid per `CONTEXT.md`'s existing definition, but nothing currently needs one, so no local-only table is built speculatively — it stays an unbuilt path for whenever a genuinely per-device Preference shows up.

Configuration narrows correspondingly to settings that must be readable before the app — or the database itself — exists: the database connection/pool settings and the telemetry level. Format stays INI via the `config` crate for every consumer; a move to TOML was considered (it was actually the original framing of this revisit) but dropped once articulated as a file-format-only change with no concrete pain point against INI — the real problem was the classification boundary and the Sync Server's search path, not the syntax. The Sync Server keeps `lib-config`'s INI loading but drops to a reduced precedence chain — defaults → one configured file path → environment variable overrides — instead of the full defaults → system → user → executable-directory → working-directory → explicit-path → env search built for Clients' locally-installed, multi-OS story; the system/user/exe-dir/cwd tiers don't correspond to anything meaningful inside a Docker container. TUI and Desktop keep the existing full search unchanged.
