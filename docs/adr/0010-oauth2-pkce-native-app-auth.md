# Native-app OAuth2 Authorization Code + PKCE for Sync Server auth

A primary-source survey (`docs/research/sync-auth-mechanisms.md`) compared OAuth2, JWT, mTLS, pre-shared tokens, HMAC-signed requests, and SPIFFE against the trusted-homelab/single-household deployment profile (PRD §6.1) and made no recommendation. That research's objection to OAuth2 was specifically its *delegated-access* machinery having no one to serve in a single-household deployment with no third-party clients. It did not evaluate the UX this ADR locks in — clicking "authenticate" in the Desktop/TUI app, logging in via a browser, and never storing a persistent username/password in the Client itself — which a follow-up survey (`docs/research/sync-auth-oauth2-pkce.md`) found maps directly onto OAuth2's Authorization Code grant with PKCE over a loopback redirect (RFC 8252 §7.3, RFC 7636), with the Sync Server itself acting as both authorization server and resource server. There is no third-party identity provider anywhere in this design, so the earlier research's core objection to OAuth2 does not apply here.

We chose this flow over the plain bearer-token options (self-issued JWT, pre-shared token) the original research favoured, accepting the extra implementation surface it costs, because it is the only candidate that satisfies the actual requirement: the password is entered once, inside the system browser (never inside the Desktop/TUI binary, per RFC 8252 §8.12's reasoning against embedded webviews), and the Client subsequently authenticates itself without ever holding a long-lived static secret typed by the user. mTLS was re-considered and again rejected for the same reason ADR-scope reconciliation gave CRDTs in ADR-0009 — it solves a different problem (transport-level identity via a provisioned certificate) than "no password in the Client," and doesn't produce the click-to-browser-login UX on its own.

**Flow.** The Client opens the system browser to the Sync Server's `/authorize` endpoint with a PKCE `code_challenge` (RFC 7636 §4.2, `S256`) and a `redirect_uri` pointing at a loopback listener (`http://127.0.0.1:{ephemeral-port}`) the Client binds just for this exchange, per RFC 8252 §7.3 — the Sync Server accepts any port on a loopback host rather than requiring a pre-registered fixed one. The Sync Server renders a login form, validates the submitted username/password against its own user store, and redirects back to the loopback listener with an authorization code. The Client redeems that code at `/token`, presenting the original `code_verifier`; the Sync Server verifies it against the `code_challenge` it recorded (RFC 7636 §4.6) and returns a short-lived JWT access token plus a refresh token. The gRPC resource-server side keeps the bearer-token `tonic::Interceptor` pattern the original research already validated (`jsonwebtoken`, HMAC-signed, single Sync-Server-held secret) — PKCE and the browser hop only change how the Client *obtains* that JWT, not how the gRPC service checks it.

**One listener, not two.** `tonic` 0.14.6's `Routes::into_axum_router()` lets the existing gRPC `Routes` merge into an `axum::Router` alongside the new `/authorize`/`/token`/login-form HTTP endpoints, served from a single Hyper listener. This avoids a second exposed port in the Docker image or Compose file (NFR.6b), keeping the deployment shape ADR-0009 assumed (one container, one persistent volume) intact.

**Refresh tokens rotate.** Per the user's decision to stay logged in indefinitely rather than re-authenticate every launch, the Sync Server issues a refresh token alongside the access token and stores it (hashed, alongside the Argon2-hashed password) in its own user-store schema. RFC 6749 leaves rotation policy undefined, so we chose **rotating** refresh tokens: each redemption both mints a new access token and invalidates/replaces the refresh token the Client held, with the Client updating its OS-keychain-stored value (`keyring` crate) each time. This is cheap to implement (one "current valid refresh token" record per account) and gives a concrete signal — reuse of an already-rotated-out token — if a Client's stored token is ever exfiltrated and used from two places, which a non-rotating token would not surface.

**Single account, for this cycle.** The PRD's deployment profile (§6.1) is one self-hoster with 2-3 of their own Clients, not multiple distinct human users of one Sync Server. The user store this cycle supports exactly one account, provisioned at first run (e.g. a config-driven bootstrap username/password, encrypted at rest per the existing `DC-ALL-001` intent for password storage) rather than building account-management UI/RPCs nothing in this cycle's requirements calls for. Multi-account support, if ever needed, is a later scope addition, not a gap in this decision.

**Schema placement.** The user-store table(s) (account, Argon2 password hash, current refresh-token hash) live in the same SQLite database as the Change Set log ADR-0009 fixed, using `lib-database`'s existing `find`/`insert`/`update`/`delete`/`builder`/`model` per-entity convention (`CLAUDE.md`) — one persistent volume, one migration history, rather than a second database file with its own connection pool for a handful of rows.

**Deferred to implementation.** Whether the Client's PKCE/token-exchange side hand-rolls the (small) verifier/challenge/HTTP logic or adopts the `oauth2` crate is left to whoever picks up [Demonstrate auth functionality](https://github.com/IanTeda/Personal-Ledger/issues/50) — the crate targets spec-conformant authorization servers more general than this Sync Server will implement (no discovery document, no dynamic client registration), so it may cost more integration effort than it saves at this scale, but that is an implementation-time call, not an architectural one. Likewise the exact login-form HTML/styling and the browser-launch mechanism (e.g. the `open` crate) are implementation detail.

This satisfies FC-SYNC-002 and unblocks [Demonstrate auth functionality](https://github.com/IanTeda/Personal-Ledger/issues/50), part of the [Sync Server feasibility](https://github.com/IanTeda/Personal-Ledger/issues/40) map.
