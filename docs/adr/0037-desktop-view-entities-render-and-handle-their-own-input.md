# Desktop View Entities render and handle their own input

> Partly superseded by [`docs/development/viper-architecture.md`](../development/viper-architecture.md) (Input, The Shell module): the key order is `input.rs`'s `route_key` (Dialog, a mode left in the bin, `lib-shell`'s global keymap, the focused module's keymap, a View not yet a module), and the `g` prefix waits in `lib-shell`'s Presenter, not on `Shell`. A View migrated to a VIPER module gets its keys through its keymap and Presenter, not through this interface. A View not yet a module still implements `key_ahead`, `handle_key`, `escape` and the rest through `ActiveViewEntity` (`view/active.rs`), offered at the bin-mode and View steps, with the root Router (`shell/router/key_dispatch.rs`) applying the focus and modifier gates.

[ADR-0032](0032-desktop-views-are-entities-that-own-their-view-state.md) moved each Desktop View's state into a gpui Entity, but its behaviour stayed on `Shell`. No View Entity implements `Render`: one `Shell::render` of about 1790 lines builds every page from Props structs and `On*` callbacks, and `Shell` reaches into Views through 111 `edit_*_state` calls. Each destination also has its own branch in Esc handling, search, the keys claimed ahead of the router, the `NoOp` fallthrough, movement and page status, spread across `app/key_dispatch.rs`, `app/focus.rs`, `app/status.rs` and `app/render.rs`. Decided in #594 on the [Deepen the domain libs and finish the View Entities](https://github.com/IanTeda/Personal-Ledger/issues/588) map.

We're making each View Entity render itself and handle its own input. `Shell` keeps navigation, Chrome, the Dialog host, Toasts, and one forwarding match over the active View.

## Decision

- **One forwarding enum.** `Shell::active_view_entity(cx)` returns an `ActiveViewEntity` enum holding the active View's typed Entity, e.g. `Bills(Entity<BillsView>)`. Each of its methods holds the one exhaustive match and forwards to an inherent method of the same name on the Entity. Every per-destination match lives in that one file (`view/active.rs`), so a new View fails to compile there and nowhere else. There is still no `View` trait and no `dyn` or `AnyView` erasure (ADR-0016).
- **The interface.** `key_ahead(&Keystroke) -> bool` for keys a View claims before `route_key`. `handle_key(&Keystroke) -> bool` for the router's `NoOp` fallthrough. `apply_movement(Movement)`. `escape() -> bool`, which reports whether the View consumed the Esc. `start_search() -> bool` and `search_key(&Keystroke) -> bool`, where `false` means the View has no Search and `/` is inert. `on_enter()`, which resets the View's own scroll and internal focus when it becomes the destination. `reveal(Reveal)`. `page_status()`, plus the existing title and hints as data.
- **Shell owns the generic gates.** `Shell` forwards a key only when the View zone has focus and applies the modifier and pending-`g` checks. A View never checks `nav.noun()` or `nav.focus()`. Esc asks the Dialog host's open select first, then the View, then falls back to `Shell`'s close-and-exit-mode.
- **Each View implements `Render`.** `Shell::render` embeds the active View's Entity as a child element. Click handlers become `cx.listener` closures on the View, and the scroll handle moves into the View. A View reads the store Entities it needs, such as Categories and Accounts for a filter's choices. The Props structs and `On*` callback aliases go as each View moves.
- **`ViewEvent` is the only View→Shell channel.** A View builds the Dialog it wants and emits `ViewEvent::OpenDialog`, or `RaiseToast`, `Navigate`, `SetStatus`, or `Reveal`. The per-View intent enums (`BillsEvent`, `AccountsEvent`, …) and their handlers in `app/*_ui.rs` are deleted, and one generic subscription replaces the per-View ones. A new variant is added only for a request that is truly cross-cutting.
- **Cross-View jumps are `Reveal`.** `ViewEvent::Reveal(Reveal::BillEntry(id))` makes `Shell` navigate to the owning destination and call that View's `reveal`. Documents' links to Bills and Settings use it; Transactions has its own entry point, `transactions::router`.
- **Dialog hints come from the Dialog.** While a Dialog is open, `Shell` takes the hints from the Dialog host (`OpenDialog::hints()`), so a View's `page_status` covers only the View's own state.
- **Tests read snapshots the View builds.** Each View Entity builds its own `#[doc(hidden)]` snapshot, and `Shell`'s accessor forwards to it, so the headless tests (ADR-0030) are unchanged. The `edit_*_state` hatches are used only inside `Shell` and are deleted.
- **Migration.** One View per PR: Bills first, then Budgets, Transactions with Import, Documents, the Settings Entity with its static pages, then each Settings page that has data, Dashboard with Help, and a final cleanup.

## Consequences

- `Shell` shrinks toward navigation, Chrome, the Dialog host, Toasts and the forwarding enum, and `app/*_ui.rs` shrinks to cross-cutting wiring.
- The Dialog host owns the confirm, refuse and reopen cycle (#596). Each form implements `DialogForm`: `command()` returns its command or a `FormError` from field validation, and `refuse()` shows a domain refusal as a Message, so the wording stays in the bin and the domain libs stay locale-free. The host runs the command through an `Apply` trait, implemented against the per-domain stores until `LedgerStore` replaces them, and closes the Dialog only on success. A Dialog stays a value in `OpenDialog`, reached through one generic `dialog_mut::<T>()`. Stale copies went with the Ledger aggregate (ADR-0038): a hosted Dialog reads the Ledger through its `DialogScope` when it draws and confirms, and nothing writes behind an open Dialog (see the 2026-10-18 Dialog host amendment below).
- A View now depends on the stores it reads, so its tests must set up those store Entities.

## Considered Options

- **Keep `Shell`'s `ActiveView` match at each call site, each arm one line.** Rejected: the per-destination matches would stay spread across four files.
- **A statically dispatched `ViewEntity` trait behind the enum.** Rejected, as in ADR-0016's #538 update: the enum already makes every View handle every method, and the trait would add nothing but uniform signatures.
- **Keep the per-View intent events and delete `ViewEvent`.** Rejected: `Shell` would keep a View-specific match that turns each intent into a Dialog. This reverses the reasoning in ADR-0016's #538 update that a View's handling needs `Shell`'s shared state. A View reads the stores itself and asks `Shell` only for what `Shell` owns.
- **Make each Dialog a gpui Entity.** Rejected (#596): a Dialog lives only while it is open and watches nothing, so an Entity would add `update(cx, …)` plumbing for no gain.

## Amendment: a Settings page lives in one folder

The Settings page moves (#618, #620) met every rule above but left each page's files spread over four or five roots: `src/<domain>/` for forms and apply, `src/view/<domain>/` for the Entity and Dialogs, `src/view/settings/<page>.rs` for the render, `app/<domain>_ui.rs` for wiring, and its variants in the Settings-wide `SettingsDialog`, `SettingsCommand` and `SettingsApply`. Units alone was 13 files in 6 directories. Decided in the 2026-10-15 architecture review, applying section 3 of `docs/development/desktop-structure-2026-10-12.html` to Settings first ([#666](https://github.com/IanTeda/Personal-Ledger/issues/666)). The interface above is unchanged; this decides where a Settings page's files live.

- **One tree.** `src/settings/` holds `SettingsView`, the page enum `SettingsPage` (GLOSSARY **Settings page**) and one folder per page. `src/view/settings/` and the separate pure `src/settings/` merge into it.
- **One folder per page.** `src/settings/<page>/` holds `mod.rs` (the page Entity: keys, movement, Esc, page status, snapshot), `render.rs`, `form.rs`, `apply.rs` (`DialogForm` and `Apply` against `LedgerStore`) and `dialogs/` (`mod.rs` holds the page's Dialog enum, which `OpenDialog` wraps in one variant, then one file per Dialog). A file the page has nothing for is left out. Static pages are folders too.
- **A page owns its Dialogs and commands.** There is no Settings-wide Dialog, command or apply type.
- **Pages never import each other.** A field widget more than one page uses lives in the top-level `form/`. Where a domain is also a main-rail destination (Documents, Inventory), only the Settings page's own code moves, and code both use stays with the destination.
- **A page reads `LedgerStore` directly** and filters `LedgerChanged` on `what`; there are no per-domain stores (ADR-0038).
- **Tests keep their names.** A page's headless tests stay `tests/ui/settings_<page>_keyboard.rs` and `_mouse.rs`, and a page without them gets them before it moves.
- **Destinations are not yet decided.** Whether destination Views copy this layout is decided on [#588](https://github.com/IanTeda/Personal-Ledger/issues/588) once it has been tested on the Settings pages.

## Amendment: Settings pages forward through a trait with default methods

The folder moves (#666) left `SettingsView` forwarding to its pages through a `FocusedPage` enum: 7 methods matched over 9 pages, 63 arms, many of them stubs that return `false`, beside separate matches for rendering, the cheat sheet and `reveal`, and Display- and Units-only branches. `Shell` also built all 13 page Entities and their subscriptions and handed them over as `SettingsSources`. Decided in the 2026-10-18 architecture review (candidate 3). Destination Views keep `ActiveViewEntity` and the decision above; this applies inside Settings only.

- **A trait for Settings pages.** Every Settings page, static pages and General included, implements one trait whose methods have defaults (`key_ahead`, `escape`, `start_search` and `search_key` → `false`, `apply_movement` → not taken, `reveal` and `set_frame` → nothing), so a page writes only what it handles. One adapter over `Entity<T>` adds `view()`, so the open page is a single `dyn` handle. The trait earns its place here where it didn't for destinations: 14 pages share most of the defaults, and the defaults are what shrink the interface.
- **One match.** `SettingsPages` holds a typed field per page and one `get(SettingsPage)` match; rendering, keys, movement, Esc, Search, status, the cheat sheet and `reveal` all go through it. A new page fails to compile there and in `SettingsPage::ALL`.
- **The frame is told, not passed.** `set_frame(PageFrame { window_size, body_width })` reaches the open page before its keys and draw; Display and Units override it.
- **Settings builds its pages.** `SettingsView::new` builds the page Entities from the `LedgerStore` and `today`, re-emits their `ViewEvent`s and repaints on their changes, so `Shell` keeps one subscription and one observer. Pages with rows emit one shared `PageRowClicked`. `Shell`'s typed page accessors no longer serve the Dialog host (see the next amendment); they stay only for the palette commands that drive a page, the Tracing capture feed and the test snapshots.

## Amendment (2026-10-18): a Dialog draws, confirms and describes itself

The Settings page folders (#666) and the page trait above still left each page's Dialogs half in `Shell`: `app/render.rs` drew each by variant, `app/dialogs.rs` held a per-domain confirm and the opener's follow-up (`select_id`, `land`, `type_removed`), and `app/snapshots/settings.rs` copied each open Dialog into fixed slots for the UI tests. Changing a Tags Dialog meant edits under `app/`. Decided in the 2026-10-18 architecture review (candidate 1) on [#700](https://github.com/IanTeda/Personal-Ledger/issues/700) and carried out page by page in #701 to #709. The rules above still hold; this decides what the Dialog host asks of a Dialog.

- **The opener receives the confirmed outcome.** A page opens a Dialog with `open_dialog::<D, P>(dialog, opener, cx)`, which emits `ViewEvent::OpenHostedDialog` carrying the Dialog and a typed closure over the page. `Enter` and the confirm button both reduce to the host's one confirm. The Dialog's `ConfirmDialog::confirm` runs its form through its page's `Apply` (`dialog_apply::confirm`, unchanged) and returns `Landed { toast, outcome }`. The host raises the Toast and closes the Dialog, and the opener runs on the page with the outcome, so selecting the new row and similar follow-ups live in the page. A page that has gone is skipped and the Toast is still raised. `DialogForm`, `Apply` and `dialog_apply::confirm` are unchanged.
- **A Dialog draws itself.** `Dialog::render` takes the `DialogScope` (the `LedgerStore` and `today`) and `DialogActions`. Its clicks edit it through `DialogActions::edit::<D>`, the one generic "edit the open Dialog" callback `Shell` supplies, and use the host's cancel and confirm. `render.rs` has no per-domain Dialog arm for a hosted Dialog. Dialogs stay values, not Entities (#596).
- **A Dialog describes its own readback.** `Dialog::readback` returns a `DialogReadback`: the Dialog's `kind` and its state as labelled values. The UI test `Harness` reads it through `Shell::dialog_readback`. The Dialog chain and its fixed slots in `app/snapshots/settings.rs` are deleted, with no old path left beside it.
- **A form holds its edits until confirm.** A change a Dialog makes is held on its form and applied on confirm, so Cancel reverts it. The Edit Category type change was the one exception and was fixed in #702.
- **`OpenDialog` stays an enum**, one variant per feature, with `DialogVariant` finding the open Dialog by type. Bills, Budgets and Documents have not moved: their Dialogs return `None` from `render` and `readback`, and `Shell` still draws and confirms them by variant until review candidate 4 moves them.

Consequences: a hosted Dialog lives wholly in its page's `dialogs/` folder and `apply.rs`, and changing one needs no edit under `bin-desktop/src/app/`. A new page's Dialogs still add their `OpenDialog` variant and its name in the hosted arm of `Shell::confirm_open_dialog`. Open, confirm and outcome are unit-tested without `Shell`.

## Amendment (2026-10-19): a Dialog confirms a Ledger command, with no per-page Apply

The Dialog host amendment above left every Settings page with a `DialogForm` + `ConfirmDialog` + `Apply` triple, 10 copies and about 1,750 non-test lines. The form returned a page-local command enum that copied the `lib_ledger` command structs field for field, a per-page `Apply` unpacked it and repacked it into those structs, and seven `ConfirmDialog` impls had the same body. `Apply` was the seam for moving off the per-domain stores, and since ADR-0038 it has had only one adapter, `LedgerStore`. Decided in the grilling of [#719](https://github.com/IanTeda/Personal-Ledger/issues/719). The amendment above still holds, except that `Apply` and `dialog_apply::confirm` go.

- **A page command wraps the Ledger commands.** A form's `command()` returns its page's command enum, but each variant wraps a `lib_ledger` struct (`UnitsCommand::Add(AddUnit)`) rather than copying its fields. The bin implements `LedgerCommand` on that enum. Its `run` dispatches to the wrapped command and builds the page's Outcome and Refusal, reading from the `Ledger` before or after the write when a Toast needs it (e.g. a Unit's code before Deactivate). Per-domain sum types stay out of `lib_ledger`, so the Outcomes that carry Toast data stay in the bin.
- **One confirm.** `dialog_host::confirm_ledger` takes a form, runs its command through `LedgerStore::apply`, hands a refusal to `DialogForm::refuse` and returns `Landed`. Each page's `ConfirmDialog` is one call to it. It is a function rather than a blanket `ConfirmDialog` impl, because a blanket impl over the foreign `LedgerCommand` would overlap with Tracing's own impl. Tracing doesn't change the Ledger and keeps its own confirm.
- **The Outcome gives the Toast.** A small trait on the Outcome supplies `toast()`, which defaults to none, so Units can still choose between ACTIVITY and a Toast in `land`. The Message for a refusal stays in `DialogForm::refuse`, and a follow-up such as Units' Delete turning into Deactivate is still a refusal that reshapes the form.
- **One confirm is one Ledger command.** A confirm that needs two writes becomes one `lib_ledger` command, so it lands atomically as one change batch (ADR-0044). Categories' Edit with its type cascade folds into the Ledger in its own ticket before that page moves. A form that needs scope data to build its command, such as Categories' `today` for the Monthly budget, keeps it on the form from when it opened; `DialogForm::command` takes no scope.
- **`OpenDialog` is unchanged.** It stays the closed enum, with no type-erased commands.
- **Migration.** First `confirm_ledger`, the Outcome trait and Institutions, then one page per ticket, then the `Apply` trait and `dialog_apply::confirm` are deleted and the doc comments in `dialog_apply.rs` and `ledger_store.rs` lose their per-domain stores. Until that last ticket, migrated pages and `Apply` pages live side by side. It runs after #718, and the Bills, Budgets and Documents Dialogs move onto this path when they become hosted.

Consequences: a new Dialog adds its command enum, its `LedgerCommand` impl and its Outcome's Toast, and no adapter. The per-page `apply.rs` unit tests become tests of the command's `run` and of `confirm_ledger`. The headless UI tests never crossed the seam and don't change.

## Amendment (2026-10-30): a Settings page's identity stays on `SettingsPage`, and `Page` holds only its View

The page trait above left a page's identity, the forwarders to it and its strays spread over `settings/page.rs`, `settings/state.rs`, `shell/router/` and the test harness, so adding a page touched about 10 files. [#721](https://github.com/IanTeda/Personal-Ledger/issues/721) proposed moving each page's metadata into its `Page` impl. Decided in its grilling, against that proposal:

- **Identity is Presenter and Router data.** `SettingsPage` keeps the order (`ALL`), the persisted `id`, the label, the description, the scope note, `has_controls` and, from #911, the scope group (This device or This Ledger). It stays `gpui`-free, so slice 12 (#815) can lift it into the Settings module unchanged. Navigation reads a page's label with no page built (`ActiveView<SettingsPage>`, the palette's Domain names), so the label can't live on a View. `icon` stays on `SettingsPage` for now as View data that stays in the bin when the rest is lifted. Which page owns a revealed record is a Router decision: `SettingsPage::for_reveal`.
- **`Page` is the View.** The trait holds only what the page draws and the keys it takes: `FILLS_PAGE`, `FULL_WIDTH`, `set_page_focused(focused, cx)` (Display's focus hooks move into Display), with `EventEmitter<PageRowClicked>` as a supertrait so every page's row clicks are followed and `page_status` defaulting to `hints()` and `status_note()`. Page metadata does not go into `Page` impls.
- **One typed accessor.** `SettingsView::page::<T: Page>()` finds a page through `T::PAGE` and replaces the per-page accessors. The root Router reaches a page's commands (Tags merge, Accounts commands) through that module's Router, not the page's methods. The Tracing log feed stays a special case on the accessor until slice 12.
- **Snapshots are keyed on their type.** A `PageSnapshot` trait, implemented beside each snapshot, gives one `Root::settings_page_snapshot::<S>()` and one `Harness::settings::<S>()`, so the typed snapshots the UI tests read (ADR-0030) need no forwarder per page.
- **Palette page commands stay written out.** `COMMANDS` is `const`, so a test checks that each page in `SettingsPage::ALL` has a `settings <id>` command that opens it.

Considered: identity in each `Page` impl (rejected: it puts Presenter data in a `gpui` View, which slice 12 would move back out) and a single `PageMeta` table (rejected: it puts `DesktopIcon`, a View type, inside the identity, for little gain over the matches).

Consequences: a new page adds an arm to each `SettingsPage` match and to `SettingsPages::get`, its `Page` impl and its snapshot's `PageSnapshot` impl, and nothing in `shell/router/` or the harness.

## Amendment (2026-10-30): the keymap is the command palette's table

The 2026-10-30 Settings page amendment ("a Settings page's identity stays on `SettingsPage`") kept `COMMANDS` a `const` table, its rows written out. The palette then showed each key as a fixed default, so a `[keybindings]` override never reached it, and it had no entry for most global commands or any module page Command. Decided in the grilling of [#846](https://github.com/IanTeda/Personal-Ledger/issues/846), partly reversing that amendment:

- **Each binding decides.** `lib_viper::keymap::Binding` carries a `Palette`, `Listed { name, description }` or `Hidden`, so a module can't add a key and forget its palette entry. The name is `<domain> <verb>` (`units set-base`), a stable English id; the description is a Message in the module's `i18n/`, or `lib-locale`'s for the global keymap.
- **The palette reads the live keymap.** The Desktop builds the palette's entries as it opens, from the global keymap, `COMMANDS` and one registration line per module keymap (`navigation::command::module_entries`), each with the key `[keybindings]` binds it to now.
- **Running one goes through the keymap.** A global Command runs as its key does (`CommandEffect::Shell`). A module Command (`CommandEffect::Module`) opens its page, whichever View is showing, and the page sends the event `Keymap::event_for` finds for the name, through one `send`, so it commits once as the key does. The Tags merge Command is now Tags' `merge` binding, reached through that module's Router as that amendment wanted.
- **What stays in `COMMANDS`.** Only the Commands no keymap has: the `settings <id>` rows (still checked against `SettingsPage::ALL`), the `accounts new|edit|delete [<name>]` commands, whose argument a keymap event can't carry (so Accounts' `new`, `edit` and `delete` bindings are hidden), the noun aliases with no jump, the Budgets and Documents verbs until their slices give them keymaps, `open`, `new`, `close`, the Colour Themes and the Toast commands, `messages` among them as an alias of `toasts`. A test checks that no `COMMANDS` row repeats a Command a keymap lists.

Considered: keeping the `const` table and reading only the key column live (rejected: the table still had to be kept in step with every module's bindings by hand, the drift the Desktop Shell's design rule 3 forbids) and a palette entry beside each module's keymap rather than on its bindings (rejected: two lists per module to keep in step).

Consequences: a new binding chooses its `Palette`, a listed one adds its description Message, and a new module keymap adds one registration line and its page's `module_command`. The TUI's command popup doesn't read `Palette` yet.
