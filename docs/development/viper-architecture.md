# Personal Ledger - VIPER Architecture

This page describes the end state the Clients are moving to. It does not describe the code as it is today: tickets take the codebase from here to there, and [During the transition](#during-the-transition) lists what stands in for the parts not built yet. Slice 1 (Units and Price Sources, [#746](https://github.com/IanTeda/Personal-Ledger/issues/746)) built one module to this page, slice 2 (paying a Bill Schedule entry, [#774](https://github.com/IanTeda/Personal-Ledger/issues/774)) the first cross-domain write and Router call into another module, slice 3 ([#820](https://github.com/IanTeda/Personal-Ledger/issues/820)) `lib-shell` and `input.rs`, and slice 4 ([#829](https://github.com/IanTeda/Personal-Ledger/issues/829)) Payees, the first Settings domain, whose steps are [Migrating a domain](#migrating-a-domain); each slice's findings are folded in. The goal is a codebase that Claude can change one module at a time, that a person can review one layer at a time, and that grows by adding modules rather than by growing a central file.

## VIPER

VIPER splits each module (one area of concern, such as Bills) into five parts, each with one job. It comes from iOS apps, where controllers grew huge because they did everything. Each part talks only to its neighbours, and data flows one way through them.

- **View:** Draws what it's told and reports what the user does. It holds no logic and makes no decisions: it never formats a number or decides whether a button is enabled. It gets a ready-made view model, draws it, and passes the user's actions back to the Presenter as events ("Pay pressed on row 3").
- **Interactor:** The business logic, or use case: "pay this bill", "delete this payee if it has no transactions", "compute this month's budget actuals". It knows the rules and reaches storage through ports (traits), but it has no idea a View exists. One Interactor maps to one user intent.
- **Presenter:** The middle part, and the one most often skipped. It takes events from the View, decides which Interactor to call, and turns the results into something the View can draw: formatted Money, localised text, which rows are selected, whether a Dialog is open, error messages from refusals. It holds the View's state but no UI toolkit code, so it can be tested without a window.
- **Entity:** The plain data model: Account, Bill Plan, Transaction, Money. Structs plus rules about themselves only, like "is this Bill Schedule entry overdue on this date?". No I/O, and no knowledge of the other parts.
- **Router:** (also called the Wireframe) Navigation and assembly. It builds its module by wiring a View, Presenter and Interactor together, and opens the next View or Dialog. When the Presenter says "show Transaction 42", the Router makes it happen.

## How VIPER maps to this workspace

The [VIPER target architecture diagram](../diagrams/viper-architecture.html) shows one module end to end, from a key press to SQLite.

Personal Ledger has two Clients, the Desktop (gpui) and the TUI (ratatui), that show the same Ledger. So a module is split across two places:

- **A feature crate per domain**, `crates/libs/lib-<domain>`, holds everything that doesn't touch a UI toolkit: Entities, Interactors, Presenters, ports, the Router trait and the keymap. Both Clients share it.
- **A folder per domain in each bin**, `crates/bins/bin-<client>/src/<domain>/`, holds what does touch the toolkit: the Views and the Router implementation.

A module is a domain, not a View. `lib-bills` holds one Presenter per Bills View (list, form, detail), so one ticket usually touches one crate, and the crate count tracks the domain count.

### Why Views are not in the libs behind `cfg` flags

An earlier draft put each module's Views in its lib behind `#[cfg(desktop)]` and `#[cfg(tui)]`. We rejected that:

- Each crate would need a build, clippy run and test run per flag, and a lint failure behind the other flag stays hidden until CI.
- rust-analyzer, and Claude reading the code through it or through `cargo check`, see only one flag's code at a time, so half the module is greyed out or unchecked.
- A lib that depends on gpui loses the rule that libs are toolkit-free. That rule is what lets a Presenter be tested without a window and reviewed without knowing gpui.

    │   │   │   │   ├── view/          # top bar, rails, status line, command palette, Toasts
    │   │   │   │   ├── state.rs       # The frame's state the Presenter doesn't hold
    │   │   │   │   ├── router.rs      # Root Router: builds the Shell, hosts Views and Dialogs
    │   │   │   │   └── router/        # impl Root blocks, one per concern
    │   │   │   └── <domain>/
    │   │   │       ├── mod.rs
    │   │   │       ├── view/<view>.rs # Draws the view model, handles mouse, sends events
    │   │   │       ├── view/dialog/<dialog>.rs  # One per Dialog Presenter

    │   │   └── tests/ui/              # Wiring and drawing tests only
    │   ├── bin-tui/                   # Same shape as bin-desktop, drawn with ratatui
    │   └── bin-sync-server/           # Not VIPER: no Views. Reuses Interactors and ports
    └── libs/
        ├── lib-core/                  # Shared value types: RowID, Money, periods
        ├── lib-database/              # Adapter: implements the modules' ports with sqlx
        ├── lib-shell/                 # The Shell module (see below)
        ├── lib-viper/                 # Generic Presenter types: Keymap, form and Dialog views
        └── lib-<domain>/              # One VIPER module, toolkit-free
            ├── Cargo.toml
            ├── i18n/                  # This module's Messages
            └── src/
                ├── lib.rs
                ├── entity.rs          # Or entity/ when large
                ├── interactor/<use_case>.rs  # One file per user intent
                ├── presenter/<view>.rs       # View model + event enum + Presenter
                ├── protocols.rs       # Ports (repository traits) and the <Domain>Router trait
                ├── keymap.rs          # Default keys: command name + chord -> event
                ├── msg.rs             # This module's msg:: accessors, generated from i18n/
                ├── contract.rs        # Port contract suite, behind the contract-tests feature
                └── fake.rs            # In-memory port impls and stub seed, for tests and UI-first work

## Rules

These are the rules Claude follows and a review checks against.

### Dependencies

- A feature crate never depends on a UI toolkit (gpui, gpui-component, ratatui, crossterm), on `lib-database`, or on another feature crate. `deny.toml`'s bans and the `cargo metadata` test (`lib-ledger/tests/viper_dependencies.rs`) check this for each migrated crate.
- A feature crate may depend on `lib-core` and the shared toolkit-free libs: `lib-config` (for `[keybindings]`), `lib-locale`, `lib-list-cursor`, `lib-toast` (a Router sends the Shell `Notice`s) and `lib-viper`, and on `tracing` for its Interactors' events (ADR-0047).
- Value types shared across domains, like `RowID` and `Money`, live in `lib-core`. Generic types every module's Presenters and keymap use live in `lib-viper`, not in the first feature crate that needed them ([#760](https://github.com/IanTeda/Personal-Ledger/issues/760)): `keymap` holds `Keymap`, `Binding` and the flat command names modules share, and `view` a form's `TextFieldView`, `SelectView` and `Choice` and a Dialog's `DialogFrame`. It is not a feature crate and holds no domain; it keeps the feature crates' bans.
- An Interactor or Presenter that only reads another domain ("is this Payee used by a Split?", "which Accounts hold this Unit?") declares a read port in its own crate's `protocols.rs`, and `lib-database` answers it. It doesn't add a crate. `lib-units`' `UnitUsage` and `UnitHoldings` are the first.
- A read port returns types its own crate declares, never another feature crate's Entity: `UnitHoldings` returns a `Holding`, not an `Account`, and `lib-bills` reads a `BillAccount`, a `BillCategory` and a `BillSplit` ([#792](https://github.com/IanTeda/Personal-Ledger/issues/792)). The type names only the fields its crate reads, so a change to the other domain's Entity recompiles nobody. A fact the reading crate's rules need, such as whether an Account takes Transactions or a Category is a leaf, is a field the answering side fills by calling the owning domain's rule, so each rule lives once, in its own domain, and the reading crate checks it against the field rather than receiving a list filtered for it.
- Two crates may declare read types of the same shape, and that's deliberate: each says what it reads, and only the few lines mapping onto it repeat. When a third wants the same shape and it is a genuine value (an id and a display name, say), it moves to `lib-core` as a shared value type.
- Operations that write more than one domain live in a cross-domain module, one per user workflow (see Persistence). It may depend on the feature crates it writes; feature crates never depend on it.
- `lib-database` depends on the feature crates and the cross-domain modules and implements their ports, a cross-domain module's atomic port included (`BillPaymentsAdapter` implements `lib-bill-payments`' `BillPayments`). Dependencies point inward, toward the Entities. Only bins depend on `lib-database`. The Sync Server follows this too: `lib-rpc` is the wire protocol only (generated types, clients and server traits), and `bin-sync-server` implements `SyncService`'s `Push`/`Pull` over `lib-database`'s `change_sets` itself, as it already does `/authorize` and `/token` over `sync_users`. Ports would only add a seam with one implementation, outside the VIPER transition's scope ([#759](https://github.com/IanTeda/Personal-Ledger/issues/759)).
- No `cfg` flag selects a UI toolkit inside a lib.

### Entity

- Plain structs and rules about themselves only. No I/O, no clock reads (take the date as a parameter), no knowledge of Interactors or Presenters.

### Interactor

- One Interactor per user intent, in its own file.
- Reaches storage only through the ports in `protocols.rs`. Refusals are variants of the crate's error type: typed, never strings. It lives in `error.rs`, or beside the Entity when the Entity's own rules raise it (`lib-bills`' `BillError` in `bills.rs`, `lib-payees`' `PayeeError` in `entity.rs`).
- Knows nothing about Views, Presenters, Messages or keys.
- Enforces every rule itself, even one a Presenter already keeps a person from reaching (the Delete unit Dialog always offers a new base Unit, so `BaseUnitNeeded` is reachable only through the Interactor). A refusal no Client can reach is tested at the Interactor.

### Presenter

- One Presenter per View, holding that View's state.
- Its contract is `handle(event, router)` and `view_model()`, where `router` is a `&mut dyn <Domain>Router`. The view model is plain data: formatted Money and dates, localised text from `msg::` accessors, selection, enabled flags, which Dialog is open. The View never formats or decides anything.
- It doesn't hold a reference to its View. Both Clients redraw from the view model, so nothing calls into the View.
- It asks for navigation only through its module's `<Domain>Router` trait, which it is lent for each `handle` call rather than holding: the Desktop can open a Dialog only through the gpui context that call runs in.
- An enabled flag or an offered action comes from a read, not from a refused write. If a Unit in use can only be deactivated, the Presenter reads its usage before the person confirms a Delete, rather than offering Deactivate after the Interactor refuses ([#763](https://github.com/IanTeda/Personal-Ledger/issues/763)).
- What a View shows and where an outcome lands are separate settings. A Client that shows a detail pane is not thereby one that logs outcomes to ACTIVITY instead of raising Toasts ([#765](https://github.com/IanTeda/Personal-Ledger/issues/765)).
- A Dialog's Presenter holds its fields' values, focus, which fields show, validity and refusal text, and it tells the page Presenter its outcome when it closes, confirmed or cancelled.
- List movement goes through `lib-list-cursor`.

### View

- Lives in the bin. Draws the view model, handles the mouse for its own layout, and sends events to the Presenter.
- No business logic, no formatting, no hardcoded display text.
- Keeps a widget's own mechanics, which are the toolkit's and decide nothing: a text field's caret, a select's open list and highlight, a secret field's typed text before it is sent.
- On the Desktop, the bin wraps each page Presenter in a gpui `Entity` and calls `cx.notify()` after `handle`. A Dialog is an `Entity` too, holding its Presenter and the widget state that is gpui's (`shell/view/dialog_entity.rs`); the Shell's Dialog host holds the open one and closes it when the Dialog's Presenter does. The TUI holds every Presenter directly.

### Router

- Each module declares a `<Domain>Router` trait in `protocols.rs` (`show_transaction(id)`, `open_pay_dialog(bill)`), and each bin implements it in `<domain>/router.rs`. Routing is a module concern; only the implementation is toolkit-specific.
- A Router builds its own module: View, Presenter, Interactor and ports. On the Desktop it is built for each `handle` call around that call's gpui context, and the module's entry point (`units::router::units_page`) builds the page.
- `open_dialog` returns whether the Dialog opened, so a Presenter whose row went away under it doesn't record a Dialog as open.
- To go to another module, a Router calls that module's public entry point in the same bin (for example `transactions::router::show(cx, id)`). It never builds another module's View or Presenter itself.
- The Router doesn't handle keys.
- Every module Router, the cross-domain and Dialog Routers included, declares `lib-toast`'s `Notify` as a supertrait, so a Presenter tells the Shell things by sending a `Notice`: a Toast (`ToastKind` and text) or a status-line message. Only these one-way notices are shared; navigating and opening a Dialog stay typed methods on each module's Router, since they need module types and an answer. A module only sets the status line: the Shell clears it on the next keypress ([ADR-0048](../adr/0048-modules-notify-the-shell-through-one-lib-toast-trait.md)).

### Input

- Each module declares its default keys in `keymap.rs` as `lib_viper::keymap::Binding`s, a command name and its default chord mapped to an event, for example `pay` / `"p"` → `BillsListEvent::Pay`. `[keybindings]` Configuration overrides a key by command name, and both Clients share one keymap.
- A command name shared across modules stays flat (`new`, `delete`, `move_down`), so one override applies in every module; its constant lives in `lib_viper::keymap`. A command only one module has is namespaced by the module, for example `units.set_base`.
- `lib-shell` owns the keys that work in every View, its global keymap (`lib_shell::keymap`), under flat names a `[keybindings]` override moves: switching View (the `g` jumps), the command palette, Search, Help, the rail toggle, moving focus between the Shell and the View, the Toast keys, and list movement. A sequence (`g d`) is one chord whose first key is a prefix: the Presenter waits for the next key, and the bin's one-second timer ends the wait with a `PrefixExpired` input, so the Presenter never reads time.
- Each bin has one `input.rs`. It turns a toolkit key into chord text and offers it, in one fixed order, to (1) an open Dialog, which takes every key; (2) a mode left in the bin (on the Desktop the palette, Search, a filter, the file explorer, or a mode the View entered); (3) the Shell's global keymap; (4) the focused module's keymap, which sends the event to that module's Presenter; (5) a View not yet a module, with its own key handler. It doesn't grow when a module is added.
- The Shell keeps most of its keys, taking them at step 3, but falls back on the rest: focus `tab`, `a` (Insert), list movement and `enter` reach the Shell only once the module and the View have declined them, so a list's own `tab` or `a` wins. The movement commands keep the flat names each module binds (`move_down`, and `arrow_down`, `home`, `end`, `page_down`, `page_up` for the arrow, Home/End and Page keys, each its own command since `[keybindings]` gives a command one chord), so one override moves a list and the rails alike. A key that finishes a sequence (`g g`) reaches the module whole.
- The keys the Shell keeps win, so a module's default chord must not be one in either Client. Slice 1 found three clashes: `units.set_base`'s `b` is the Desktop's rail toggle, and `ctrl+u` and `g g` are TUI View jumps. `units.set_base` moved to `B` and the TUI dropped its `ctrl+u` shortcut to Units; `g g` stays the TUI's Tags jump. A test per Client checks every module's defaults against its global keys (`no_module_default_chord_is_a_key_the_shell_keeps` in the Desktop's `input.rs`, reading `lib_shell::keymap::keeps`, and `no_module_default_chord_is_a_global_key` in the TUI's `shell.rs`); a new module adds its bindings to each test's `module_defaults` ([#764](https://github.com/IanTeda/Personal-Ledger/issues/764)).
- A Dialog's keys are the Dialog keymap in `lib-shell` (`lib_shell::dialog`), under flat names: `select` (`enter`), `back` (`esc`), `next_field`, `previous_field`, `select_next`, `select_previous` and `submit` (`ctrl+enter`), so a `[keybindings]` override reaches every module's Dialogs. Not `confirm` and `cancel`, which `[keybindings]` binds to the TUI's `y` and `x`. What `select` means is the Dialog's call: it opens a closed select, picks from an open one, and otherwise confirms only a valid form; `submit` confirms a valid form from any field. On `back` the host closes an open select first, otherwise sends the Dialog's Presenter its `Cancel` and closes it. A key the keymap doesn't bind types into the focused field.
- A Presenter receives events (`Pay`), never keys (`p`).

### Tracing

- An Interactor logs each intent that changes the Ledger at `info`, done or refused; reads never log. Presenters, Views and Routers never log. Adapters and the writer log at `debug`, a failed write at `error` (ADR-0047, `/tracing`).
- A log field holds ids, kinds, counts and dates only, never an amount, a name or user-entered text.

### Localisation

- New UI text is a Message. A module's Messages live in its crate's `i18n/` and are read by its Presenter. A bin's own catalogue holds only text that belongs to one toolkit, such as the Desktop menu bar.
- A module's Message ids carry its domain as a prefix (`units-`), generated by `lib-locale-build` with `id_prefix`. A count in a plural is `{ $count }`, never a typed digit.
- A time or date in a view model is formatted by `lib-locale`, never by `chrono` in the Presenter ([#762](https://github.com/IanTeda/Personal-Ledger/issues/762) adds the minutes-only time ACTIVITY needs).

### Tests

- Entities, Interactors and Presenters have unit tests in their crate, run against the in-memory ports in `fake.rs`. These carry the behaviour coverage: a Presenter test is "send events, assert on the view model". `fake.rs`'s `RecordingRouter` records what the Presenter asked for, its Notices in one variant.
- Each View still has `<view>_keyboard.rs` and `<view>_mouse.rs` in the bin's `tests/ui/`, but they check wiring and drawing (the key reaches the Presenter, the view model is drawn), not behaviour the Presenter tests already cover. They run on the `fake.rs` ports, which the Desktop's `shell::router::build` takes as parameters, so they never open SQLite.
- An end-to-end smoke test per module runs the real app on a temporary SQLite file: start, change a row, restart, see it. It runs when a parent ticket closes and before a merge to `main`.

## The Shell module

The Shell is the always-present frame around the current View (see GLOSSARY.md). `lib-shell` is a VIPER module like any other:

- Its Presenter holds the Shell's state (the active View, focus and the input mode, the status line, the Toasts, the open Dialog) and builds the Shell view model, owned values with the Shell's own status-line hints keyed as the global keymap binds them after `[keybindings]`. A status message answers one key: the bin hands the Presenter every key before routing it (`keypress`), which clears the message, so one the key sets survives; clicks and ticks leave it. The Notices the Routers queue reach it when `send` drains them, each stamped with the local time for the Toast history.
- Its keymap holds the global keys, and it owns the `Noun` and `ActiveView` the bins navigate by (`ActiveView` generic over the bin's Settings page, whose names are Messages).
- It owns the Clock (`lib_core::Clock`), which each bin builds on the local date (`wall_clock`) and a test on a day it sets; every View and module is built with it rather than a date. The Presenter never reads time: the bin keeps every timer and delivers each tick: as an input, `DayTick` from the 60s day poll and `PrefixExpired` from the `g` timeout, and the Toast timer's time to `tick_toasts(now)` while a Toast is up, which writes nothing so it's no input, and answers whether the stack changed, the only time the bin redraws. In a new calendar month it calls `month_turned(today)` on its Router.
- Its Router, implemented in each bin's `shell/router.rs`, is the root Router: `main` calls `shell::router::build`, and it hosts whichever module's View is active and the one open Dialog.

## Out of scope

- **The Sync Server** has no Views, so it isn't split into VIPER modules. It reuses Interactors and ports where it needs domain rules.
- **The transition** from today's code to this layout is planned in tickets, not here: it starts with the slices decided in [#745](https://github.com/IanTeda/Personal-Ledger/issues/745). [During the transition](#during-the-transition) lists only what stands in meanwhile.

## Persistence

Each module owns its repository ports, replacing the single `LedgerRepository` ([ADR-0039](../adr/0039-ledger-persists-through-one-store-wide-repository.md), amended).

Ports are synchronous, and `sqlx` is async ([ADR-0046](../adr/0046-per-domain-adapters-hold-rows-in-memory-behind-one-shared-writer.md)). Each `lib-database` adapter holds its domain's rows in memory, loaded when the Client starts, and serves reads from there. A write changes memory at once and goes to one writer thread shared by every domain, which runs it in one database transaction. A failed write is reported on a channel the bin listens on, so it can reload, redraw and show an error Toast.

What that means for a module, as slice 1 built it (`lib-database`'s `adapter/units.rs` and `writer.rs`):

- **The bin ends each input.** A port write is one row (`upsert_unit`, `set_base_unit`), so a port can't tell where an Interactor call ends. Every adapter adds its writes to one pending batch on the writer, and the Desktop's `input.rs` `send` calls `commit()` exactly once after each Presenter `handle`, whether or not it wrote (an empty commit is a no-op), which sends the batch to the writer as one transaction. No port or store commits for itself, and a call from one module to another runs inside the current `send`, so its writes join that commit. Deleting a Price Source (N Unit moves and the delete) and deleting the base Unit (the move and the delete) each land whole, and so does a call that writes through two domains' adapters, or a month turn's Bills. Slice 1 kept the batch per adapter; slice 2 shares it ([#757](https://github.com/IanTeda/Personal-Ledger/issues/757)); slice 3 commits it in one place ([#823](https://github.com/IanTeda/Personal-Ledger/issues/823)).
- **The bins build on one bundle.** `Stores`, beside `Storage` in `lib-database`, holds each module's store, the commit and the failure channel, built by `Stores::from(storage)`; `Stores::fake` builds it on in-memory stores with a `CountingCommit`, so a test asserts one commit per input. The Desktop's `shell::router::build` and the TUI's `build_shell` take it as their one storage argument.
- **The bin reloads.** Ports know nothing about the failure channel, so on a `WriteFailure` the bin calls `reload()` on each adapter the failure names. On the Desktop a task polls the channel and sends each failure as an input (`ShellInput::WriteFailed`), so its Error Toast shows and the window redraws without a keypress. A failure also names the domains of the writes dropped behind it, since their adapters are stale too. If the reload fails, the rows in memory stand and the Toast says they aren't saved.
- **Loads go through the writer**, queued behind the writes, so a reload sees every earlier write and one runtime owns the pool.
- **A row may name a row defined in code.** A Unit's Price Source can be Manual entry (never stored) or a built-in with no override row (ADR-0043), so `units.price_source_id` has no foreign key. The schema says why, and the Interactor guards the link.
- **A port's rules match the schema's.** A foreign key the in-memory ports don't model fails only in SQLite, as a rollback the person can't explain. Each such constraint is an Interactor rule and a contract check ([#761](https://github.com/IanTeda/Personal-Ledger/issues/761): deleting a Unit other Units quote).

Each module's ports have a contract suite in its crate, behind a `contract-tests` feature, run against both `fake.rs` and the `lib-database` adapter: write, reload, and get the same rows.

An operation that writes more than one domain belongs to a cross-domain module, one crate per user workflow rather than per operation. It holds one Interactor per operation and one atomic port, which `lib-database` implements with one database transaction, so all of an operation's changes are saved or none are. The expected cross-domain modules are:

| Module | Operations | Domains written |
|---|---|---|
| `lib-bill-payments` | Pay a Bill Schedule entry directly | Bills, Transactions |
| `lib-document-filing` | Accept a Document, accept all | Documents, Transactions, Payees |
| `lib-transaction-import` | Commit an Import | Transactions, Payees |
| `lib-reassign` | Delete or merge a Category, Tag or Location, re-pointing the rows that use it | Categories, Tags, Inventory, Transactions, Bill Plans, Budgets, Documents |
| `lib-account-deletion` | Delete an Account with its Transactions, Unmatching the Bill Schedule entries they paid | Accounts, Transactions, Bills |

`lib-reassign` may split per domain if it grows. Account delete is today's forwarding shim (see [During the transition](#during-the-transition)), which fixed the stale Paid link it used to leave; it becomes `lib-account-deletion` when Accounts migrate. An operation that writes one domain and only reads another is not cross-domain: Match writes only the Bill Schedule entry and reads Transactions through a read port, so it is a `lib-bills` Interactor.

A cross-domain module may own the Dialog whose confirm calls its Interactor. `lib-bill-payments` holds the Pay Dialog's Presenter, both panels, because Pay it directly is its Interactor; the Match panel calls `lib-bills`' Match Interactor, which the module may depend on. It has its own `i18n/`, and each bin gives it a folder like a domain's (`bill_payments/view/dialog/`, `bill_payments/router.rs`). The Bills Router opens it through that folder's entry point (`bill_payments::router::open_pay(cx, entry)`), as it would another module's View.

A cross-domain module's atomic port serves the reads its Interactors check, as owned values, rather than an Interactor taking a feature module's port beside it. `BillPayments` answers `bill_plan` and `entry` as well as `record_payment`: the Bills ports and the payments adapter hold one shared Bills store, so an Interactor given both would borrow it twice ([#779](https://github.com/IanTeda/Personal-Ledger/issues/779)).

Units and Price Sources are one domain, `lib-units`, since they only change together, so deleting a Price Source and setting the base Unit are single-domain Interactors. The transition tickets confirm the list against the code.

## Migrating a domain

Slice 4 ([#829](https://github.com/IanTeda/Personal-Ledger/issues/829)) moved Payees, the first Settings domain, onto this page, and these are the steps it took, written from its findings log. A later domain's build tickets link here rather than restate them. The worked example is [Payees (development)](payees.md) and its code: `crates/libs/lib-payees/`, `lib-database`'s `adapter/payees.rs` and `bin-desktop/src/payees/`. Payees took four tickets, a straight chain: the prefactor ([#830](https://github.com/IanTeda/Personal-Ledger/issues/830)), persistence ([#831](https://github.com/IanTeda/Personal-Ledger/issues/831)), the page and Dialogs ([#832](https://github.com/IanTeda/Personal-Ledger/issues/832)) and the docs ([#833](https://github.com/IanTeda/Personal-Ledger/issues/833)). Each step below names the one that did it.

1. **The crate layout, and dropping feature-crate dependencies (#830).** Lay `lib-<domain>` out as [Layout](#layout) shows, after `lib-units`. Delete what exists only to read another domain, and grep the bins as well as the crates before calling a function dead: `lib_payees::usage` looked unused, but the Desktop's Delete Dialog counted Splits through it. Dev-dependencies count too, so a seed check that needs another domain's seed (a Payee's Default category is a leaf Category) moves to `lib-ledger`'s seed tests, which see both seeds.
2. **`MIGRATED` (#830).** Once the crate depends on no other feature crate, add it to `MIGRATED` in `lib-ledger/tests/viper_dependencies.rs`. `deny.toml`'s bans name the toolkits and `lib-database`, not each feature crate, so it needs no edit.
3. **A rule another caller still runs (#830).** While `lib-ledger` still applies one of the domain's rules to its own rows, write the rule over rows and a read port, not over the repository: `delete_payee(&mut Vec<Payee>, &dyn PayeeUsage, id)` let `lib-ledger` lend its Splits and Bill Plans as the usage port. The Interactor reads the rows from the repository, runs the rule and writes what changed.
4. **Read ports for domains not yet migrated (#830, #831, #832).** Declare each read of another domain as a port with the crate's own read type, by [Dependencies](#dependencies): `PayeeUsage` answers a `PayeeUse { splits, bill_plans }`, and `PayeeCategories` a leaf Category's id and label only. Answer it in `lib-database` where the other domain persists (the Payees adapter counts `splits` and `bill_plans`), and otherwise with an `impl` for `Ledger` in `lib-ledger` that the bin's ports copy before each event (`PayeeCategories` in `bill_reads.rs`), which is a transition row. Fill the port in every in-memory store, not only the adapter: the Desktop's in-memory Ledger and the UI harness count the stub's Splits and Bill Plans, or a used stub Payee is offered Delete. Decide what a failed read answers: Payees' usage fails open, offering Delete, because the foreign keys refuse the write and its Error Toast reloads. A cross-domain port that a shared store answers for another crate (`lib-bills`' `BillPayees`) needs a method on the store trait and a small bin-side wrapper, since the orphan rule stops `lib-database` implementing it for the domain's fake.
5. **Schema edits and the foreign keys a persisted domain lets in (#831).** Edit the domain's `create_<table>_table.sql` in place, then `mise run db` and commit `.sqlx`. The tables that name the domain gain foreign keys (`splits.payee_id`, `bill_plans.payee_id`), with no cascade where the Interactor's refusal is the person-facing rule and the key its backstop. A column that names a domain not yet persisted gets none (`payees.default_category_id`) and joins the foreign-keys transition row. Then grep every `::seed(` and adapter test factory that writes the referencing tables: the Transactions, Bills and Bill Payments factories had to seed the stub Payees first. Run the older per-entity modules' `sqlx::test`s as well, because they encode the old schema: `payees/delete.rs` asserted that an alias blocks a delete, the opposite of the new cascade.
6. **The one-file adapter, the store trait and `Stores` (#831, #832).** Write `adapter/<domain>.rs` after `adapter/units.rs` ([ADR-0041](../adr/0041-lib-database-one-file-per-entity.md), ADR-0046), its `<Domain>Store` trait and the in-memory fake's impl in `adapter/store.rs`, and its field in `Stores` and `Stores::fake`. `Stores::with_units` fills the new field with an empty store for the TUI's test fixture, so the TUI needs no edit (#849). Add a `Failing<Domain>` store, `Harness::with_failing_<domain>` (`bin-desktop/tests/ui/common/mod.rs`), an arm in the Desktop's `roll_back` (`shell/router/write_failures.rs`) and its two `desktop-toast-write-failed-<domain>` Messages. When the store is already shared (`SharedPayeesStore`, held by `LedgerStore`'s shim and the Bills reads), the module's ports own the boxed store and implement the store trait as well as the module's ports, so one `Rc<RefCell<…>>` coerces to every holder (`bin-desktop/src/payees/ports.rs`).
7. **The contract suite (#830, #831).** `contract.rs` sits behind the crate's `contract-tests` feature, which `lib-database`'s dev-dependencies enable, so `cargo test -p lib_<domain>` alone doesn't run it. A `PortsFactory` hook makes other domains name a row (`name_payee`), and the adapter's factory writes real rows for it, with whatever their foreign keys need. Leave out what the schema doesn't keep: the contract sorts a Payee's aliases, since `payee_aliases` has no order column. Its writes go through the Interactors, as `lib-units`' do; Payees' still apply the rules themselves ([#836](https://github.com/IanTeda/Personal-Ledger/issues/836)).
8. **Seed order (#831).** The domain's stub seed is its one seed, with ids that match the stub Ledger. Write it through `lib-database`'s `seed::stub` and the first-launch seed in `open_storage`, ahead of every domain whose rows reference it, and add it to the first-launch seed row. A cross-domain read the stub's own seed needs keeps a copy in `lib-ledger` until that seed goes, since a feature crate can't reach `lib-database` (the `Payee` to `BillPayee` mapping exists in both).
9. **The read copy and the forwarding shim (#831, #832).** The Views that aren't modules keep reading the domain from `Ledger`, through a read copy refreshed from the port after each write and on rollback (`LedgerStore::refresh_payees`, `reload_payees`). The writers that aren't modules keep their `LedgerCommand`s, and `LedgerStore::apply` forwards their changes to the port (`payees::ports::forward`), ahead of the domains whose rows name it: Import creates a Payee and books Splits naming it in one command. The module's own page leaves the shim, and the `LedgerChange` variants only it wrote go with it (`DeletePayee`); tests that used one as a sample move to another (`DeleteTag`).
10. **Dialogs on the Entity host (#832).** Move the page into `bin-desktop/src/<domain>/` (`ports.rs`, `router.rs`, `view/`), and delete its Settings page code and `OpenDialog` arm. A Settings module's ports reach `Root` through `settings::pages::SettingsSetup`: add a field there, not a parameter. Each Dialog is an Entity on the Dialog host reading its keys through `lib-shell`'s Dialog keymap, and raises its own Toast before it closes, so the page lands only the outcome. A module page overrides `Page::hints` with its Presenter's hints, which the default `page_status` and the `?` cheat sheet both read, so both follow `[keybindings]` ([#839](https://github.com/IanTeda/Personal-Ledger/issues/839)). A top-level View instead hands `?` a `HelpGroup` under its own heading Message through `ActiveViewEntity::help_group`, read from the hints its status line shows, as Bills does ([#845](https://github.com/IanTeda/Personal-Ledger/issues/845)). A Settings page overrides `page_status` as well only for a right-hand text of its own, as Payees does for its count. Take the domain out of the legacy-Dialogs row.
11. **The clash tests (#832).** Add the keymap's bindings to `module_defaults` in the Desktop's `no_module_default_chord_is_a_key_the_shell_keeps` (`input.rs`) and the TUI's `no_module_default_chord_is_a_global_key` (`shell.rs`), even while the TUI draws none of the module's Views.
12. **The "During the transition" rows (#831, #832, #833).** Each ticket's acceptance criteria name the row it adds, narrows or removes, and the last ticket checks every one of the domain's rows against the code.
13. **The UI tests (#831, #832).** Update `settings_<domain>_keyboard.rs` and `settings_<domain>_mouse.rs` for the Entity host, and add a test for each hand-off into the page (a Document's Payee link) and each shim writer reaching it (an Import's new Payee: `import_keyboard.rs`' `a_committed_new_payee_shows_on_the_payees_page_with_its_remembered_rule`, [#838](https://github.com/IanTeda/Personal-Ledger/issues/838)), asserting one commit for the writer's input: a legacy writer that commits through `send`'s legacy arm once per `apply` runs its handler inside `crate::input::send` and queues its Toast as a Notice (`TransactionsView::continue_import`). The keyboard test also opens `?` and checks it lists the status line's keys under the page's heading (`Harness::assert_cheat_sheet_matches_status`, [#839](https://github.com/IanTeda/Personal-Ledger/issues/839), [#845](https://github.com/IanTeda/Personal-Ledger/issues/845)). A smoke test shows a row surviving a restart and its readers seeing it from the adapter; a reader's Dialog may need a readback for it (`BillsSnapshot::plan_payee`).
14. **The docs and the findings log (#833).** Each build ticket adds its findings to a log on the parent, and the last brings `docs/<domain>.md` and `docs/development/<domain>.md` into line with `/end-user-docs` and turns every entry into a doc edit, an ADR or a ticket. The persistence and Ledger steps touch `migrations/`, `.sqlx/`, `lib-database` and `lib-ledger`, so expect those tickets to gate for review (`docs/agents/ticket-labels.md`).

## During the transition

Until every domain is a module and `lib-shell` is whole, these stand in, each removed when its condition is met. Slice 1 added them for Units (`bin-desktop/src/units/`, `bin-tui/src/units/`); slice 2 ([#774](https://github.com/IanTeda/Personal-Ledger/issues/774)) adds the Transactions and Bills ones (`bin-desktop/src/transactions/ports.rs` and `router.rs`, `bin-desktop/src/bills/ports.rs` and `router.rs`, `ledger_store.rs`); slice 4 ([#829](https://github.com/IanTeda/Personal-Ledger/issues/829)) adds the Payees ones (`bin-desktop/src/payees/ports.rs`, `ledger_store.rs`); slice 5 ([#847](https://github.com/IanTeda/Personal-Ledger/issues/847)) adds the Institutions ones (`bin-desktop/src/institutions/ports.rs`, `ledger_store.rs`).
