Desktop app: module structure and the road to persistence

A snapshot of crates/bins/bin-desktop four days after the 2026-10-08 review. Since then about 30 commits have moved Dialogs onto the host's confirm cycle, made LedgerStore the only copy of the Ledger, put writes onto Ledger commands, and moved four Views to render and handle their own input. The codebase is still mostly Shell, Chrome and Views over stub data. The next phase adds the service, controller and database layers behind each View, and this review is written with that in mind.

What changed since 2026-10-08

GoodView Entities render and handle their own input (ADR-0037)

Bills, Budgets, Transactions with Import, and Documents now implement Render. Settings is in progress in the working tree, which moves about 1.7k lines out of app/settings_ui.rs, app/render.rs and app/key_dispatch.rs into view/settings/. Every per-destination match is now in view/active.rs, and all 111 edit_*_state hatches are gone. This is the most valuable change in the period: it gives each screen a natural home for a controller.

It isn't finished. Accounts, Categories, Tags, Payees, Units, Inventory, Institutions, Dashboard and Help still render through Shell. There are still 48 *Props structs and 132 On* callback aliases. Shell also still builds and renders domain Dialogs: app/budgets_ui.rs is 978 lines of open_budgets_*, render_budgets_form_dialog and run_budgets_manage_action.

GoodOne Dialog confirm cycle (DialogForm and Apply)

Every domain Dialog now goes through the host's confirm, refuse and reopen cycle, and dialog_mut::<T>() replaces 20 accessors. A form describes a command, Apply runs it against the Ledger, and a refusal comes back as a Message. This is the right shape for a controller: validation in the form, the decision in the Ledger, the wording in the bin.

One thing to change: the traits live in chrome::dialog_apply, so every domain module's apply.rs imports chrome, and chrome::dialog_host imports every domain's Dialog type for OpenDialog. The closed OpenDialog enum is fine as the single registration point, like ActiveViewEntity. But the traits belong in the existing dialog module, not in Chrome.

GoodUnfinishedLedgerStore is the only copy, and writes go through Ledger commands (ADR-0038)

Payees, Categories, Tags, Accounts, Transactions with Import, Bills and Budgets now write through typed LedgerCommands with per-command refusals. LedgerStore::apply drains the recorded LedgerChanges and emits one LedgerChanged { what }. This is the seam the database will plug into (ADR-0039), and it was the right thing to do before persistence.

The migration has left three dual paths:

  • Hatch writes. LedgerStore::write/try_write are deprecated but still have 17 callers, in view/documents/state.rs and the inventory, units and institutions stores. A hatch write records no LedgerChange, so when persistence lands these writes will be silently lost on save.
  • Per-domain stores. Payees, Units, Institutions and Inventory stores, and the ledger_data::LedgerDataEvent they emit, still re-broadcast LedgerChanged. ADR-0038 says they go.
  • Direct domain-crate dependencies. The bin still depends on all 11 domain crates (about 60 references) next to lib_ledger. ADR-0038 says Clients depend on lib-ledger only, so Cargo can enforce that writes go through the Ledger. Until then nothing stops a new View from mutating domain types directly.

GoodSmaller fixes

  • lib-list-cursor (#591): one movement model for every list.
  • The Unit kind is stored as lib_core::UnitKind instead of a localised label. Data no longer depends on the Locale, which would have broken the moment it reached the database.
  • Dialog key tests moved out of dialog_host.rs into their domains.

WatchOverall

The direction is sound and matches the ADRs. The risk isn't any one decision; it's that four migrations are each part-way done: Render, the per-domain stores, the hatch writes, and the domain-crate dependencies. Each one keeps two ways of doing the same thing alive. Adding services, controllers and a database now would mean writing a third path next to two old ones. Finish the migrations first.

Recommended architecture changes

1. Don't add a separate service and controller layer per View: you already have them

The usual web-app "service, controller, repository" vocabulary maps onto what ADRs 0037 to 0039 already decided. Adding a PayeesService and PayeesController in the bin would bring back the per-domain stores ADR-0038 removed.

Layer you're about to addWhere it already livesOwns
Service (business rules)lib-ledger commands and queries, single-entity rules in domain cratesValidation that needs data, cross-domain writes, refusals, the LedgerChange list
Controller (input → intent)The View Entity, plus its forms' DialogForm and ApplyView state, keys, clicks, which command to build, mapping refusals to Messages
Model store and eventsLedgerStoreThe one Ledger, LedgerChanged { what }
Repository (database)LedgerRepository in lib-ledger, SQLite adapter (ADR-0039, #636)load(), apply(changes) in one transaction
View Entity ── DialogForm::command() ──▶ Apply ──▶ LedgerStore::apply(cmd)
     ▲                                                 │  cmd.run(&mut ledger)   (sync, pure)
     │                                                 │  drain_changes()
     └──── LedgerChanged { what } ◀───────────────────┤
                                                       └─▶ LedgerRepository::apply(changes)   (one tx)

The database plugs in at exactly one place: LedgerStore::apply. If a View needs "a service", that's a new Ledger query or command, not a new type in the bin.

2. Finish the migrations, in this order, before #636

  1. Move the 17 hatch writes onto Ledger commands, then delete LedgerStore::write, try_write and Ledger::hatch. This is the hard gate, because hatch writes can't be persisted.
  2. Delete the Payees, Units, Institutions and Inventory stores and ledger_data.rs. Views subscribe to LedgerStore and filter on what.
  3. Re-export what the bin needs from lib_ledger and remove the 11 domain crates from bin-desktop/Cargo.toml.
  4. Switch ids to RowID newtypes (ADR-0040, #635). Every command in the bin still carries u32 (for example PayeeCommand::Edit(u32, …)), and that churn is cheaper before a schema depends on it.
  5. Finish ADR-0037 for the remaining Views, so that every View has a controller home before it gets real data.

3. Organise the bin by feature, not by layer

Today one domain lives in three places: src/payees/ (forms, apply, store), src/view/payees/ (View Entity, Dialog rendering) and src/app/payees_ui.rs (Shell wiring). That split causes the upward edges in the graph (domain modules importing view and chrome) and means touching three directories per change. As each View finishes ADR-0037, fold all three into one slice:

src/view/payees/
  mod.rs        PayeesView: Render, keys, page_status, snapshot
  state.rs      list state, selection (lib-list-cursor)
  form.rs       PayeeForm, DialogForm impl
  apply.rs      Apply impl → lib_ledger commands
  dialogs.rs    Dialog rendering

The target is app/*_ui.rs at zero files, and Shell at navigation, Chrome, the Dialog host, Toasts and view/active.rs. Shared building blocks (form, dialog, theme, locale, format) stay at the top level and never import a feature.

4. Decide the async boundary in LedgerStore, once

Keep Ledger commands synchronous and pure, as ADR-0039 says. Then LedgerStore::apply applies the command in memory, emits LedgerChanged straight away so the UI stays responsive, and hands the drained changes to one serial writer task on gpui's background executor. If a write fails, raise an error Toast (ADR-0027) and reload with load(). The serial queue keeps writes in command order, and that same queue can become the Change Set outbox for sync (ADR-0009). Views never await storage.

5. Smaller structural fixes

  • Rename persistence. It saves window and navigation restart state, not Ledger data. Call it session_state (or similar) before "persistence" starts meaning the database. That also clears up the navigation ↔ persistence cycle.
  • Move DialogForm, Apply and FormError from chrome::dialog_apply into dialog, so domain code doesn't import Chrome and the chrome ↔ dialog cycle goes away.
  • Collect the reusable field widgets into form: view/accounts/select_field.rs, view/payees/rules_field.rs, view/tags/colour_field.rs and view/form_fields.rs are general widgets living inside one feature.
  • Test persistence through one contract suite. Write one LedgerRepository test suite and run it against both the stub adapter and SQLite (sqlx::test). The headless UI tests stay on the stub (ADR-0030), and the contract suite proves the two adapters agree.
  • Watch the big files as real data arrives: documents/form.rs (1.5k lines), app/render.rs (1.3k), view/budgets/state.rs (1.3k), inventory/form.rs (1.2k). They're not urgent, but they're where the controllers will grow.
