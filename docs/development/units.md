# Units (development)

End-user documentation: [Units](../units.md).

## Overview

A Unit is what a balance, principal or holding quantity is denominated in — fiat money like AUD, or a tradeable non-currency instrument like AAPL or bitcoin. Every Account has exactly one Unit, fixed at creation. `lib-core` owns the `UnitKind` enum, `lib-database` owns the `units` table and its CRUD, and the desktop Client has the most complete Unit UI in the codebase: a real Settings section with working add, edit and delete dialogs.

The defining constraint on this domain is that **Personal Ledger does not convert between Units in V1.** There is no exchange-rate table and no price-snapshot table, and the units migration says so explicitly.

## Data model

`units` (`crates/libs/lib-database/migrations/client/20260904100000_create_units_table.sql`):

| Column | Type | Notes |
| --- | --- | --- |
| `id` | UUID | Primary key, a `RowID` (UUIDv7) |
| `code` | TEXT | Unique, not null — e.g. `AUD`, `AAPL` |
| `name` | TEXT | Not null — note **not** unique, unlike `code` |
| `unit_kind` | TEXT | Not null; `CHECK`ed against the six Unit Kind tokens |
| `precision` | INTEGER | Not null, `CHECK`ed 0 to 18; defaults to 2 only for the older per-entity queries, which don't write it |
| `price_source_id` | TEXT | Not null; **no foreign key** (below) |
| `price_symbol` | TEXT | Not null |
| `quote_unit_id` | UUID | Not null, references `units`; the base Unit quotes itself |
| `is_active` | BOOLEAN | Not null, defaults true |
| `created_on`, `updated_on` | TEXT | ISO-8601 UTC; `updated_on` maintained by `trg_units_set_updated_on` |

`unit_prices` (`20260904100100_create_unit_prices_table.sql`) holds a Unit's Weekly Prices (ADR-0052): one row per Unit per ISO week, keyed by `(unit_id, week)` where `week` is that week's Monday, with a required `close`, optional `open`, `high` and `low` as decimal strings, and `written_on`, when the row was last written. `unit_id` cascades on delete, so a deleted Unit takes its Weekly Prices with it. The adapter writes a Unit's whole list afresh on each upsert.

`price_sources` (`20260904090000_create_price_sources_table.sql`) holds a Custom source's endpoint and key placement, or a person's name and update interval for a built-in. `ledger` (`20260909100000_create_ledger_table.sql`) holds the one `base_unit_id`, referencing `units`.

Invariants and gaps:

- **`units.price_source_id` has no foreign key.** Manual entry is never stored, and a built-in has a `price_sources` row only once it is renamed or retimed (ADR-0043), so a valid Unit can name an id with no row. `lib-units`' `AddUnit` and `EditUnit` refuse a link to a source that doesn't exist instead (#746's findings, #752).
- **`price_sources` has no Unit Kinds column.** `lib_units::CustomSource` declares none: a Custom source is offered for every Kind, so the column would always be empty. Add it if Custom sources gain Kinds.
- **No column holds an API key** (ADR-0043's amendment); only where a key goes in the request.
- **A Unit referenced by an Account, a Bill Plan or a Budget must not be deleted**, only deactivated, the same lifecycle as Category, Payee and Account. `lib-units`' `DeleteUnit` Interactor refuses it through the `UnitUsage` read port. The Delete unit and Edit unit Presenters read the same port when the Dialog opens, so Deactivate, its disabled state for the base Unit and the usage counts are offered up front; the Interactor's refusal stays for a Unit that came into use under an open Dialog (#763).
- **Deleting a Unit an Institution names as its Usual unit reassigns the Institution**, in the same write. Units and Institutions are two domains, so this delete is the cross-domain module `lib-unit-deletion` (#902), not `lib-units`: its `DeleteUnit` runs `lib-units`' delete rules unchanged through `DeleteUnit::check`, but without the Institutions in the usage, then writes each Institution's new Usual unit (or none, the default, never silently the base Unit), the base's move and the Unit's removal through one atomic port, `UnitDeletion`, which `lib-database`'s `UnitDeletionAdapter` implements over the Units and Institutions stores. Its Delete unit Dialog Presenter adds one Usual unit select per Institution to `lib-units`' Dialog, and hands a Unit anything else names to `lib-units`' Dialog, which deactivates. `lib-units`' own `DeleteUnit` still refuses a Unit an Institution names (`UnitUse::institutions`), since it can't reach them; the TUI, with no Institutions screen, keeps that refusal. The Desktop hosts the new Dialog from `unit_deletion/` (#903): the Units page's Router opens it for Delete unit in place of `lib-units`' Dialog, and its adapter shares the Units and Institutions ports the two modules hold, which implement `UnitsStore` and `InstitutionsStore` for it, so the delete joins the input's one commit.
- **A Unit other Units are quoted in must not be deleted**, since `units.quote_unit_id` references `units` and SQLite refuses the delete. `DeleteUnit` counts the quoting Units from the Unit repository itself and refuses with `QuotedBy(n)` before any write; it doesn't re-quote them, which would clear their Weekly Prices. `contract::deleting_a_quoted_unit_is_refused_and_writes_nothing` runs against the in-memory ports and the adapter (#761).
- **A Unit's quote must be a Unit on the Ledger**, for the same foreign key. `AddUnit` and `EditUnit` refuse a quote Unit that isn't there with `QuoteGone` before any write, which only happens when it was deleted under an open Dialog. A Unit may quote itself, as the base Unit does: `AddUnit` takes the new Unit's id from its caller so a self-quote names a Unit, and the Add unit form quotes the first Unit on an empty Ledger in itself. `contract::a_gone_quote_unit_is_refused_and_writes_nothing` runs against the in-memory ports and the adapter (#789).
- **No conversion tables exist, by decision.** FR.2 and FR.3's cross-Unit exchange-rate machinery is superseded by the "no cross-Unit conversion in V1" rule in `GLOSSARY.md`'s Unit entry and the Constraints section of `docs/product-requirements.md`. A Unit's own Weekly Prices, in its quote Unit, are kept (ADR-0052), but nothing converts between Units with them.

## Domain types

- `lib_core::UnitKind` (`unit_kind.rs`) — the six Unit Kinds: `Currency`, `Crypto`, `Equity`, `FixedIncome`, `Commodity`, `Custom`, stored as `currency`, `crypto`, `equity`, `fixed_income`, `commodity`, `custom`. Parsing it is the only guard on the `unit_kind` column.
- `lib_units::Precision` (`entity/precision.rs`) — a Unit's decimal places, 0 to 18 (`Precision::MAX`, Ether's wei; `Money` itself has no limit). `Precision::of_kind` is what Add unit starts on: 8 for Crypto, 2 for every other Kind. It only formats: the Units pane shows a balance at its Unit's Precision (`AmountStyle::fixed`) and a price or value at its quote Unit's, and `WeeklyPrice::value` rounds to the quote's; no stored amount is rewritten when it changes (#914). Formatting an amount in a Unit elsewhere (Accounts, Bills, Bill Payments, Account Deletion, both Clients' amount helpers) still uses the amount's own places.
- `lib_core::PriceSourceId` (`ids.rs`) — a Price Source's id. Manual entry and the built-ins have fixed ids (`lib_units::MANUAL_ENTRY`, `COINGECKO`, `YAHOO_FINANCE`, `FRANKFURTER`).
- `lib_core::Money` (`money.rs`) — a `BigDecimal`-backed amount, stored as arbitrary-precision TEXT. Amounts are converted with `to_plain_string()` and never through `f64`, and are summed in Rust rather than by SQL `SUM()`.
- `lib_core::RowID` — UUIDv7 primary key.

`UnitKind` has a `Label` implementation in `lib-locale` (`vocabulary.rs`), so variants render through `unit_kind.label()` rather than their stored token. Currency formatting is Locale-aware and lives in `lib-locale`'s `format/currency.rs`: the **Unit** decides what is shown (its code and fraction digits), the **Locale** decides how (separators, symbol placement, disambiguation such as `A$` for an `en-US` reader). Fiat Units go through the ICU4X currency formatter; non-fiat Units format the quantity as a decimal and place the Unit code through a Message. See [ADR-0021](../adr/0021-locale-owns-formatting-and-replaces-number-and-date-preferences.md).

## Price Sources

Saved to SQLite by both Clients (see Persistence); fetching is not built. `lib-units` (`price_source.rs`) holds the model, following [ADR-0043](../adr/0043-built-in-price-sources-are-code-referenced-by-id-and-api-keys-never-sync.md):

- `BUILT_IN_SOURCES` is a `const` table of `BuiltInSource`s, each with an `Endpoint` (address, request template with `{symbol}` and `{quote}`, a JSON-pointer price path, and `PriceSourceAuth`, which names an API key's parameter or header but never holds the key), default `Updates` and the Unit Kinds it prices.
- The Ledger stores `PriceSourceRecord`s: a `BuiltInOverride` (a built-in's id with the person's name and `Updates`) or a whole `CustomSource`. Manual entry is never stored.
- `price_sources` resolves the records into `PriceSource` views, sorted by current name ignoring case, with Manual entry sorted in. Manual entry's name is a Message, so the Client passes it in. `sources_for_kind` filters to the sources able to price a Kind; `last_fetched` is the newest last price's `written_at` among a source's Units.
- Each `UnitRow` carries a `PriceLink` (`source_id`, `symbol`, `quote`) and its `prices`, a `Vec<WeeklyPrice>` oldest week first (ADR-0052). `last_price()` is the newest Weekly Price, whose `close` is the last price and `written_at` its age. `record_price` writes a price into the Clock's week: a new week starts with a close only, and the current week's entry is provisional, its close overwritten and its high and low widened. Editing a Unit keeps its Weekly Prices unless the quote Unit changes, which clears them. They sit on the row rather than a store of their own because the Units page reads every Unit's last price and the Unit prices view one Unit's history, both from the Units it already holds.

`lib-units`' Interactors (`interactor/`) hold the rules, one per user intent: `AddPriceSource` (Custom only), `EditPriceSource` (refused for Manual entry, or for a built-in given an endpoint) and `DeletePriceSource` (refused for a built-in or Manual entry; it moves the source's Units to Manual entry, keeping their Weekly Prices, in the same Interactor call). `AddUnit` and `EditUnit` carry the link and refuse one naming a source that doesn't exist. `SetPrice` writes a Weekly Price by hand through `UnitRow::set_price`: the week holding the Clock's day takes it as `record_price` does, an earlier week is written final, its entry replaced by the close alone, and it refuses a Unit not on Manual entry (`PricedBySource`) and a week after the current one (`FutureWeek`) (#917). Its Dialog, `SetPricePresenter`, reads the Week as a date through `lib-locale`'s `parse_date_with`, shows the Monday it snaps to, and pads the Close to the quote Unit's Precision, never rounding it; the page offers it as `MenuAction::SetPrice` (menu, pane button and the `units.set_price` key, `p`) only on a Manual entry Unit, and a Manual entry Unit's PRICE SOURCE pane group shows its Last price and Last updated.

The Unit prices view (#918) is `presenter/unit_prices.rs`'s `UnitPricesPresenter`, one Unit's Weekly Prices in a 52-week window ending in the week of the Clock's day less a count of months: `[` (`units.earlier`) adds a month and `]` (`units.later`) takes one off, stopping at the current week. A count rather than a stored day, so `]` after `[` returns to the same week whatever the month's length. Its view model carries the PRICE figures (last price and age, week change, 52w range, symbol · priced in), the chart's weeks oldest first as plain numbers (a close-only week repeats its close as open, high and low, `candle: false`), the table's rows newest first at the quote Unit's Precision with the change on the week before, and an empty-state Message. The page opens it through `UnitsRouter::open_prices`, from `MenuAction::Prices` (menu, pane button) and `UnitsPageEvent::Open` (`units.open`, `enter`, which on a Price Source row edits it instead); `UnitPricesEvent::Back` asks `close_prices`. Each Client holds the prices Presenter beside the page's and draws it in place of the tables, so closing it leaves the page's selection as it was: the Desktop's `UnitsPage` (`view/page/prices.rs`, `gpui-component`'s `CandlestickChart`; `Esc` reaches it through `Page::escape`), the TUI's `UnitsView` (`view/prices.rs`, drawn cell by cell; the Shell's back key reaches it through `View::back`), which Settings › Units hosts too. Its keymap is `keymap::UNIT_PRICES_BINDINGS`; `esc` is the Shell's, so it isn't in it.

## Persistence

The Desktop saves Units, Price Source records and the base Unit through `lib-database`'s `UnitsAdapter` (`adapter/units.rs`) and the shared `Writer` (`writer.rs`), per [ADR-0046](../adr/0046-per-domain-adapters-hold-rows-in-memory-behind-one-shared-writer.md). At start `main` calls `lib-database`'s `open_storage` (`storage.rs`), which the TUI calls on `:open` or `:new` instead: `Writer::open_ledger` creates the `[Personal-Ledger]` `file` if it is missing and runs the client migrations, then the adapter loads, blocking. If any of that fails, the Desktop logs the error and exits. A Ledger with no base Unit is new, so it is first seeded with `InMemoryPorts::stub`'s Units and base Unit, which the stub Accounts, Bill Plans and Budgets name (#746's first-launch seed, removed once every domain persists). `build_shell` takes `lib-database`'s `Stores` (`storage.rs`), built from `Storage`: a `UnitsStore` (`adapter/store.rs`), implemented by the adapter and by the in-memory ports the UI tests use (`Stores::fake`), and a `Commit` (`commit.rs`), `Storage`'s `PendingWrites`, the one batch every adapter adds its writes to, or a counting fake. Every Units key, click and Dialog confirm is one input (`input.rs`'s `send`), which commits its writes, every adapter's, as one transaction once the Presenter has handled it; `ports::refresh` then brings the `Ledger` read copy in line. The app flushes the writer when it quits. `Stores` also carries the writer's failure channel, which the Shell polls (`app/write_failures.rs`), sending each failure as an input: when a failure names the Units, `ports::reload` puts the adapter back to the rows as stored and refreshes the `Ledger` read copy, so the Units page and the Bill Plan form's Unit picker redraw, and an error Toast says so. If the reload fails too, the rows in memory stand and the Toast says they aren't saved. The UI tests `a_failed_write_…` and `a_failed_reload_…` in `settings_units_keyboard.rs` drive this on a failing store (`Harness::with_failing_units`). The end-to-end smoke test, `tests/ui/smoke_units_persist.rs`, runs this start-up on a temporary file: it adds a Unit, restarts and finds it.

The older per-entity queries:

`crates/libs/lib-database/src/units/` — `model.rs`, `builder.rs`, `find.rs`, `insert.rs`, `update.rs`, `delete.rs`, `mod.rs`. No `totals.rs`: totals are always per-Account or per-Category within a Unit, never across Units.

The base Unit is the one-row `ledger` table's `base_unit_id` (ADR-0044); `Preferences::get_or_create_default` no longer seeds a Unit, and `preferences/update.rs` tests that it doesn't.

## UI

- **Desktop** — the first View on a VIPER module (#751). `crates/bins/bin-desktop/src/units/` holds the Units Views and `impl UnitsRouter`; every rule, every piece of text and the keymap are `lib-units`'. `view/page.rs` wraps `lib-units`' page Presenter in a gpui Entity, which the Settings View hosts through `units_page`, the module's entry point in `router.rs`: it looks up each key the Shell passes on, as chord text, in the Units keymap (step 4 of `input.rs`'s key route: the keys the Shell keeps, `b` among them, never reach it, and `g g` arrives whole once the Shell's `g` prefix finishes it; the arrow, Home/End and Page keys are the keymap's own bindings), a click into an event, and draws the page view model (`view/page/render.rs`) and, at X-Large, its detail pane (`view/page/pane.rs`). `view/dialog.rs` holds each Dialog's Presenter in a gpui Entity in the Dialog host (`chrome/dialog_entity.rs`), one View per Dialog in `view/dialog/`, keeping only gpui's widget state (which select's list is open); its keys come through `lib-shell`'s Dialog keymap, Confirm and `back`'s Cancel go to the Presenter, and a Dialog that closes hands its outcome back to the page, which raises the Toast or logs ACTIVITY. `build_shell` takes a `UnitsStore`: the app passes the SQLite adapter (see Persistence), and the UI tests pass `lib_units::fake::InMemoryPorts::stub`. `ports.rs` holds #746's halfway shims: `UnitUsage` and `UnitHoldings` answered from the `Ledger`, and the Ledger's read copy of the Units, the base Unit and the Price Sources refreshed after every Units event (`LedgerStore::refresh_units`, announcing `Domain::Units`), so Bills, Budgets, Transactions, the Dashboard and the Bill and Budget forms see a write at once. The General page's *Base unit* select and the Units page's Set base unit Dialog both run `lib-units`' `SetBaseUnit` Interactor on the same ports. The Dialog opens with `units.set_base`, `B` by default, since `b` is the Shell's rail toggle ([#764](https://github.com/IanTeda/Personal-Ledger/issues/764)). Tests: `settings_units_keyboard.rs` and `settings_units_mouse.rs` check wiring and drawing only; the rules are the Presenter tests'. Spec: `docs/ux/desktop-mockups/16-settings/README.md`.
- **TUI** — the second Client on the same Presenters (#755). `crates/bins/bin-tui/src/units/view/units.rs` holds `lib-units`' page Presenter and draws its view model in the §4a layout of `docs/ux/tui-mockups/07-units/README.md`: the Units and Price Sources tables above the selected row's summary on the left, the weekly close and weekly prices regions (which say `Enter` opens a Unit's prices) above the keys box on the right. A key becomes chord text for the shared Units keymap; the arrows walk the tables and `Enter` opens the selected Unit's prices view, or edits a Price Source. The Shell's global keys come first (`Shell::global_key`), so `g g` (Tags) never reaches the keymap and `Home` moves to the first row instead. The rest of `crates/bins/bin-tui/src/units/` holds: `view/dialog.rs` hosts each Dialog Presenter as a floating window (text fields append and backspace, `←`/`→` step a select, `Tab` moves, `Enter` confirms, `Esc` cancels), and while one is open the View takes every key but `Ctrl+C` (`View::dialog_open`); `router.rs` is `impl UnitsRouter`, which collects what a Presenter asked for, a status Notice reading as an Info Toast; `ports.rs` answers `UnitUsage` and `UnitHoldings` from `Ledger::stub()` (#746's shim; the TUI's other Views keep their fixtures, so there is no read copy to refresh). The TUI starts with no Ledger open (#871): the Shell opens a Ledger file through `lib-database`'s `open_storage` on `:open [path]` (the `[Personal-Ledger]` `file` with no path) or `:new <path>`, and builds the Units on the same `UnitsStore` and `Commit` as the Desktop's from the `Stores` it returns. It commits after every Presenter call, polls the failure channel on each tick (rolling the Units back with an error Toast) and flushes the writer on `:close` and on quit. Tests: `tests/units_keyboard.rs` on the in-memory ports checks wiring and drawing; `tests/ledger_file_keyboard.rs` adds a Unit after `:new` on a temporary file and finds it after `:close` and `:open`.

## Open questions and known gaps

- **Price Sources never fetch.** Where fetching runs and where a Client keeps API keys are open (ADR-0043). The Desktop's Test price source and Test with symbol still say "not yet built".
- **The Bill Plan form's Unit picker offers only Units an Account is in**, since a Bill Plan's Unit follows its Account, so a Unit just added appears there only once an Account holds it.
- **No Change Set emission**, so Unit writes do not sync.
