# Settings (development)

End-user documentation: [Settings](../settings.md).

## Overview

"Settings" covers two genuinely different things in this codebase, and confusing them is the commonest mistake in this domain:

- **Configuration** — deployment-time values needed before the app, or its database, can start. Read from INI files, environment variables and CLI flags by `lib-config`. Edited outside the running app. Never synced.
- **Preferences** — runtime values a user edits from inside a running Client. Ledger-scoped ones are stored in the Ledger's own database by `lib-database` and sync via Change Sets like other Ledger data; a device's settings (Toasts, Colour Theme, Colour Appearance, date style and On start) are Configuration in the `[General]` and `[Display]` sections (ADR-0053, ADR-0057), which Settings writes back through `lib_config::ConfigWriter`, and never sync. The TUI reads and writes them there (#981); the Desktop still keeps them in `desktop-state.json` until #982, so until then the two Clients don't share them.

[ADR-0014](../adr/0014-preferences-table-and-leaner-sync-server-config.md) draws the line: Configuration covers only what is needed before the database can run — the database location and the tracing level. Everything else the user might tweak is a Preference. A third category, the **Locale**, is Configuration rather than a Preference by [ADR-0021](../adr/0021-locale-owns-formatting-and-replaces-number-and-date-preferences.md), because it must be resolved before any UI string is rendered.

## Data model

### Configuration

No tables. `lib-config` deserialises INI into `LedgerConfig` (re-exported as `lib_config::Config`), whose sections are:

| Section | Type | Read by |
| --- | --- | --- |
| `[General]` | `GeneralConfig` | `bin-tui`, `bin-desktop` |
| `[Display]` | `DisplayConfig` | `bin-tui`, `bin-desktop` |
| `[Logs]` | `LogsConfig` | All three binaries |
| `[keybindings]` | `KeyBindingConfig` | `bin-tui`, `bin-desktop` (the Sync Server merges defaults but never reads them) |
| `[theme]` (plus `[theme.light]`, `[theme.dark]`) | `ThemeConfig` | `bin-tui`, `bin-desktop` |
| `[Sync-Server]` | `SyncServerConfig` | `bin-sync-server` only |

Each Settings page with keys has its own section (ADR-0057), a field of `LedgerConfig`. `GeneralConfig`: `on_start: OnStart`, `start_view: StartView`, `toasts: bool`, `locale: Option<String>`, `data: PathBuf` (the folder `:open` starts in) and `file: Option<PathBuf>` (an explicit override of On start, with no default). `DisplayConfig`: `colour_theme: Option<String>`, `colour_appearance: ColourAppearance`, `date_style: Option<DateStyle>`, `row_density: RowDensity` (Desktop only), `status_glyphs: StatusGlyphs` (both Clients), and `hint_bar: bool` and `terminal_colours: bool` (TUI only, ADR-0024). `LogsConfig`: `log: lib_tracing::Levels` and `log_file_path: Option<PathBuf>`. There is no `config` key: only `--config` picks the file. `[Personal-Ledger]` is neither read nor migrated. `StatusGlyphs` and `RowDensity` are `lib_core`'s, re-exported by `lib_config` and `lib_viper::display`, so the file is read into the type the Presenters draw with; they spell themselves (`StatusGlyphs::key`: `unicode`/`ascii`, the TUI's spellings since #904; `RowDensity::key`: `compact`/`regular`/`roomy`) and read case-insensitively (#1045). `colour_appearance`, `date_style`, `on_start` and `start_view` are read and written by their `:set` spellings (`light`, `default`/`iso`, `reopen`/`none`, `last`/`units`) through `serde(with)` modules, not their lib-core derives, so the file, the environment and `:set` take one value; `lib_config::date_style_key`, `on_start_key` and `StartView::key` spell them. `SyncServerConfig`: `bind_address: String`, `database_uri: String`. `KeyBindingConfig`: a fixed `super_key: String` plus a `#[serde(flatten)]` `BTreeMap<String, String>` of command name to key, so commands stay open-ended.

#### The key catalogue

The catalogue of keys Settings writes lives in `lib_core::configuration` (#1153, ADR-0058), so `lib-config` and `lib-settings` name the same keys: `ConfigKey`, with its `name()` and `section()`, and `ConfigValue`, a written value typed by its key (`ConfigValue::Toasts(bool)`, `ConfigValue::DateStyle(Option<DateStyle>)`, …), which `lib-config` re-exports. The file side is `lib-config`'s `keys.rs`: `KEYS` lists every `(section, key)` the structs parse, `lib_config::env_var(key)` names a key's variable, `ConfigWriter::set(ConfigValue)` spells a value in the file (`spelt`) by the same functions the structs' `serde(with)` modules read it back with and refuses a Locale tag the parser would refuse, and `lib_config::read_value(key, &config)` takes it back out of a parsed `Config`. A stored Locale tag becomes a choice through `lib_locale::Locale::choice` alone: a supported, non-pseudo Locale matched ignoring case, else **System**. Neither Client spells a file value: the Desktop's `settings/device.rs` holds no per-key code, handing `set` the `ConfigValue` a Presenter wrote, and the TUI's `SettingField::config_key` is its one key table, with `Configuration::config_value` turning a `:set` word into a `ConfigValue`. `ConfigWriter::stored` reads the target file alone back through the parser, section by section, which the Desktop's `DeviceConfigFile::read` answers each key's `stored` with.

What outranks the user's file is recorded where precedence is applied (#1154), as `lib_config::Overrides`, the overrides report the parse hands the `ConfigWriter` it builds (`ConfigWriter::overrides`), so the writer stays the one object the Clients hold. `LedgerConfig::parse` records each file above the user's (beside the executable, the working directory's, `--config`) as it layers it in, asking `config`'s own INI reading of that file which keys it sets, then each environment variable, read by the parse's own environment source (`LedgerConfig::environment`, whose constants `env_var` spells a name by) and named as it is set; `ConfigArgs::apply_overrides` records each flag as it applies it, as typed (`--locale en-GB`), each flag's arm answering the key it set, so `--log` and `--file` report too, and `cli.rs`' `every_flag_that_overrides_a_key_reports_it` finds the flags through clap and fails for one that changes a key without reporting it. The last source recorded for a key wins, as in the parse: a `Shadow::Flag`, `Shadow::Env` or `Shadow::File`, `Shadow::source` naming it. Nothing re-reads a file after the parse: the Desktop's `DeviceConfigFile::read` and the TUI's `Configuration::shadow` look the key up in the report.

To add a key Settings writes: add its field to the section's struct (`general.rs`, `display.rs` or `logs.rs`, with a `serde(with)` module when its spelling isn't serde's), its row in `KEYS`, its `ConfigKey` variant in `lib_core::configuration` (`ALL`, `name`, `section`) and its `ConfigValue` variant there (`key`) and in `keys.rs` (`spelt`, `read_value`), then a line in the shipped `config/personal-ledger.conf`. The tests fail until they agree: `key_table_matches_the_structs` and `shipped_conf_holds_exactly_the_tables_keys` tie the structs, `KEYS` and the shipped file; `keys.rs`' tests tie `ConfigKey` to `KEYS` both ways (a parsed key Settings never writes goes in `NOT_WRITTEN`); and `writer.rs`' `every_value_of_every_key_is_written_and_read_back_by_the_parser` needs the new key's values in `every_value`. A Desktop page's key then needs only its control in the page's Presenter, taking its value from `DeviceSnapshot::shown` with a match on its `ConfigValue` variant and writing with `DeviceConfiguration::write`: the port, the adapter, the fake and the contract (which runs over `ConfigKey::ALL`, given the key's values in `contract::first_values` and `second_values`) need nothing new; a TUI row a `SettingField` arm in `config_key` and `Configuration::config_value`.

Section headers are normalised before parsing — lower-cased with `-` replaced by `_` (`normalise_ini` in `ledger.rs`) — so `[Sync-Server]`, `[sync-server]` and `[sync_server]` are one section.

### Preferences

`preferences` (`migrations/client/20260909000000_create_preferences_table.sql`):

| Column | Type | Notes |
| --- | --- | --- |
| `id` | UUID | Primary key, a `RowID` (UUIDv7) |
| `created_on` | TEXT | ISO-8601 UTC |
| `updated_on` | TEXT | Maintained by `trg_preferences_set_updated_on` |

Invariants the schema does not enforce:

- **Singleton by convention, not constraint.** There is a plain `RowID` primary key and no `CHECK (id = ...)`, mirroring `sync_users`. The singleton property rests on `find_only` and `get_or_create_default`.
- **No seed row in the migration.** `get_or_create_default` inserts the row in Rust at first use, because its `id` must be a genuine UUIDv7 and plain SQL cannot generate one.
- **No Preference columns yet.** The base Unit is the `ledger` table's (ADR-0044) and the display Preferences are Client-scoped (ADR-0051); the row waits for the Ledger name, owner and financial year.

### A device's settings

ADR-0053 makes them Configuration: six keys of `[General]` and `[Display]` (ADR-0057), `toasts`, `colour_theme`, `colour_appearance`, `date_style`, `on_start` and `start_view`, which both Clients read at start and write from Settings through `ConfigWriter` (#981, #982, #983, #984). Each Client's state file keeps only what it remembers itself: `tui-state.json` (`state::TuiState`) the `last_ledger` and the `last_view` Start view's `last` reads, and `desktop-state.json` (`persistence::PersistedState`) the `last_ledger`, the window geometry, the last noun (which Start view's `last` reads) and Settings page, the `:open` browser's filters and the Documents mode, scope and sort. A state file from before still loads, its `preferences` ignored and not migrated.

Both state files live in `dirs::state_dir()`, else `dirs::data_local_dir()`, under `personal-ledger/`. A missing or corrupt file loads as the defaults.

Invariants:

- **`date_style` nullability is load-bearing.** `None` is not "unset, use a hardcoded default" — it means defer to the Locale. Only an explicit ISO value overrides the Locale for both display and typed input.
- **`colour_theme` is kept raw.** A Client that doesn't know an id draws Modernist, logs a `warn` and never writes the default back (ADR-0023).

### On start

`lib_core::OnStart` is `ReopenLastLedger` (the default) or `NoLedger`. `lib_core::ledger_to_open(on_start, file, remembered)` is the one resolver both Clients ask at start: an explicit `file` wins; otherwise Reopen last Ledger opens the remembered path, or none, and Start with no Ledger open always says none. The Desktop asks it through `bin_desktop::ledger_path` in `start`, which returns a `Started`: `Opened` on the named file, `NoLedger` with none named, or `Failed` for a named file that is missing or won't open. Start-up checks the file before `open_storage`, so a missing or empty file is reported rather than opened: `unopenable` fails a path that is missing, not a file or empty, and that reason is the Toast's, so start-up never creates or writes a Ledger file (#977). `run` builds the Shell on `Opened`'s stores, or with no Open Ledger, raising `toast-ledger-open-failed` through `Root::ledger_open_failed` on `Failed`, and `last_ledger_at_quit` keeps the remembered Ledger after a failure. Start-up and the Desktop's `:open` open a file through the one `bin_desktop::open_ledger_file`, which runs those checks, then `open_storage`, generates the Bill Schedule and commits it, and returns an `OpenFailure` whose reason is a Message, never the error's own text. `:open`'s file explorer starts in the `data` folder (else home); on Open, `Root::open_ledger_file` flushes the Open Ledger's writes, opens the picked file and only then swaps it in as a `shell::router::LedgerFile` (the stores, the path and the writer), landing on the Dashboard with `toast-ledger-opened`; a failure keeps the Open Ledger, or none, and raises `toast-ledger-open-failed` (#978). An `OpenLedger` flushes its writer as it drops, and the app flushes the Open Ledger and remembers its path (`Root::ledger_path`) at quit; the status line shows that path with the home folder as `~`. The TUI asks it through `Shell::open_on_start`, which opens the named file as `:open <path>` would: one that won't open raises `toast-ledger-open-failed` and the TUI runs with no Ledger open. The TUI remembers the Open Ledger's path as it quits, so `:close` then quit forgets it.

### Start view

`lib_core::StartView` is `Dashboard` (the default), `Last`, `Settings` or `Noun(String)`, the `start_view` key both Clients share (ADR-0053). Any word but the three is a noun, kept lower case and raw as `colour_theme` is, so a noun only one Client has, or a newer release's, never stops the other starting; a Client that doesn't know it lands on the Dashboard. `StartView::resolve(remembered)` turns `Last` into the View remembered at the last quit, or the Dashboard with none. The TUI's nouns and landing rule are `bin_tui::start_view`: `units`, `accounts`, `categories`, `payees` and `tags`, the Views a `g` jump opens, each needing a Ledger, so with none open `landing` returns the Dashboard; `settings` opens the index either way. `main` calls `Shell::land_on_start` after `open_on_start`, and `Shell::quit` keeps the View showing as `quit_view` (`start_view::noun`, `None` for Help and the placeholder Views), which `main` saves as `tui-state.json`'s `last_view`. Settings › General's row is a Choice of `start_view::CHOICES`, and `:set start-view` takes only those, so the TUI never writes a noun it can't land on. A Choice too wide for its row scrolls to keep the chosen segment in view (`FieldEditor::choice_scroll`). The Desktop's are `bin_desktop::start_view` (#983): every `Noun`, spelled lower case with `credit-cards` hyphenated, of which all but the Dashboard and Settings need a Ledger (`navigation::nav::needs_ledger`), so `landing(start_view, remembered, ledger_open)` returns the Dashboard for them with none open. `shell::router::build` takes the Start view and starts `NavState` on `landing`'s noun, in place of the unconditional restore of the state file's `noun`; Settings opens on the restored page, which the frame's Presenter (`lib_settings`, `SettingsFrameEvent::Restore`) swaps for General with no Ledger open. At quit `start_view::noun_at_quit` keeps the state file's `noun` while no Ledger is open, unless Settings is showing. Settings › General's Start view is a dropdown of `start_view::CHOICES` (the Dashboard, `last`, Settings and the built Views: Transactions, Documents, Bills and Budgets), saved through `lib_settings::DeviceConfiguration::write` (`ConfigValue::StartView`); a value from the file that isn't a choice shows nothing chosen and is named under it (`general-start-view-unlisted`). General is the first Settings page with a dropdown (#1156): `GeneralPresenter` holds one `lib_viper::view::SelectList` each for Start view and the Locale and hands it to the View beside the `ControlView`, as a Dialog's Presenter does, driven by the page keymap instead of `DialogInput`. While a list is open the Presenter takes `j`/`k` (the highlight), `enter` (`GeneralEvent::Select`, which picks) and `h`/`l` (swallowed), and `esc` reaches it as `GeneralEvent::CloseList` through `PageView::escape`, so neither the frame nor the Shell's `back` sees them; no Shell mode is entered. The View draws `form::select_field` from `SelectState::drawn`, keeping each list's scroll in `GeneralWidgets`.

## Domain types

- `lib_core::DateStyle` (`date_style.rs`) — short, medium, long or ISO, behind the nullable `date_style` column. It replaced the former `NumberFormat` and `DateFormat` types.
- `lib_colour_theme` — the Colour Theme id set, `ColourAppearance` (`from_key` parses the `colour_appearance` column) and `resolve`, which turns the two Preferences, the `[theme]` overrides and the system light/dark setting into `ResolvedColours` plus contrast failures. See [Colour Themes design](../colour-themes-design.md).
- `lib_config::ThemeConfig` (`theme.rs`) — the `[theme]` role-to-`HexColor` map per Colour Variant; unparseable values and unknown keys are dropped with a `warn`.
- `lib_tracing::Levels` (`levels.rs`) — the `log` Configuration value.
- `lib_config::LocaleSource` — records whether the effective Locale came from `Default`, `System` or `Config`, so the Settings screen can show the Locale read-only with its provenance.
- `lib_config::DEFAULT_LOCALE` — `en-US`.

The number-separator Preference was deleted outright by ADR-0021: `en-US`, `en-GB` and `en-AU` all render `1,234.56`, so there was nothing for it to decide.

## Persistence

**Configuration** — `crates/libs/lib-config/src/`: `ledger.rs` (the loader and section normalisation), `personal_ledger.rs`, `sync_server.rs`, `keybindings.rs`, `theme.rs`, `cli.rs` (the shared `--config`/`--data`/`--file`/`--log`/`--locale` argument group flattened into each binary's parser), `error.rs`.

Two entry points, per ADR-0014:

- `Config::parse` — Clients. Precedence lowest to highest: built-in defaults, system config, user config, executable-directory config, the working directory's `config/personal-ledger.conf`, an explicit path, then environment variables.
- `Config::parse_for_sync_server` — the Sync Server. Defaults, explicit path, environment only. The system, user, executable-directory and working-directory tiers mean nothing inside a container.

Environment variables use the `PERSONAL_LEDGER_` prefix with double-underscore nesting, by section, e.g. `PERSONAL_LEDGER_GENERAL__LOCALE`. This requires `prefix_separator("_")` and `separator("__")` to be set separately on the `config` crate's `Environment` source, because it otherwise reuses one separator for both and nested keys never resolve.

**Preferences** — `crates/libs/lib-database/src/preferences/`: `model.rs`, `builder.rs`, `find.rs` (`Preferences::find_only`), `update.rs` (`Preferences::get_or_create_default`). There is no `delete.rs`: the row is never deleted, and no update until it has a column to update.

**A device's settings** — the Desktop applies the device's keys in `lib.rs`'s `run`: the colours through `theme::colours::set_device_colours` before the window opens, and the rest through the one device it hands `shell::router::build` (#1164), `DeviceConfigFile::new(&config, writer)` (`settings/device.rs`, re-exported from the crate root for the UI tests): the bin's `lib_settings::DeviceConfiguration` over the `ConfigWriter` and the overrides report its parse recorded, with no code per key (#1163). The port has three methods. `read` answers a `DeviceSnapshot`: the file (`ConfigWriter::target`) and, for every `ConfigKey`, a `KeyState` of `stored` (the file's own value, `ConfigWriter::stored`), `effective` (start-up's parse, `lib_config::read_value`) and `shadow` (the source above the file, `Overrides::get`). `write(ConfigValue)` and `remove(ConfigKey)` (the Locale's **System**) answer the saved value and file, the source that shadows the key, or a refusal (no file to write, or a failed write, logged at `error`); `lib_settings::writes_when_shadowed` (the Locale and the Data folder) is the Settings rule for which keys write under an override. What a control shows is one rule, `DeviceSnapshot::shown`: the key's `stored` value for a key that writes when shadowed, else its `effective` one, the Locale's tag becoming a choice through `Locale::choice`; `GeneralSettings::read` and `DisplaySettings::read` take each control's value with a match on its `ConfigValue` variant. `build` hands the device to `Root::with_clock`, which reads its snapshot once for the Toasts (`GeneralSettings::read`), the file explorer's start (`DeviceSnapshot::data_folder`, Data's value in force) and the configuration file the status line names (the snapshot's `file`), and on to `SettingsView::new` and `SettingsPages::new`, which build Settings › General's and Display's Presenters (`lib_settings::GeneralPresenter`, `DisplayPresenter`, #1039) on it once; the date style, Row density and Status glyphs reach the Views as a Ledger opens. Each Presenter reads once, in `new`, and then keeps what each write answers, never re-reading: a saved value is the one in force, or for the Locale and the Data folder the file's. The Presenter puts the answer on the status line and shows, or hands on, only a saved value, and draws a control's `Set by` note from the snapshot's `shadow`. The pages' Router (`settings::router::DeviceRouter`) emits saved Toasts as `ViewEvent::ToastsChanged` and the Display output (date style, Row density, Status glyphs, Start Sidebar minimised) as `ViewEvent::DisplayChanged`, which `Root` hands every hosted page through `PageHandle::display` (`DisplayOutput::page`, read by the Transactions, Bills, Dashboard, Documents and Budgets Presenters' `PagePresenter::display`, #1167), and applies a saved Colour Theme or Appearance (`theme::colours::apply`, deferred so every window refreshes after the input). Start Sidebar minimised is remembered in `desktop-state.json`, the one Display control that isn't Configuration. `:toasts`, `:theme` and `:appearance` go through the same Presenters (`SettingsView::set_toasts`, `choose_colour`). The contract every `DeviceConfiguration` keeps is `lib_settings::contract`, run on the in-memory fake (`lib_settings::fake::InMemoryDeviceConfiguration`, its file a `StoredDevice` map from `ConfigKey` to `ConfigValue`, with `reading` and `storing` for a test's start-up and file values) and on `DeviceConfigFile` over a temporary conf file: every key written reads back as `stored`, a later write replaces it and `remove` takes it out, a shadowed key reads its source and is left unwritten (but for those that write when shadowed), the read names the file a save names, and with no file or a failed write every write is refused, each check over `ConfigKey::ALL`. `start` reads On start from the configuration for `ledger_path`. The UI tests' `Harness` builds each Shell on a device of its own as `run` does, its own conf file unless a `Device` names another (`Harness::conf`, `Harness::with_configuration`, `Harness::on_device`, `Harness::starting_on`); `common::browsing` makes a folder the Data folder in force, and `Harness::browse_from` points only the file explorer at a folder made after the Shell was built. General's THIS DEVICE box shows the configuration file from the snapshot and the Ledger file open, which `run` hands it through `Root::set_last_ledger` and `:open` and `:close` change; the Data folder in force is General's `data_folder`. The TUI's `Shell::with_configuration` applies the keys from `[General]` and `[Display]` (Toasts onto its `Toasts`, the colour keys onto its `Colours`, the date style and On start into Settings' `Configuration`), and every change goes through `Shell::save_configuration`, which refuses a key with no file to write or one a higher source shadows, writes it, and only then lets the change apply: the `set` arms, `set_toasts` (the Toasts row and `:toasts`) and `keep_colour_preference` (`Enter` in a colour popup, which reverts the preview when the save is refused). `main` loads `tui-state.json` for `Shell::open_on_start` and saves `Shell::quit_ledger` after `run`.

## UI

Neither Client's Settings screen is wired to `lib_database::Preferences`.

- **Desktop** — `crates/bins/bin-desktop/src/settings/`, one folder per page. The frame (the page on show, the Index, Page or Dock focus, Dock being a page on show with the keyboard on the docked index after a docked click (#1110), the Medium drill-down and the page picker) is `lib_settings::SettingsFramePresenter`, held by `SettingsView` (`state.rs`), drawn from its view model with `PageClicks`, its keys offered at the key route's module step after the open page's own, its page picker a `PageMode::Filter` (`SettingsFramePresenter::mode`) whose keys the mode step offers through `SettingsView::mode_key`, a movement the Shell falls back on stepping the index or scrolling the body (#1100), and its `SettingsRouter` (`router.rs`) raising `PageChanged`, which `Root` feeds to `NavInput::SettingsPage` (#1038), and applying what the frame reports as it reports it: the page losing and gaining the keyboard (`keyboard_left`, `keyboard_entered`, both for a page reopened), a newly selected page starting at its top (`page_selected`, never for a restore) and the index scrolling to its cursor's row (`index_revealed`), so `SettingsView::handle` works none of it out and the frame's tests cover it without gpui (#1160); the bin keeps a page's icon and `for_reveal` (`mod.rs`). `lib_settings::SettingsPage` lists the pages in index order and `SettingsPage::scope_group` puts each in `ScopeGroup::ThisDevice` (`general`, `display`, `tracing`, `about`) or `ScopeGroup::ThisLedger` (`ledger` and the rest); the docked index, the Medium index page and the picker draw a heading per group, and `[`/`]` step through `SettingsPage::ALL`, so they run from one group into the next (#976). The Settings View is `Root`'s own, outside the Open Ledger: `SettingsPages` always holds the This device pages and holds the This Ledger ones (`LedgerPages`) only once `SettingsView::open_ledger` builds them on the Open Ledger, and the frame's Presenter refuses a This Ledger page with no Ledger open, so with no Ledger open the selection never lands on a This Ledger page (#977). `general/` holds On start, Start view, Toasts, the Locale and the Data folder (DESKTOP-178). The Data folder (#1148) is written in one place, `lib_settings::GeneralPresenter::set_data_folder`, which answers a `DataFolderOutcome` (`Unchanged`, `Applied`, `SavedOverridden`, `NotWritten`; #1155), through `DeviceConfiguration::write` (`ConfigValue::Data`, `[General] data`): it writes nothing for the folder the field shows already, raises the Success Toast "Data folder is now …" in place of the status line's word, and, like the Locale, `writes_when_shadowed`, showing the file's own value (the snapshot's `stored`) with a note naming the override (`--data` is a `Shadow::Flag`) and the folder in effect. **Change…** (`GeneralEvent::ChangeDataFolder` on `enter`, `PressChange` on a click) asks `DeviceRouter::pick_data_folder`, which the Desktop emits as `ViewEvent::PickDataFolder` for `Root` to run the Shell's `ShellCommand::ChangeDataFolder`; `:data` runs it from the palette. It opens `lib-shell`'s file explorer in `ExplorerMode::PickFolder`, whose pick (`ExplorerOutcome::FolderPicked`) reaches `ShellRouter::set_data_folder`, which the root Router answers through `SettingsView::set_data_folder` (`ModulePage::answer` hands back the Presenter's outcome) mapped by `DataFolderOutcome::in_effect`, the explorer's start following when the folder is now in effect. The Locale writes `[General] locale` through `DeviceConfiguration::write` (`ConfigValue::Locale`; **System** is `DeviceConfiguration::remove`), shows the file's own value (the snapshot's `stored`) and, like the Data folder, `writes_when_shadowed`, so a `--locale` (`Shadow::Flag`), variable or higher file outranking it still lets it write, with a note naming the override (DESKTOP-185, DESKTOP-186, #1146); `ledger/` runs on `lib-settings` (#1041): `lib_settings::LedgerPresenter` keeps the identity fields and summary as the mockup's placeholders, with no real `Preferences` wiring, beside a real Base unit select that reads the active Units through the `LedgerUnits` port, answered by `lib-database`'s `StoredSettingsReads` over the Units store, and sets the base Unit through `LedgerPreferences`, `lib-database`'s `LedgerPreferencesAdapter`, which runs `lib-units`' `SetBaseUnit` on that store; the input door announces `Domain::Units` from the commit (#1081). Units and Institutions have working dialogs, and both pages are aliases of the generic `ModulePage` (Units since #1099, its prices view a state of `UnitsPagePresenter`; see [Units development](units.md)); at X-Large the Units page also keeps a selected row (`j`/`k`, `e`, `d`, `n`, `t`) and docks a 400px detail pane (`units/page/pane.rs`'s `detail_pane`, drawn by the Settings View at its right edge), where the row ACTIONS columns are dropped and Success outcomes land in the pane's ACTIVITY instead of raising Toasts (DESKTOP-125). The Documents page does too: the Documents page (`settings/documents/`, Document Types per ADR-0031, with its Add, Edit and Remove dialogs in `dialogs/`; see [Documents development](documents.md)). Inventory runs on `lib-inventory`'s Presenters (#867): `inventory/` holds the `InventoryPage` Entity (`view/page.rs`, `view/page/render.rs`), its Dialogs as Entities in the Dialog host (`view/dialog/`), and the Router (`router.rs`), over `lib-database`'s `StoredInventoryPorts` from `LedgerPorts`. The pure model is `lib_inventory`, re-exported as `src/inventory/mod.rs` (Locations, Areas, Items, the cover and every removal rule, `gpui`-free and unit-tested), which Documents reads for Inventory Item Document Links. Tests are `settings_inventory_keyboard.rs` and `settings_inventory_mouse.rs`. Display runs on `lib_settings::DisplayPresenter` as `settings/display/`'s `DisplayPage`, an alias of the generic `ModulePage<DisplayPresenter>` (#1098): `PageView::framed` turns the body width the Settings View hands the page into `DisplayEvent::SetGridColumns` outside any input (the Presenter declines a count it already has), and the Colour Theme grid's keymap binds focus `tab` and the half-page moves to `DisplayEvent::LeaveGrid`, which `PageView::passes_on` hands on to the Shell's fallback once the grid has left (`shift+tab`, which the Shell keeps, leaves it by taking the keyboard off the page); `Esc` in the grid is `PageView::escape`, and the status line and the `?` cheat sheet read the view model's `hints` and `help`. Tracing is live rather than stubbed and runs on `lib-settings` (#1040): `lib_settings::TracingPresenter` mirrors the capture behind the level filter (a session-only view that opens on the configured `log` level) through the `TracingLog` read port, and tells its `TracingRouter` how the list changed; `settings/tracing/` holds `TracingPage`, an alias of the generic `ModulePage<TracingPresenter>` (#1097; `mod.rs`, the Presenter's `PageView`, whose widget state is the list's `ListState` as `LogList`, updated in `after` from what the `TracingRouter` queued, and whose keys are `lib_settings::keymap::tracing_keymap`'s), `render.rs` (the level row and a virtualised `gpui::list` log box, drawn from the view model with `PageClicks`), the Clear logs Dialog (`dialogs/clear_logs.rs`, an Entity in the Dialog host over `lib_settings::ClearLogsPresenter`) and `log.rs`, `CaptureLog`, which answers `TracingLog` over `lib_tracing::LogBuffer`. The capture feed (`shell/router/log_feed.rs`) signals `log.rs`' `LogFeed` Entity on a `Notify`-driven loop; the page subscribes to it (`PageView::subscribe`) and sends each signal as a `TracingEvent::LogChanged` input. `build_shell` takes the capture as `ShellLogs`, so the tests in `settings_tracing_keyboard.rs` and `settings_tracing_mouse.rs` push entries straight into a buffer and call `Harness::settle_logs`. See [Tracing](../tracing.md). Expanded state is session-only and nothing persists yet. `lib_settings::SettingsPage` carries each page's label, description and scope note. At X-Large the Settings index docks a 400px detail pane (`settings/pane.rs`'s `index_pane`, DESKTOP-182, #1111): `SettingsView::pane_summary` builds `lib_settings::SummarySources` from the General, Display, Tracing and About pages' Presenters and, with a Ledger open, `LedgerPages::summaries` (`CachedCounts` over the `StoredSettingsReads` behind `LedgerPorts::settings_reads`, counted once and dropped on each `LedgerChanged`, so a repaint never recounts), and draws `summarise`'s `PageSummary` for the index's cursor. The settings snapshot's `pane` and `pane_open_enabled` read it back for the UI tests. The Settings index rail is `chrome/rail/settings_index.rs`. Spec: `docs/ux/desktop-mockups/16-settings/README.md`.
- **TUI** — `crates/bins/bin-tui/src/view/settings.rs` is at wireframe stage: the two-pane layout from `docs/ux/tui-mockups/05-settings/README.md` §4a, built before the database-backed registry behind it. It has no real row-navigation state — `selected` is hardcoded to `base unit` rather than driven by `j`/`k` — so the two popups in `popup/settings` are reached by fixed keys (`e` for the in-place editor, `enter` for the base-unit guard), each always showing its own worked example, rather than acting on a selected row. **Colour Theme and Colour Appearance** are the one working colour pair in both Settings screens, held in memory while the Client runs and kept between runs in `personal-ledger.conf`:

## Open questions and known gaps

- **Neither Settings screen reads or writes `Preferences`.** The row has no columns yet, so `get_or_create_default` has no production call site.
- **The TUI Settings registry does not exist.** The wireframe is explicitly built ahead of "the database-backed registry behind it", and the view has no selection state.
- **Keybindings are parsed but unused.** `KeyBindingConfig::key_for` is called only from `lib-config`'s own tests; neither bin reads its shortcuts from configuration, and the `g`-leader grammar in [navigation-design.md](../navigation-design.md) is not wired to it.
- **No Change Set emission.** The preferences table is sync-ready in shape — a normal `RowID` and an `updated_on` trigger — but nothing emits Change Sets on write, so Ledger-scoped Preferences do not actually sync yet.
- **TUI System appearance is read once.** Live mode 2031 notifications aren't followed: crossterm 0.29's parser would swallow input after the unknown `CSI ?` sequence.

The TUI's Data folder picker (#1149) is `crates/bins/bin-tui/src/popup/folder_picker.rs`: `lib-shell`'s `ExplorerPresenter` in `ExplorerMode::PickFolder` over the TUI's own `std::fs` `LedgerFolders` adapter, `FsLedgerFolders`, hosted by the Shell as a popup over whichever View is showing, so its `return_to` is the View itself. `u` stands in for the Desktop's `ctrl-enter`. `Shell::use_data_folder` writes `[General] data` through `ConfigWriter`, writes nothing for the folder already set, and raises the Success Toast.
