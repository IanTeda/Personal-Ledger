# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Personal Ledger is a Rust Cargo workspace for a personal finance/accounting application (expenses, investments, assets). It is still in concept: the Desktop and TUI Clients are built UI-first, with most screens rendering in-memory sample data and persistence wiring a later phase, and the Sync Server serves a feasibility-cycle surface (`Push`/`Pull` behind an auth interceptor, plus `/authorize` and `/token`) rather than a finished sync protocol.

## Setup

Toolchain and dev tools (Rust, protoc, mdBook, sqlx-cli, bacon, cargo-deny) are pinned in `mise.toml`. Run `mise install` once per checkout before `cargo`, or `protoc` and `sqlx-cli` won't be on `PATH`. Run `mise run install-hooks` once so `.githooks/pre-push` runs the lint.

`lib-database` uses `sqlx` compile-time query macros, so the workspace won't build without a `DATABASE_URL` or `SQLX_OFFLINE=true`. For local dev (rust-analyzer included), create a gitignored `.env` at the repo root with `DATABASE_URL=sqlite:<absolute-path-to-repo>/.personal-ledger-dev.db`; `sqlx` and `sqlx-cli` auto-load it. Then:

- `mise run db` resets the dev DB (drop, create, migrate) **and regenerates the `.sqlx` cache**, so commit any `.sqlx` changes it leaves.
- `mise run db-migrate` applies new migrations and keeps existing data.
- `mise run db-fresh` drops, creates and migrates a fresh dev DB with no rows (`mise run db` is this plus the `.sqlx` regeneration).
- `mise run db-seed` adds to the migrated dev DB, without dropping it: the Sample Ledger through `lib-database` (`lib_database::seed::sample`), so ids match `seed::sample_ledger` and `FakeStores::sample`, then deterministic `fake` rows on top (`seed::fake`). It is idempotent, setting the base Unit only when there is none. For a clean seeded DB run `db-fresh` then `db-seed`. A module's sample rows are the one seed for its domain: a change to a persisted entity updates them, and the Sample Ledger and `db-seed` follow (`docs/development/database.md`).

Migrations come in two sets: `migrations/client/` (the Client Ledger) and `migrations/sync-server/` (`change_sets`, `sync_users`). While the schema is in concept there is one `create_<table>_table.sql` per table: edit that file rather than adding an `ALTER` migration, then `mise run db`.

## Commands

Most work is plain `cargo`; `mise tasks` lists the rest.

```sh
cargo build                                    # whole workspace
cargo run --package bin_sync_server            # Sync Server
mise run watch-tui                             # TUI, rebuilt on change (bacon tui)
mise run watch-desktop                         # Desktop, rebuilt on change (bacon desktop)
mise run watch                                 # clippy on save (bacon, the inner loop)

cargo test --package lib_config                # one crate
cargo test --package lib_config parse_with_explicit_config_file  # one test
mise run end-to-end-ui <view>                  # Desktop UI tests for one View, e.g. settings_inventory
bacon ui -- <view>                             # the same, re-run on each save

mise run lint           # exactly what CI runs: fmt --check + SQLX_OFFLINE clippy -D warnings
mise run lint-fix       # cargo fmt + clippy's machine-applicable fixes
mise run deny           # cargo-deny (deny.toml)
mise run docs-build     # rustdoc + mdBook; docs-serve serves on :8001
```

Package names and binary names differ: `bin_sync_server` → `sync-server`, `bin_tui` → `tui`, `bin_desktop` → `desktop` (the `bin_` prefix is a codebase convention end users shouldn't see).

## Workspace layout

Bins live in `crates/bins/bin-*`, libraries in `crates/libs/lib-*`. Members are listed by hand in the root `Cargo.toml`, so add a new crate there; the exception is `lib-core`, which joins only as a path dependency.

- **`bin-sync-server`** — serves `UtilitiesService` (open `Ping`) and `SyncService` (behind `auth::interceptor::AuthInterceptor`) merged with the `auth` HTTP routes on one listener (ADR-0010). Config comes via `Config::parse_for_sync_server`. The JWT key and bootstrap `sync_users` credentials are feasibility placeholders. See the [Sync Server feasibility](https://github.com/IanTeda/Personal-Ledger/issues/40) map.
- **`bin-desktop`** — `gpui`/`gpui-component` Client. Lib plus thin bin: modules live in `src/lib.rs`, and the app and the tests both build the Shell's root Router, `shell::router::Root`, through `shell::router::build`. `shell/router.rs` defines `Root`; `shell/router/` holds `impl Root` blocks per concern (`render.rs`, `focus.rs`, `key_dispatch.rs` are `impl` blocks, not modules of that name; `_ui` marks per-domain wiring), except `open_ledger.rs`'s `OpenLedger`: everything built on a Ledger, which `Root` holds as an `Option` and reads whether a Ledger is open from (#975). `shell/view/` draws the Shell's frame (ADR-0016, ADR-0045) and `shell/state.rs` holds what of it `lib-shell`'s Presenter doesn't, `view/` the screens, `navigation/` the keyboard grammar (`docs/navigation-design.md`). A module's Dialog is an Entity holding its Presenter (`shell/view/dialog_entity.rs`). `input.rs`'s `send` is the one door an input reaches a Presenter through: it commits once per input, so no port or store commits for itself. `OpenLedger` holds `lib-database`'s `LedgerPorts` as `LedgerStores { ports }` (`open_ledger/stores.rs`) and hands each page its ports and reads from it; the raw stores (`ports.stores`) are for a failed write's reload and the `*_for_test` hooks. No module announces its writes: `send` takes the commit's `Committed { wrote, cascaded }`, reloads `cascaded`, and emits one `LedgerChanged { what }` of `lib_database::Domain`s through `announcer.rs`'s `Announcer`, for `notify_on` to repaint the Entities reading that domain. Headless UI tests live in `tests/ui/`, one test binary (ADR-0030).
- **`bin-tui`** — Ratatui Client: `shell.rs`, a screen per domain in `view/`, `popup/` for dialogs. The Units View runs on `lib-units`' Presenters, with the View, its Dialogs and Router in `units/` on `LedgerPorts`' `StoredUnitsPorts`, and the Ledger file opened by `lib_database::open_storage`; the other Views draw fixtures. Transactions, budgets, balance checks, reports and CSV import are wireframe placeholders; their old logic is in Git history (pre-#254 `screen/`), not in a dead module.
- **Domain crates** — `lib-accounts`, `lib-bills`, `lib-budgets`, `lib-categories`, `lib-documents`, `lib-institutions`, `lib-inventory`, `lib-payees`, `lib-tags`, `lib-transactions`, `lib-units`: one pure, `gpui`-free, I/O-free crate per domain (model, rules, sample seed) shared by both Clients. `lib-database`'s `Stored<Domain>Ports` answers each one's ports, and the Desktop hosts its Views and Dialogs. Follow this split for a new domain. **`lib-documents`** is a VIPER module (#960): it depends only on `lib-core` and `lib-viper`, reads other domains through its own read ports (`DocumentTransactions`, `DocumentPayees`, `DocumentAccounts`, `DocumentBillPlans`, `DocumentItems`) and the disk through `DocumentFiles`, and holds the Interactors and the Presenters for the Library, the Inbox, Settings › Documents and every Dialog; filing writes only Documents, so there is no `lib-document-filing`.
- **`lib-bill-payments`** — the first cross-domain module (`docs/development/viper-architecture.md`): Pay it directly and the Pay Dialog's Presenter, writing a Transaction and the Bill Schedule entry it settles through one atomic port, `BillPayments`, which `lib-database`'s `BillPaymentsAdapter` implements. It depends only on `lib-bills` and `lib-transactions`, and no feature crate depends on it (`deny.toml` and `lib-database`'s `viper_dependencies.rs` enforce both). Follow it for the next workflow that writes two domains. **`lib-account-deletion`** is the second (#854): Account delete and its Dialog's Presenter, through one atomic port, `AccountDeletion`, which `lib-database`'s `AccountDeletionAdapter` implements over the Accounts, Transactions and Bills stores; the Desktop hosts the Dialog from `account_deletion/`. **`lib-unit-deletion`** is the third (#902): Unit delete, reassigning the Institutions that name it as their Usual unit, and its Dialog's Presenter, through one atomic port, `UnitDeletion`, which `lib-database`'s `UnitDeletionAdapter` implements over the Units and Institutions stores; the Desktop hosts the Dialog from `unit_deletion/` (#903). **`lib-transaction-import`** is the fourth (#943): the Import's rules, its `ImportPlan`, one atomic port, `TransactionImport`, which `lib-database`'s `TransactionImportAdapter` implements over the Payees and Transactions stores, a `StatementSource` (the seeded statement), its reads and the step's Presenter; the Desktop hosts the step from `transaction_import/`, shown in place of the Transactions list on `:import`. **`lib-tag-removal`** is the fifth (#1002): Tag remove and merge and the Remove tag and Merge tags Dialogs' Presenters, through one atomic port, `TagRemoval`, which `lib-database`'s `TagRemovalAdapter` implements over the Tags and Transactions stores, and the read port `TagRemovalReads` (`StoredTagRemovalReads`); the Desktop hosts the Dialogs from `tag_removal/`, opened by the Tags page's Router (#1003). **`lib-category-deletion`** is the sixth (#1004): Category delete, moving the Category's Splits and Bill Plans to the Uncategorised of its type, clearing Payee defaults and dropping Budget Limits, and the Delete category Dialog's Presenter, through one atomic port, `CategoryDeletion`, which `lib-database`'s `CategoryDeletionAdapter` implements over the Categories, Transactions, Bills, Payees and Budgets stores, and the read port `CategoryDeletionReads` (`StoredCategoryDeletionReads`); the Desktop hosts the Dialog from `category_deletion/`, opened by the Categories page's Router (#1005). **`lib-ledger-creation`** is the seventh (#912, ADR-0054) and the one whose atomic port, `LedgerCreation`, takes a path, not stores, since no Ledger exists yet: `NewLedger` (the Personal Institution with no Usual unit, the base Unit, an empty Personal spending Budget on no Accounts and the default Document Types, nothing else), the Interactor `CreateLedger`, a fake and contract, and the Create ledger Dialog's Presenter, `CreateLedgerPresenter`. `lib-database`'s `LedgerCreationAdapter` claims the file name with create_new, migrates and writes in one transaction, removing the file on failure. It is in `viper_dependencies.rs`' `CROSS_DOMAIN`, and `deny.toml` lets only `bin_desktop`, `bin_tui` and `lib_database` depend on it; the Desktop hosts the Dialog from `ledger_creation/` (`:new`, after the explorer's New mode), and the TUI's `:new` creates the same Ledger with the Locale's Currency as base Unit, without a Dialog.
- **`lib-core`** — shared domain value types with no I/O (`RowID`, `Money`, `CategoryTypes`, periods, the `Clock` every View reads the day from, …). SQLite-only assumptions, even though `sqlx`'s Postgres feature is on workspace-wide.
- **`lib-database`** — SQLx persistence. A migrated domain's adapter is one file, `adapter/<domain>.rs` (ADR-0041), holding its rows in memory and sending writes to the one shared `writer.rs` thread (ADR-0046); follow `adapter/units.rs` for the next domain, not the older per-entity directories. `adapter/store.rs` holds the `<Domain>Store` traits (an adapter or the in-memory fakes, and `Stores::fake` with a `CountingCommit`), each answering only its own domain's rows, and the `Stored<Module>Reads` structs that answer a reading module's ports from other domains' stores (#994), and `storage.rs` the `open_storage` the Desktop starts on and the TUI's Shell calls on `:open`, which only opens (it writes nothing, and refuses a migrated file with no base Unit, Budget or Document Type as `Error::IncompleteLedger`, writing nothing), and the `Stores` bundle the Desktop's `shell::router::build` takes, each store wrapped in a `Recorded` that notes its `Domain` (the one enum; Document Types are their own) so `Commit::commit` returns `Committed { wrote, cascaded }`. `ports.rs`' `LedgerPorts::new(stores, clock)` is how either Client reaches an Open Ledger: one `Stored<Domain>Ports` per domain (`ports/<domain>.rs`) implementing the domain crate's ports trait, the cross-domain adapters, the module reads, the commit and the failure channel. Reads and adapters hold only stores (the cycle invariant in its module doc); a new domain adds a store, its `Stored<Domain>Ports` and a `Domain` variant (ADR-0055). `seed.rs` holds the Sample Ledger (`GLOSSARY.md`), a permanent fixture for development and tests with one definition, `seed::SampleLedger`: `NewLedger`'s rows with each domain's sample rows on top (the sample Transactions, Bills, Budgets and Documents fed the rows they name), every row dated from `today`. `seed::sample` (`db-seed`), `seed::sample_ledger(path, today)` (creates a Ledger through `LedgerCreationAdapter`, then writes the sample on top, for tests) and `FakeStores::sample(today)`, the tests' in-memory stores, all read it, and a seed test fails if the file and the in-memory stores drift; the cross-domain seed tests sit beside it. `tests/viper_dependencies.rs` enforces the dependency rule over `cargo metadata`: no feature crate depends on another (`docs/development/viper-architecture.md`), and a new feature crate joins its `FEATURE_CRATES`. `adapter/documents.rs` holds the Documents, Document Types and Document Links, `StoredDocumentReads` answers `lib-documents`' read ports from the other stores, and a delete the file cascades into Document Links makes the Desktop's `send` reload the Documents after the commit. See the Persistence section of `docs/development/viper-architecture.md`. The Sync Server's auth table is `sync_users` so it never collides with the domain `accounts`.
- **`lib-config`** — layered INI config, `lib_config::Config`. Sections `[Personal-Ledger]`, `[sync-server]`, `[keybindings]`; precedence and env-var naming in `docs/settings.md`.
- **`lib-tracing`** (imported as `telemetry`) — `init` returns a guard that must live for all of `main`. See `docs/tracing.md`.
- **`lib-rpc`** — the wire protocol only: protos in `proto/personal-ledger/v001/`, packages `personal_ledger.<service>.v001`. `SyncService`'s handlers live in `bin-sync-server`'s `sync/`, so `lib-rpc` never reaches `lib-database`. `src/generated/*.rs` is regenerated by `tonic_prost_build` on every build: checked in, but build output, never hand-edited.
- **`lib-locale`** / **`lib-locale-build`** — Fluent Catalogues, generated `msg::` accessors, ICU4X formatting and date parsing for both Clients. The Locale is Configuration, not a Preference (ADR-0021). See `docs/localisation-design.md`.
- **`lib-shell`** — the Shell as a toolkit-free VIPER module, its Router the bin's root Router (`docs/development/viper-architecture.md`, The Shell module). It grows ticket by ticket (#820); today its Presenter holds the status line, the Toasts and `NavState` (the noun showing, focus and the input mode), holds the Clock and notices a month turn, knows whether a Dialog is open, holds the Help Dialog's Presenter (#1025) and the Toast History Dialog's (#1043), the command palette's Presenter (#1063: its input, matching and history over the `PaletteEntry`s the Desktop hands it; the Shell runs the chosen `PaletteEffect`, a Desktop one through the root Router's `run_effect`), the file explorer's Presenter behind `:open` and `:new` (#1064: reading folders through the `LedgerFolders` port, which the Desktop's `FsLedgerFolders` answers over `std::fs`), the Dialog keymap (`select`, `back`, `next_field`, `submit`, …) the Desktop's module Dialogs read their keys through and the global keymap with its `g` prefix, and owns `Noun` and `ActiveView`. It runs each global command itself, inside the key's one input, and reaches a View or the frame through `ShellRouter`'s typed methods, which the Desktop's `RootRouter` (`shell/router/root_router.rs`) answers over every field of `Root` but the Presenter (#1065). The order every Desktop key is offered in (Dialog, a mode the View or the Shell entered, global keymap, module keymap, View) is `input.rs`'s `route_key`. Only the bins and `lib-database` (its `StoredShellReads` answers the `ShellRailCounts` rail-count port) may depend on it (`deny.toml`, `viper_dependencies.rs`).
- **`lib-dashboard`** — the Dashboard as a VIPER module (#1021): it depends only on `lib-core`, `lib-locale` (for its Messages), `lib-toast` and `lib-viper`, holds the Dashboard's Presenter, view model and read ports (`DashboardBills`, `DashboardBudgets`), which `lib-database`'s `StoredDashboardReads` answers from the Bills and Budgets stores; the Desktop hosts it from `dashboard/` (#1022–#1024). Only `bin-desktop` and `lib-database` may depend on it (`deny.toml`); the TUI's Dashboard waits on its redesign (#805).
- **`lib-settings`** — the Desktop's Settings frame as a VIPER module (#1036): it depends only on `lib-core`, `lib-colour-theme`, `lib-list-cursor`, `lib-locale` (for its Messages), `lib-toast` and `lib-viper`, never on `lib-config`, `lib-tracing` or `lib-units`. It holds `SettingsPage`, the frame's Presenter and keymap (emitting `PageChanged` for Back and Forward), and the Presenters for the config pages: General and Display over the `DeviceConfiguration` write port, Tracing and its Clear logs Dialog over the `TracingLog` read port, Ledger over the `LedgerUnits` read port and `LedgerPreferences` write port (`lib-database`'s `StoredSettingsReads` and `LedgerPreferencesAdapter`), and Sync server, Data & backup and About. The bin implements `DeviceConfiguration` over `lib_config::ConfigWriter` and `TracingLog` over the log buffer, and hosts it from `settings/`; the domain pages stay in their own modules. Only `bin-desktop` and `lib-database` may depend on it (`deny.toml`, `viper_dependencies.rs`); the TUI keeps its own Settings until its redesign (#805).
- **`lib-toast`** — pure Toast model shared by both Clients (`docs/toasts-design.md`). **`lib-list-cursor`** — list selection and movement (`step`, `step_id`, `resolve`, `HALF_PAGE`); every list View moves through it rather than hand-rolling clamps. **`lib-colour-theme`** — Colour Themes (ADR-0025). **`lib-viper`** — the generic types every VIPER module's Presenters and keymap use (`Keymap`, `Binding`, the shared command names, `TextFieldView`, `SelectView`, `Choice`, `DialogFrame`, the status line's `Hint`, which `lib-shell` re-exports for the bins), so a new module imports them rather than copying `lib-units`'; not a feature crate, but toolkit-free and I/O-free like one.

Crates in `docs/directories-files.md` or `README.md` that aren't listed here (e.g. the web/Leptos frontend) don't exist yet.

## Conventions

- **New UI text is a Message:** add it to the `en-US` Catalogue (`crates/libs/lib-locale/i18n/` if shared, else the bin's `i18n/`) and read it through a `msg::` accessor; no hardcoded display literals. What is deliberately not a Message is listed in `docs/localisation-design.md`.
- **Lint clean before every push:** run `mise run lint`. CI's Lint workflow runs only on `main`, so a break on `concept` otherwise surfaces late. Fix at the source; where a lint is deliberately left, use `#[expect(clippy::<lint>, reason = "...")]`, never relax `[workspace.lints]` or drop `-D warnings`. The `SQLX_OFFLINE=true` in the lint matters: a local build reads the live dev DB and hides a stale `.sqlx` cache. On "no cached data for this query", run `mise run db-prepare-generate` and commit `.sqlx`. See `/lint-fix`.
- **Desktop Views need UI tests:** every View under `bin-desktop/src/view/` and every Settings page has `<view>_keyboard.rs` and `<view>_mouse.rs` in `bin-desktop/tests/ui/`, declared in `tests/ui/main.rs`. When adding or changing Desktop UI, add the missing ones without being asked (`/ui-tests`) and run `mise run end-to-end-ui <view>`. A View without tests is incomplete; report the gap in reviews, and say why in the commit or PR if one is deliberately left untested.
- **Full suites and review at parent-ticket close only:** the full UI suite (bare `mise run end-to-end-ui`), the end-to-end smoke test (`mise run end-to-end-ui smoke`, also before any merge to `main`), the full workspace `cargo test` and a `/code-review` of the parent's commits are required when closing a parent ticket (a Wayfinder map or any issue with sub-issues), not for each child ticket or push, even where a skill such as `/implement` asks for them. Run the targeted tests for what you changed.
- **Tests:** unit tests alongside the code in `#[cfg(test)] mod tests`; DB tests use `sqlx::test`; generated data uses `fake` with deterministic seeds. No doctests: every library sets `[lib] doctest = false`, and doc comments explain why rather than carrying `# Examples`.
- **Commits:** `<area>: <short description>`, e.g. `desktop: move the Inventory into a store Entity behind lib_inventory's service`.
- **Ticket labels:** when you create, claim, finish, release or rank a ticket, set its `category:`, `priority:`, `flow:` and `state:` labels by `docs/agents/ticket-labels.md` (`flow:` and `wayfinder:` defined in `docs/agents/flow-labels.md`, which wins over the `/wayfinder` skill), recording each label decision in the ticket body's `## Labels` section; on finishing, it also decides whether you close the ticket or gate it for review.
- **Issue titles:** prefix every GitHub issue title with its bin crate, `TUI: `, `DESKTOP: ` or `SYNC: `, or `CORE: ` for none or several; an issue for a lib crate inherits the prefix of the bin being worked on when it was created (`docs/agents/issue-tracker.md`).
- **Signing key check before committing:** commits are SSH-signed with a key held by the Bitwarden ssh-agent (`SSH_AUTH_SOCK`), which is only reachable while Bitwarden is open and unlocked. Before `git commit`, run `ssh-add -l | grep -qF "$(ssh-keygen -lf "$(git config user.signingkey)" | cut -d' ' -f2)"`. If it fails, don't commit (and never bypass signing): ask the user to open or unlock Bitwarden, then check again.

## Tickets and model choice

A self-contained ticket body is the spec: the user usually `/clear`s between independent tickets, so don't rely on earlier conversation. If the body lacks what you need (acceptance criteria, files, decisions), stop and ask.

Pick the model, for a ticket or a subagent, by the `agent:` label rules in `docs/agents/triage-labels.md`.

A ticket that migrates in steps lists under "Seams to decide" the halfway state it leaves and the new types or events it needs, or "None". Its acceptance criteria name that halfway state, and any test file they name either exists or is listed as new. If you hit a seam the ticket didn't decide, stop and relabel the ticket up rather than guess.

## graphify

A knowledge graph lives in `.graphify-out/` (`GRAPHIFY_OUT` in `mise.toml`). For codebase questions, start with `graphify query "<question>"`, `graphify path "<A>" "<B>"` or `graphify explain "<concept>"`; they return a scoped subgraph, smaller than `GRAPH_REPORT.md` or raw grep. Read `GRAPH_REPORT.md` only for broad architecture review. After modifying code, run `graphify update .` (AST-only, no API cost).
